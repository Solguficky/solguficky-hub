## 0. Зачем нужен этот документ

`solegufobot-context-base.md` хорошо выполняет роль переходного списка изменений относительно старого canvas, но после новых замечаний его уже нельзя механически разнести по `docs/`. В нём смешаны:

1. факты о реально существующем коде;
2. ранее принятые ADR;
3. новые решения владельца проекта;
4. сильные кандидаты, которые ещё предстоит проверить;
5. дальние учебные идеи без обязательств по реализации.

Главная задача актуализации — не просто заменить `Rust` на `TypeScript` или `Railway` на мини-ПК. Нужно сделать видимым **статус каждого утверждения**. Иначе очередной архитектурный обзор снова будет выглядеть так, будто ещё не спроектированные сервисы уже существуют, будущие гипотезы утверждены, а legacy-прототип входит в критический путь.

Для дальнейшей документации предлагается использовать пять явных статусов:

| Статус | Значение |
|---|---|
| **Current** | Фактически существует в текущей ветке и подтверждается кодом |
| **Target v1** | Принятое направление ближайшего продуктового цикла |
| **Candidate** | Сильный вариант, но решение ещё требует проектирования или ADR |
| **Future hypothesis** | Дальняя учебная или продуктовая идея без текущего обязательства |
| **Legacy / frozen** | Существующий код, который не входит в активное направление |

Это не ещё одна система управления проектом. Это минимальная маркировка, предотвращающая смешение настоящего, целевого и возможного.

## 2. Главные выводы

### 2.1 Продуктовое ядро ещё не реализовано

Репозиторий в текущем виде — преимущественно аукционный прототип и инфраструктурный задел. `meetups` и `identity`, которые должны стать ядром ближайшей итерации, отсутствуют даже на уровне межсервисных контрактов.

Следовательно, ближайшая работа — не развитие существующего аукционного решения, а создание первого продуктового вертикального среза вокруг сходок.

### 2.2 Старый gateway не соответствует новой роли

Rust/Teloxide gateway реализует в основном аукционные сценарии, работает с `MockAuctionService`, хранит диалоги в памяти и содержит незавершённую миграцию NATS payload с JSON на Protobuf.

При смене продуктового центра с аукциона на сходки новая реализация на TypeScript + grammY является обоснованной не только сменой языка, но и сменой назначения сервиса.

### 2.3 Аукционная ветка должна стать явно legacy

Существующий C#/Akka.NET аукцион нельзя считать подтверждённой основой будущего Scala/Pekko сервиса. Он полезен как эксперимент и источник гипотез, но не входит в v1 и не должен определять default-топологию, CI и актуальную архитектурную диаграмму.

### 2.4 Языки нельзя заранее распределять по выдуманным сервисам

`Go → scheduler`, `Kotlin → content-feed`, `Ruby → admin` — искусственное заполнение языковых слотов. Интерес к языку нужно хранить как learning pool. ADR появляется только тогда, когда есть реальный сервис, требования и осознанный выбор.

### 2.5 Процесс проектирования должен принадлежать человеку

Текущий ADR-013 начинает процесс с предложения архитектурного решения агентом. Это противоречит учебной цели проекта. Агент должен собирать факты, спорить, расширять варианты, проверять согласованность и реализовывать утверждённые срезы. Первичная гипотеза, компромисс и окончательное решение принадлежат владельцу проекта.

### 2.6 Документация нуждается в статусной модели

Сейчас `Current`, `Target` и `Future` смешаны в одном тексте. Это более серьёзная проблема, чем отдельные устаревшие строки. Даже после исправления языков документы быстро снова разойдутся, если не маркировать статус утверждений.

## 3. Фактическое состояние репозитория

### 3.1 Telegram Gateway

**Статус:** Current implementation, target for replacement.

Текущая реализация:

- Rust + Teloxide;
- аукционный UI: просмотр лотов, ставки, создание лота;
- роли `Admin/User` из `configuration.yaml`;
- `MockAuctionService` вместо реального gRPC-клиента;
- in-memory dialogue storage;
- публикация аукционных команд в NATS;
- два фоновых NATS listener;
- in-memory idempotency cache для callback query.

Полезные архитектурные идеи:

- handler возвращает `BotAction`, а не вызывает Bot API напрямую;
- UI builders вынесены в чистые функции;
- переходы FSM выражены явно;
- callback query подтверждается отдельно;
- есть тесты FSM и UI без Telegram API;
- авторизация изолирована за отдельным модулем.

Ограничения и долги:

1. **Данные аукциона mock-only.** `MockAuctionService` создаётся непосредственно при старте gateway.
2. **FSM хранится в памяти.** Рестарт процесса завершает активные диалоги.
3. **Контрактная миграция не закончена.** Один путь декодирует `BidPlacedEvent` как Protobuf, другой — как JSON.
4. **`SendMessageCommand` читается как JSON**, хотя notifications публикует Protobuf.
5. **Два пути outbid-уведомления:** gateway реагирует на `BidPlacedEvent` напрямую, а notifications создаёт команду отправки сообщения.
6. **Gateway почти полностью аукционный**, поэтому перенос строка-в-строку в новую реализацию не имеет смысла.
7. **Idempotency локальна процессу** и теряется при рестарте; параметр TTL хранится в структуре, но cleanup использует жёстко заданный час.

Вывод: сохранять следует идеи и тестовые приёмы, а не Rust-код или аукционную структуру каталогов.

### 3.2 Auction Service

**Статус:** Current legacy prototype, out of v1.

Реализовано:

- C# / .NET 10;
- Akka.NET actors `AuctionRegistry → AuctionActor → LotActor`;
- Event Sourcing через Akka.Persistence SQL;
- PostgreSQL;
- gRPC queries и CRUD лотов;
- NATS command handlers;
- публикация части событий через Persistence Query;
- UUIDv7;
- EF Core migration для таблицы лотов;
- автоматическое применение EF-миграций при старте;
- unit tests для части логики `LotActor`.

Два пункта из переходной базы уже устарели:

- EF-миграция существует;
- scoped `LotRepository` больше не внедряется напрямую в singleton `NatsCommandHandler`: handler создаёт scope через `IServiceScopeFactory`.

Остаются важные ограничения:

- код не проверялся в production;
- нет доказанного e2e восстановления полного аукциона;
- покрытие тестами сосредоточено на `LotActor`, а не на всём lifecycle;
- рефакторинг фаз не завершён;
- таймеры и anti-sniping были удалены/отложены;
- `op_id` не обеспечивает фактическую дедупликацию;
- деньги по-прежнему представлены `double`;
- набор событий, публикуемых во внешнюю шину, привязан к ручному списку event-adapter bindings;
- архитектура родилась до окончательного продуктового решения по формату аукциона.

Вывод: это ценный эксперимент, но не подтверждённая база будущего сервиса. Перед удалением необходимо извлечь знания и явно пометить непроверенные гипотезы.

### 3.3 Notifications Service

**Статус:** Current auction-oriented scaffold; candidate for reuse in v1.

Реализовано:

- C# / .NET 10;
- подписка на `events.auction.>` через core NATS;
- диспетчер protobuf-событий в handlers;
- единственный содержательный handler `BidPlacedHandler`;
- формирование `SendMessageCommand`;
- unit tests для `BidPlacedHandler`.

Это пока не сервис напоминаний. В нём отсутствуют:

- модель подписок;
- расписание напоминаний;
- persistent jobs;
- retry policy;
- consumer idempotency;
- quiet hours;
- дедупликация уведомлений;
- связь Telegram user с реальным `chat_id` через Identity.

Текущий код прямо предполагает `user_id == chat_id`, помечая это как временное ограничение.

Вывод: язык и базовую границу сервиса можно оставить, но продуктовую механику напоминаний предстоит спроектировать заново.

### 3.4 WebSocket Gateway

**Статус:** Current legacy/frozen, out of v1.

Реализовано:

- C# / .NET 10;
- SignalR;
- подписка на `events.auction.>`;
- маппинг только `events.auction.bid_placed`;
- отправка всех событий в общий `auction:live` group;
- unit tests event mapper.

Сервис не обслуживает текущую цель сходок. Он может остаться в репозитории как замороженный элемент будущего аукционного модуля, но не должен запускаться в default v1 topology и создавать впечатление активного компонента.

### 3.5 Meetups, Identity и Mini App

**Статус:** Not started.

- каталогов сервисов нет;
- proto-контрактов нет;
- схем данных нет;
- язык Meetups и Identity фактически не выбран;
- frontend/admin-app пуст;
- существующие диаграммы изображают эти сервисы более определёнными, чем они являются.

### 3.6 Контракты

**Статус:** Current auction-only contract set.

Существуют:

- общие типы;
- gRPC `auction_service.proto`;
- NATS auction commands;
- NATS auction events;
- Telegram `SendMessageCommand`.

Нет контрактов для:

- meetup lifecycle;
- meetup queries;
- RSVP;
- identity resolution;
- ролей и разрешений;
- reminders.

Перед их появлением желательно решить минимальную политику эволюции контрактов, не обязательно возвращая runtime Schema Registry.

### 3.7 Aspire и локальная инфраструктура

**Статус:** Implemented in code, not runtime-verified.

AppHost содержит:

- PostgreSQL;
- NATS с JetStream enabled на сервере;
- режимы `Local / Container / Off`;
- профили `infra / core / full`;
- C# projects;
- Rust gateway через `cargo run`;
- secrets parameter для Telegram token.

Но:

- профиль `core` всё ещё означает `auction-service + telegram-gateway`;
- AppHost и ServiceDefaults нацелены на `net8.0`, сервисы — на `net10.0`;
- документация прямо говорит, что `aspire run` не был подтверждён;
- container build contexts содержат TODO/риски;
- topology не знает о будущих Meetups/Identity;
- часть документации по compose уже расходится с реальным деревом файлов.

Вывод: Aspire остаётся хорошим local-dev решением, но его текущую реализацию нельзя описывать как полностью работающую.

### 3.8 CI

**Статус:** Exists, configuration drift present.

GitHub Actions содержит path-filtered jobs для четырёх текущих сервисов. Однако:

- C# jobs устанавливают .NET 8;
- проекты уже используют `net10.0`;
- AppHost вообще не проверяется;
- Meetups/Identity, естественно, отсутствуют;
- `ROADMAP.md` одновременно утверждает, что CI нет, и ниже отмечает CI выполненным.

Вывод: наличие YAML нельзя считать подтверждением зелёного CI на текущем target framework.

## 4. Главная проблема документации: смешение временных слоёв

Существующие документы одновременно утверждают, что:

- gateway — Rust и одновременно должен быть переписан;
- Meetups/Identity — C#, хотя язык обсуждается;
- Railway выбран, хотя roadmap считает hosting открытым;
- Scala исключена, хотя принято направление Scala/Pekko для auction v2;
- Schema Registry не нужен, хотя причина отказа была временной;
- Aspire — текущая точка запуска, хотя живой запуск не подтверждён;
- auction v2 продолжает текущий C#-код, хотя теперь планируется отдельная реализация с нуля.

Это нельзя исправить одной новой таблицей стека. Требуется разделение минимум на три представления:

### Current

Что находится в репозитории и насколько подтверждено:

- Rust gateway — существует, legacy target;
- C#/Akka auction — существует, frozen;
- C# notifications — auction scaffold;
- C# websocket — auction-only legacy;
- Aspire — код написан, запуск не подтверждён;
- Meetups/Identity — отсутствуют.

### Target v1

Что строится для первой живой сходки:

- TypeScript/grammY gateway;
- Meetups Service, язык TBD;
- отдельный Identity Service, язык TBD;
- C# Notifications после проектирования reminders;
- PostgreSQL, NATS, Protobuf, gRPC;
- Aspire для локального запуска.

### Future hypotheses

- Scala/Pekko auction v2;
- C#/Orleans achievements;
- Mini App stack;
- локальный или staging k3s;
- Schema Registry;
- Kotlin/Go/Ruby slots;
- WebSocket reuse или replacement.

## 5. Продуктовые принципы

### 5.1 Что убрать из списка принципов

Следующие формулировки являются вариантами интерфейса, а не продуктовыми принципами:

- «вся интерактивность только в личке»;
- «в общем чате только обновляемый закреп»;
- «`/start` сразу показывает ближайшую сходку»;
- «одна кнопка до главного»;
- «всегда редактировать сообщения вместо новых».

Они могут оказаться хорошими решениями отдельных сценариев, но это выясняется при проектировании UX и ограничений Telegram.

### 5.2 Предлагаемая формулировка принципов

#### Принцип 1. Тишина и ненавязчивость

Бот минимизирует шум в общем чате и не конкурирует с человеческим общением. Любое сообщение в общий чат должно быть связано с явно сформулированным сценарием и давать участникам больше ценности, чем создаваемого шума.

Следствия определяются позднее. Возможные механизмы:

- команды;
- silent messages;
- личные сообщения;
- Mini App;
- редактирование ранее созданных сообщений;
- публикация организатором от имени бота;
- закреп — только если оправдан требуемый уровень прав.

#### Принцип 2. Privacy by design и минимальные привилегии

Бот проектируется без необходимости читать произвольную переписку сообщества и получает минимально возможные Telegram permissions.

Практические guardrails:

- Group Privacy Mode включён;
- бот не получает права администратора без отдельного use case и оценки последствий;
- `allowed_updates` ограничивается необходимыми типами;
- неизвестные update types отбрасываются;
- сырые payload сообщений не сохраняются «на всякий случай»;
- текст произвольных сообщений не попадает в аналитику, LLM или долговременные логи;
- service messages и явно адресованные команды обрабатываются только в объёме сценария.

Нельзя обещать абсолютное «бот технически никогда не получает сообщения»: Telegram всё равно присылает некоторые service updates, личные обращения и явно адресованные команды. Корректная гарантия — **бот не запрашивает широкий доступ, не использует и не сохраняет произвольную переписку**.

#### Принцип 3. Минимизация и целевое использование данных

Сохраняются только данные, необходимые для конкретных продуктовых сценариев. Для каждого класса данных должны быть понятны:

- цель обработки;
- владелец;
- срок хранения;
- где данные логируются;
- кто имеет доступ;
- как пользователь может отказаться от уведомлений или удалить необязательные данные.

Особенно это касается:

- Telegram user/profile data;
- RSVP;
- ролей и membership;
- истории уведомлений;
- фотографий и post-event content;
- любых будущих AI-функций.

### 5.3 Закреп как пример конфликта принципа и реализации

Для pin/unpin сообщения в группе Telegram-бот должен быть администратором с соответствующим правом. При этом администратор-бот получает более широкий доступ к сообщениям группы. Поэтому «автоматический закреп» нельзя считать нейтральной UX-деталью: он меняет security/privacy boundary.

Отсюда правильный порядок:

1. определить, действительно ли закреп нужен пользователям;
2. сравнить альтернативы без admin rights;
3. явно принять расширение привилегий, если ценность выше риска;
4. только после этого включать его в требования.

## 7. TypeScript + grammY для Telegram Gateway

### 7.1 Оценка решения

Решение технически обосновано.

Gateway имеет характеристики изменчивого edge-сервиса:

- много UI-сценариев;
- Telegram-specific routing;
- быстрые изменения текстов, кнопок и FSM;
- интеграция с несколькими backend services;
- мало тяжёлых вычислений;
- нет задачи управлять конкурентным доменным агрегатом;
- ценность создаётся скоростью итерации, а не максимальной производительностью на CPU.

Преимущества TypeScript + grammY в этом контексте:

- зрелая Telegram-экосистема;
- сильная типизация Bot API updates;
- быстрый цикл разработки;
- естественная совместимость с будущим TypeScript Mini App;
- возможность разделять runtime-neutral presentation packages;
- доступные библиотеки для gRPC, Protobuf, NATS и OpenTelemetry;
- более низкая стоимость привлечения агента и ручного сопровождения, чем у Rust для UI glue.

### 7.2 Почему не Rust

Rust даёт memory safety, предсказуемый runtime и низкий footprint, но эти преимущества не совпадают с реальными рисками gateway.

Фактические издержки:

- более медленные продуктовые итерации;
- сложнее поддерживать макросы и wrapper plumbing;
- выше порог изменения кода после паузы;
- Telegram gateway не раскрывает ownership/borrowing или системное программирование как учебную цель;
- большая часть кода — orchestration и presentation, а не область преимуществ Rust.

### 7.3 Почему не Go

Go был бы нормальным техническим выбором:

- простой deployment;
- низкий footprint;
- хорошая конкурентность;
- зрелые NATS/gRPC библиотеки.

Но он не даёт сопоставимой комбинации Telegram UX ecosystem и типизированного переиспользования с браузерным TypeScript. После появления grammY Go перестаёт быть лучшим кандидатом именно для этого сервиса.

### 7.4 Почему не Python

Python остаётся сильной альтернативой по скорости разработки и библиотекам Telegram. Он проигрывает выбранному варианту прежде всего по:

- сквозной типизации;
- совместному toolchain с Mini App;
- переиспользованию transport/presentation models;
- compile-time проверкам изменения интерфейсов.

### 7.5 Что можно разделять с Mini App

Можно:

- generated API/protobuf types;
- view models;
- error codes;
- form schemas;
- client-side input validation;
- date/status formatting;
- navigation/action identifiers;
- runtime-neutral utilities.

Нельзя:

- authoritative Meetups aggregates;
- Identity authorization policies;
- серверную проверку Telegram Mini App `initData`;
- bot token;
- NATS credentials;
- gRPC server infrastructure;
- grammY Context/session;
- Node-only code в browser bundle.

Поэтому общий пакет следует называть `presentation-model`, `interaction-model` или `shared-contracts`, но не `domain-core`.

### 7.6 Предварительная структура TypeScript workspace

Это пример границ, а не принятое решение:

```text
apps/
  telegram-gateway/
  mini-app/

packages/
  interaction-model/   # runtime-neutral TS
  generated-contracts/ # Protobuf/API types
  api-client/           # browser/server clients с явными entrypoints
  telegram-auth/        # server-only validation
```

`package.json` exports должны не позволять браузеру случайно импортировать server-only пакеты.

### 7.7 FSM и grammY Conversations

`@grammyjs/conversations` — replay engine, а не обычная последовательная FSM. Это создаёт дополнительные правила:

- внешние DB/network calls должны проходить через `conversation.external`;
- результаты external calls сохраняются для replay;
- conversation storage требует persistence;
- бесконечные разговоры накапливают историю;
- state migrations нужно проектировать при изменении flow;
- конкурентные conversations на одного пользователя требуют явного решения.

Поэтому есть два кандидата:

1. **Явная application FSM**, концептуально похожая на текущую Rust-реализацию.
2. **grammY Conversations**, если spike подтвердит понятную persistence/replay модель.

Выбор между ними не обязан входить в основной ADR языка. Его можно сделать отдельным коротким design decision после реализации одного тестового flow.

### 7.8 Что должен зафиксировать ADR gateway

- контекст смены продуктового центра;
- TypeScript strict + поддерживаемая Node.js LTS + grammY;
- альтернативы Rust, Go и Python;
- gateway не владеет доменом сходок или ролей;
- допустимые общие packages с Mini App;
- privacy/minimal privilege guardrails;
- ordering/concurrency per chat/user;
- persistent dialogue strategy;
- `int64`/`bigint` handling в protobuf;
- Protobuf/NATS/gRPC toolchain;
- long polling против webhook как отдельное deployment decision;
- OTel и structured logging;
- вертикальная стратегия замены Rust gateway;
- критерий удаления старого кода.

## 8. Meetups: как выбирать язык

### 8.1 Почему выбор пока преждевременен

Фраза «F# хорош для домена» сама по себе недостаточна. Сначала нужно понять, является ли Meetups богатым доменом или преимущественно CRUD/workflow.

Потенциальные признаки богатого домена:

- lifecycle `Draft → Published → RegistrationClosed → Cancelled/Completed`;
- правила изменения уже опубликованной сходки;
- RSVP capacity и waitlist;
- дедлайны регистрации;
- организаторы конкретной сходки;
- модерация предложений;
- перенос даты и повторное подтверждение участия;
- отмена и уведомление участников;
- privacy видимости участников;
- повторяемые сходки;
- конкурентные RSVP на последнее место.

Если эти правила действительно входят в ближайший scope, F# становится сильнее. Если v1 — карточка, календарь и простой RSVP без capacity, C# может дать лучший product throughput.

### 8.2 Метод выбора

Не рекомендуется сразу назначать числовые веса и складывать субъективные баллы. Лучше использовать два этапа.

#### Этап 1. Обязательные ограничения

Кандидат исключается, если не проходит must-have:

- приемлемая скорость итерации владельца;
- зрелый Postgres stack;
- gRPC/Protobuf;
- NATS integration;
- тестирование;
- observability;
- поддержка CI и контейнеризации;
- понятный upgrade path;
- отсутствие второго тяжёлого учебного stack одновременно с gateway rewrite.

#### Этап 2. Сравнение прошедших кандидатов

Оценивать:

- выразительность lifecycle и invariants;
- стоимость последующих изменений;
- ergonomics ошибок и validation;
- transaction/outbox support;
- tooling и debugger;
- integration с Aspire;
- runtime footprint;
- знакомство владельца;
- учебную ценность именно этого сервиса;
- качество agent-assisted разработки;
- стоимость возвращения к проекту после паузы.

### 8.3 Предварительная оценка кандидатов

| Кандидат | Сильные стороны | Основные риски | Предварительный статус |
|---|---|---|---|
| **C# + ASP.NET Core** | Максимальная скорость, знакомая экосистема, EF/gRPC/OTel/Aspire | Меньше принуждения к моделированию инвариантов типами | Прагматичный baseline |
| **F# + ASP.NET Core** | ADT, pattern matching, making illegal states unrepresentable, общий .NET runtime | Tooling/interop, меньше примеров библиотек, цена поддержки функционального стиля | Сильный кандидат при богатом домене |
| **Kotlin + Ktor/Spring** | Выразительная модель, зрелая JVM, хороший компромисс OO/FP | Новый Gradle/JVM контур в критическом пути, конкурирует с будущей Scala-целью за внимание | Сильный кандидат, если учебная цель оправдывает цену |
| **Go** | Простота, deployment, observability, concurrency | Слабее моделирует сложные состояния, больше ручных validation/state checks | Кандидат только для простого CRUD/workflow |

### 8.4 Рекомендуемый decision experiment

До ADR не нужно писать четыре сервиса. Достаточно одного human-led domain sketch:

1. жизненный цикл сходки;
2. RSVP с одним нетривиальным ограничением, например capacity/waitlist;
3. отмена или перенос опубликованной сходки;
4. role check организатора конкретной сходки;
5. список ошибок, которые должен увидеть пользователь.

Затем для C#, F# и Kotlin сравнить, как выражаются:

- состояния;
- команды;
- переходы;
- ошибки;
- persistence boundary;
- тесты инвариантов.

Это может быть paper design или маленький throwaway spike. Цель — не выбрать «самый красивый код», а понять совокупную стоимость реального сервиса.

## 9. Identity как отдельный сервис

### 9.1 Решение о границе

Владелец проекта решил оставить Identity отдельным сервисом. Это допустимое стратегическое решение, особенно если и Telegram gateway, и Mini App станут отдельными потребителями.

Но сервис не должен превращаться в абстрактный RBAC-framework ради микросервисности.

### 9.2 Предлагаемая граница ответственности

Identity, вероятно, владеет:

- internal user ID;
- связью с Telegram user ID;
- membership в сообществе;
- статусом пользователя;
- глобальными ролями `admin` и `owner`;
- глобальными grants/blocks;
- минимальными consent/preferences, если они не принадлежат Notifications.

Meetups, вероятно, владеет:

- организаторами конкретной сходки;
- участием/RSVP;
- правом редактировать конкретную сходку;
- приглашениями и делегированием внутри meetup lifecycle.

Telegram gateway владеет только:

- проверкой подлинности входящего Telegram update;
- переводом Telegram principal во внутренний запрос;
- presentation-level routing;
- краткоживущим кэшем authorization facts, если это будет принято отдельно.

### 9.3 Вопросы до выбора языка

- Что считать регистрацией пользователя?
- Нужен ли internal user до первого `/start`?
- Как подтверждается membership в приватном сообществе?
- Какие данные Telegram сохраняются?
- Что происходит, если Identity недоступен?
- Допустим ли cached authorization?
- Как инвалидировать роли?
- Нужен ли audit trail назначения ролей?
- Какие роли глобальны, а какие context-specific?
- Как Mini App получает и обновляет identity context?

### 9.4 Предварительные кандидаты

- **C#** — самый безопасный прагматичный выбор.
- **Kotlin** — сильный кандидат при желании изучать JVM на реальном security/data сервисе.
- **F#** — оправдан, только если policy model действительно сложна.
- **Go** — возможен для простой identity mapping, но решение не должно появляться только потому, что Go «освободился».

## 10. Notifications и вопрос scheduler

### 10.1 Scheduler пока не является сервисом

Слово `scheduler` сейчас описывает механизм, а не bounded context. До требований нет оснований создавать отдельный deployable unit.

Правильные вопросы:

- кто определяет момент напоминания;
- кто хранит расписание;
- что происходит при переносе/отмене сходки;
- как пережить рестарт;
- как предотвращается повторная доставка;
- нужны ли quiet hours;
- кто хранит notification preferences;
- как обрабатываются временные зоны;
- какая допустима задержка;
- что делать после длительного outage;
- как пользователь отписывается.

### 10.2 Основные варианты

#### Вариант A. Scheduling внутри Notifications

Notifications хранит jobs и владеет доставкой.

Плюсы:

- единая ответственность за reminder lifecycle;
- не нужен новый сервис;
- текущий C# stack можно расширить Quartz/Hangfire/background worker.

Минусы:

- сервис становится stateful;
- нужно явно синхронизировать переносы и отмены сходок.

#### Вариант B. Scheduling внутри Meetups

Meetups создаёт due events/commands.

Плюсы:

- время тесно связано с источником данных;
- перенос сходки обрабатывается рядом с доменом.

Минусы:

- доменный сервис начинает владеть механикой доставки;
- сложнее отделить повторные каналы уведомлений.

#### Вариант C. Отдельный Scheduler

Плюсы:

- переиспользование для разных доменов;
- отдельная учебная задача.

Минусы:

- ещё один сервис, контракт, deployment и failure modes;
- сейчас нет второго реального потребителя;
- высокий риск создать инфраструктурный сервис ради Go.

Предварительно вариант A выглядит наиболее экономным, но решение должно появиться после flows и reliability requirements.

### 11.4 Зависимости удаления

Полное удаление `auction-service` не равно удалению одного каталога. Аукционный slice включает:

- `services/auction-service`;
- значительную часть Rust gateway;
- `BidPlacedHandler` в notifications;
- websocket-gateway;
- auction proto contracts;
- nats-tester samples;
- Aspire topology;
- CI jobs;
- service docs и ADR references.

#### Минимальная

Удалить producer, но временно оставить contracts и frozen consumers. Быстрее, но legacy продолжает влиять на build и docs.

#### Чистая

Архивировать и убрать весь auction slice из active topology/build, оставив только долговечные артефакты и Git tag. Требует больше одномоментной работы, но резко снижает когнитивный шум.

Предпочтительна чистая стратегия после завершения archaeology pass.

### 11.5 Auction v2

Стратегическое направление можно сформулировать узко:

> После завершения ядра сходок аукцион проектируется как новый отдельный сервис на Scala + Apache Pekko. Это не миграция существующего C#/Akka.NET кода. Продуктовые правила и уроки прототипа используются как входные данные, но архитектура переоценивается заново.

Такой ADR не должен заранее выбирать:

- конкретную версию Scala/Pekko;
- JDBC против R2DBC;
- Projection/read model stack;
- cluster sharding;
- actor hierarchy;
- schema evolution;
- WebSocket topology.

## 12. Инфраструктура и hosting

### 12.1 Три разных контура

#### Daily local development

Цель: быстрый цикл разработки.

Кандидат: Aspire.

- инфраструктура контейнерами;
- сервисы Local/Container/Off;
- dashboard;
- service discovery;
- logs/traces;
- минимум Kubernetes complexity.

#### Production-like integration

Цель: изучение оркестрации и репетиция deployment.

Кандидат: локальный k3s/k3d или отдельный staging VPS.

- manifests/Helm;
- ingress;
- secrets;
- persistence;
- restart/recovery;
- resource limits;
- upgrades.

#### Production hosting

Цель: надёжно провести реальную сходку.

Кандидаты:

- домашний mini-PC;
- VPS;
- Railway fallback.

### 12.2 Почему deployment не обязан быть M0

Ранний deployment снижает поздний операционный риск, но инфраструктура без продукта тоже может стать формой прокрастинации. Поскольку:

- mini-PC ещё нет;
- ядро Meetups/Identity не начато;
- текущий stack будет существенно меняться;
- Linear уже отражает более поздний milestone;

разумно сначала стабилизировать локальный вертикальный срез, затем поднимать production-like и production окружение.

Важно лишь не откладывать первый внешний запуск до недели перед живой сходкой.

### 12.3 Как заменить ADR-006

ADR не должен притворяться, что mini-PC уже выбран. Возможное решение:

- self-managed infrastructure — основной учебный вектор;
- VPS и домашний сервер остаются кандидатами;
- Railway сохраняется как fallback;
- критерии окончательного выбора: наличие оборудования, публичный HTTPS для Mini App, доступность, стоимость, backup, энергопитание, удалённый доступ, recovery time;
- решение принимается перед первым production deployment.

Это честное архитектурное решение о стратегии и критериях, а не преждевременный выбор железа.

### 12.4 Aspire и k3s не конкуренты

ADR-021 можно оставить, уточнив scope:

- Aspire — основной local developer experience;
- k3s — отдельный integration/deployment environment;
- `aspire publish` может помогать генерировать артефакты, но не должен быть единственным способом понять production manifests;
- production topology требует отдельного ADR.

## 13. Protobuf, Schema Registry и эволюция контрактов

### 13.1 Что остаётся правильным

- Protobuf является wire format;
- `contracts/proto/` — source of truth в Git;
- кодогенерация выполняется для каждого языка;
- изменение контрактов должно проверять всех потребителей;
- JSON в NATS остаётся нарушением.

### 13.2 Какие задачи ошибочно объединены словом Registry

#### Source control

Где хранится авторитетная версия схем. Git уже решает эту задачу.

#### Compatibility validation

Можно ли безопасно изменить поле, enum, package или message. Это может решаться CI-инструментом без runtime registry.

#### Distribution/discovery

Как независимые команды или репозитории получают схемы и generated clients.

#### Runtime schema resolution

Передаётся ли schema ID вместе с сообщением и загружает ли consumer схему динамически.

#### Учебная эксплуатация

Хочется ли отдельно изучить registry, compatibility modes, auth, backup и upgrades.

### 13.3 Рекомендуемая ближайшая ступень

До возврата Apicurio:

1. добавить `buf lint`;
2. добавить `buf breaking` относительно main/tag;
3. определить правила reserved fields/numbers;
4. определить versioning packages/messages;
5. убедиться, что CI действительно пересобирает всех потребителей;
6. добавить wire compatibility tests для важных событий.

Это решает наиболее вероятную текущую проблему — случайный breaking change — без runtime-компонента.

### 13.4 Когда Registry становится оправдан

- сервисы деплоятся независимо;
- одновременно живут несколько поколений consumers;
- контракты потребляются вне монорепозитория;
- нужен каталог и discoverability;
- нужна централизованная compatibility policy;
- generated artifacts распространяются независимо;
- runtime schema identifiers дают конкретную пользу;
- операционная стоимость является осознанной учебной целью.

### 13.5 Статус ADR

- ADR-014 пока остаётся действующим;
- ADR-008 нужно явно пометить заменённым ADR-014;
- возврат Schema Registry — Proposed/research;
- даже при возврате Registry Git может остаться source of truth.

## 14. NATS, JetStream и синхронные команды

### 14.1 Текущее несоответствие

ADR-003 выбирает NATS JetStream, а текущие сервисы используют core NATS subscriptions. JetStream enabled на сервере не делает сообщения durable автоматически.

Фактическая семантика сейчас:

- at-most-once;
- потеря сообщений при downtime consumer;
- отсутствие durable consumer state;
- отсутствие системной идемпотентности;
- `op_id` сам по себе ничего не гарантирует.

### 14.2 Когда JetStream становится продуктовым требованием

Для live UI потеря промежуточного события может быть допустима, если клиент перечитывает текущее состояние.

Для reminder delivery потеря события или job может привести к невыполненному обещанию пользователю. Поэтому delivery semantics нужно решить до реализации гарантированных напоминаний, а не обязательно до первого `GetNearestMeetup`.

### 14.3 Ограничение ADR-016

Текущее правило «CRUD/query → gRPC, команда к stateful aggregate → NATS» выросло из аукциона. Его нельзя автоматически применять к Meetups.

Например, RSVP требует немедленного ответа:

- пользователь должен узнать, принят ли RSVP;
- capacity может быть исчерпан;
- ошибка должна быть показана сразу;
- UI не должен гадать, обработалась ли команда.

Возможный вариант:

1. синхронный command endpoint через gRPC/HTTP;
2. транзакционное изменение состояния;
3. outbox;
4. асинхронная публикация `RsvpConfirmed`;
5. notifications реагирует на событие.

Это не готовое решение, а причина пересмотреть универсальность ADR-016.

## 15. Матрица языков и technology pool

### 15.1 Принцип

Язык выбирается не потому, что он интересен, и не потому, что для него нашёлся свободный микросервис. Должны одновременно существовать:

- реальная продуктовая граница;
- требования;
- преимущество языка или учебная цель;
- приемлемая операционная цена;
- готовность поддерживать сервис после окончания учебного интереса.

### 15.2 Предварительная карта

| Язык | Текущий разумный статус |
|---|---|
| TypeScript | Выбранное направление для gateway; Mini App естественно будет TS |
| C# | Прагматичный backend baseline; notifications остаётся C# |
| F# | Сильный кандидат для богатого Meetups domain |
| Kotlin | Пул интереса; кандидат Meetups/Identity при осознанной цене JVM stack |
| Go | Пул интереса без назначенного сервиса |
| Scala | Стратегически зарезервирована для будущего auction v2 |
| Ruby | Пул интереса; конкретного продукта/admin use case пока нет |
| Python | Tooling и nats-tester; не выбран для продуктового backend |
| Rust | Текущий legacy gateway; нового подходящего слота пока нет |

### 15.3 Почему не нужен ADR «список интересных языков»

ADR фиксирует принятое решение и его последствия. «Мне интересен Ruby» не меняет архитектуру и не создаёт обязательств. Для этого достаточно technology radar или секции learning interests в roadmap.

Нужны:

- один ADR о критериях выбора языка, если это cross-cutting правило;
- отдельный stack ADR для каждого реально начинаемого сервиса.

## 16. Процесс проектирования: что сохранить из D0–D8

### 16.1 Общая оценка

D0–D8 содержит хорошие инженерные вопросы, но как обязательный конвейер создаёт риск:

- имитировать архитектурную работу;
- плодить документы раньше понимания;
- отдавать агенту фактическое авторство решения;
- тратить одинаковое время на разные риски;
- считать заполненный шаблон доказательством качества.

Правильная роль D0–D8 — **чеклист доступных техник**, а не pipeline, который обязан пройти каждый сервис.

### 16.2 Разбор шагов

#### D0 — проблема и границы

Сохранить обязательно для новой инициативы.

Полезно:

- роли;
- наблюдаемый результат;
- scope/non-scope;
- затронутые стороны.

Слишком жёстко:

- запрет любого технического термина. Иногда constraint вроде Telegram-only или отсутствия чтения сообщений является частью проблемы.

#### D1 — сценарии и потоки

Сохранить для продуктовых функций.

Обязательно включать:

- happy path;
- отказ;
- отмену/повтор;
- административный сценарий;
- результат, наблюдаемый человеком.

Не нужно искусственно требовать ровно 3–5 сценариев.

#### D2 — домен и события

Использовать при наличии lifecycle, invariants и конкуренции.

Не каждый сервис нуждается в event storming. Gateway adapter или websocket relay не становятся лучше от искусственного поиска агрегатов.

Если инвариантов нет, это действительно сигнал к упрощению дизайна, но не обязательно «понижение тира» как формальная процедура.

#### D3 — функциональные и нефункциональные требования

Сохранить risk checklist:

- consistency;
- idempotency;
- concurrency;
- failure mode;
- time;
- privacy;
- observability;
- evolution;
- volume.

Требования должны быть проверяемыми. Число требуется там, где оно осмысленно. Нельзя искусственно придумывать числовой privacy target ради шаблона.

#### D4 — варианты и ADR

Сохранить для решений с последствиями.

Хорошие элементы:

- альтернатива status quo/defer;
- что становится сложнее;
- prediction/revisit trigger.

Не нужно требовать ровно три варианта для каждой библиотеки или механической задачи.

#### D5 — контракты

Внешний контракт действительно следует проектировать до реализации consumer/producer.

Но нельзя считать DB schema таким же необратимым, как публичный proto. Внутренняя схема может развиваться вместе с vertical slice, особенно до production data.

#### D6 — декомпозиция

Сохранить принцип вертикальных срезов. Каждая задача должна завершаться наблюдаемым результатом или проверяемой capability.

Декомпозиция живёт в Linear, а не дублируется полностью в Markdown.

#### D7 — реализация

Сохранить правило: существенное отклонение от принятой архитектуры возвращается на обсуждение.

Но не каждое локальное уточнение требует нового ADR. ADR нужен, когда меняется решение или его последствия, а не при переименовании внутреннего класса.

#### D8 — ретро

Сохранить обязательно для дорогих или учебных решений.

Триггер лучше привязать не к календарным 2–4 неделям, а к событию:

- первый production-like прогон;
- первый реальный meetup;
- неверное prediction;
- incident;
- обнаружение новой границы;
- завершение миграции.

## 17. Предлагаемый процесс человек–агент

### 17.1 Четыре контрольные точки

#### A. Сформулировать

Ведёт человек.

Минимальный brief:

- проблема;
- роли;
- наблюдаемый успех;
- scope/non-scope;
- исходная гипотеза владельца;
- что хочется изучить;
- что нельзя ухудшить.

#### B. Оспорить

Агент:

- проверяет текущее состояние кода;
- исследует незнакомые технологии;
- ищет противоречия;
- расширяет список вариантов;
- строит failure/privacy/concurrency cases;
- проверяет предположения по первичным источникам;
- задаёт неприятные вопросы.

Агент не превращает свою рекомендацию в принятое решение.

#### C. Решить и нарезать

Человек:

- выбирает компромисс;
- может пересказать, почему отклонены альтернативы;
- принимает риски.

Агент:

- оформляет ADR;
- проверяет согласованность с другими документами;
- предлагает contracts;
- режет работу на vertical slices;
- создаёт черновики Linear issues.

#### D. Реализовать и проверить

Агент:

- реализует только утверждённый slice;
- пишет тесты;
- обновляет документацию в том же изменении;
- сообщает об отклонении от дизайна;
- не расширяет scope без согласования.

Человек:

- ревьюит результат и архитектурные отклонения;
- принимает следующий slice;
- проводит содержательное ретро.

### 17.2 Матрица ответственности

| Область | Человек | Агент |
|---|---|---|
| Продуктовая цель | Владеет | Уточняет и проверяет противоречия |
| Первая гипотеза | Формулирует | Критикует |
| Технологические факты | Оценивает значимость | Исследует и даёт источники |
| Альтернативы | Участвует | Расширяет список |
| Trade-off | Принимает | Делает последствия явными |
| ADR | Утверждает аргументацию | Черновик и consistency audit |
| Контракт | Утверждает semantics | Генерирует варианты и проверяет consumers |
| Linear decomposition | Приоритизирует | Предлагает vertical slices |
| Реализация | Контролирует scope/review | Выполняет после checkpoint |
| Ретро | Интерпретирует результат | Собирает факты и расхождения |

### 17.3 Как выбирать глубину проектирования

Вместо T1/T2/T3 использовать risk triggers.

Полный дизайн нужен, если присутствует хотя бы несколько факторов:

- новый service boundary;
- ownership данных;
- privacy/security;
- публичный контракт;
- миграция production data;
- новый язык/runtime;
- распределённая согласованность;
- гарантированная доставка;
- сложный lifecycle;
- высокая стоимость отмены решения.

Короткого design note достаточно, если:

- изменение внутреннее;
- contract не меняется;
- данные не мигрируют;
- решение легко обратимо;
- отсутствуют новые failure modes;
- механика уже закреплена ADR.

### 17.4 Где живут артефакты

| Артефакт | Место | Чего там не должно быть |
|---|---|---|
| Product/service brief | `docs/02_SERVICES/` | Текущего task status |
| Долговечное решение | ADR | Полного implementation plan |
| Межсервисный контракт | `contracts/proto/` | Бизнес-объяснений без ссылок |
| Семантика subjects/errors | `docs/03_CONTRACTS/` | Дублированных generated types |
| Работа и приоритет | Linear | Долговечной причины решения только в комментарии |
| Крупный технический план | `docs/06_TASKS/` | Копии каждой мелкой Linear-задачи |
| Дизайн UI | `docs/05_DESIGN/` | Неутверждённого вида без статуса Draft |
| Ретро | service doc или archive | Переписывания истории ADR |

Для design docs полезен короткий header:

```markdown
Status: Draft | Reviewed | Accepted | Superseded
Decision owner: <name>
Last validated: YYYY-MM-DD
Related ADR: ADR-XXX | none
```

## 22. Рекомендуемая последовательность следующей работы

### Этап A. Синхронизация контекста

Без реализации сервисов:

1. утвердить новые продуктовые/privacy-принципы;
2. утвердить статусную модель Current/Target/Future/Legacy;
3. оформить ADR gateway;
4. заменить ADR-013;
5. пометить устаревшие ADR;
6. привести roadmap к Linear.

### Этап B. Human-led проектирование ядра

Владелец проекта готовит короткий первый черновик:

- D0 Meetups;
- основные user/admin flows;
- набросок lifecycle и invariants;
- границу Identity;
- исходную гипотезу по языку.

Агент после этого:

- оппонирует;
- исследует технологии;
- добавляет failure/privacy cases;
- формирует сравнительную матрицу;
- не принимает решение вместо владельца.

### Этап C. Решения

1. ADR boundary Meetups/Identity.
2. ADR stack Meetups.
3. ADR stack Identity.
4. Contract governance minimum.
5. Contracts первого vertical slice.

### Этап D. Первый вертикальный срез

Предлагаемый демонстрируемый результат:

```text
Telegram user
  → gateway принимает явную команду/callback
  → Identity разрешает internal principal
  → Meetups возвращает ближайшую опубликованную сходку
  → gateway показывает карточку
```

В этом срезе не нужны:

- аукцион;
- закреп;
- Mini App;
- scheduler;
- notifications;
- JetStream;
- production deployment;
- rich RBAC;
- content feed.

Срез проверяет главные архитектурные границы и даёт пользователю первый продуктовый результат.

### Этап E. Последующие срезы

1. календарь сходок;
2. RSVP;
3. organizer permissions;
4. создание/публикация сходки;
5. перенос/отмена;
6. reminders;
7. production-like запуск;
8. deployment до реальной сходки с достаточным запасом.

## 24. Итоговая позиция

1. **Главное направление верное:** v1 строится вокруг сходок, а не аукциона.
2. **TypeScript + grammY — обоснованный выбор gateway**, если не превращать общий TS-код в источник backend-инвариантов.
3. **Meetups нельзя заранее назначать F#**, но F# остаётся сильным кандидатом наряду с C# и Kotlin.
4. **Identity остаётся отдельным сервисом**, однако meetup-specific authorization, вероятно, принадлежит Meetups.
5. **Notifications можно оставить на C#**, но текущий auction handler не делает его готовым reminder service.
6. **Старый аукцион лучше убрать из active tree после извлечения знаний**, а не держать вечным замороженным кодом.
7. **Scala/Pekko — стратегическое направление будущего auction v2**, не текущая задача.
8. **Kotlin, Go и Ruby остаются пулом интереса**, а не заранее выданными назначениями.
9. **Aspire и k3s решают разные задачи**; поздний production deployment не отменяет локальную оркестрацию.
10. **Schema Registry можно вернуть в исследование**, но compatibility checks в CI следует отделить от runtime registry.
11. **D0–D8 нужно упростить до human-owned design loop**, сохранив полезные вопросы и отказавшись от одинаковой церемонии для каждого сервиса.
12. **Первый vertical slice должен пройти через Gateway → Identity → Meetups**, потому что он проверяет новое ядро и даёт реальный пользовательский результат.

Главный критерий успеха актуализации: после чтения документации должно быть невозможно перепутать существующий аукционный прототип, принятые решения v1 и дальние учебные гипотезы.
