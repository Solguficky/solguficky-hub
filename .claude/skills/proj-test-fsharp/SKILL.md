# Тестировать F#-код

Порядок работы ниже, форма теста и примеры на каждое правило — в нормативе [testing/fsharp.md](../../../docs/standards/testing/fsharp.md). Открой его вместе с этим skill: примеры живут там и здесь не повторяются. Выбор уровня задаёт [testing-strategy.md](../../../docs/standards/testing/testing-strategy.md), языковые правила дополняет `proj-write-fsharp`.

## 1. Выбери минимальный честный уровень

Сформулируй наблюдаемое свойство и возьми самый дешёвый уровень, способный его опровергнуть.

| Свойство | Уровень |
|---|---|
| доменное решение, переход состояния, отклонённый переход, идемпотентный повтор | чистый unit |
| отображение границы: `null`, отсутствующее поле, неизвестный enum, round trip | чистый unit |
| оркестрация workflow с подставленными зависимостями | unit с `Deps` |
| SQL, транзакция, миграция, Protobuf serialization, реальный transport | integration |
| сквозное пользовательское обещание | E2E |

Доменную комбинацию не поднимай в Aspire и E2E. SQL, Protobuf и transport не объявляй проверенными тестом над моком клиента.

Прочитай `.fsproj`, управление пакетами и `--help` настроенного xUnit v3 runner до копирования команды фильтрации. Рецепты xUnit v2 и старого VSTest сюда не переносятся; рукописный `Program.fs` в тестовом проекте не заводится — точку входа даёт сам xUnit v3.

## 2. Собери детерминированный сценарий

Время, UUID, random seed и ответы зависимостей передавай явно. Arrange описывает значимые факты, act вызывает один публичный workflow или функцию, assert проверяет результат через Unquote одной цитатой: он печатает разобранное выражение с фактическими значениями, и разбиение на подготовительные проверки эту диагностику теряет.

Покрой happy path, каждый затронутый case error DU, пограничное значение и безопасный повтор изменяющей команды. Private-функцию напрямую не проверяй, если то же свойство видно через публичную сигнатуру.

Имя теста — обратные кавычки с предложением, описывающим проверяемое свойство. Одна форма имени на файл.

## 3. Используй подходящий double

Порядок выбора: чистая функция, record of functions, маленький handwritten fake, затем Moq для неудобной .NET-interface boundary.

Поле `Deps`, которое тест не переопределил, обязано падать с внятным сообщением. Заглушка, молча возвращающая `None` или пустой список, превращает пропущенный вызов в зелёный тест.

F#-record и DU не мокаются: их создают значением. Не воспроизводи implementation sequence цепочкой `Verify` — проверяй наблюдаемый результат.

Реальную PostgreSQL и другую инфраструктуру поднимай Testcontainers только ради свойства самой границы. Контейнер получает уникальные данные, readiness check и гарантированный disposal; production endpoint запрещён.

## 4. Добавь property там, где это инвариант

FsCheck закрывает пространство значений, а не заменяет примеры. Property формулирует инвариант — «применение принятого события увеличивает версию один раз», «encode/decode сохраняет смысл», — а не повторяет реализацию.

Домен с приватным конструктором требует своего generator: произвольный `int` не является `Quantity`. Валидные доменные значения и невалидные примитивы границы генерируются раздельно. Полезный сокращённый counterexample сохраняй отдельным regression example.

## 5. Проверь тест

Сначала узкий проект или class filter, затем общий one-shot test command компонента. Повтори тест, если он затрагивает concurrency, время или инфраструктуру.

Убедись, что тест краснеет при нарушении заявленного свойства, а не только зеленеет на текущей реализации, и что все поднятые ресурсы освобождены.
