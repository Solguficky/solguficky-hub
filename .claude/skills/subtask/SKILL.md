# Делегирование подзадачи

Оркестратор (эта сессия) остаётся единственной точкой, где живёт общий контекст.
Подзадачи уезжают подагентам на Opus в изолированные worktree, результат
собирается в интеграционной ветке.

## Топология

```
main
 └── integration/<тема>          ← постоянный worktree .claude/worktrees/integration-<тема>
      ├── (merge --no-ff) ← ветка подагента A
      ├── (merge --no-ff) ← ветка подагента B
      └── ...
```

Оркестратор **никогда не переключает ветку в своей рабочей копии**. Git не
позволяет зачекаутить одну ветку в двух worktree, а сессия оркестратора уже
занимает свою. Поэтому все операции с интеграционной веткой делаются снаружи
через `git -C <путь-к-integration-worktree>`.

## Шаг 1. Интеграционная ветка

Определи тему (короткий kebab-case, например `sxodki-core`). Спроси
пользователя, если она не очевидна из задачи.

```bash
INTEGRATION_WT=".claude/worktrees/integration-<тема>"

# Создать, если ещё нет. Ветка ответвляется от main.
git show-ref --verify --quiet refs/heads/integration/<тема> \
  || git worktree add -b integration/<тема> "$INTEGRATION_WT" main

# Если ветка есть, а worktree нет — подцепить существующую ветку.
test -d "$INTEGRATION_WT" \
  || git worktree add "$INTEGRATION_WT" integration/<тема>
```

Одна тема — одна интеграционная ветка, живёт через несколько подзадач.

## Шаг 2. Промпт для подагента

**Это самый важный шаг.** Подагент стартует холодным: он не видит ни истории
диалога, ни того, что ты уже выяснил. Всё, что ему нужно, должно быть в промпте.
Плохой промпт здесь — главная причина, по которой такой флоу разваливается.

Включи в промпт:

- **Задачу** — конкретно, с критерием готовности.
- **Куда смотреть** — пути к файлам/сервисам, релевантные ADR (номера), темы
  NATS, если задача их касается. Ты уже знаешь, где это; подагент — нет.
- **Границы** — что явно НЕ трогать. Особенно важно, если параллельно бежит
  другая подзадача: перечисли файлы, занятые соседом.
- **Решения, уже принятые в этой сессии** — иначе подагент переоткроет вопрос
  и может решить иначе.

Не пересказывай `AGENTS.md` — подагент прочитает его сам, это в его инструкции.

## Шаг 3. Запуск

```
Agent(
  subagent_type: "subtask-impl",
  isolation: "worktree",
  description: "<3-5 слов>",
  prompt: "<промпт из шага 2>"
)
```

`model` не указывай — он зафиксирован как `opus` в `.claude/agents/subtask-impl.md`.
`isolation: "worktree"` сам создаст подагенту worktree и ветку.

Подзадачи, не пересекающиеся по файлам, можно запускать параллельно — несколькими
вызовами `Agent` в одном сообщении. Пересекающиеся — только последовательно,
иначе гарантированный конфликт при мерже.

## Шаг 4. Мерж

Подагент возвращает имя своей ветки в финальном отчёте. Если не вернул — достань
его: `git branch --sort=-committerdate --format='%(refname:short)' | head -5`.

Мержишь **автоматически, если чисто**. Порядок:

```bash
BRANCH="<ветка подагента>"

# 1. Проверки подагента должны быть зелёными. Если он отчитался о красных
#    тестах или о нерешённом архитектурном вопросе — НЕ мержи, докладывай.

# 2. Мерж
git -C "$INTEGRATION_WT" merge --no-ff "$BRANCH" -m "merge: <краткое описание подзадачи>"
```

Если мерж упал с конфликтом:

```bash
git -C "$INTEGRATION_WT" merge --abort
```

и доложи пользователю: какая ветка, какие файлы конфликтуют, что предлагаешь.
**Конфликты не разрешай молча** — это решение пользователя, и оно часто означает,
что подзадачи были нарезаны неправильно.

## Шаг 5. Проверка объединённого результата

Мерж двух зелёных веток может дать красный результат — каждый подагент проверял
только свою половину. Прогони сборку по затронутым сервисам уже в интеграционном
worktree:

```bash
git -C "$INTEGRATION_WT" status --short   # должно быть пусто
# затем dotnet build && dotnet test / cargo test — из соответствующей папки
# внутри $INTEGRATION_WT
```

Если после мержа красно — доложи и предложи откат:
`git -C "$INTEGRATION_WT" reset --hard HEAD~1`. Сам не откатывай.

## Шаг 6. Уборка и отчёт

```bash
git worktree list                    # посмотреть, что накопилось
git worktree remove <path>           # убрать worktree отработавшего подагента
```

Ветку подагента после успешного мержа не удаляй сразу — она дешёвая, а история
подзадачи иногда нужна. Предложи почистить, когда интеграционная ветка уедет в
`main`.

Доложи пользователю коротко: что сделал подагент, смержено или нет, состояние
проверок. Полный отчёт подагента не пересказывай целиком — только то, что влияет
на решения.

## Чего не делать

- Не пушить ничего в remote и не открывать PR без явной просьбы.
- Не мержить интеграционную ветку в `main` самостоятельно.
- Не запускать подагента на задаче, которая требует нового архитектурного
  решения. Сначала ADR (скилл `adr`), потом делегирование — по ADR-013 решение
  обсуждается до кода.
- Не дробить на подзадачи то, что быстрее сделать самому. Каждый подагент
  стартует холодным, и стоимость передачи контекста реальна.
