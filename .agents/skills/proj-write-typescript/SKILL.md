# Писать TypeScript

Правила ниже задают форму кода, примеры на каждое — [references/patterns.md](references/patterns.md). Проектирование модулей ведёт `codebase-design`, порядок test-first — `tdd`, состав полей лога — [logging.md](../../../docs/standards/observability/logging.md). Здесь только язык.

## 1. Прочитай конфигурацию

Ближайший `AGENTS.md`, `package.json`, `tsconfig*` и настроенные lint, typecheck, test и build scripts. Существующая конфигурация — источник правды: следуй её module system, strictness flags и стилю импортов.

Конфигурации ещё нет — остановись и спроси владельца про package manager, module system, linter и test runner. Выбор стека принадлежит ему.

Сгенерированный код Protobuf лежит в `gen/`, рождается командой `buf generate` и меняется только правкой `.proto` ([стандарт](../../../docs/standards/contracts/protobuf.md#кодогенерация-typescript)). Формат сообщения там уже проверил рантайм `@bufbuild/protobuf`: схему поверх сгенерированного типа не заводят, доменные инварианты проверяет юзкейс.

## 2. Граница данных

- Внешние данные принимай как `unknown` и разбирай Zod-схемой в именованный доменный тип. `Record<string, unknown>` заканчивается на этом разборе, внутри границы типам доверяют.
- Тип выводи из схемы через `z.infer`, чтобы схема и тип не разошлись. Общие части собирай `.extend()`, `.pick()`, `.omit()` и `.merge()`, нормализацию делай `.transform()` в момент разбора.
- Ожидаемо некорректный ввод разбирай `safeParse` и возвращай отказ значением. `parse` оставь месту, где невалидные данные означают дефект соседа, а не ошибку человека.

## 3. Типы

- Варианты моделируй discriminated union с литеральным дискриминантом, а набор связанных optional-полей заменяй вариантами. Полноту разбора закрепляй `const _exhaustive: never = x` в default-ветке.
- Стройся так, чтобы недопустимое значение нельзя было собрать: `[T, ...T[]]` для непустого списка, проверенный положительный тип для длительности. Это дешевле повторной проверки и не требует «этого не бывает».
- Литеральный union выводи из `as const`-массива через `typeof ROLES[number]`, чтобы список значений и тип оставались одним фактом.
- До объявления нового интерфейса проверь, выводится ли он из существующего: `Pick`, `Omit`, `Parameters`, `ReturnType`, `Awaited`, `typeof`.
- Branded type заводи там, где одинаковые primitives реально смешиваются на границе, и брендируй один раз при создании из проверенного значения. Generic или conditional type — когда он снимает повторение у нескольких потребителей, а не предсказывает будущее расширение.
- В остальных случаях бери простейший достаточный тип и усиливай его там, где слабый вынуждает cast, `!` или бросок «этого не бывает».

## 4. Сужение

- Порядок предпочтения: дискриминант в `switch`, затем `in`, затем `typeof` и `instanceof`, затем собственный type guard, и только потом `as`.
- Type guard проверяет ровно то, что обещает, и называется `isX` или `hasX`. Guard, который лжёт, хуже `as`: ошибка прячется за именем, утверждающим безопасность.
- Форму литерала проверяй `satisfies`: он валидирует значение, не расширяя литеральные типы.
- `as`, non-null assertion и `any` требуют доказанного внешнего ограничения, невыразимого типами, и пояснения рядом с местом ослабления.

## 5. Ошибки, асинхронность и логи

- Ожидаемый отказ возвращай именованным результатом, неожиданную ошибку сохраняй вместе с причиной в `cause`.
- Для I/O бери async API, а независимые операции запускай конкурентно, когда их порядок не несёт семантики.
- Пиши структурным логгером по каркасу [logging.md](../../../docs/standards/observability/logging.md). В рабочем коде остаётся логгер, а не `console.log`.

## 6. Сигнатуры

Три и больше параметра передавай объектом, чтобы на месте вызова читался смысл, а не порядок. Позиционные аргументы оставь горячему пути.

## 7. Проверь изменение

Прогоняй существующие one-shot scripts: как минимум lint, typecheck и test, а build добавляй, когда менялись exports, конфигурация пакета или сборочный выход. Watch и serve проверкой не являются.

Изменение готово, когда эти команды зелёные, а каждое ослабление типа объяснено рядом с местом ослабления.
