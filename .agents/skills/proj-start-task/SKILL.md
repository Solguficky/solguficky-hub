# Открыть контур задачи

Норматив — [agent-execution-loop.md](../../../docs/development/agent-execution-loop.md) и [branching.md](../../../docs/standards/git/branching.md). Не воспроизводи их по памяти: границы контура, условия чекпоинта, стоп-триггеры и формат имени ветки читаются оттуда. Здесь только последовательность.

Контур, открытый этим скиллом, закрывает `proj-deliver-task` открытым pull request. Раньше он не закрывается.

## 1. Возьми идентификатор задачи

`PER-N` приходит от владельца — аргументом команды `/proj-take-task` или прямым вызовом этого скилла. Не выводи его из недавнего разговора, не выбирай задачу из бэклога сам и не бери из имени существующей ветки как повод начать новую работу: контур открывается на конкретную названную задачу.

Идентификатора нет — спроси и остановись.

## 2. Заведи ветку

Текущая ветка уже `feature/PER-N` той же задачи — контур на неё открыт, ветку не создавай и переходи к шагу 3, чтобы восстановить контекст.

Иначе: `git status --short`, затем `git fetch origin` и `git switch -c feature/PER-N origin/develop`.

- Рабочее дерево грязное — остановись и покажи `git status --short`. Чужая незакоммиченная правка не переезжает в ветку задачи молча.
- Текущая ветка `feature/PER-M` другой задачи — назови её и спроси. Вторая задача поверх первой ломает правило «одна задача — одна ветка — один pull request».

## 3. Прочитай контур задачи

Инструмент и его особенности — [issue-tracker.md](../../../docs/agents/issue-tracker.md).

- `get_issue` по `PER-N` с `includeRelations: true`, затем `list_comments`. Комментарии часто несут решение, которого нет в описании.
- Документы, на которые задача ссылается, целиком. Родительскую задачу, если срез от неё зависит.
- Текущее состояние файлов, которые задача трогает, и соседних с ними: срез читается по коду, а не по описанию.

Отчитайся списком прочитанного — задача, документы, файлы. По этому списку владелец ловит, что ты читал не тот срез, до того как появится код.

## 4. Останови работу, если решение не принято

Проверь до кода:

- у задачи метка `Decision` или непустой `blockedBy`;
- раздел «Что сделать» допускает два решения с разными последствиями, и выбор не сделан ни в задаче, ни в ADR;
- задача ссылается на документ, которого нет, или на решение, которое ещё не принято.

Сработало — назови, чего не хватает, и остановись. Решения принимает владелец ([design-process.md](../../../docs/development/design-process.md)); выбрать вариант за него и начать код — не ускорение, а работа, которую придётся выбросить. Уже созданная ветка при этом остаётся: она пустая и ничего не стоит.

## 5. Пройди чекпоинт плана

Условия чекпоинта — в [нормативе](../../../docs/development/agent-execution-loop.md). Проверь их по прочитанному, а не по ощущению объёма работы.

План называет развилку, варианты и рекомендацию. Список файлов планом не является: он не показывает, что именно ты решил за владельца.

Показал план — жди ответа. Не начинай правки «пока обсуждаем».

Ни одно условие не сработало — иди дальше без плана.

## 6. Реализуй срез

Границы — раздел «Что сделать» этой задачи. Документация меняется тем же изменением, что и код.

Стоп-триггеры из норматива действуют всю дорогу, а не только в конце. Сработал — остановись на состоянии «правки есть, коммита нет», назови триггер и предложи варианты.

Срез готов — сдавай через `proj-deliver-task`.
