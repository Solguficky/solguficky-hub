# Identity Service

> **Слой:** MVP. **Граница, модель и язык:** Accepted. **Retention допуска к хабу:** [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md). **Круги сообщества и блокировка:** статус допуска заменён набором ролей, [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md); схема под него изменена в [PER-252](https://linear.app/anticnvm/issue/per-252), поведение выдачи, отзыва и блокировки — в [PER-191](https://linear.app/anticnvm/issue/per-191), контракт ролей и отметки блокировки расширен в [PER-254](https://linear.app/anticnvm/issue/per-254), вызов автовыдачи роли `public` остаётся открытым. **Первая выдача роли администратора в срезе:** только служебный endpoint, [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md). **Аутентификация служебного endpoint:** общий секрет в metadata gRPC, [ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md). **Wire-контракты:** контракт разрешения личности Accepted; служебные операции Open.

## Ответственность

Identity отвечает за общие факты идентичности:

- сопоставление Telegram user с внутренним participant identity;
- принадлежность человека к кругу сообщества и системные роли — одним набором ролей ([ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md));
- отметку блокировки, закрывающую человеку все поверхности сразу;
- минимальные данные профиля, если они нужны нескольким сервисам;
- публикацию фактов о регистрации, смене ролей и блокировке для тех, кому синхронного ответа недостаточно.

Граница формулируется одной строкой: **Identity отвечает на вопрос «кто это», а «что можно» отвечает владелец ресурса** — Meetups для сходок, аукцион для ставок. Поэтому имена `roles` или `permissions` для этого сервиса были бы неверны: контекстные роли живут в доменах, а централизованный владелец всех разрешений обязан был бы знать все действия всех сервисов.

Identity не решает, кто может изменить конкретную сходку. Он сообщает факты и общие роли, а Meetups применяет правила своего домена.

Authentication в MVP выполняет Telegram, а доверенной границей продукта является Telegram Bot: при long polling доверенностью входа служит владение bot token, входящего HTTP у бота нет ([ADR-030](../decisions/ADR-030-telegram-bot.md)). Identity не принимает и не проверяет authentication material: бот передаёт установленный Telegram user id, Identity отвечает внутренним идентификатором и глобальными ролями.

## Регистрация и данные профиля

Внутренний профиль создаётся при обработке `/start`. Это и есть регистрация в MVP: произвольное последующее действие не создаёт новую identity неявно. Иначе нечего показывать при ручной сверке состава и некуда выдавать роль администратора.

Минимальная модель профиля:

| Поле | Назначение и ограничение |
|---|---|
| внутренний идентификатор | стабильный первичный ключ identity в формате [UUIDv7](../decisions/ADR-020-uuidv7-identifiers.md); его используют другие домены в ссылках на человека |
| Telegram user id | стабильный внешний ключ для поиска профиля; уникален среди профилей |
| ник Telegram | nullable-кэш для сверки состава человеком; обновляется только при фактическом изменении и не хранит истории |
| глобальные роли | активные записи `identity_roles`: `maintainer`, `admin`, `member` или `public`; конкретная поверхность сама выбирает принимаемую роль |
| блокировка | обязательное булево поле `blocked`, отдельное от ролей; при миграции блокировка отзывает активные роли |
| created_at / updated_at | служебные метки; `updated_at` меняется только вместе с ником |

Ник хранится только с явно заданной целью — сверка состава сообщества человеком. Остальные поля профиля Telegram не сохраняются.

Ник никогда не является ключом связи, потому что у Telegram он:

- необязателен — у части людей его просто нет;
- изменяем владельцем в любой момент;
- переиспользуем: освобождённый ник может занять другой человек.

Междоменные ссылки используют внутренний идентификатор. Telegram user id — уникальная внешняя привязка, по которой бот разрешает identity. На нике нет уникального индекса: он nullable, не используется для связи, авторизации или поиска identity.

Физическая схема среза — таблицы `profiles`, `identity_roles` и `identity_access_journal` в `apps/identity/internal/migrations/`. Идентификатор хранится типом `uuid`. Глобальные роли хранятся отдельными строками, отзыв роли — колонка `revoked_at`, строка не удаляется. Профиль содержит `blocked BOOLEAN NOT NULL DEFAULT false`. Миграция `004` переносит `allowed` в роли `member` и `public`, `blocked` в отметку блокировки без активных ролей, а `pending` оставляет без ролей. Миграция `005` заводит журнал доступа и закрепляет инвариант «заблокированный не держит активных ролей» триггером `identity_roles_blocked_guard`. Профиль создаётся через `/start`; роль администратора миграцией не выдаётся и назначается maintainer'ом. Миграции применяются при старте процесса.

Параллельные и повторные `/start` выполняются одной идемпотентной операцией `INSERT ... ON CONFLICT (telegram_user_id) DO UPDATE`. Последующие взаимодействия разрешают уже существующую identity и обновляют ник только при отличии; они не регистрируют отсутствующий профиль. Условие `username IS DISTINCT FROM excluded.username` не создаёт запись при неизменившемся нике. Это устраняет гонку между параллельными Telegram updates без акторов и версий строк.

## Круги сообщества и роли

Целевая модель доступа — набор ролей, а не одно поле статуса ([ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md)). Правило словаря: **роль называет круг людей, а не поверхность; поверхность объявляет, какие роли принимает.** Поэтому новый клиент не заводит своей роли, а перечисляет принимаемые.

| Роль | Круг | Кто выдаёт |
|---|---|---|
| maintainer | эксплуатирует систему | maintainer через служебный endpoint |
| admin | заводит и ведёт сходки, курирует состав, управляет подключённым к сходке аукционом | maintainer через служебный endpoint |
| `member` | внутренний круг сообщества | администратор: whitelist при регистрации или ручной допуск |
| `public` | внешний круг: пришёл по пересланной ссылке | система автоматически при `/start` в боте аукциона |

Круги вложенные: `member` входит в `public`, поэтому допуск к хабу выдаёт обе роли одной транзакцией. Хаб проверяет `member`, аукцион проверяет `public`, и каждая поверхность проверяет ровно одну роль. Понижение человека — отзыв роли `member`: `public` остаётся, торги доступны, сходки нет.

Роль `public` выдаётся самозаписью по публичной ссылке и означает ровно «нажал `/start` в боте аукциона». Признаком знакомства с сообществом она не является, и ни один сценарий не должен читать её так.

Роль maintainer — факт, а не путь авторизации. Право на служебные RPC по-прежнему доказывает общий секрет в metadata ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)); роль нужна там, где у maintainer'а есть разрешения в сервисе без служебного endpoint'а.

Ролей аукциона в Identity нет. Отдельный администратор аукциона не заводится: аукцион существует в рамках сходки, и её администратор управляет им. Ведущий и помощник в зале — доменные факты аукциона, привязанные к сессии торгов: они меняются между блоками одного события и не являются фактами о человеке за его пределами.

**Блокировка — отдельное поле профиля**, не роль и не отсутствие ролей. Она отзывает все активные роли и проверяется в двух местах: на любой выдаче роли, включая автоматическую, и при выборе текста отказа. В проверке доступа поле не участвует — там решает отсутствие роли. Формулировка правила: отметка блокировки это защита на выдаче, а не на чтении. Заблокированный, нажавший `/start` в боте аукциона, роль `public` не получает; администратор не может выдать роль заблокированному, не сняв блокировку.

Схема и миграции под этот словарь сделаны в PER-252, поведение выдачи, отзыва, блокировки и допуска к хабу — в PER-191, расширение `identity.v1.GlobalRole` и отметка блокировки в ответе — в [PER-254](https://linear.app/anticnvm/issue/per-254). Вызова автовыдачи роли `public` в контракте нет: он отложен до [PER-265](https://linear.app/anticnvm/issue/per-265) и декомпозиции бота аукциона ([PER-150](https://linear.app/anticnvm/issue/per-150)).

Выдача, отзыв и блокировка живут внутренним ядром сервиса. Выдача роли идемпотентна: повтор активной выдачи не создаёт второй строки и отвечает «изменения не было». Блокировка ставит отметку профиля и отзывает все активные роли одной транзакцией; снятие блокировки ролей не возвращает. Допуск к хабу выдаёт обе вложенные роли одной транзакцией. Отказ в выдаче заблокированному enforced дважды: проверкой под блокировкой строки профиля и триггером `identity_roles_blocked_guard`, который закрывает и возврат доступа снятием отметки отзыва. Поверхности у блокировки, снятия и выдачи кругов пока нет: их откроют команды администратора и контрактное изменение. Единственная живая поверхность — служебные `GrantAdminRole` и `RevokeAdminRole`, которые ходят в то же ядро. Выдачи роли `public` по wire нет: автовыдача при `/start` в боте аукциона отложена до [PER-265](https://linear.app/anticnvm/issue/per-265) и появления самого бота.

Разделы ниже описывают премодерацию хаба как целевое поведение, которое ещё не входит в текущий срез.

## Контроль состава сообщества

Премодерация входит в MVP. Ссылка на бота публична по устройству Telegram, поэтому без неё расписание сходок сообщества доступно любому, кто нажал `/start`.

Membership моделируется ролями профиля. Роль `member` — **допуск к хабу**, не ко всей платформе ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Профиль без активной роли `member` ожидает допуска и получает её одним из двух путей:

| Путь | Когда срабатывает | Для кого |
|---|---|---|
| whitelist ников | один раз при `/start`, если ник совпал с непогашенной записью | основная масса участников сообщества |
| ручной допуск администратором | в любой момент после `/start` | любой профиль без роли `member`, в том числе люди без ника |

Одноразовая инвайт-ссылка из [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md) в этом срезе не реализуется: наблюдаемой потребности нет, общая ссылка на бота уже публична. Человек без ника остаётся без роли `member` до ручного допуска. Сигнал вернуть инвайт и кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32), [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md).

Человеку без роли `member` бот отвечает отказом с указанием, к кому обратиться, и не показывает никаких данных сходок. Это отличается от `blocked`, где повторное обращение ничего не меняет.

Проверка ролей и этот отказ — целевое поведение Feature премодерации ([PER-76](https://linear.app/anticnvm/issue/per-76)), не текущего среза. Принятый `ResolveIdentity` блокировку не проверяет — проверка стоит на выдаче, — но возвращает её отметку отдельным полем `blocked` ([integration.md](../architecture/integration.md)); различать по ней ожидающий профиль и заблокированный — работа политики поверхности ([PER-76](https://linear.app/anticnvm/issue/per-76), [PER-194](https://linear.app/anticnvm/issue/per-194)).

**Whitelist применяется один раз, а не на каждом действии.** Постоянная проверка сделала бы ник ключом доступа: человек, сменивший ник, терял бы доступ, а человек, занявший освободившийся ник, получал бы чужой. Совпадение ника служит входным сигналом, результат допуска записывается за внутренним идентификатором, использованная запись списка **помечается** и остаётся. Уникальность — только среди непогашенных. TTL нет: непогашенное живёт, пока администратор не удалит. Список не становится реестром identity и не меняет ключи профиля. Сам список составляет человек своим клиентом Telegram — это его действие, а не вызов Bot API, поэтому боту по-прежнему не требуется никаких прав в группе.

**Блокировка** переводит профиль в `blocked`, сохраняет профиль и стабильный внутренний идентификатор и автоматически отзывает активные глобальные роли. Повторный допуск возвращает ту же identity, но роли не восстанавливает.

**Журнал доступа.** Таблица `identity_access_journal` пишется append-only в той же транзакции, что и изменение: субъект `identity_id`, выполнивший `performed_by`, действие `grant` | `revoke` | `block` | `unblock`, роль и момент `occurred_at`. Роль названа у выдачи и отзыва, у блокировки и снятия она NULL: это решения о профиле, а не о роли. Пустой `performed_by` означает системный переход, а также операцию maintainer'а: профиля maintainer'а нет, и `granted_by` остаётся NULL ([PER-169](https://linear.app/anticnvm/issue/per-169)). Блокировка пишет одну строку: отзыв ролей — следствие одного решения, а метка времени у отозванных строк общая с ней, потому что `now()` внутри транзакции не меняется. Людей называет внутренний `identity_id`; Telegram user id и ник в журнал не входят. Внешнего ключа на `profiles` нет: журнал переживает профиль как история UUID, TTL в первой схеме нет ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Append-only держится схемой: UPDATE, DELETE и TRUNCATE отвергаются триггерами. Он не является источником истины и не участвует в проверке доступа — активные роли читаются из `identity_roles`, а блокировка из поля профиля. Журнал нужен потому, что допуск и блокировка это решения человека о человеке в сообществе, у которых нет другой поверхности аудита.

Ручная сверка постфактум сохраняется поверх премодерации, а не вместо неё: она закрывает окно между освобождением ника и первым `/start`.

Автоматическая проверка членства через `getChatMember` не используется. Причина техническая и жёсткая: метод гарантированно отвечает про **чужих** пользователей только когда бот является администратором чата, а бот-администратор по устройству Telegram получает все сообщения группы независимо от Privacy Mode. Это прямо противоречит принципу минимальных привилегий из [product/overview.md](../product/overview.md). Возврат к этому варианту потребует сначала переписать принцип, а не просто добавить вызов.

Премодерация входит в MVP, но не в [первый вертикальный срез](../architecture/first-slice.md): срез проверяет границы трёх сервисов, и допуск состава к этой проверке ничего не добавляет.

## Роль администратора

Роль хранится отдельно от профиля в таблице `identity_roles` как данные вида `(identity_id, role, granted_at, granted_by, revoked_at)`, а не как список Telegram `user_id` в конфигурации или коде. Первый администратор назначается maintainer'ом после того, как человек уже начал пользоваться ботом и получил внутренний идентификатор. `ResolveIdentity` роли не выдаёт и не восстанавливает: повторный `/start` возвращает только активные записи. Выдача и отзыв — maintainer-операции через служебный endpoint, защищённый общим секретом `IDENTITY_MAINTAINER_TOKEN` в metadata gRPC ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Другого пути в срезе нет: bootstrap переменной окружения отвергнут вместе с [PER-167](https://linear.app/anticnvm/issue/per-167), прямой SQL путём не является ([ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md)).

Операции делятся по владельцу вопроса, и из этого следуют поверхности:

| Операция | Кто | Где |
|---|---|---|
| посмотреть профили с фильтром по статусу | администратор | команды бота |
| допустить, заблокировать, вернуть допуск | администратор | команды бота |
| загрузить whitelist, посмотреть и удалить непогашенные записи | администратор | команды бота |
| выдать и отозвать глобальную роль администратора | maintainer | служебный endpoint |

Курирование состава — вопрос администратора, и он решается там, где администратор уже работает. Права в системе — вопрос maintainer'а, и его нельзя решать инструментом, доступ к которому сам зависит от роли; этим же путём назначается первый администратор, когда нажать в боте ещё некому. Отдельная веб-админка в MVP не вводится.

Служебный endpoint идемпотентен и не является публичным API. Право на вызов доказывает секрет в metadata: локально и в развёрнутом контуре проверка одна, обхода нет ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Прямое редактирование БД и hardcoded-список не являются штатными путями ни для одной группы операций. Команды бота не содержат доменных правил: бот маршрутизирует вызов, решение принимает Identity.

Контракт служебных операций ещё не принят; authentication выбран и реализацию не блокирует. Чем запись роли назовёт `granted_by` — вопрос схемы [PER-169](https://linear.app/anticnvm/issue/per-169): колонка сейчас ссылается на `profiles(id)`, профиля maintainer'а нет. Тем же NULL журнал называет актора операции maintainer'а; записи, сделанные до решения PER-169, от системных в журнале не отличимы, и backfill append-only не допускает.

Это заменяет hardcoded-список из [ADR-016](../decisions/ADR-016-rbac-action-pattern-and-transport.md), который относился к удалённой аукционной ветке.

## Взаимодействие и отказ

Бот синхронно обращается к Identity по gRPC на каждом Telegram update, требующем продуктового действия. В срезе это одна операция: Telegram user id и ник, если он есть, в обмен на внутренний идентификатор, общие роли и отметку блокировки отдельным полем. Схема и запись в каталоге — [integration.md](../architecture/integration.md). Кэш фактов доступа и ролей в боте не используется: устаревшее разрешение равносильно пропущенной проверке. При недоступности Identity продуктовая операция завершается fail-closed; повторное рассмотрение кэша начинается только по наблюдаемому p95.

PostgreSQL — единственный источник истины, команды выполняются обычными ACID-транзакциями, а чтение идёт из тех же таблиц без CQRS, Event Sourcing, акторов и отдельной read model. Журнал доступа пишется в той же транзакции, но источником истины не является: он отвечает на вопрос «кто и когда это сделал», а не «что сейчас».

## Исходящие события

Синхронного gRPC оказалось недостаточно: [Notifications](notifications.md) ведёт собственную реплику людей и их глобальных ролей, потому что кто-то должен разворачивать аудиторию глобальной категории уведомлений. Сигнал пересмотра, записанный в [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), сработал — появился потребитель, которому синхронной проверки недостаточно ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)).

Из этого следуют три требования к Identity. Они описывают целевую архитектуру, а не текущий срез: схема таблицы outbox, устройство релея и словарь исходящих событий остаются открытыми вопросами ниже.

- **события о регистрации профиля, выдаче и отзыве роли и блокировке** публикуются наружу в Protobuf через NATS. Событие является данными, а не сигналом: получателю должно хватать его для восстановления состояния с нуля. По [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md) сменой допуска становится выдача или отзыв роли, поэтому событие несёт роль, а не значение статуса, и отдельно несёт отметку блокировки;
- **outbox.** Запись для отправки кладётся в той же транзакции, что и изменение состояния, и публикуется релеем. Прямая отправка из обработчика теряет событие при сбое между записью и публикацией. Отдельная таблица нужна потому, что журнала домена у Identity нет: журнал доступа покрывает только смену роли или блокировки и не покрывает регистрацию, поэтому подменять им outbox нельзя;
- **метод перечисления текущего состава** — вне MVP. Он понадобится, когда появятся люди, зарегистрированные до подключения потребителя, или потребуется пересборка его реплики. В первом запуске Identity и Notifications стартуют вместе, поэтому наполнять нечем; вопрос вынесен отдельной задачей.

Модель самого сервиса при этом не меняется: событий Identity не потребляет, состояние из них не выводит и read model у себя не заводит.

Отсюда же следует граница адресации. [Notifications](notifications.md) ведёт реплику людей и их допуска и сам разворачивает аудиторию глобальной категории ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)). Пока допуск был одним значением, разворот был однозначен; с кругами он перестаёт им быть. Поэтому **реплика хранит роли, а разворот глобальной аудитории всегда называет круг**: повод хаба адресуется `member`, повод торгов — `public`. Рассылки «всем профилям» не существует, иначе объявление сходки уходит людям, пришедшим по ссылке аукциона и не состоящим в сообществе. Identity этой границы не исполняет: он обязан лишь публиковать смену роли так, чтобы круг был виден получателю.

Отдельно от событий потребителю нужен **метод разрешения внутреннего идентификатора в Telegram id**: канал доставки получает уведомление с внутренним идентификатором получателя, а ADR-026 описывает только обратный путь.

## Стек

Identity реализуется на Go. Сложного домена здесь нет; исследовательская ценность находится в operational-контуре gRPC/Protobuf, PostgreSQL, миграций, контейнера, Railway, Aspire и observability. Сгенерированный Protobuf-код живёт в отдельном пакете `gen/` без рукописного кода. Кодогенерация выполняется командой `buf generate --template apps/identity/buf.gen.yaml` с локальными официальными Go-плагинами по [стандарту Protobuf](../standards/contracts/protobuf.md#кодогенерация-go).

Текущий код в `apps/identity`: gRPC-сервер, `ResolveIdentity` поверх PostgreSQL, `grpc.health.v1`, структурные логи `log/slog` и миграции. Операция создаёт профиль без активных ролей и с `blocked = false` при первом обращении, обновляет ник только при отличии и возвращает внутренний идентификатор с активными общими ролями. Отметка блокировки в ответ входит отдельным полем `blocked` и из набора ролей не выводится. Внутреннее ядро сервиса реализует выдачу, отзыв, блокировку и снятие блокировки с записью журнала в той же транзакции; отказ в выдаче заблокированному отвечает `FAILED_PRECONDITION`, отличимо от `NOT_FOUND` для отсутствующего профиля. Запись границы называет человека внутренним идентификатором из ответа: Telegram user id и ник — персональные данные и в лог не идут ([logging.md](../standards/observability/logging.md#персональные-данные)). У отказа идентификатора ещё нет, и запись связывается с вызовом бота по `request_id`.

## Цена отдельного сервиса

Разделение требует явно спроектировать:

- отдельный deployment unit и хранилище;
- migrations и ownership данных;
- межсервисные контракты;
- timeout и degraded behavior;
- согласованность общих ролей и доменных полномочий;
- наблюдаемость authentication/authorization пути.

Контракт разрешения личности принят и описан в [integration.md](../architecture/integration.md). Схема профиля и глобальных ролей лежит в `apps/identity/internal/migrations/` и применяется при старте процесса. Identity зарегистрирован в Aspire как узел графа: `identity-proto` генерирует Go-код, `identity-build` собирает бинарник, `identity` запускает его и проверяется gRPC health.

## Открытые вопросы реализации

- точная схема whitelist;
- схема таблицы outbox, устройство релея и его наблюдаемость; словарь исходящих событий и их полнота;
- форма перечисления состава: отдельный метод, пагинация и поведение при параллельных изменениях — вне MVP;
- метод разрешения внутреннего идентификатора в Telegram id: отдельный вызов или расширение существующего;
- чем запись роли назовёт `granted_by` при выдаче maintainer'ом — [PER-169](https://linear.app/anticnvm/issue/per-169);
- набор и формат административных команд бота;
- одноразовые приглашения хаба отложены до наблюдаемой потребности ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)); кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32);
- timeout при fail-closed; тексты ответов человеку — часть дизайн-сессии [PER-32](https://linear.app/anticnvm/issue/per-32);
- вызов автовыдачи роли `public` при `/start`: caller, доказательство права и поведение при повторном `/start` — отложен до [PER-265](https://linear.app/anticnvm/issue/per-265) и декомпозиции бота аукциона ([PER-150](https://linear.app/anticnvm/issue/per-150));
- срок жизни профилей, созданных посетителями аукциона: ADR-043 его не выбирает, а переносить на них «`blocked` навсегда» и вечный журнал хаба запрещено ([RFC-009](../rfcs/RFC-009-identity-access-data-retention.md));
- останется ли роль `public` глобальной, когда одновременных аукционов станет два.

Контракт разрешения личности зафиксирован в `contracts/proto/` и [integration.md](../architecture/integration.md). События, обратное разрешение в Telegram id и служебные endpoints остаются после закрытия открытых вопросов. Решения по модели, стеку, retention допуска, первому администратору и authentication endpoint — в [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), [ADR-027](../decisions/ADR-027-identity-go-stack.md), [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md), [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md) и [ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md).
