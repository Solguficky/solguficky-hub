# Identity Service

> **Слой:** MVP. **Граница, модель и язык:** Accepted. **Retention допуска к хабу:** [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md). **Круг, наборы и права:** круг без ранга, допуск по правам с глаголом, живые наборы `admin` и `maintainer`, [ADR о наборах](../decisions/ADR-065-circle-presets-and-verb-rights.md) (RFC-016); до него — круги-роли [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md) и [ADR-064](../decisions/ADR-064-two-bots-by-audience-circle-and-rights.md); схема под него изменена в [PER-252](https://linear.app/anticnvm/issue/per-252), поведение выдачи, отзыва и блокировки — в [PER-191](https://linear.app/anticnvm/issue/per-191), контракт ролей и отметки блокировки расширен в [PER-254](https://linear.app/anticnvm/issue/per-254). **Премодерация аукциона, заявка и источник прихода:** самозапись `public` отменена, [ADR-060](../decisions/ADR-060-auction-access-premoderation.md); контракт входа описан в [PER-304](https://linear.app/anticnvm/issue/per-304), с RFC-016 вход называется `RequestAccess`. **Первая выдача роли администратора в срезе:** только служебный endpoint, [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md). **Аутентификация служебного endpoint:** общий секрет в metadata gRPC, [ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md). **Wire-контракты:** контракт разрешения личности Accepted; служебные операции Open.

## Ответственность

Identity отвечает за общие факты идентичности:

- сопоставление Telegram user с внутренним participant identity;
- круг человека — членство и аудиторию, — его наборы и права, которые Identity из них выводит ([ADR о наборах](../decisions/ADR-065-circle-presets-and-verb-rights.md));
- отметку блокировки, закрывающую человеку все поверхности сразу;
- минимальные данные профиля, если они нужны нескольким сервисам;
- публикацию фактов о регистрации, смене круга, наборов и прав и блокировке для тех, кому синхронного ответа недостаточно.

Граница формулируется одной строкой: **Identity отвечает на вопрос «кто это», а «что можно» отвечает владелец ресурса** — Meetups для сходок, аукцион для ставок. Поэтому имена `roles` или `permissions` для этого сервиса были бы неверны: контекстные роли живут в доменах, а централизованный владелец всех разрешений обязан был бы знать все действия всех сервисов.

Identity не решает, кто может изменить конкретную сходку. Он сообщает факты и права на сообщество целиком, а Meetups применяет правила своего домена.

Authentication в MVP выполняет Telegram, а доверенной границей продукта является Hub Bot: при long polling доверенностью входа служит владение bot token, входящего HTTP у бота нет ([ADR-030](../decisions/ADR-030-telegram-bot.md)). Identity не принимает и не проверяет authentication material человека: бот передаёт установленный Telegram user id, Identity отвечает внутренним идентификатором, кругом, наборами и правами. Вызывающий процесс — бот, Meetups, Notifications — доказывает себя своим токеном, и Identity допускает его только к методам из колонки Caller ([ADR-056](../decisions/ADR-056-service-calls-per-caller-token-and-closed-network.md), [integration.md](../architecture/integration.md#service-authentication)).

## Регистрация и данные профиля

Внутренний профиль создаётся при обработке `/start`. Это и есть регистрация в MVP: произвольное последующее действие не создаёт новую identity неявно. Иначе нечего показывать при ручной сверке состава и некуда выдавать набор администратора.

Минимальная модель профиля:

| Поле | Назначение и ограничение |
|---|---|
| внутренний идентификатор | стабильный первичный ключ identity в формате [UUIDv7](../decisions/ADR-020-uuidv7-identifiers.md); его используют другие домены в ссылках на человека |
| Telegram user id | стабильный внешний ключ для поиска профиля; уникален среди профилей |
| ник Telegram | nullable-кэш для сверки состава человеком и для связи с организатором сходки; обновляется только при фактическом изменении и не хранит истории |
| круг | одна активная запись `identity_circles`: `member` или `guest`; вторую активную строку отвергает схема. Ранга у круга нет: он решает аудиторию, а не допуск |
| наборы | живые строки `identity_presets`: `admin`, `maintainer`; их может быть несколько |
| права | `access_hub`, `place_bids`, `admit_bidders`, `manage_members`, `manage_meetups`, `grant_admins`: Identity выводит их из круга, наборов и активных записей `identity_rights`; любой допуск решает право |
| блокировка | обязательное булево поле `blocked`, отдельное от круга; блокировка отзывает круг, наборы и записи |
| created_at / updated_at | служебные метки; `updated_at` меняется только вместе с ником |

Ник хранится только с явно заданными целями. Первая — сверка состава сообщества человеком. Вторая — связь с организатором: карточка сходки называет ник её автора, и отдаёт его только `ResolveOrganizerUsername` и только для держателя `manage_meetups` ([PER-404](https://linear.app/anticnvm/issue/per-404), [integration.md](../architecture/integration.md)). Остальные поля профиля Telegram не сохраняются.

Ник никогда не является ключом связи, потому что у Telegram он:

- необязателен — у части людей его просто нет;
- изменяем владельцем в любой момент;
- переиспользуем: освобождённый ник может занять другой человек.

Междоменные ссылки используют внутренний идентификатор. Telegram user id — уникальная внешняя привязка, по которой бот разрешает identity. На нике нет уникального индекса: он nullable, не используется для связи, авторизации или поиска identity.

Физическая схема — таблицы `profiles`, `identity_circles` (до миграции `017` — `identity_roles`), `identity_presets`, `identity_rights`, `identity_applications`, `identity_access_journal`, `allowed_usernames` и `identity_outbox` в `apps/identity/internal/migrations/`. Идентификатор хранится типом `uuid`. Круг, наборы и записи прав хранятся отдельными строками, отзыв — колонка `revoked_at`, строка не удаляется. Профиль содержит `blocked BOOLEAN NOT NULL DEFAULT false`. Миграция `004` переносит `allowed` в роли `member` и `public`, `blocked` в отметку блокировки без активных ролей, а `pending` оставляет без ролей. Миграция `005` заводит журнал доступа и закрепляет инвариант «заблокированный не держит активных ролей» триггером `identity_roles_blocked_guard`. Миграция `006` добавляет список разрешённых ников и основание записи журнала, миграция `010` — круг записи `grants_role` (`member` у записи хаба, `public` у аукционной); записи до неё получают `member`. Миграция `014` сводит строки к одной активной роли-кругу и переименовывает `public` в `guest`; миграция `016` добавляет кругу `admin` право `manage_auction`. Миграция `017` (RFC-016) переименовывает таблицу в `identity_circles`, оставляет активными только `member` и `guest`, заводит живые наборы `identity_presets`, переименовывает права и ключи (`queue` у заявки, `grants_circle` у белого списка, `circle` и `preset` в журнале) — раздел «Круг, наборы и права». Строка списка не удаляется: погашение допуском (`used_at`, `used_by`) и снятие администратором (`removed_at`, `removed_by`) — отметки, уникальность действует только среди записей без обеих. Профиль создаётся через `/start`; набор администратора миграцией новому человеку не выдаётся — его назначает держатель `grant_admins`. Миграции применяются при старте процесса.

Административная поверхность состава принимает установленную ботом личность на каждом вызове. Identity, а не бот, требует право `manage_members` и читает его из своего текущего состояния: в `IdentityActor` только идентификатор. Список состава — все незаблокированные люди, держатели наборов `admin` и `maintainer` в своём круге тоже (решение владельца 14 октября 2026 года, [PER-618](https://linear.app/anticnvm/issue/per-618)), — несёт у каждого круг и запись модерации аукциона и сужается фильтром по кругу или по модерации. Право модерации набора `admin` записью не хранится, поэтому у держателя набора `auction_moderation` ложно и в фильтр модераторов он не попадает. Карточку одного человека отдаёт `GetCommunityMember`, а ожидаемый отказ — человека нет, он заблокирован или держит набор — приходит значением ответа ([PER-547](https://linear.app/anticnvm/issue/per-547)): держатель набора в списке есть, но карточка его — отказ, потому что `CommunityMember` признака набора не несёт, а понизить или заблокировать держателя набора нельзя и сервер отвергает такую команду сам. Источника прихода у человека нет: его стирает решение по заявке ([ADR-060](../decisions/ADR-060-auction-access-premoderation.md), пункт 20). Разрешённые ники читаются отдельно, и после каждой команды экран перечитывает то, что показывает. Допуск выдаёт круг `member` на место прежнего; закрытие доступа ставит блокировку и отзывает круг и права; повтор целевой команды возвращает `changed = false` без второй записи изменения.

Параллельные и повторные `/start` выполняются одной идемпотентной операцией `INSERT ... ON CONFLICT (telegram_user_id) DO UPDATE`. Последующие взаимодействия разрешают уже существующую identity и обновляют ник только при отличии; они не регистрируют отсутствующий профиль. Условие `username IS DISTINCT FROM excluded.username` не создаёт запись при неизменившемся нике. Это устраняет гонку между параллельными Telegram updates без акторов и версий строк.

## Круг, наборы и права

Модель доступа — круг без ранга, наборы и права с глаголом ([ADR о наборах](../decisions/ADR-065-circle-presets-and-verb-rights.md), RFC-016). Она заменила круги-ранги [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md) и [ADR-064](../decisions/ADR-064-two-bots-by-audience-circle-and-rights.md), при которых сервисы решали одни вопросы по праву, другие по кругу, третьи по проекции `global_roles`.

- **Круг** — `member` или `guest`, ровно один или никакого: строка `identity_circles`, вторую активную отвергает индекс `identity_circles_one_active`. Он решает аудиторию — какой бот отвечает человеку и в какую очередь ляжет заявка — и несёт права: `member` даёт `access_hub` и `place_bids`, `guest` — ничего. Ни одно решение о допуске круг не читает.
- **Набор** — живая строка `identity_presets`: `admin` даёт `admit_bidders`, `manage_members` и `manage_meetups`, `maintainer` — `grant_admins`. Набор выдаётся и снимается целиком, людям показывается его название, а ни один сервис его не проверяет. Наборы держатся одновременно.
- **Запись** — право, выданное поштучно: `place_bids` гостю и `admit_bidders` участнику. Записью выдаются только они.
- **Права** = права круга ∪ права наборов ∪ записи; у заблокированного прав нет. Вывод один — функции схемы `identity_carried_rights` (круг и наборы), `identity_access_rights` (с записями) и `identity_active_presets` из миграции `017`: их читают ответы `ResolveIdentity` и `RequestAccess`, `CheckAccessRight`, `ResolveOrganizerUsername`, право актора во всех операциях и снимок outbox. Права друг друга не подразумевают.

**Таблица выдачи** — данные `issuers` в `internal/server/access.go`, а не ветки обработчиков; запрет на каждую строку держит тест:

| Что выдаётся или снимается | Нужное право |
|---|---|
| круг `member` (допуск в сообщество), понижение в `guest`, блокировка и её снятие | `manage_members` |
| запись `place_bids` гостю (допуск и отзыв в очереди аукциона) | `admit_bidders` |
| запись `admit_bidders` участнику | `manage_members` |
| набор `admin` | `grant_admins` |
| набор `maintainer` | только общий секрет |

Себе можно: держатель права-выдавателя выдаёт и снимает то, что разрешает его право, кому угодно, включая себя. Служебные права требуют круг `member`: набор и запись `admit_bidders` гостю и человеку без круга не выдаются (`FAILED_PRECONDITION`). **Держатель набора защищён:** понизить его в `guest` или заблокировать нельзя (`FAILED_PRECONDITION`) — сначала набор снимает его выдаватель; иначе `manage_members` снимал бы набор в обход `grant_admins`. Мейнтейнера из бота не снять ничем.

Выдача круга идёт через одну функцию `grantCircleTxWithReason`. Выдача `member` заменяет круг гостя и снимает его запись `place_bids` — участник держит право кругом; выдача `guest` человеку без круга даёт круг с записью `place_bids`, гостю без записи — запись, а участнику холостая. Понижение `member` → `guest` снимает служебные записи и выдаёт `place_bids`. Выдача набора `admin` снимает запись `admit_bidders` — набор несёт право сам, — а снятие набора записи человека не трогает. Холостые операции событий не пишут.

Хаб пускает по `access_hub`, ставки — по `place_bids`, очередь аукциона решает `admit_bidders`, очередь сообщества и состав — `manage_members`, сходки и каталог лотов — `manage_meetups`, экран администраторов — `grant_admins`. Правила и коды ответов — [integration.md](../architecture/integration.md#круг-наборы-права-и-очереди).

Самозаписи `guest` нет: вход в аукцион идёт через премодерацию, как и вход в хаб (раздел «Контроль состава сообщества»). Круг `guest` — курируемый факт: его выдал белый список или модератор торгов, но признаком знакомства с сообществом он не является.

Ролей аукциона в Identity нет. Отдельный администратор аукциона не заводится: аукцион существует в рамках сходки, и её ведёт держатель `manage_meetups`. Решено, но не реализовано ([ADR-070](../decisions/ADR-070-auction-floor-bids-by-assistant.md), PER-564): аукцион у сходки, пульт, каталог лотов и ставки зала переходят к новому праву `run_auctions` из набора `admin` и поштучной записи участнику от держателя `manage_members`, а ведущий и помощник в зале — его держатели, а не доменные факты аукциона.

**Блокировка — отдельное поле профиля**, не круг и не отсутствие прав. Она отзывает круг, наборы и записи и проверяется на любой выдаче, включая автоматическую, и при выборе текста отказа. В выводе прав отметка участвует как страховка: функции вывода у заблокированного отдают пустой набор, даже если строка осталась мимо блокировки. Заблокированный, нажавший `/start` в любом боте, ничего не получит; выдать что-то заблокированному нельзя, не сняв блокировку. Отказ в выдаче держат проверка под блокировкой строки профиля и триггеры `identity_circles_blocked_guard`, `identity_rights_blocked_guard` и `identity_presets_blocked_guard` (`ID003`).

Перенос stage (вопрос О-6 RFC-016) — миграция `017`: круг `admin` стал участником с набором `admin`, круг `maintainer` — участником с наборами `maintainer` и `admin`; записи `auction` и `moderate_auction` переименованы в `place_bids` и `admit_bidders`, а записи управления, которые несёт набор, сняты. Событий перенос не пишет и щит `ID006` на время переноса выключает, как `014`; неотправленные строки outbox прежнего словаря получают отметку публикации — новый контракт их выразить не может, а следующий снимок человека несёт его состояние целиком.

## Контроль состава сообщества

Премодерация входит в MVP. Ссылка на бота публична по устройству Telegram, поэтому без неё расписание сходок сообщества доступно любому, кто нажал `/start`.

Membership моделируется кругом профиля. Круг `member` — **допуск к хабу**, не ко всей платформе ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Профиль вне этого круга ожидает допуска и получает круг `member` одним из двух путей:

| Путь | Когда срабатывает | Для кого |
|---|---|---|
| whitelist ников | один раз при `/start`, если ник совпал с непогашенной записью | основная масса участников сообщества |
| ручной допуск держателем `manage_members` | в любой момент после `/start` | любой профиль без круга `member`, в том числе люди без ника |

Одноразовая инвайт-ссылка из [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md) в этом срезе не реализуется: наблюдаемой потребности нет, общая ссылка на бота уже публична. Человек без ника остаётся без круга `member` до ручного допуска. Сигнал вернуть инвайт и кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32), [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md).

Человеку без `access_hub` бот отвечает отказом с указанием, к кому обратиться, и не показывает никаких данных сходок. Это отличается от `blocked`, где повторное обращение ничего не меняет.

### Премодерация обеих поверхностей и заявка

Принято [ADR-060](../decisions/ADR-060-auction-access-premoderation.md). Заявка и модерация реализованы в [PER-437](https://linear.app/anticnvm/issue/per-437): таблица `identity_applications`, закрытие заявок выдачей и блокировкой, очередь, решение, список отказанных и пересмотр по контракту [PER-436](https://linear.app/anticnvm/issue/per-436) ([Identity gRPC](../architecture/integration.md#identity-grpc)). Вход `RequestAccess` (до RFC-016 — `RequestRole`) по контракту [PER-304](https://linear.app/anticnvm/issue/per-304) и белый список по кругу реализованы в [PER-266](https://linear.app/anticnvm/issue/per-266), реестр каналов прихода — в [PER-438](https://linear.app/anticnvm/issue/per-438). Оба бота зовут вход на `/start` ([PER-316](https://linear.app/anticnvm/issue/per-316)): хаб с очередью сообщества, бот аукциона с очередью аукциона. На остальных действиях боты заявок не ставят и ожидание выводят из отсутствия права своей поверхности.

- **Вход.** На `/start` в любом боте Identity устанавливает личность и затем по порядку: заблокированному ничего не выдаёт и заявки не ставит; гасит непогашенную запись белого списка по нику всегда, даже при холостой выдаче; если права очереди всё ещё нет — ставит заявку в её очередь (хаб — сообщество, аукцион — аукцион).
- **Белый список** — та же `allowed_usernames` с колонкой круга: запись хаба выдаёт круг `member`, запись аукциона — `guest` с записью `place_bids`. Гасится на `/start` в любом боте, независимо от очереди этого бота. Один ник — одна непогашенная запись: запись хаба поверх аукционной повышает её — аукционная снимается, запись хаба заводится, строка не переписывается; аукционная поверх записи хаба — холостое добавление. Гашение идёт по кругу записи на любом пути, в том числе в `ResolveIdentity`. Заблокированному запись не гасится. Контракт `AddAllowedUsername` заводит только запись хаба: поля круга в запросе нет, и аукционный список через него не пополняется.
- **Заявка** — ожидание на пару «человек, очередь» с источником прихода и именем для карточки. Открыта не больше одной на пару: это держит частичный уникальный индекс, а согласие исхода, решившего и обнулённых полей — ограничения схемы. Выдача круга любым путём закрывает открытые заявки в очередях, чьё она уже выдала (`member` — обе, `guest` — очередь аукциона), блокировка — все открытые заявки исходом «закрыта блокировкой»: «Закрыть» на экране состава, а до PER-527 и отказ в `guest`, у которого собственная заявка получала исход отказа, а остальные заявки человека — этот исход ([integration.md](../architecture/integration.md#identity-grpc)); любое закрытие обнуляет источник и имя. Закрытие делает ядро в той же транзакции: все пути выдачи идут через одну функцию выдачи, а блокировка — через одну функцию блокировки, поэтому новый путь закрытие не обходит. Решение — условное обновление «открытая → решённая» под блокировкой строки профиля: из двух решений по одной заявке проходит первое, второе получает «уже решено». Ручной допуск в сообщество — решение по открытой заявке в очередь сообщества. Круг и блокировку по-прежнему пишут журнал доступа и outbox. Открытие новой заявки — событие `application_submitted` с очередью: доступ оно не меняет, но версию профиля занимает, а пишет его `RequestAccess` той же транзакцией после регистрации и только если заявка открыта этим вызовом, а не найдена ([ADR-062](../decisions/ADR-062-access-request-notification.md), [PER-435](https://linear.app/anticnvm/issue/per-435)). Исход `declined` доступ не меняет и событием не является.
- **Отказ по очереди.** Отказ закрывает заявку исходом `declined` только в её очереди и доступа не трогает ([ADR-064](../decisions/ADR-064-two-bots-by-audience-circle-and-rights.md), пункт 15; [PER-527](https://linear.app/anticnvm/issue/per-527)): отказанный в аукцион ставит заявку в сообщество, как любой посторонний. Отказы в `guest`, принятые до PER-527, остались блокировками с исходом `blocked`, и их пересмотр снимает блокировку прежним путём. Отзыв записи `place_bids` у гостя записывается заявкой в очередь аукциона, закрытой в момент создания исходом `declined`, как понижение. Отказ в сообщество всегда закрывает заявку исходом `declined`, доступа не трогает. Понижение `DemoteCommunityMember` ([PER-456](https://linear.app/anticnvm/issue/per-456)) одной транзакцией меняет круг `member` на `guest`, снимает служебные записи, выдаёт `place_bids` и вставляет заявку в очередь сообщества, закрытую в момент создания исходом `declined`, с модератором в `decided_by`. Держателя набора оно не понижает (`FAILED_PRECONDITION`). С `declined` новая заявка в ту же очередь не создаётся, пока её выдача не случится любым путём; на `/start` такой человек видит отказ, а не «на рассмотрении». Признак «отказ в силе» — условие `standingRefusalSQL` в ядре: его читает список отказанных, и его же с исходом `declined` берёт создание заявки во входе.
- **Пересмотр.** Список отказанных — заявки, закрытые отказом (блокировкой или `declined`), выдача очереди которых после отказа не случилась; блокировка не по заявке и заявки, закрытые ею, в него не входят — она снимается прежним путём. «Выдан после отказа» — отметка `refusal_lifted_at`, которую ставит выдача под блокировкой строки профиля, а не сравнение моментов: `now()` — начало транзакции, и выдача, ждавшая блокировку, получила бы момент раньше отказа. Пересмотр выдаёт то, что выдаёт очередь закрытой заявки. Пересмотр блокировки — снятие блокировки и допуск в аукцион одной операцией, пересмотр `declined` — допуск по закрытой заявке. Блокировку пересмотр снимает, только если её поставил сам отказ: последняя запись `block` в журнале доступа сделана транзакцией решения. Блокировка, поставленная позже — «Закрыть» после снятия прежним путём, — даёт `FAILED_PRECONDITION`.
- **Допуск по заявке** объявляется поводом `application_admitted` с очередью заявки ([PER-442](https://linear.app/anticnvm/issue/per-442)): его пишут решение-допуск с карточки, пересмотр отказа и ручной допуск в сообщество, если он выдал `member`, — с заявкой или без её строки: ручной допуск — решение по заявке (ADR-060, пункт 11); бот хаба его больше не зовёт, допуск идёт через очередь «Заявки» ([PER-547](https://linear.app/anticnvm/issue/per-547)). Пишется повод после выдач той же транзакцией, поэтому снимок уже держит выданное. По нему заявитель получает сообщение о допуске в бот своей поверхности. Белый список, выдача, которую человек уже держал кругом, и повторное решение по уже решённой заявке повода не дают; ограничения outbox знают его с миграции `013_application_admitted`.
- **Источник прихода** приходит payload'ом deep link `s_<код>`. Коды ведёт реестр каналов «код → подпись» — таблица `source_channels` и три операции администратора ([PER-438](https://linear.app/anticnvm/issue/per-438), [integration.md](../architecture/integration.md#identity-grpc)); реестр доступа не меняет, поэтому событий у него нет. Код разрешается при создании заявки во входе, и сырой код заявка не хранит: она ссылается на канал (`source_channel`) или несёт отметку «неизвестный источник» (`source_unknown`). Неизвестный код, код чужого формата и код длиннее лимита дают отметку и во входе не отказывают; каналом такой код стать не может. Канал, заведённый после прихода человека, его заявку не подписывает, а переименование видно и на открытых заявках. Разрешение — функция ядра `resolveApplicationSource`, её вызывает `RequestAccess` той же транзакцией, что и вставку заявки. Источник и имя (`first_name`) живут в заявке и обнуляются при решении. Профиль и журнал доступа их не получают.
- **Очередь и модератор.** Ключ очереди в хранилище — колонка `queue`: `community` или `auction` ([ADR-064](../decisions/ADR-064-two-bots-by-audience-circle-and-rights.md), пункты 8 и 12; миграция `017`). «Уже есть» на входе читается по праву очереди — `access_hub` или `place_bids`, — а не по кругу: гость, у которого отозвали запись, в очередь аукциона попадает, если отказа в силе нет. Модератор очереди — держатель права-выдавателя по таблице выдачи: аукциона — `admit_bidders`, сообщества — `manage_members`; обе очереди вместе — только тот, кто держит оба. Право актора читается из состояния по `identity_id`. Журнал доступа выдачу и отзыв прав отдельно от круга не пишет: их историю держат строки `identity_rights` и повод outbox.
- **Миграция `009`.** Незаблокированные профили без активных ролей, прошедшие `/start` в хабе до неё, получили заявку в сообщество без источника и без имени.

Проверка права `access_hub` и выбор кадра отказа — политика поверхности хаба ([PER-194](https://linear.app/anticnvm/issue/per-194)). Принятый `ResolveIdentity` блокировку не проверяет — проверка стоит на выдаче, — но возвращает её отметку отдельным полем `blocked` ([integration.md](../architecture/integration.md)); различать по ней ожидающий профиль и заблокированный — работа политики поверхности.

**Whitelist применяется один раз, а не на каждом действии.** Ник хранится без ведущего `@` и без пробелов по краям, в нижнем регистре, и обязан быть ником Telegram: строку, которой ник никогда не будет равен, операция отвергает, а не кладёт в список сиротой. Добавление и снятие ещё не сработавшей записи — внутренние идемпотентные операции Identity. При совпадении `ResolveIdentity` в одной транзакции гасит запись полями `used_at` и `used_by`, выдаёт круг записи и пишет выдачу в журнал с основанием `allowed_username` и пустым актором. Частичный уникальный индекс запрещает дубликат только среди записей, которые ещё могут сработать. Постоянная проверка сделала бы ник ключом доступа: человек, сменивший ник, терял бы доступ, а человек, занявший освободившийся ник, получал бы чужой. Совпадение ника служит входным сигналом, результат допуска записывается за внутренним идентификатором. TTL нет: непогашенное живёт, пока администратор не снимет. Список не становится реестром identity и не меняет ключи профиля. Сам список составляет человек своим клиентом Telegram — это его действие, а не вызов Bot API, поэтому боту по-прежнему не требуется никаких прав в группе.

**Блокировка** переводит профиль в `blocked`, сохраняет профиль и стабильный внутренний идентификатор и отзывает круг, наборы и записи. Повторный допуск возвращает ту же identity, но доступ не восстанавливает.

**Журнал доступа.** Таблица `identity_access_journal` пишется append-only в той же транзакции, что и изменение: субъект `identity_id`, выполнивший `performed_by`, действие `grant` | `revoke` | `block` | `unblock`, круг (`circle`) или набор (`preset`), основание `reason` и момент `occurred_at`. Выдача и отзыв называют ровно одно из двух, у блокировки и снятия оба NULL: это решения о профиле. Строки до миграции `017` хранят прежние имена кругов `admin` и `maintainer`. Поштучные записи прав журнал не называет: их историю держат строки `identity_rights` и повод outbox. Пустой `performed_by` означает системный переход, а также операцию через maintainer-секрет: профиля у владельца секрета нет, и `granted_by` остаётся NULL ([PER-169](https://linear.app/anticnvm/issue/per-169)). Выдачу и снятие набора `admin` из бота журнал записывает за профилем держателя `grant_admins` ([PER-33](https://linear.app/anticnvm/issue/per-33)). Блокировка пишет одну строку: отзыв круга и наборов — следствие одного решения, а метка времени у отозванных строк общая с ней, потому что `now()` внутри транзакции не меняется. Людей называет внутренний `identity_id`; Telegram user id и ник в журнал не входят. Внешнего ключа на `profiles` нет: журнал переживает профиль как история UUID, TTL в первой схеме нет ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Append-only держится схемой: UPDATE, DELETE и TRUNCATE отвергаются триггерами. Он не является источником истины и не участвует в проверке доступа — круг, наборы и записи читаются из своих таблиц, а блокировка из поля профиля. Журнал нужен потому, что допуск и блокировка это решения человека о человеке в сообществе, у которых нет другой поверхности аудита.

**Список ников — тоже запись решения.** Ни одно состояние строки её не удаляет: видно, кто ник завёл (`created_by`), кто снял (`removed_at`, `removed_by`) и кто по ней прошёл (`used_at`, `used_by`). Иначе основание, по которому человек получил круг, исчезало бы вместе с записью, а журнал доступа подхватить его не может: он называет людей внутренним `identity_id`, а у записи списка identity ещё нет — есть только ник. Пустой актор здесь означает операцию maintainer'а, как и `performed_by` журнала.

Ручная сверка постфактум сохраняется поверх премодерации, а не вместо неё: она закрывает окно между освобождением ника и первым `/start`.

Автоматическая проверка членства через `getChatMember` не используется. Причина техническая и жёсткая: метод гарантированно отвечает про **чужих** пользователей только когда бот является администратором чата, а бот-администратор по устройству Telegram получает все сообщения группы независимо от Privacy Mode. Это прямо противоречит принципу минимальных привилегий из [product/overview.md](../product/overview.md). Возврат к этому варианту потребует сначала переписать принцип, а не просто добавить вызов.

Премодерация входит в MVP, но не в [первый вертикальный срез](../architecture/first-slice.md): срез проверяет границы трёх сервисов, и допуск состава к этой проверке ничего не добавляет.

## Наборы admin и maintainer

Наборы хранятся отдельно от профиля в таблице `identity_presets` как данные вида `(identity_id, preset, granted_at, granted_by, revoked_at)`, а не как список Telegram `user_id` в конфигурации или коде. `ResolveIdentity` наборов не выдаёт и не восстанавливает: повторный `/start` возвращает только активные. Первый набор на пустой базе — `maintainer` — выдаёт служебный endpoint, защищённый общим секретом `IDENTITY_MAINTAINER_TOKEN` в metadata gRPC ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)): `GrantPreset` делает человека без круга участником тем же вызовом, потому что набор требует круг `member`. Дальше мейнтейнер назначает себя администратором сам — из бота, правом `grant_admins` (С-7, О-4 RFC-016). Bootstrap переменной окружения отвергнут вместе с [PER-167](https://linear.app/anticnvm/issue/per-167), прямой SQL путём не является ([ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md)).

Операции делятся по праву, и из этого следуют поверхности:

| Операция | Право | Где |
|---|---|---|
| посмотреть состав, допустить, понизить, заблокировать, вернуть допуск | `manage_members` | бот хаба |
| вести белый список и реестр каналов | `manage_members` | бот хаба |
| выдать и снять запись `admit_bidders` участнику | `manage_members` | бот хаба |
| решать очередь аукциона, отозвать `place_bids` у гостя | `admit_bidders` | бот хаба |
| выдать и снять набор `admin`, в том числе себе | `grant_admins` | бот хаба |
| выдать и снять любой набор, включая `maintainer` | владелец секрета | служебный endpoint |

Набор `maintainer` нельзя выдавать инструментом, доступ к которому сам зависит от прав, поэтому его выдаёт и снимает только служебный endpoint. `admin` держатель `grant_admins` назначает и снимает из бота хаба: бот передаёт, от чьего имени действие, а право Identity читает сам из текущего состояния. Назначаемого бот называет ником, который Identity разбирает сам и при неоднозначности отказывает; назначить можно только участника. Отдельная веб-админка в MVP не вводится.

Служебный endpoint идемпотентен и не является публичным API. Право на вызов доказывает секрет в metadata: локально и в развёрнутом контуре проверка одна, обхода нет ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Прямое редактирование БД и hardcoded-список не являются штатными путями ни для одной группы операций. Команды бота не содержат доменных правил: бот маршрутизирует вызов, решение принимает Identity.

Служебные операции — `GrantPreset` и `RevokePreset` ([integration.md](../architecture/integration.md#identity-grpc)). У пути через секрет `granted_by` пуст ([PER-169](https://linear.app/anticnvm/issue/per-169)): колонка ссылается на `profiles(id)`, а у владельца секрета профиля нет. Тем же NULL журнал называет актора операции через секрет; у выдачи и снятия `admin` из бота и `granted_by`, и актор журнала — профиль держателя `grant_admins`.

Это заменяет hardcoded-список из [ADR-016](../decisions/ADR-016-rbac-action-pattern-and-transport.md), который относился к удалённой аукционной ветке.

## Взаимодействие и отказ

Бот синхронно обращается к Identity по gRPC на каждом Telegram update, требующем продуктового действия. В срезе это одна операция: Telegram user id и ник, если он есть, в обмен на внутренний идентификатор, круг, наборы, права и отметку блокировки отдельным полем. Схема и запись в каталоге — [integration.md](../architecture/integration.md). Кэш фактов доступа в боте не используется: устаревшее разрешение равносильно пропущенной проверке. При недоступности Identity продуктовая операция завершается fail-closed; повторное рассмотрение кэша начинается только по наблюдаемому p95.

PostgreSQL — единственный источник истины, команды выполняются обычными ACID-транзакциями, а чтение идёт из тех же таблиц без CQRS, Event Sourcing, акторов и отдельной read model. Журнал доступа пишется в той же транзакции, но источником истины не является: он отвечает на вопрос «кто и когда это сделал», а не «что сейчас».

## Исходящие события

Синхронного gRPC оказалось недостаточно: [Notifications](notifications.md) ведёт собственную реплику людей, их круга и прав, потому что кто-то должен разворачивать аудиторию глобальной категории уведомлений. Сигнал пересмотра, записанный в [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), сработал — появился потребитель, которому синхронной проверки недостаточно ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)).

Из этого следуют три требования к Identity. Словарь событий и конверт приняты и описаны в [integration.md](../architecture/integration.md), раздел «Identity NATS»; устройство outbox и релея — раздел [«Outbox и релей»](#outbox-и-релей) ниже.

- **события о регистрации профиля, смене круга, выдаче и снятии наборов и записей прав и блокировке** публикуются наружу в Protobuf через NATS. Событие является данными, а не сигналом: получателю должно хватать его для восстановления состояния с нуля, поэтому снимок несёт круг, наборы и права и отдельно отметку блокировки. Поводы — `profile_registered`, `circle_changed`, `preset_granted`, `preset_revoked`, `right_granted`, `right_revoked`, `profile_blocked`, `profile_unblocked`, `application_submitted` и `application_admitted`, — и каждый называет свой subject `events.identity.<повод>`; схема — `contracts/proto/identity/v1/identity_events.proto`;
- **outbox.** Запись для отправки кладётся в той же транзакции, что и изменение состояния, и публикуется релеем. Прямая отправка из обработчика теряет событие при сбое между записью и публикацией. Отдельная таблица нужна потому, что журнала домена у Identity нет: журнал доступа покрывает только смену круга, наборов или блокировки и не покрывает регистрацию, поэтому подменять им outbox нельзя. Принятый конверт возлагает на неё ещё одно обязательство: монотонный счётчик версии профиля, который двигается той же транзакцией, что и изменение состояния, включая выдачу и отзыв в дочерних таблицах, и чью уникальность в пределах профиля держит схема. Без него потребитель не отбросит устаревший снимок при повторной публикации;
- **метод перечисления текущего состава** — вне MVP. Он понадобится, когда появятся люди, зарегистрированные до подключения потребителя, или потребуется пересборка его реплики. В первом запуске Identity и Notifications стартуют вместе, поэтому наполнять нечем; вопрос вынесен отдельной задачей.

Модель самого сервиса при этом не меняется: событий Identity не потребляет, состояние из них не выводит и read model у себя не заводит.

### Outbox и релей

Реализовано в [PER-210](https://linear.app/anticnvm/issue/per-210). Очередь — таблица `identity_outbox`, версия профиля — колонка `profiles.version`; миграция `007_identity_outbox.sql`. Колонку `traceparent` добавила `008_outbox_traceparent.sql` ([PER-373](https://linear.app/anticnvm/issue/per-373)), повод `application_submitted` и его ограничения — `012_application_submitted.sql` ([PER-435](https://linear.app/anticnvm/issue/per-435)).

**Носитель версии.** `profiles.version` — счётчик агрегата «профиль вместе с кругом, наборами и записями». Он считает события, а не изменения снимка: `application_submitted` доступа не меняет, но версию занимает. Каждое событие двигает его на единицу той же транзакцией, что и изменение, и оставляет строку outbox ровно с этим номером; `UNIQUE (identity_id, version)` стоит на outbox. Ноль означает профиль, о котором не выпущено ни одного события: так выглядят профили, созданные до outbox, и первое их событие приходит версией 1.

**Строка несёт снимок колонками, а не готовое сообщение.** Повод и то, что он называет (`previous_circle`, `preset`, `access_right`, `queue`), круг, наборы и права после применения и отметка блокировки лежат отдельными полями, и их согласие проверяет `CHECK`: `profile_blocked` приходит с отметкой и пустым снимком, `circle_changed` — с кругом, отличным от прежнего, `preset_granted` — с выданным набором в снимке, `preset_revoked` — без снятого, `profile_registered` — первым и незаблокированным. Колонки `role` и `global_roles` остались у строк до миграции `017`; новые строки их не несут, а ограничения нового словаря стоят `NOT VALID` — история неизменяема. Сообщение `IdentityEvent` собирает релей чистой функцией; subject выводится из повода, а не хранится рядом.

**Щиты схемы.** Кроме `UNIQUE` и `CHECK` — триггеры со своими кодами, как у журнала доступа:

| Код | Что запрещено |
|---|---|
| `ID004` | менять строку outbox, кроме одной отметки `published_at` из NULL |
| `ID005` | удалять строки outbox и очищать очередь |
| `ID006` | зафиксировать изменение без события: регистрацию, запись в `identity_circles`, `identity_presets` или `identity_rights`, смену `blocked` или `version` без строки outbox той же транзакции, а сдвиг версии — без строки ровно с этим номером. Проверка отложена до коммита |
| `ID007` | сдвигать версию не на единицу, начинать новый профиль не с нуля и писать строку outbox с номером, не равным текущей версии профиля |

`ID006` делает «изменение только вместе с событием» свойством схемы, а не соглашением. Цена названа прямо: ручная правка состояния в базе обязана писать событие тем же способом, что и сервис, а тестовая фикстура, которой нужно состояние мимо сервиса, создаёт его транзакцией с выключенными триггерами (`testdb.ExecBypassingShields`). Правка ника и служебных меток времени событием не является и триггер не задевает; удаление строк доступа и профилей не покрыто — продукт их не удаляет.

**Где пишутся события.** Регистрация — одно `profile_registered` после допуска по списку ников той же транзакции, поэтому круг приходит в его снимке, а не отдельной выдачей. Смена круга — одно `circle_changed` с прежним кругом и снимком после всей замены; записи, которые несёт переход, едут в том же снимке. Набор — своё `preset_granted` или `preset_revoked`; выдача набора общим секретом человеку без круга — два события: `circle_changed`, затем `preset_granted`. Поштучная запись — `right_granted` или `right_revoked`; запись, которую перекрывает круг или набор, не снимается и повода не даёт. Переход в блокировку — одно `profile_blocked`; блокировка уже заблокированного профиля убирает оставшиеся строки и пишет снова `profile_blocked`, круга ниже не выдавая. Холостые операции событий не пишут. Изменение блокирует строку профиля раньше строк доступа: событие двигает версию профиля, и обратный порядок встречно шёл бы к блокировке. Момент события — `now()` транзакции, тот же, что у журнала доступа и меток выдачи и отзыва.

**Релей.** Публикует раз в секунду пачками до 100 записей в порядке колонки `position`. Её номер выдаётся при вставке под блокировкой строки профиля, поэтому внутри профиля порядок совпадает с версией; `occurred_at` этого не гарантирует — `now()` фиксирует начало транзакции, и транзакция, начатая раньше, может получить профиль позже соседней. Экземпляры изолированы ходом: advisory-блокировка `pg_try_advisory_lock` на одном соединении, и экземпляр без хода пропускает тик, поэтому одну запись одновременно не публикуют двое. Параллельной публикации нет — это та же цена, что у Meetups ([ADR-035](../decisions/ADR-035-meetups-dispatch-mark-in-journal.md)). Публикация ставит `Nats-Msg-Id` равным `event_id` и `Nats-Expected-Stream: IDENTITY_EVENTS`, ждёт ack до 4 секунд без встроенных повторов клиента и только после ack ставит `published_at`. Отказ шины останавливает тик на первой записи, и следующая попытка — следующий тик. Доставка at-least-once: запись, опубликованная, но не отмеченная, уходит снова с тем же `event_id`.

Адрес шины приходит в `IDENTITY_NATS_URL`. Без него релей не запускается, сервис работает, а события копятся в очереди. Недоступная при старте шина старт не валит: клиент переподключается сам.

**Наблюдаемость.** Каждый тик пишет запись `operation = identity.outbox.dispatch` без `use_case`: `pending` — размер неотправленного набора, `oldest_pending_age_us` — возраст старейшей записи, `published`, а `repeats` — только когда повтор был. Холостой тик и занятый ход (`turn = busy`) — `Debug`, публикация — `Info`, повтор и отказ шины (`dependency_unavailable`) — `Warning`, отказ собственной базы — `Error`. Метрик нет: задача допускает структурный лог, и форма совпадает с релеем Meetups.

**Трассировка публикации.** `outbox.Append` кладёт в строку заголовок W3C `traceparent` спана запроса, записавшего событие; без записываемого спана Identity — экспорт выключен или сэмплер спан отбросил — колонка остаётся NULL, а формат проверяет `CHECK`. Колонка входит в кортеж `ID004` и после вставки не меняется. Каждая публикация — корневой спан `publish <subject>` вида Producer со ссылкой (span link) на спан запроса, а не его дочерний спан: тик публикует записи разных запросов, а публикация идёт после ответа и повторяется при отказе шины, так что трейс запроса к этому моменту закрыт. Отметка `published_at` — дочерний спан публикации. Строка без контекста или с неразборчивым значением публикуется без ссылки, а не отказом. В сообщение шины `traceparent` не уходит: конверт и заголовки публикации прежние.

Отсюда же следует граница адресации. [Notifications](notifications.md) ведёт реплику людей и их допуска и сам разворачивает аудиторию глобальной категории ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)). Пока допуск был одним значением, разворот был однозначен; с кругами он перестаёт им быть. Поэтому **реплика хранит круг и права, а разворот глобальной аудитории всегда называет право**: повод хаба адресуется держателям `access_hub`, оповещение о заявке — держателям права модерации её очереди ([ADR-064](../decisions/ADR-064-two-bots-by-audience-circle-and-rights.md), пункт 14; [PER-529](https://linear.app/anticnvm/issue/per-529)). Рассылки «всем профилям» не существует, иначе объявление сходки уходит людям, пришедшим по ссылке аукциона и не состоящим в сообществе. Identity этой границы не исполняет: он обязан лишь публиковать снимок с кругом и правами так, чтобы получатель их видел.

Отдельно от событий каналу доставки нужен **метод разрешения внутреннего идентификатора в Telegram id**: уведомление называет получателя внутренним идентификатором, а ADR-026 описывает только обратный путь. Метод принят отдельным вызовом `ResolveTelegramUserId`, а не режимом `ResolveIdentity`: последний устанавливает личность и создаёт профиль при первом обращении, а обратное разрешение обязано ответить `NOT_FOUND`. Метод реализован в [PER-231](https://linear.app/anticnvm/issue/per-231) и служебный: актора в запросе нет. Недопущенным он считает только заблокированный профиль и отвечает ему `FAILED_PRECONDITION`, отличимо от `NOT_FOUND` для отсутствующего; по правам не фильтрует, потому что круг получателя выбирает Notifications. Ответ несёт только Telegram id. Коды и правило для канала — [integration.md](../architecture/integration.md); вызывающего метод принимает по токену ([ADR-056](../decisions/ADR-056-service-calls-per-caller-token-and-closed-network.md)).

Второй служебный вызов для соседей — **синхронная проверка права** `CheckAccessRight`. Вызывающий называет право, которое требует его поверхность, и получает вердикт «право есть» или «права нет»; Identity не знает, какую поверхность охраняет вызов. Ответ читается из текущего состояния, без кэша, поэтому снятие набора или записи меняет следующий же ответ. Заблокированный получает «права нет», а не код отказа; отметка читается рядом как страховка поверх инварианта «у заблокированного нет прав». Неизвестный профиль — `NOT_FOUND`. Метод служебный: актора в запросе нет. Потребители — Notifications (объявление сообществу авторизует `manage_meetups`) и Meetups: отношение «ведёт сходки» он проверяет этим вызовом сам, правом `manage_meetups`, а не по правам, присланным вызывающим ([ADR-051](../decisions/ADR-051-meetup-relation-check-at-resource-owner.md)). Боты спрашивают `place_bids` получателя вести о лоте, без которого Auction не отдаст лот для её текста: бот аукциона — гостя ([PER-328](https://linear.app/anticnvm/issue/per-328)), бот хаба — участника ([PER-598](https://linear.app/anticnvm/issue/per-598)); Auction — кандидатов розыгрыша ([PER-499](https://linear.app/anticnvm/issue/per-499)). Прежний `CheckGlobalRole` снят RFC-016. Коды — [integration.md](../architecture/integration.md).

## Стек

Identity реализуется на Go. Сложного домена здесь нет; исследовательская ценность находится в operational-контуре gRPC/Protobuf, PostgreSQL, миграций, контейнера, Railway, Aspire и observability. Сгенерированный Protobuf-код живёт в отдельном пакете `gen/` без рукописного кода. Кодогенерация выполняется командой `buf generate --template apps/identity/buf.gen.yaml` с локальными официальными Go-плагинами по [стандарту Protobuf](../standards/contracts/protobuf.md#кодогенерация-go).

Текущий код в `apps/identity`: gRPC-сервер, `ResolveIdentity`, обратное `ResolveTelegramUserId`, проверка права `CheckAccessRight`, вход `RequestAccess`, операции наборов и ник организатора `ResolveOrganizerUsername` поверх PostgreSQL, `grpc.health.v1`, структурные логи `log/slog`, трейсы OpenTelemetry по OTLP (сервер, PostgreSQL и публикация outbox), миграции, outbox исходящих событий (`internal/outbox`) и его релей в JetStream (`internal/relay`). Операция создаёт профиль без круга и с `blocked = false` при первом обращении, обновляет ник только при отличии и возвращает внутренний идентификатор с кругом, наборами и правами. Отметка блокировки в ответ входит отдельным полем `blocked` и из прав не выводится. Внутреннее ядро сервиса реализует выдачу, отзыв, блокировку и снятие блокировки с записью журнала в той же транзакции; отказ в выдаче заблокированному отвечает `FAILED_PRECONDITION`, отличимо от `NOT_FOUND` для отсутствующего профиля. Запись границы называет человека только внутренним идентификатором: Telegram user id и ник — персональные данные и в лог не идут ([logging.md](../standards/observability/logging.md#персональные-данные)). У `ResolveIdentity` идентификатор берётся из ответа, поэтому у отказа его нет, и запись связывается с вызовом бота по `request_id`. У `ResolveTelegramUserId` он приходит в запросе и пишется и на отказе, если строка в канонической форме UUID.

## Цена отдельного сервиса

Разделение требует явно спроектировать:

- отдельный deployment unit и хранилище;
- migrations и ownership данных;
- межсервисные контракты;
- timeout и degraded behavior;
- согласованность прав на сообщество и доменных полномочий;
- наблюдаемость authentication/authorization пути.

Контракт разрешения личности принят и описан в [integration.md](../architecture/integration.md). Схема профиля, кругов, наборов и записей прав лежит в `apps/identity/internal/migrations/` и применяется при старте процесса. Identity зарегистрирован в Aspire как узел графа: `identity-proto` генерирует Go-код, `identity-build` собирает бинарник, `identity` запускает его и проверяется gRPC health.

## Открытые вопросы реализации

- точная схема whitelist;
- очистка опубликованных строк outbox: [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md) закрывает данные доступа, а не очередь публикации, и `ID005` удаление пока запрещает; если очистка понадобится, она заводится отдельной задачей;
- форма перечисления состава: отдельный метод, пагинация и поведение при параллельных изменениях — вне MVP;
- чем запись назовёт `granted_by` при выдаче через общий секрет — [PER-169](https://linear.app/anticnvm/issue/per-169);
- набор и формат административных команд бота;
- одноразовые приглашения хаба отложены до наблюдаемой потребности ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)); кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32);
- timeout при fail-closed; тексты ответов человеку — часть дизайн-сессии [PER-32](https://linear.app/anticnvm/issue/per-32);
- срок жизни профилей, созданных посетителями аукциона: ADR-043 его не выбирает, а переносить на них «`blocked` навсегда» и вечный журнал хаба запрещено ([RFC-009](../rfcs/RFC-009-identity-access-data-retention.md));
- останется ли право `place_bids` глобальным, когда одновременных аукционов станет два; права на отдельную сходку RFC-016 оставил вне границ.

Контракт разрешения личности, словарь исходящих событий и обратное разрешение в Telegram id зафиксированы в `contracts/proto/` и [integration.md](../architecture/integration.md). Обратное разрешение реализовано в [PER-231](https://linear.app/anticnvm/issue/per-231); outbox и релей реализованы в [PER-210](https://linear.app/anticnvm/issue/per-210); служебные endpoints остаются после закрытия открытых вопросов. Решения по модели, стеку, retention допуска, первому администратору и authentication endpoint — в [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), [ADR-027](../decisions/ADR-027-identity-go-stack.md), [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md), [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md) и [ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md).
