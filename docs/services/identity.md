# Identity Service

> **Слой:** MVP. **Граница, модель и язык:** Accepted. **Retention допуска к хабу:** [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md). **Круги сообщества и блокировка:** статус допуска заменён набором ролей, [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md); схема под него изменена в [PER-252](https://linear.app/anticnvm/issue/per-252), поведение выдачи, отзыва и блокировки — в [PER-191](https://linear.app/anticnvm/issue/per-191), контракт ролей и отметки блокировки расширен в [PER-254](https://linear.app/anticnvm/issue/per-254), вызов автовыдачи роли `public` остаётся открытым. **Первая выдача роли администратора в срезе:** только служебный endpoint, [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md). **Аутентификация служебного endpoint:** общий секрет в metadata gRPC, [ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md). **Wire-контракты:** контракт разрешения личности Accepted; служебные операции Open.

## Ответственность

Identity отвечает за общие факты идентичности:

- сопоставление Telegram user с внутренним participant identity;
- принадлежность человека к кругу сообщества и системные роли — одним набором ролей ([ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md));
- отметку блокировки, закрывающую человеку все поверхности сразу;
- минимальные данные профиля, если они нужны нескольким сервисам;
- публикацию фактов о регистрации, смене ролей и блокировке для тех, кому синхронного ответа недостаточно.

Граница формулируется одной строкой: **Identity отвечает на вопрос «кто это», а «что можно» отвечает владелец ресурса** — Meetups для сходок, аукцион для ставок. Поэтому имена `roles` или `permissions` для этого сервиса были бы неверны: контекстные роли живут в доменах, а централизованный владелец всех разрешений обязан был бы знать все действия всех сервисов.

Identity не решает, кто может изменить конкретную сходку. Он сообщает факты и общие роли, а Meetups применяет правила своего домена.

Authentication в MVP выполняет Telegram, а доверенной границей продукта является Telegram Bot: при long polling доверенностью входа служит владение bot token, входящего HTTP у бота нет ([ADR-030](../decisions/ADR-030-telegram-bot.md)). Identity не принимает и не проверяет authentication material: бот передаёт установленный Telegram user id, Identity отвечает внутренним идентификатором и глобальными ролями.

## Регистрация и данные профиля

Внутренний профиль создаётся при обработке `/start`. Это и есть регистрация в MVP: произвольное последующее действие не создаёт новую identity неявно. Иначе нечего показывать при ручной сверке состава и некуда выдавать роль администратора.

Минимальная модель профиля:

| Поле | Назначение и ограничение |
|---|---|
| внутренний идентификатор | стабильный первичный ключ identity в формате [UUIDv7](../decisions/ADR-020-uuidv7-identifiers.md); его используют другие домены в ссылках на человека |
| Telegram user id | стабильный внешний ключ для поиска профиля; уникален среди профилей |
| ник Telegram | nullable-кэш для сверки состава человеком; обновляется только при фактическом изменении и не хранит истории |
| глобальные роли | активные записи `identity_roles`: `maintainer`, `admin`, `member` или `public`; конкретная поверхность сама выбирает принимаемую роль |
| блокировка | обязательное булево поле `blocked`, отдельное от ролей; при миграции блокировка отзывает активные роли |
| created_at / updated_at | служебные метки; `updated_at` меняется только вместе с ником |

Ник хранится только с явно заданной целью — сверка состава сообщества человеком. Остальные поля профиля Telegram не сохраняются.

Ник никогда не является ключом связи, потому что у Telegram он:

- необязателен — у части людей его просто нет;
- изменяем владельцем в любой момент;
- переиспользуем: освобождённый ник может занять другой человек.

Междоменные ссылки используют внутренний идентификатор. Telegram user id — уникальная внешняя привязка, по которой бот разрешает identity. На нике нет уникального индекса: он nullable, не используется для связи, авторизации или поиска identity.

Физическая схема среза — таблицы `profiles`, `identity_roles`, `identity_access_journal` и `allowed_usernames` в `apps/identity/internal/migrations/`. Идентификатор хранится типом `uuid`. Глобальные роли хранятся отдельными строками, отзыв роли — колонка `revoked_at`, строка не удаляется. Профиль содержит `blocked BOOLEAN NOT NULL DEFAULT false`. Миграция `004` переносит `allowed` в роли `member` и `public`, `blocked` в отметку блокировки без активных ролей, а `pending` оставляет без ролей. Миграция `005` заводит журнал доступа и закрепляет инвариант «заблокированный не держит активных ролей» триггером `identity_roles_blocked_guard`. Миграция `006` добавляет список разрешённых ников и основание записи журнала. Строка списка не удаляется: погашение допуском (`used_at`, `used_by`) и снятие администратором (`removed_at`, `removed_by`) — отметки, уникальность действует только среди записей без обеих. Профиль создаётся через `/start`; роль администратора миграцией не выдаётся и назначается maintainer'ом. Миграции применяются при старте процесса.

Административная поверхность состава принимает установленную ботом личность и глобальные роли на каждом вызове. Identity, а не бот, требует роль `admin`. Экран получает одним чтением ожидающие и допущенные профили, отдельно читает активные разрешённые ники и после каждой команды перечитывает оба списка. Допуск выдаёт `member` и `public` одной транзакцией; закрытие доступа ставит блокировку и отзывает роли; повтор целевой команды возвращает `changed = false` без второй записи изменения.

Параллельные и повторные `/start` выполняются одной идемпотентной операцией `INSERT ... ON CONFLICT (telegram_user_id) DO UPDATE`. Последующие взаимодействия разрешают уже существующую identity и обновляют ник только при отличии; они не регистрируют отсутствующий профиль. Условие `username IS DISTINCT FROM excluded.username` не создаёт запись при неизменившемся нике. Это устраняет гонку между параллельными Telegram updates без акторов и версий строк.

## Круги сообщества и роли

Целевая модель доступа — набор ролей, а не одно поле статуса ([ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md)). Правило словаря: **роль называет круг людей, а не поверхность; поверхность объявляет, какие роли принимает.** Поэтому новый клиент не заводит своей роли, а перечисляет принимаемые.

| Роль | Круг | Кто выдаёт |
|---|---|---|
| maintainer | эксплуатирует систему | maintainer через служебный endpoint |
| admin | заводит и ведёт сходки, курирует состав, управляет подключённым к сходке аукционом | maintainer через служебный endpoint |
| `member` | внутренний круг сообщества | администратор: whitelist при регистрации или ручной допуск |
| `public` | внешний круг: пришёл по пересланной ссылке | система автоматически при `/start` в боте аукциона (вызов — [PER-266](https://linear.app/anticnvm/issue/per-266)) |

Круги вложенные: `admin` и `maintainer` входят в `member`, `member` входит в `public`. Допуск к хабу выдаёт `member` и `public` одной транзакцией. Хаб принимает круг `member` — роли `admin`, `maintainer` и `member`, потому что Identity отдаёт плоский набор и вложенность не разворачивает. Аукцион принимает `public`. Понижение человека — отзыв роли `member`: `public` остаётся, торги доступны, сходки нет.

Роль `public` будет выдаваться самозаписью по публичной ссылке; вызова под неё в контракте пока нет ([PER-266](https://linear.app/anticnvm/issue/per-266)), а означает она ровно «нажал `/start` в боте аукциона». Признаком знакомства с сообществом она не является, и ни один сценарий не должен читать её так.

Роль maintainer — факт, а не путь авторизации. Право на служебные RPC по-прежнему доказывает общий секрет в metadata ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)); роль нужна там, где у maintainer'а есть разрешения в сервисе без служебного endpoint'а.

Ролей аукциона в Identity нет. Отдельный администратор аукциона не заводится: аукцион существует в рамках сходки, и её администратор управляет им. Ведущий и помощник в зале — доменные факты аукциона, привязанные к сессии торгов: они меняются между блоками одного события и не являются фактами о человеке за его пределами.

**Блокировка — отдельное поле профиля**, не роль и не отсутствие ролей. Она отзывает все активные роли и проверяется в двух местах: на любой выдаче роли, включая автоматическую, и при выборе текста отказа. В проверке доступа поле не участвует — там решает отсутствие роли. Единственное исключение — служебная проверка глобальной роли `CheckGlobalRole`: она читает отметку рядом с ролями как страховку поверх этого инварианта и при расхождении отказывает, но правила не меняет (раздел «Исходящие события» ниже). Формулировка правила: отметка блокировки это защита на выдаче, а не на чтении. Заблокированный, нажавший `/start` в боте аукциона, роль `public` не получит; администратор не может выдать роль заблокированному, не сняв блокировку.

Схема и миграции под этот словарь сделаны в PER-252, поведение выдачи, отзыва, блокировки и допуска к хабу — в PER-191, расширение `identity.v1.GlobalRole` и отметка блокировки в ответе — в [PER-254](https://linear.app/anticnvm/issue/per-254). Вызова автовыдачи роли `public` в контракте нет: он отложен до [PER-266](https://linear.app/anticnvm/issue/per-266), заблокированной выбором механизма аутентификации ([PER-265](https://linear.app/anticnvm/issue/per-265)).

Выдача, отзыв и блокировка живут внутренним ядром сервиса. Выдача роли идемпотентна: повтор активной выдачи не создаёт второй строки и отвечает «изменения не было». Блокировка ставит отметку профиля и отзывает все активные роли одной транзакцией; снятие блокировки ролей не возвращает. Допуск к хабу выдаёт обе вложенные роли одной транзакцией. Отказ в выдаче заблокированному enforced дважды: проверкой под блокировкой строки профиля и триггером `identity_roles_blocked_guard`, который закрывает и возврат доступа снятием отметки отзыва. Поверхности у блокировки, снятия и выдачи кругов пока нет: их откроют команды администратора и контрактное изменение. Единственная живая поверхность запроса — служебные `GrantAdminRole` и `RevokeAdminRole`, которые ходят в то же ядро. Роли `member` и `public` выдаёт допуск по списку разрешённых ников внутри `ResolveIdentity`, и это выдача без запроса: поверхности, где их просят по wire, нет. Самозапись `public` при `/start` в боте аукциона отложена до [PER-266](https://linear.app/anticnvm/issue/per-266).

Премодерация по списку ников реализована внутри Identity; публичной поверхности управления списком пока нет, её добавят команды администратора.

## Контроль состава сообщества

Премодерация входит в MVP. Ссылка на бота публична по устройству Telegram, поэтому без неё расписание сходок сообщества доступно любому, кто нажал `/start`.

Membership моделируется ролями профиля. Круг `member` — **допуск к хабу**, не ко всей платформе ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Профиль вне этого круга ожидает допуска и получает роль `member` одним из двух путей:

| Путь | Когда срабатывает | Для кого |
|---|---|---|
| whitelist ников | один раз при `/start`, если ник совпал с непогашенной записью | основная масса участников сообщества |
| ручной допуск администратором | в любой момент после `/start` | любой профиль без роли `member`, в том числе люди без ника |

Одноразовая инвайт-ссылка из [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md) в этом срезе не реализуется: наблюдаемой потребности нет, общая ссылка на бота уже публична. Человек без ника остаётся без роли `member` до ручного допуска. Сигнал вернуть инвайт и кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32), [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md).

Человеку без роли `member` бот отвечает отказом с указанием, к кому обратиться, и не показывает никаких данных сходок. Это отличается от `blocked`, где повторное обращение ничего не меняет.

Проверка роли `member` и выбор кадра отказа — политика поверхности хаба ([PER-194](https://linear.app/anticnvm/issue/per-194)). Принятый `ResolveIdentity` блокировку не проверяет — проверка стоит на выдаче, — но возвращает её отметку отдельным полем `blocked` ([integration.md](../architecture/integration.md)); различать по ней ожидающий профиль и заблокированный — работа политики поверхности.

**Whitelist применяется один раз, а не на каждом действии.** Ник хранится без ведущего `@` и без пробелов по краям, в нижнем регистре, и обязан быть ником Telegram: строку, которой ник никогда не будет равен, операция отвергает, а не кладёт в список сиротой. Добавление и снятие ещё не сработавшей записи — внутренние идемпотентные операции Identity. При совпадении `ResolveIdentity` в одной транзакции гасит запись полями `used_at` и `used_by`, выдаёт роли `member` и `public` и пишет выдачи в журнал с основанием `allowed_username` и пустым актором. Частичный уникальный индекс запрещает дубликат только среди записей, которые ещё могут сработать. Постоянная проверка сделала бы ник ключом доступа: человек, сменивший ник, терял бы доступ, а человек, занявший освободившийся ник, получал бы чужой. Совпадение ника служит входным сигналом, результат допуска записывается за внутренним идентификатором. TTL нет: непогашенное живёт, пока администратор не снимет. Список не становится реестром identity и не меняет ключи профиля. Сам список составляет человек своим клиентом Telegram — это его действие, а не вызов Bot API, поэтому боту по-прежнему не требуется никаких прав в группе.

**Блокировка** переводит профиль в `blocked`, сохраняет профиль и стабильный внутренний идентификатор и автоматически отзывает активные глобальные роли. Повторный допуск возвращает ту же identity, но роли не восстанавливает.

**Журнал доступа.** Таблица `identity_access_journal` пишется append-only в той же транзакции, что и изменение: субъект `identity_id`, выполнивший `performed_by`, действие `grant` | `revoke` | `block` | `unblock`, роль, основание `reason` и момент `occurred_at`. Роль названа у выдачи и отзыва, у блокировки и снятия она NULL: это решения о профиле, а не о роли. Пустой `performed_by` означает системный переход, а также операцию maintainer'а: профиля maintainer'а нет, и `granted_by` остаётся NULL ([PER-169](https://linear.app/anticnvm/issue/per-169)). Блокировка пишет одну строку: отзыв ролей — следствие одного решения, а метка времени у отозванных строк общая с ней, потому что `now()` внутри транзакции не меняется. Людей называет внутренний `identity_id`; Telegram user id и ник в журнал не входят. Внешнего ключа на `profiles` нет: журнал переживает профиль как история UUID, TTL в первой схеме нет ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Append-only держится схемой: UPDATE, DELETE и TRUNCATE отвергаются триггерами. Он не является источником истины и не участвует в проверке доступа — активные роли читаются из `identity_roles`, а блокировка из поля профиля. Журнал нужен потому, что допуск и блокировка это решения человека о человеке в сообществе, у которых нет другой поверхности аудита.

**Список ников — тоже запись решения.** Ни одно состояние строки её не удаляет: видно, кто ник завёл (`created_by`), кто снял (`removed_at`, `removed_by`) и кто по ней прошёл (`used_at`, `used_by`). Иначе основание, по которому человек получил роли, исчезало бы вместе с записью, а журнал доступа подхватить его не может: он называет людей внутренним `identity_id`, а у записи списка identity ещё нет — есть только ник. Пустой актор здесь означает операцию maintainer'а, как и `performed_by` журнала.

Ручная сверка постфактум сохраняется поверх премодерации, а не вместо неё: она закрывает окно между освобождением ника и первым `/start`.

Автоматическая проверка членства через `getChatMember` не используется. Причина техническая и жёсткая: метод гарантированно отвечает про **чужих** пользователей только когда бот является администратором чата, а бот-администратор по устройству Telegram получает все сообщения группы независимо от Privacy Mode. Это прямо противоречит принципу минимальных привилегий из [product/overview.md](../product/overview.md). Возврат к этому варианту потребует сначала переписать принцип, а не просто добавить вызов.

Премодерация входит в MVP, но не в [первый вертикальный срез](../architecture/first-slice.md): срез проверяет границы трёх сервисов, и допуск состава к этой проверке ничего не добавляет.

## Роль администратора

Роль хранится отдельно от профиля в таблице `identity_roles` как данные вида `(identity_id, role, granted_at, granted_by, revoked_at)`, а не как список Telegram `user_id` в конфигурации или коде. Первый администратор назначается maintainer'ом после того, как человек уже начал пользоваться ботом и получил внутренний идентификатор. `ResolveIdentity` роли не выдаёт и не восстанавливает: повторный `/start` возвращает только активные записи. Выдача и отзыв — maintainer-операции через служебный endpoint, защищённый общим секретом `IDENTITY_MAINTAINER_TOKEN` в metadata gRPC ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Другого пути в срезе нет: bootstrap переменной окружения отвергнут вместе с [PER-167](https://linear.app/anticnvm/issue/per-167), прямой SQL путём не является ([ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md)).

Операции делятся по владельцу вопроса, и из этого следуют поверхности:

| Операция | Кто | Где |
|---|---|---|
| посмотреть профили с фильтром по статусу | администратор | команды бота |
| допустить, заблокировать, вернуть допуск | администратор | команды бота |
| загрузить whitelist, посмотреть и удалить непогашенные записи | администратор | команды бота |
| выдать и отозвать глобальную роль администратора | maintainer | служебный endpoint |

Курирование состава — вопрос администратора, и он решается там, где администратор уже работает. Права в системе — вопрос maintainer'а, и его нельзя решать инструментом, доступ к которому сам зависит от роли; этим же путём назначается первый администратор, когда нажать в боте ещё некому. Отдельная веб-админка в MVP не вводится.

Служебный endpoint идемпотентен и не является публичным API. Право на вызов доказывает секрет в metadata: локально и в развёрнутом контуре проверка одна, обхода нет ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Прямое редактирование БД и hardcoded-список не являются штатными путями ни для одной группы операций. Команды бота не содержат доменных правил: бот маршрутизирует вызов, решение принимает Identity.

Контракт служебных операций ещё не принят; authentication выбран и реализацию не блокирует. Чем запись роли назовёт `granted_by` — вопрос схемы [PER-169](https://linear.app/anticnvm/issue/per-169): колонка сейчас ссылается на `profiles(id)`, профиля maintainer'а нет. Тем же NULL журнал называет актора операции maintainer'а; записи, сделанные до решения PER-169, от системных в журнале не отличимы, и backfill append-only не допускает.

Это заменяет hardcoded-список из [ADR-016](../decisions/ADR-016-rbac-action-pattern-and-transport.md), который относился к удалённой аукционной ветке.

## Взаимодействие и отказ

Бот синхронно обращается к Identity по gRPC на каждом Telegram update, требующем продуктового действия. В срезе это одна операция: Telegram user id и ник, если он есть, в обмен на внутренний идентификатор, общие роли и отметку блокировки отдельным полем. Схема и запись в каталоге — [integration.md](../architecture/integration.md). Кэш фактов доступа и ролей в боте не используется: устаревшее разрешение равносильно пропущенной проверке. При недоступности Identity продуктовая операция завершается fail-closed; повторное рассмотрение кэша начинается только по наблюдаемому p95.

PostgreSQL — единственный источник истины, команды выполняются обычными ACID-транзакциями, а чтение идёт из тех же таблиц без CQRS, Event Sourcing, акторов и отдельной read model. Журнал доступа пишется в той же транзакции, но источником истины не является: он отвечает на вопрос «кто и когда это сделал», а не «что сейчас».

## Исходящие события

Синхронного gRPC оказалось недостаточно: [Notifications](notifications.md) ведёт собственную реплику людей и их глобальных ролей, потому что кто-то должен разворачивать аудиторию глобальной категории уведомлений. Сигнал пересмотра, записанный в [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), сработал — появился потребитель, которому синхронной проверки недостаточно ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)).

Из этого следуют три требования к Identity. Словарь событий и конверт приняты и описаны в [integration.md](../architecture/integration.md), раздел «Identity NATS»; устройство outbox и релея — раздел [«Outbox и релей»](#outbox-и-релей) ниже.

- **события о регистрации профиля, выдаче и отзыве роли и блокировке** публикуются наружу в Protobuf через NATS. Событие является данными, а не сигналом: получателю должно хватать его для восстановления состояния с нуля. По [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md) сменой допуска становится выдача или отзыв роли, поэтому событие несёт роль, а не значение статуса, и отдельно несёт отметку блокировки. Поводов пять — регистрация, выдача роли, отзыв роли, блокировка и снятие блокировки, — и каждый называет свой subject `events.identity.<повод>`; схема — `contracts/proto/identity/v1/identity_events.proto`;
- **outbox.** Запись для отправки кладётся в той же транзакции, что и изменение состояния, и публикуется релеем. Прямая отправка из обработчика теряет событие при сбое между записью и публикацией. Отдельная таблица нужна потому, что журнала домена у Identity нет: журнал доступа покрывает только смену роли или блокировки и не покрывает регистрацию, поэтому подменять им outbox нельзя. Принятый конверт возлагает на неё ещё одно обязательство: монотонный счётчик версии профиля, который двигается той же транзакцией, что и изменение состояния, включая выдачу и отзыв роли в дочерней таблице, и чью уникальность в пределах профиля держит схема. Без него потребитель не отбросит устаревший снимок при повторной публикации;
- **метод перечисления текущего состава** — вне MVP. Он понадобится, когда появятся люди, зарегистрированные до подключения потребителя, или потребуется пересборка его реплики. В первом запуске Identity и Notifications стартуют вместе, поэтому наполнять нечем; вопрос вынесен отдельной задачей.

Модель самого сервиса при этом не меняется: событий Identity не потребляет, состояние из них не выводит и read model у себя не заводит.

### Outbox и релей

Реализовано в [PER-210](https://linear.app/anticnvm/issue/per-210). Очередь — таблица `identity_outbox`, версия профиля — колонка `profiles.version`; миграция `007_identity_outbox.sql`.

**Носитель версии.** `profiles.version` — счётчик агрегата «профиль вместе с ролями». Каждое событие двигает его на единицу той же транзакцией, что и изменение, и оставляет строку outbox ровно с этим номером; `UNIQUE (identity_id, version)` стоит на outbox. Ноль означает профиль, о котором не выпущено ни одного события: так выглядят профили, созданные до outbox, и первое их событие приходит версией 1.

**Строка несёт снимок колонками, а не готовое сообщение.** Повод, роль повода, активные роли после применения и отметка блокировки лежат отдельными полями, и их согласие проверяет `CHECK`: `profile_blocked` приходит с отметкой и пустым набором, `role_granted` — с выданной ролью в наборе, `role_revoked` — без отозванной, `profile_registered` — первым и незаблокированным. Сообщение `IdentityEvent` собирает релей чистой функцией; subject выводится из повода, а не хранится рядом.

**Щиты схемы.** Кроме `UNIQUE` и `CHECK` — триггеры со своими кодами, как у журнала доступа:

| Код | Что запрещено |
|---|---|
| `ID004` | менять строку outbox, кроме одной отметки `published_at` из NULL |
| `ID005` | удалять строки outbox и очищать очередь |
| `ID006` | зафиксировать изменение без события: регистрацию, запись в `identity_roles`, смену `blocked` или `version` без строки outbox той же транзакции, а сдвиг версии — без строки ровно с этим номером. Проверка отложена до коммита |
| `ID007` | сдвигать версию не на единицу, начинать новый профиль не с нуля и писать строку outbox с номером, не равным текущей версии профиля |

`ID006` делает «изменение только вместе с событием» свойством схемы, а не соглашением. Цена названа прямо: ручная правка состояния в базе обязана писать событие тем же способом, что и сервис, а тестовая фикстура, которой нужно состояние мимо сервиса, создаёт его транзакцией с выключенными триггерами (`testdb.ExecBypassingShields`). Правка ника и служебных меток времени событием не является и триггер не задевает; удаление ролей и профилей не покрыто — продукт их не удаляет.

**Где пишутся события.** Регистрация — одно `profile_registered` после допуска по списку ников той же транзакции, поэтому роли приходят в его снимке, а не отдельными выдачами. Допуск к хабу выдаёт `public` раньше `member`: каждая выдача — своё событие, и промежуточный снимок `{member}` без `public` нарушил бы вложенность кругов. Переход в блокировку — одно `profile_blocked`; блокировка уже заблокированного профиля отзывает оставшиеся роли по одной, каждую своим `role_revoked`. Холостые операции событий не пишут. `revokeRoleTx` блокирует строку профиля раньше строки роли: событие двигает версию профиля, и обратный порядок встречно шёл бы к `blockIdentity`. Момент события — `now()` транзакции, тот же, что у журнала доступа и меток выдачи и отзыва.

**Релей.** Публикует раз в секунду пачками до 100 записей в порядке колонки `position`. Её номер выдаётся при вставке под блокировкой строки профиля, поэтому внутри профиля порядок совпадает с версией; `occurred_at` этого не гарантирует — `now()` фиксирует начало транзакции, и транзакция, начатая раньше, может получить профиль позже соседней. Экземпляры изолированы ходом: advisory-блокировка `pg_try_advisory_lock` на одном соединении, и экземпляр без хода пропускает тик, поэтому одну запись одновременно не публикуют двое. Параллельной публикации нет — это та же цена, что у Meetups ([ADR-035](../decisions/ADR-035-meetups-dispatch-mark-in-journal.md)). Публикация ставит `Nats-Msg-Id` равным `event_id` и `Nats-Expected-Stream: IDENTITY_EVENTS`, ждёт ack до 4 секунд без встроенных повторов клиента и только после ack ставит `published_at`. Отказ шины останавливает тик на первой записи, и следующая попытка — следующий тик. Доставка at-least-once: запись, опубликованная, но не отмеченная, уходит снова с тем же `event_id`.

Адрес шины приходит в `IDENTITY_NATS_URL`. Без него релей не запускается, сервис работает, а события копятся в очереди. Недоступная при старте шина старт не валит: клиент переподключается сам.

**Наблюдаемость.** Каждый тик пишет запись `operation = identity.outbox.dispatch` без `use_case`: `pending` — размер неотправленного набора, `oldest_pending_age_us` — возраст старейшей записи, `published`, а `repeats` — только когда повтор был. Холостой тик и занятый ход (`turn = busy`) — `Debug`, публикация — `Info`, повтор и отказ шины (`dependency_unavailable`) — `Warning`, отказ собственной базы — `Error`. Метрик нет: задача допускает структурный лог, и форма совпадает с релеем Meetups.

Отсюда же следует граница адресации. [Notifications](notifications.md) ведёт реплику людей и их допуска и сам разворачивает аудиторию глобальной категории ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)). Пока допуск был одним значением, разворот был однозначен; с кругами он перестаёт им быть. Поэтому **реплика хранит роли, а разворот глобальной аудитории всегда называет круг**: повод хаба адресуется `member`, повод торгов — `public`. Рассылки «всем профилям» не существует, иначе объявление сходки уходит людям, пришедшим по ссылке аукциона и не состоящим в сообществе. Identity этой границы не исполняет: он обязан лишь публиковать смену роли так, чтобы круг был виден получателю.

Отдельно от событий каналу доставки нужен **метод разрешения внутреннего идентификатора в Telegram id**: уведомление называет получателя внутренним идентификатором, а ADR-026 описывает только обратный путь. Метод принят отдельным вызовом `ResolveTelegramUserId`, а не режимом `ResolveIdentity`: последний устанавливает личность и создаёт профиль при первом обращении, а обратное разрешение обязано ответить `NOT_FOUND`. Метод реализован в [PER-231](https://linear.app/anticnvm/issue/per-231) и служебный: актора в запросе нет. Недопущенным он считает только заблокированный профиль и отвечает ему `FAILED_PRECONDITION`, отличимо от `NOT_FOUND` для отсутствующего; по ролям не фильтрует, потому что круг получателя выбирает Notifications. Ответ несёт только Telegram id. Коды и правило для канала — [integration.md](../architecture/integration.md); service authentication вызова — [PER-265](https://linear.app/anticnvm/issue/per-265).

Второй служебный вызов для соседей — **синхронная проверка глобальной роли** `CheckGlobalRole`. Её первый потребитель — Notifications: объявление сообществу авторизует Identity, а не реплика рассылки. Вызывающий называет роли, которые принимает его поверхность, и получает вердикт «право есть» или «права нет»; Identity не знает, какую поверхность охраняет вызов. Набор сравнивается плоско, как везде в этом словаре. Ответ читается из текущего состояния, без кэша, поэтому отзыв роли меняет следующий же ответ. Заблокированный получает «права нет», а не код отказа. Это единственное чтение, где отметка блокировки участвует в решении о доступе, и участвует она как страховка, а не как правило: инвариант «у заблокированного нет активных ролей» держат ядро, триггер на выдаче и `CHECK` снимка `profile_blocked`, но профиль, заблокированный до outbox или правкой с выключенными триггерами, мог остаться с активной ролью. При расхождении отметки и ролей побеждает отказ. Метод реализован в [PER-232](https://linear.app/anticnvm/issue/per-232) и служебный: актора в запросе нет. Коды — [integration.md](../architecture/integration.md). Второй потребитель — Meetups: отношение «администратор» к сходке он проверяет этим вызовом сам, а не по ролям, присланным вызывающим ([ADR-051](../decisions/ADR-051-meetup-relation-check-at-resource-owner.md), [PER-349](https://linear.app/anticnvm/issue/per-349)).

## Стек

Identity реализуется на Go. Сложного домена здесь нет; исследовательская ценность находится в operational-контуре gRPC/Protobuf, PostgreSQL, миграций, контейнера, Railway, Aspire и observability. Сгенерированный Protobuf-код живёт в отдельном пакете `gen/` без рукописного кода. Кодогенерация выполняется командой `buf generate --template apps/identity/buf.gen.yaml` с локальными официальными Go-плагинами по [стандарту Protobuf](../standards/contracts/protobuf.md#кодогенерация-go).

Текущий код в `apps/identity`: gRPC-сервер, `ResolveIdentity`, обратное `ResolveTelegramUserId` и проверка глобальной роли `CheckGlobalRole` поверх PostgreSQL, `grpc.health.v1`, структурные логи `log/slog`, миграции, outbox исходящих событий (`internal/outbox`) и его релей в JetStream (`internal/relay`). Операция создаёт профиль без активных ролей и с `blocked = false` при первом обращении, обновляет ник только при отличии и возвращает внутренний идентификатор с активными общими ролями. Отметка блокировки в ответ входит отдельным полем `blocked` и из набора ролей не выводится. Внутреннее ядро сервиса реализует выдачу, отзыв, блокировку и снятие блокировки с записью журнала в той же транзакции; отказ в выдаче заблокированному отвечает `FAILED_PRECONDITION`, отличимо от `NOT_FOUND` для отсутствующего профиля. Запись границы называет человека только внутренним идентификатором: Telegram user id и ник — персональные данные и в лог не идут ([logging.md](../standards/observability/logging.md#персональные-данные)). У `ResolveIdentity` идентификатор берётся из ответа, поэтому у отказа его нет, и запись связывается с вызовом бота по `request_id`. У `ResolveTelegramUserId` он приходит в запросе и пишется и на отказе, если строка в канонической форме UUID.

## Цена отдельного сервиса

Разделение требует явно спроектировать:

- отдельный deployment unit и хранилище;
- migrations и ownership данных;
- межсервисные контракты;
- timeout и degraded behavior;
- согласованность общих ролей и доменных полномочий;
- наблюдаемость authentication/authorization пути.

Контракт разрешения личности принят и описан в [integration.md](../architecture/integration.md). Схема профиля и глобальных ролей лежит в `apps/identity/internal/migrations/` и применяется при старте процесса. Identity зарегистрирован в Aspire как узел графа: `identity-proto` генерирует Go-код, `identity-build` собирает бинарник, `identity` запускает его и проверяется gRPC health.

## Открытые вопросы реализации

- точная схема whitelist;
- очистка опубликованных строк outbox: [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md) закрывает данные доступа, а не очередь публикации, и `ID005` удаление пока запрещает; если очистка понадобится, она заводится отдельной задачей;
- форма перечисления состава: отдельный метод, пагинация и поведение при параллельных изменениях — вне MVP;
- чем запись роли назовёт `granted_by` при выдаче maintainer'ом — [PER-169](https://linear.app/anticnvm/issue/per-169);
- набор и формат административных команд бота;
- одноразовые приглашения хаба отложены до наблюдаемой потребности ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)); кадр «вход по приглашению» — [PER-32](https://linear.app/anticnvm/issue/per-32);
- timeout при fail-closed; тексты ответов человеку — часть дизайн-сессии [PER-32](https://linear.app/anticnvm/issue/per-32);
- вызов автовыдачи роли `public` при `/start`: caller, доказательство права и поведение при повторном `/start` — отложен до [PER-266](https://linear.app/anticnvm/issue/per-266), заблокированной [PER-265](https://linear.app/anticnvm/issue/per-265);
- срок жизни профилей, созданных посетителями аукциона: ADR-043 его не выбирает, а переносить на них «`blocked` навсегда» и вечный журнал хаба запрещено ([RFC-009](../rfcs/RFC-009-identity-access-data-retention.md));
- останется ли роль `public` глобальной, когда одновременных аукционов станет два.

Контракт разрешения личности, словарь исходящих событий и обратное разрешение в Telegram id зафиксированы в `contracts/proto/` и [integration.md](../architecture/integration.md). Обратное разрешение реализовано в [PER-231](https://linear.app/anticnvm/issue/per-231); outbox и релей реализованы в [PER-210](https://linear.app/anticnvm/issue/per-210); служебные endpoints остаются после закрытия открытых вопросов.
