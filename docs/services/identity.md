# Identity Service

> **Слой:** MVP. **Граница отдельного сервиса, регистрация, модель профиля, контроль состава и выдача роли администратора:** Accepted. **Failure semantics, язык и контракты:** Open.

## Ответственность

Identity отвечает за общие факты идентичности:

- сопоставление Telegram user с внутренним participant identity;
- membership в сообществе;
- системные роли вроде owner/admin;
- минимальные данные профиля, если они нужны нескольким сервисам;
- серверную проверку Telegram authentication material, если эта boundary будет назначена сюда.

Граница формулируется одной строкой: **Identity отвечает на вопрос «кто это», а «что можно» отвечает владелец ресурса** — Meetups для сходок, аукцион для ставок. Поэтому имена `roles` или `permissions` для этого сервиса были бы неверны: контекстные роли живут в доменах, а централизованный владелец всех разрешений обязан был бы знать все действия всех сервисов.

Identity не решает, кто может изменить конкретную сходку. Он сообщает факты и общие роли, а Meetups применяет правила своего домена.

## Регистрация и данные профиля

Внутренний профиль создаётся при обработке `/start`, до первого значимого действия. Повторный `/start` находит тот же профиль по Telegram user id и обновляет кэш ника, но не создаёт новую identity. Иначе нечего показывать при ручной сверке состава и некуда выдавать роль администратора.

Минимальная модель профиля:

| Поле | Назначение и ограничение |
|---|---|
| внутренний идентификатор | стабильный первичный ключ identity; его используют другие домены в ссылках на человека |
| Telegram user id | стабильный внешний ключ для поиска профиля; уникален среди профилей |
| ник Telegram | nullable-кэш для ручной сверки состава; обновляется при каждом взаимодействии и не хранит историю |

Ник хранится только с явно заданной целью — сверка состава сообщества человеком. Остальные поля профиля Telegram не сохраняются.

Ник никогда не является ключом связи, потому что у Telegram он:

- необязателен — у части людей его просто нет;
- изменяем владельцем в любой момент;
- переиспользуем: освобождённый ник может занять другой человек.

Ключ связи между доменами — внутренний идентификатор; Telegram user id используется только для привязки входящего Telegram user к identity. На ник не ссылаются профили, роли, сходки и другие доменные данные, и уникальность ника в хранилище не требуется.

## Контроль состава сообщества

В MVP контроль ручной и постфактум: администратор время от времени просматривает список тех, кто начал пользоваться продуктом. Список участников общего чата человек при необходимости выгружает своим клиентом Telegram — это действие человека, а не вызов Bot API, поэтому боту не требуется никаких прав в группе.

Автоматическая проверка членства через `getChatMember` не используется. Причина техническая и жёсткая: метод гарантированно отвечает про **чужих** пользователей только когда бот является администратором чата, а бот-администратор по устройству Telegram получает все сообщения группы независимо от Privacy Mode. Это прямо противоречит принципу минимальных привилегий из [product/overview.md](../product/overview.md). Возврат к этому варианту потребует сначала переписать принцип, а не просто добавить вызов.

Премодерация остаётся возможным усилением после MVP: человек выгружает allowlist ников, а Identity проверяет его до допуска к продуктовым действиям. Allowlist не становится реестром identity и не меняет ключи профиля: совпадение ника служит входным сигналом, а результат допуска записывается за внутренним идентификатором. Для человека без ника нужен отдельный ручной путь по его уже созданному внутреннему идентификатору; смена ника требует повторной сверки человеком. Сам allowlist, интерфейс его загрузки и состояния модерации в MVP не реализуются.

## Роль администратора

Роль хранится как данные Identity, связанные с внутренним идентификатором, а не как список Telegram `user_id` в конфигурации или коде. Первый и последующие администраторы назначаются maintainer'ом только после `/start`, когда профиль уже существует.

Штатный путь MVP — минимальная служебная операция Identity «выдать глобальную роль администратора» по внутреннему идентификатору. Она недоступна через пользовательский Telegram flow, вызывается maintainer'ом из ограниченного эксплуатационного контура и идемпотентна: повторная выдача оставляет роль выданной. Прямое редактирование БД не является штатным способом, а Telegram user id и ник не принимаются как ключ назначения. Конкретные transport и authentication служебной операции проектируются вместе с контрактами Identity; до их принятия это требование к реализации, а не готовый API-контракт.

Это заменяет hardcoded-список из [ADR-016](../decisions/ADR-016-rbac-action-pattern-and-transport.md), который применим только к legacy-ветке аукциона. Отзыв роли остаётся отдельным открытым сценарием и не должен решаться удалением профиля.

## Цена отдельного сервиса

Разделение требует явно спроектировать:

- отдельный deployment unit и хранилище;
- migrations и ownership данных;
- межсервисные контракты;
- timeout и degraded behavior;
- согласованность общих ролей и доменных полномочий;
- наблюдаемость authentication/authorization пути.

Граница не означает, что сервис уже спроектирован.

## Открытые вопросы

- Как отзывается роль и что происходит с данными человека, которого убрали из сообщества?
- Что происходит при недоступности Identity?
- Нужна ли синхронная проверка на каждом действии?
- Как разделить authentication и authorization?

Закрыто решением владельца: identity создаётся при `/start`; хранятся внутренний id, Telegram user id и ник как кэш для сверки состава; контроль в MVP ручной и постфактум; роль администратора выдаётся maintainer'ом через минимальную служебную операцию. Премодерация allowlist'ом отложена, но её границы определены. Вопрос про Mini App `initData` снят вместе с выносом Mini App за границы MVP.

Язык выбирается после ответов. C#, F#, Kotlin и Go остаются кандидатами. По [ADR-007](../decisions/ADR-007-polyglot-service-stacks.md) совпадение runtime с Meetups не обязательно: стоимость ещё одного operational stack остаётся критерием сравнения, но не запретом.
