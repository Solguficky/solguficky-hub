# Telegram Mini App

> **Слой:** Deferred. **Стек:** TypeScript-клиент вероятен; framework и backend boundary не выбраны.

Mini App **не входит в MVP**. Решение принято владельцем 15 августа 2026 года: ни один сценарий MVP не потребовал поверхности, которой нет у бота, а второй клиент удваивает работу над представлением. Отказ не является запретом навсегда — Mini App возвращается, когда появится сценарий, который действительно не помещается в бота.

Два следствия этого решения для других документов:

- контракт представления в [RFC-001](../rfcs/RFC-001-meetup-modules-topology.md) теряет второго потребителя, поэтому декларативное описание экрана перестаёт окупаться до появления первого модуля;
- хранение изображений через Telegram `file_id` перестаёт конфликтовать с чем-либо: показывать их вне Telegram некому. Возврат Mini App потребует проксирующего эндпоинта, но не смены хранилища.

Mini App вводится только для сценариев, которые неудобно или невозможно качественно реализовать в интерфейсе бота.

До выбора framework необходимо определить:

- пользователя и задачу каждого экрана;
- какие действия действительно неудобны в боте;
- состояния загрузки, ошибки и отсутствия данных;
- операции с elevated permissions;
- данные, доступные браузеру;
- backend boundary;
- server-side проверку Telegram `initData`.

TypeScript является естественным языком клиента. Из этого не следует автоматический выбор React, Vue или Svelte и не следует прямой доступ браузера к внутренним сервисам.

С Telegram Bot допустим общий presentation package, описанный в [брифе компонента](telegram-bot.md). Пакет не создаётся заранее и не становится источником инвариантов Meetups или решений авторизации ([ADR-030](../decisions/ADR-030-telegram-bot.md)).

## Следующая работа

Работа возобновляется только при появлении сценария, который бот не закрывает. Тогда:

1. Утвердить сценарии и первые макеты.
2. Выбрать browser/backend transport.
3. Только затем принять решение о framework и структуре workspace.
