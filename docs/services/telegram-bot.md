# Hub Bot и Auction Bot

> **Слой:** Hub Bot — MVP, Auction Bot — Future. **Устройство и стек:** Accepted, [ADR-030](../decisions/ADR-030-telegram-bot.md), разбор вариантов — [RFC-006](../rfcs/RFC-006-telegram-bot-edge-design.md). **Два входа и общий слой аукциона:** Accepted, [ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md). **Форма сообщений хаба:** Accepted, [ADR-034](../decisions/ADR-034-telegram-bot-rich-presentation.md). **Дизайн-код экранов:** Accepted, не реализован — [design-code.md](../design/bot/design-code.md). **Не спроектированы:** transport к Auction, второй вход для уведомлений, контракт вклада модуля в карточку, экран настроек и возврат разблокированного человека.

Два компонента **владеют своими Telegram-представлениями продукта**. Они не «делают работу бота»: работу выполняют Meetups, Auction, Identity и Notifications. Бот хаба имеет идентификатор `hub-bot` и код `apps/hub-bot`; публичный вход аукциона — `auction-bot` и `apps/auction-bot`. Полное переименование принято 2026-10-03 в [уточнении ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md#уточнение-2026-10-03-полное-переименование-бота-хаба); имя файла этого брифа сохранено ради ссылок.

## Ответственность MVP

- принимает разрешённые Telegram updates;
- реализует интерфейс бота и его экраны;
- преобразует Telegram-ввод в вызовы юзкейсов;
- маршрутизирует вызовы к Identity, Meetups и Notifications;
- показывает человеку успешный или ошибочный результат;
- потребляет уведомления из шины и доставляет их в Telegram ([доставка уведомлений](#доставка-уведомлений));
- соблюдает privacy, least privilege и ограничения Telegram API.

Компоненты не владеют инвариантами Meetups, системными ролями и доменными решениями авторизации. Политика поверхности из [ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md) исключением не является: край сверяет уже разрешённую Identity личность с требованием своей поверхности и выбирает ответ человеку, но не выводит из этого продуктовых разрешений и не заменяет authorization-решение владельца ресурса.

## Два входа аукциона

Оба бота — отдельные процессы grammY с long polling и отдельными токенами. Они не импортируют код друг друга. Правило общее и вторым входом не исчерпывается: любой следующий бот, включая административный, становится отдельным компонентом с отдельным токеном — два поллера на одном токене конфликтуют. Общий аукционный код появляется физически один раз в `shared/typescript/auction-bot-ui`: намерения и юзкейсы края, диспетчер, каноническое тело экрана, parser `callback_data` и рендеринг общих блоков. Composition root, lifecycle, telemetry name, верхняя навигация, тексты входа и отказов принадлежат каждому приложению.

Единственная публичная точка продуктового входа общего пакета сначала применяет политику поверхности, затем зовёт аукционный диспетчер. Хаб требует круг `member` — роли `admin`, `maintainer` и `member` — и ничего не выдаёт; один `public` хаб не открывает. Бот аукциона на `/start` вызывает `RequestRole` с кругом `public`: Identity атомарно устанавливает личность и гасит белый список или ставит заявку, а роль сам по просьбе не выдаёт ([ADR-060](../decisions/ADR-060-auction-access-premoderation.md)). Это целевое поведение: контракт описан в [PER-304](https://linear.app/anticnvm/issue/per-304), реализация в Identity — [PER-266](https://linear.app/anticnvm/issue/per-266), вызов из ботов — [PER-316](https://linear.app/anticnvm/issue/per-316). На остальных действиях бот требует эту роль. Допуск решает наличие роли круга. На хабе политика уже выбирает текст отказа по отметке `blocked` ([PER-194](https://linear.app/anticnvm/issue/per-194), [ADR-043](../decisions/ADR-043-identity-roles-and-community-circles.md)): вне круга `member` человек видит кадр ожидания P-14, при `blocked` — кадр отказа P-17, пустой список и «не найдено» вместо них не показываются. У бота аукциона той же политики ещё нет. Отметка приходит в `ResolveIdentityResponse` отдельным полем `blocked` ([PER-254](https://linear.app/anticnvm/issue/per-254)); различать по ней два отказа — работа политики поверхности, а не разрешения личности. Повторный `/start` идемпотентен: вторая активная запись роли не заводится, человек видит обычный экран аукциона. Личность разрешается один раз на update и передаётся в шлюз, а не разрешается повторно внутри него. Сырые аукционные юзкейсы наружу пакета не экспортируются. Это не заменяет проверку разрешений в Auction как владельце ресурса.

Человек только с доступом к аукциону, написавший боту хаба, не видит ни сходки, ни аукцион внутри неё: получает кадр ожидания P-14. Кнопки в бот аукциона в текущем макете этого кадра нет. Хаб не выдаёт роль `member`. Заблокированный получает кадр P-17 на любом действии, а не только на `/start`.

Общими остаются данные и действия аукциона, тело экрана и кнопки. В хабе тело оборачивается навигацией сходки и возвратом к ней; в боте аукциона оно корневое, добавляет контекст пересланной ссылки и помощь и не обещает доступ к хабу. Конкретные тексты и макет выбираются отдельно.

Поведенческий contract test запускает одинаковую таблицу намерений через фабрики обоих приложений и сравнивает вызовы портов, `AuctionScreenBody` и `callback_data`. Различия оболочек имеют собственные тесты. Отдельная матрица доказывает, что до Auction не доходит запрещённый вызов: роль `public` в хабе, человек без ролей в хабе, заблокированный в хабе и заблокированный в публичном входе. Она же требует, чтобы отказ заблокированному отличался от отказа человеку без ролей на той же поверхности.

### Конфигурация и Aspire

#### Общий FAQ и меню Auction Bot

Реализованный вход PER-294 использует `ResolveIdentity`, но не выдаёт роли и не заводит заявки: шлюз премодерации поверх `RequestRole` остаётся [PER-316](https://linear.app/anticnvm/issue/per-316) по [ADR-060](../decisions/ADR-060-auction-access-premoderation.md). Пока шлюза нет, отсутствие `public` показывает экран ожидания; по этому ответу нельзя определить существование или исход заявки. Заблокированный видит отдельный отказ даже при наличии роли. FAQ и каталог ему недоступны.

Первый допущенный `/start` открывает один общий FAQ всех аукционов. Явное «В меню» сохраняет в Auction отметку завершения ознакомления через [RPC](../architecture/integration.md#auction-grpc), после чего повторный `/start` открывает меню с «Аукционы» и «Правила и FAQ». Отметка не зависит от аукциона или выбранного имени и переживает рестарт бота. Отправка сообщения сама отметку не создаёт. При отказе чтения или записи меню не открывается; участник может повторить действие. Каталог пока обозначен местом подключения PER-306, без нового API выбора активного аукциона.

Оболочка добавляет возврат к FAQ в один переход к общему экрану лота, меню, местам каталога/помощи и техническим отказам. Каждая локальная кнопка `v1:entry:<action>` вновь проверяет Identity, как и кнопки `auc`; старый экран не даёт доступа. Тексты FAQ и его навигация в общий пакет торгов не входят.

Тексты пишет организатор. Процесс принимает `AUCTION_FAQ_ITEMS`, `AUCTION_FAQ_PURPOSE`, `AUCTION_FAQ_SIMULTANEOUS_BIDS`, `AUCTION_FAQ_CONNECTION_FAILURE` и `AUCTION_FAQ_DELIVERY` (до 500 UTF-16 единиц каждый). Пустое или отсутствующее значение показывает явное место для текста, не выдуманные условия. Запрет отмены ставки уже принят и присутствует всегда. `AUCTION_FAQ_DETAILS_URL` и `AUCTION_FAQ_QUESTION_URL` задают внешние кнопки; допустим HTTPS без credentials, до 2048 символов. Без адреса кнопка показывает отсутствие ссылки с возвратом к FAQ. Текст отправляется без parse mode. Эти переменные читает конфигурация самого бота; отдельных параметров AppHost для них пока нет.

| Компонент | Ресурс | Secret parameter | Переменная процесса |
|---|---|---|---|
| бот хаба, среда `prod` | `hub-bot` | `hub-bot-token` | `HUB_BOT_TOKEN` |
| бот хаба, среда `test` | `hub-bot` | `hub-bot-test-token` | `HUB_BOT_TOKEN` |
| бот аукциона, среда `prod` | `auction-bot` | `auction-bot-token` | `AUCTION_BOT_TOKEN` |
| бот аукциона, среда `test` | `auction-bot` | `auction-bot-test-token` | `AUCTION_BOT_TOKEN` |

Среда Telegram — вторая ось рядом с профилем ([ADR-046](../decisions/ADR-046-telegram-test-contour.md)): она выбирает, какой из двух параметров объявляется, и уходит процессу в `HUB_BOT_ENVIRONMENT`, а боту аукциона — в `AUCTION_BOT_ENVIRONMENT`. Объявляется ровно один параметр на запуск, поэтому прод- и тестовый токен не делят ключ и не подменяют друг друга; переменная процесса у обеих сред одна, потому что бот про имя параметра не знает. Умолчание — продакшн. Вход в тестовую среду и её ограничения — [local-development.md](../development/local-development.md).

Кроме токенов бот аукциона получает пояс сообщества `AUCTION_BOT_COMMUNITY_TIME_ZONE` — тот же `Europe/Moscow`, что у бота хаба, Meetups и Notifications, — и необязательный `AUCTION_BOT_AUCTION_ID` из настройки AppHost `AuctionBot:AuctionId`: аукцион, ленту которого открывает пункт меню «Аукционы». Настройка не секрет и не параметр Aspire: пустой параметр дашборд спросил бы после старта, а без значения пункт просто отвечает, что каталог ещё не открыт. Чтения «текущего аукциона» в контракте нет ([integration.md](../architecture/integration.md#auction-grpc)), поэтому аукцион назван конфигурацией процесса ([PER-306](https://linear.app/anticnvm/issue/per-306)).

Fallback между переменными запрещён. Отсутствующий токен бота аукциона и токен, совпавший с любым параметром бота хаба, останавливают сборку графа до старта поллеров. Сравнение строже «одного графа» из ADR-044: оно читает значения параметров бота хаба из конфигурации AppHost в любом профиле, который владеет `auction-bot`, потому что user-secrets у профилей общие и профиль `auction-bot`, поднятый рядом с `hub`, иначе повтора не увидел бы. Параметр бота хаба при этом не объявляется, а причина отказа называет параметры, но не значения. Совпадение с токеном, которого в конфигурации этого AppHost нет, — например с ботом хаба на другой машине, — по-прежнему проявится только конфликтом polling у Telegram. Параметр объявляется только когда профиль владеет ресурсом и передаётся только ему. `hub` содержит только бот хаба; профиль `auction-bot` поднимает бот аукциона с Identity, Auction, PostgreSQL и NATS ([PER-305](https://linear.app/anticnvm/issue/per-305)). Бот аукциона ходит в Identity и Auction своим токеном вызывающего `AUCTION_BOT_SERVICE_TOKEN`; maintainer-секрета у него нет. В чарт прода он не входит.

### Лента и карточка лота

Лента и карточка — общие юзкейсы пакета, одинаковые в обоих ботах ([PER-306](https://linear.app/anticnvm/issue/per-306)); встроен пока только бот аукциона, бот хаба подключает их в [PER-307](https://linear.app/anticnvm/issue/per-307).

- **Лента.** `ListAuctionLots` листает непрозрачным токеном в порядке сервера, а лента сортируется по цене, поэтому пакет выкачивает её целиком на каждое нажатие: страницы сервера до пустого токена, не больше 200 и не больше 8000 лотов, повтор токена — отказ. Порядок — по возрастанию цены: текущей в торгах, стартовой до них, цены продажи у проданного; лоты без цены — черновик, непроданный, снятый — в конце, равные цены — по `lot_id`, чтобы страница держала один набор между нажатиями. Восемь лотов на странице; номер страницы едет в кнопке, а номер за пределом ленты показывает последнюю страницу — лоты могли снять, пока сообщение висело. Пустая лента — свой текст, а не пустой экран; недоступный Auction — кадр «недоступно», а не пустая лента.
- **Карточка.** Название, описание, статус и цена, `next_price` как «следующая ставка — от», шаг — только когда политика шага одна на все цены: сетку шагов край не вычисляет, это правило Auction. Дедлайн — в поясе сообщества. Лидер в торгах и победитель проданного лота — по имени из `GetDisplayNames` одним вызовом на один идентификатор; непроданный и снятый лот имён не запрашивают. Отказ `GetDisplayNames` карточку не роняет: исход и цена остаются, вместо имени — «лидер есть» или «победитель определён», идентификатор на экран не выходит, а порт бота пишет отказ на `warn`. Своя последняя ставка и прокси-лимит — лист ставки [PER-317](https://linear.app/anticnvm/issue/per-317).
- **Изображение** показывает только карточка ([ADR-057](../decisions/ADR-057-auction-lot-catalog-as-state.md), дополнение). Лента — одно текстовое сообщение: у медиагруппы нет клавиатуры, и листание правкой на месте с ней невозможно. Байты бот берёт `GetLotImage` и отправляет загрузкой файла, а `file_id` наибольшего размера из ответа держит в кэше памяти процесса под ключом «лот и версия изображения» — не больше 200 записей, вытесняется самая давняя. Тёплый кэш файл повторно не тянет; `file_id`, который Telegram больше не принимает, вытесняется, и показ один раз повторяется загрузкой. Это кэш, а не хранилище из [ADR-030](../decisions/ADR-030-telegram-bot.md): рестарт его теряет, и следующий показ берёт файл у Auction. Изображение не получилось — карточка уходит текстом, отказ пишется на `warn`.
- **Смена вида сообщения.** Текстовое сообщение не правится в фото и обратно, поэтому переход «лента ↔ карточка с фото» — новое сообщение и удаление прежнего; отказ удаления (сообщение старше 48 часов) не мешает, новое уже ушло. Фото в фото — `editMessageMedia`, текст в текст — `editMessageText`. Подпись к фото ограничена 1024 символами, сообщение — 4096: под лимит режется описание.

### Обязательства перед Identity

Из [ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md) и [ADR-030](../decisions/ADR-030-telegram-bot.md):

- бот — доверенная граница authentication. При long polling доверенностью входа является владение bot token; входящего HTTP у компонента нет, secret token не используется. Authentication material дальше не передаётся. Сервисам за собой бот доказывает себя собственным токеном в `authorization: Bearer`, а не материалом Telegram ([ADR-056](../decisions/ADR-056-service-calls-per-caller-token-and-closed-network.md));
- на каждом update, требующем продуктового действия, бот синхронно вызывает `IdentityService.ResolveIdentity`. Кэш фактов доступа и ролей не используется: устаревшее разрешение равносильно пропущенной проверке;
- при недоступности Identity операция завершается fail-closed. Деградации до режима «показываем только чтение» нет;
- `/start` может нести deep link payload перехода к сходке (`m_<uuid>`). Принят и второй префикс — источник прихода `s_<код>` для заявки на премодерацию ([ADR-060](../decisions/ADR-060-auction-access-premoderation.md)); он не реализован, и одна ссылка не несёт оба. Одноразовое приглашение в этом срезе не разбирается ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Разбор payload принадлежит боту, решение о допуске — Identity;
- административные команды управления составом и ролями бот только маршрутизирует. Выводить право на продуктовое действие из роли в краю нельзя: его решает владелец ресурса. Разрешённое сравнение ровно одно — политика поверхности ([ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md)): поверхность требует названную роль на входе и по отметке блокировки выбирает текст отказа.

### Обязательства перед Notifications

[ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md) заканчивает ответственность Notifications на публикации уведомления в шину. Всё, что дальше, принадлежит каналу, и в MVP единственный канал — этот бот. Отсюда его вторая сторона, независимая от входа апдейтов:

- **бот является потребителем шины.** Он подписывается на уведомления **собственным** durable consumer и получает сообщение с внутренним идентификатором получателя, типом и структурированными данными. Consumer именно свой: общий на все каналы превратил бы их в конкурентов за одно сообщение;
- **автор в карточке.** Ник автора сходки бот спрашивает вызовом `IdentityService.ResolveOrganizerUsername` с зрителем в роли актора и только по автору из снимка, который Meetups уже отдал этому зрителю; автор, смотрящий свою сходку, Identity не зовёт. Любой отказ или недоступность Identity оставляют карточку без строки автора, но карточку не роняют. Ник в запись границы не попадает;
- **резолвинг получателя принадлежит боту.** Внутренний идентификатор разрешается в Telegram id вызовом `IdentityService.ResolveTelegramUserId`; неизвестный идентификатор приходит статусом `NOT_FOUND`, а не нулём, заблокированный получатель — `FAILED_PRECONDITION`. Оба отказа окончательные, и канал отбрасывает такое уведомление без повторов ([PER-217](https://linear.app/anticnvm/issue/per-217)). `chat_id` Notifications не знает и знать не должен;
- **текст формирует бот.** Из кода типа и данных собираются формулировка, клавиатура, deep link и кнопка отключения категории;
- **ненавязчивость реализуется здесь.** Единственный механический рычаг — отправить сообщение без звука, и он есть только у канала;
- **retry, журнал попыток и выбор между риском дубля и риском потери принадлежат боту.** Он единственный видит ответ Telegram;
- **обратных событий о доставке нет.** Диагностика «дошло ли» двухшаговая по построению;
- **человек, заблокировавший бота, остаётся получателем.** Notifications продолжит порождать поводы, обработка отказа Telegram — задача канала;
- **уведомление может протухнуть.** Если у сообщения появится срок годности, решение «доставлять или нет» принимает потребитель.

Устройство этого входа — durable consumer, журнал попыток, повторы, текст и кнопка отключения — описано в разделе [«Доставка уведомлений»](#доставка-уведомлений). Журнал попыток стал первым фактом, который обязан пережить рестарт, и первой причиной завести компоненту хранилище ([ADR-052](../decisions/ADR-052-telegram-bot-delivery-journal-in-jetstream-kv.md)).

Notifications при этом остаётся и обычным синхронным соседом: команды подписки и настроек категорий бот маршрутизирует в его command plane, предъявляя внутренний идентификатор человека. Эта сторона реализована ([PER-214](https://linear.app/anticnvm/issue/PER-214)): клиент живёт в `src/notifications/`, вызывается из `src/application/` наравне с Meetups и настраивается переменной `NOTIFICATIONS_GRPC_URL`. Тем же клиентом бот подаёт обе ручные рассылки ([PER-226](https://linear.app/anticnvm/issue/PER-226)); кадры описаны в разделе [«Ручные рассылки»](#ручные-рассылки).

Нажатие «Подписаться на сходку» возвращает карточку P-04 с разовой заметкой: какие категории по этой сходке будут приходить и, если напоминание выключено, что включается оно в «Уведомлениях сходки» ([PER-402](https://linear.app/anticnvm/issue/PER-402)). Кнопка «Уведомления сходки» появляется только у подписанного: эти настройки решают, что присылать по подписке, и рядом с «Подписаться» читались как второй способ получать уведомления. Без подписки карточка вместо неё несёт строку о том, что даёт подписка; когда Notifications не ответил и состояние подписки неизвестно, вход в настройки остаётся. Общие настройки открываются из главного меню и с экрана сходки и делят категории на две группы — приходящие всем без подписки и приходящие по подписке ([PER-395](https://linear.app/anticnvm/issue/per-395)). Перечень строится по действующим значениям из ответа команды подписки, а не по умолчаниям продукта, поэтому не врёт человеку, который менял настройки. При отписке и обычном просмотре карточки заметки нет.

## Дизайн-код экранов

Принято владельцем 2 октября 2026 года ([PER-343](https://linear.app/anticnvm/issue/per-343)) и реализовано в [PER-444](https://linear.app/anticnvm/issue/per-444). Полный текст правил и проверка возможностей клиентов — [design/bot/design-code.md](../design/bot/design-code.md); здесь только то, что меняет описание компонента.

- **Опорные клиенты** — Telegram Desktop и мобильные. Web K целью не является.
- **Дерево.** У экрана один родитель, переходов между соседними разделами нет. Последний ряд клавиатуры — `[‹ Родитель] [Меню]`; родителя карточки выбирает состояние сходки. Постоянный вход — кнопка меню клиента; reply-клавиатуры и «домашнего» сообщения нет.
- **Доставка.** Нажатие правит своё сообщение, ответ на вопрос даёт одно новое сообщение с заметкой, команда — новое сообщение. Экран не живёт в сообщении с файлом, а кнопка под уведомлением открывает экран новым сообщением и уведомление не затирает.
- **Вопрос** несёт `force_reply` в inline-клавиатуре и кнопку «Отмена». Шаг лежит в `callback_data` этой кнопки и возвращается в `reply_to_message.reply_markup`. Закрывается вопрос удалением: «Отмена» и уход от вопроса удаляют его сообщение, потому что правка режим ответа в мобильном клиенте не снимает.
- **Клавиатура.** Подтверждение — «Да, <глагол>» и «Нет»; цвет один — `danger` у «Да, …» необратимого действия; переключатель — «Вкл · Категория» и «Выкл · Категория»; «Обновить» остаётся только на составе сообщества.
- **Формат.** Жирный заголовок на каждом экране, разметка HTML; rich остаётся только у карточки сходки ([ADR-034](../decisions/ADR-034-telegram-bot-rich-presentation.md)).
- **Ожидание.** Ответ на нажатие уходит вместе с результатом, и кнопка крутится, пока его нет. На все сервисы у нажатия общий бюджет, сторож отвечает на нажатие раньше лимита Telegram, а при заметной задержке бот шлёт `sendChatAction`; числа — в [разделе «Ожидание»](../design/bot/design-code.md#ожидание). Всплывающий текст возвращается в кадры P-08, E-09 и на повтор после сбоя.
- **Mini App не вводится.** Ввод даты и времени, форма создания, состав сообщества и архив улучшаются внутри чата.

Дизайн-код реализован целиком: правило ожидания, доставка результата, дерево экранов с возвратом, списки, карточка, настройки уведомлений, подтверждения, кадры отказа, вопросы с «Отменой», состав сообщества, форма создания и заготовки даты в коде. Постеры карточки добавлены в [PER-443](https://linear.app/anticnvm/issue/per-443). Каждое место брифа правится в том же изменении, что и код.

## Устройство, принятое в ADR-030

### Стек и вход

TypeScript, Node.js LTS, grammY. Плагин Conversations для продуктового диалога не используется. Вход апдейтов — **только long polling**, ровно один экземпляр процесса.

| | Long polling (выбрано) | Webhook |
|---|---|---|
| Публичный адрес | не нужен | обязателен: HTTPS и открытый вход |
| Локальная разработка | работает как есть | нужен туннель во внутреннем цикле |
| Доверенность входа | владение bot token | secret token, проверяется обязательно |
| Экземпляров процесса | **ровно один на токен** | сколько угодно за балансировщиком |
| Повторная доставка | редка: апдейт подтверждается следующим запросом | штатна: Telegram ретраит на любой не-2xx и таймаут |
| Деплой | окно простоя, пока токен не отпущен | без окна |

Компромиссы приняты сознательно: горизонтального масштабирования нет, деплой останавливает приём апдейтов. Возврат к вебхуку — сигнал пересмотра ADR-030, а не конфигурация.

Основной вход — пользовательская команда `/start` в личном чате, в том числе с упоминанием бота и без учёта регистра. Допустимый Telegram deep link payload разбирается Zod-схемой: `m_<uuid>` классифицируется как переход к сходке, остальной валидный payload остаётся неклассифицированным — формат инвайт-токена не выбран и в срез не входит ([ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)). Разобранный payload передаётся диспетчеру; в `ResolveIdentity` он не входит — в контракте среза нет поля под инвайт, допуск по payload в этот срез не входит. Форма создания спрашивает только название. Дальше бот показывает черновик (A-06) — ту же карточку, а под ней ряды `[Дата и время]`, `[Место]`, `[Описание]`, `[Опубликовать]`, `[Опубликовать позже]` и возврат `[‹ Скрытые] [Меню]`. Название с черновика не правится: оно меняется из карточки, «Изменить». Кнопка поля задаёт вопрос о нём; принятый ответ возвращает черновик новым сообщением, «Отмена» под вопросом удаляет вопрос и тоже присылает черновик новым сообщением. Порядок полей человек выбирает сам, отдельного предпросмотра нет, а выйти можно в любой момент: черновик остаётся в «Скрытых». Дата — и в форме, и в точечной правке — открывается экраном выбора без режима ответа: заголовок, кнопки-заготовки дня (четыре ближайших дня и выходные двух недель, которых среди них нет, подписью «сб 3»), «Другая дата» и «Отмена». Экран правит нажатое сообщение. Выбор дня правит его же: вместо дней встают восемь заготовок времени и «Другой день». Кнопка времени несёт момент цифрами `ДДММГГГГЧЧММ`, идёт тем же разбором, что и текст, и правит экран в результат; при таймауте или недоступности сервиса экран остаётся как был, а прошедшая дата из устаревшей кнопки получает тот же кадр о прошедшей дате. «Другая дата» удаляет экран и задаёт вопрос с режимом ответа: текст `ДД.ММ.ГГГГ ЧЧ:ММ` — путь для даты, которой среди заготовок нет. «Отмена» экрана — обычный возврат правкой: на черновик, карточку или «Статус». Режима ответа у экрана нет намеренно: выбор кнопкой не снял бы его в клиенте. Момент отложенной публикации выбирается тем же экраном. Кнопка черновика, под которой сходку уже опубликовали, открывает обычную карточку, а кнопка поля и ответ на вопрос формы идут как точечная правка и тоже возвращают карточку. После публикации бот отвечает карточкой сходки (A-07) правкой того же сообщения; над карточкой стоит строка «Сходка опубликована. Теперь она видна в списке.» и ссылка `https://t.me/<username>?start=m_<uuid>`. Отдельного кадра с кнопками «Открыть сходку» / «К управлению» больше нет: под результатом стоят ряды самой карточки. Имя бота берётся из уже разрешённого `ctx.me`, идентификатор кодируется тем же base64url, которым разбирается входящий `/start`. В записи границы публикации пишется `meetup_id`; сырой payload и собранная ссылка в лог не попадают. Невалидный хвост после `/start` не мешает регистрации: команда выполняется без payload. Вопросы добавления материала принимают только ответ на конкретный `ForceReply`: пересланное сообщение канала, документ или фото, затем короткое название. Отказ в источнике или названии сам задаёт вопрос заново с `ForceReply`: обычное сообщение после отказа ушло бы мимо формы ([PER-395](https://linear.app/anticnvm/issue/per-395)). Так же вопрос рассылки принимает только ответ на себя, и только текстом. Вне этих сценариев и команд меню (раздел «Меню команд» ниже) остальной текст, неизвестная команда, стикер, фото, `new_chat_members` и пустой текст не зовут Identity и не получают ответа. Процесс закрывает HTTP/2-сессию Identity на остановке; watchdog 15 с не снимает себя с event loop (`unref`), пока `stop()` не завершился.

### Меню команд

Кнопка меню в клиенте показывает команды бота. Меню даёт вход на экраны, которые уже открываются кнопками, и новых сценариев не вводит ([PER-345](https://linear.app/anticnvm/issue/PER-345)). Общий формат меню решён в [PER-343](https://linear.app/anticnvm/issue/PER-343): состав команд остаётся, а кнопка меню клиента — единственный постоянный вход ([дизайн-код](#дизайн-код-экранов)).

| Команда | Подпись в меню | Экран | Та же кнопка |
|---|---|---|---|
| `/menu` | Главное меню | меню | «‹ Меню» и «Меню» на любом экране, `v1:nav:start` |
| `/meetups` | Ближайшие сходки | P-02 | `v1:nav:hub` |
| `/archive` | Архив сходок | P-08 | `v1:nav:archive` |
| `/notifications` | Настройки уведомлений | P-09 | `v1:notify:global` |

`/start` в меню не показывается: его читают как команду первого запуска ([PER-401](https://linear.app/anticnvm/issue/PER-401)). `/menu` открывает тот же стартовый ответ, что `/start` без payload, а сам `/start` и deep link на сходку работают по-прежнему.

Команды меню разбираются по тем же правилам, что `/start`: только личный чат, упоминание чужого бота отбрасывает команду, регистр не важен, хвост после команды игнорируется. Команда проходит тот же путь, что кнопка: личность разрешается в Identity, политика поверхности показывает P-14 или P-17 вместо экрана, отказ Meetups или Notifications даёт тот же кадр, что и нажатие кнопки. Отличие одно — экран приходит новым сообщением, потому что править нечего. Команда, выбранная, пока клиент держит режим ответа на вопрос `ForceReply`, приходит ответом на него и всё равно исполняется как команда: значением поля она не становится, а вопрос продолжает ждать ответа.

Управления сходками в меню нет: список администраторов живёт в Identity, на старте он недоступен, и сузить меню до администраторов `BotCommandScope` не может. Администратор входит в управление со стартового ответа; остальным вход на нём не показывается, потому что создание сходки и состав сообщества Meetups и Identity разрешают только роли `admin`, скрытые сходки видит администратор и их автор, а автор в срезе всегда администратор ([ADR-031](../decisions/ADR-031-meetups-domain-vocabulary-and-event-form.md)). Вход, который ведёт в отказ, хуже его отсутствия. Кнопка входа, оставшаяся в чате у того, кто роли не имеет, получает отказ вместо меню: за меню сервиса нет, и решать некому.

Список регистрируется на каждом старте вызовом `setMyCommands` с областью `all_private_chats`: в группах бот молчит, и меню там не нужно. Вызов не ждут перед long polling. Отказ Telegram пишется в лог как `warn` с категорией `dependency_unavailable` и процесс не останавливает: в клиенте остаётся прежний список, а следующий старт повторяет запись.

### Внутренняя граница

- **Представление** знает Telegram и grammY: разбор апдейта и deep link, `callback_data`, сборка экранной модели, вызов рендерера `rich` или `plain`, вызовы Bot API, отказы и лимиты платформы. Режим задаёт `HUB_BOT_PRESENTATION`, дефолт `rich` ([ADR-034](../decisions/ADR-034-telegram-bot-rich-presentation.md)). Юзкейсы по-прежнему не принимают и не возвращают типы Telegram.
- **Юзкейсы** не принимают и не возвращают типы Telegram, `Context` или `Bot`. Вход — установленная личность, намерение, параметры, ключ команды при необходимости. Выход — результат или отказ, пригодный для любого представления.
- **Диспетчер приложения** — единственная внутрипроцессная точка входа в юзкейс. Его зовут адаптер апдейтов, компонентный тест и, когда появится, адаптер потребителя шины.

Проверка границы: сценарий «администратор создал и опубликовал сходку» проходится тестом **без единой телеграмовской структуры**. Без такого теста разделение декларативно. Тест — [create-and-publish.test.ts](../../tests/contour/bot-wire/create-and-publish.test.ts) уровня L2: бот говорит с настоящими Identity и Meetups, итог читается из Meetups напрямую, а update и `callback_data` собирает test kit бота, так что сценарий их не видит.

### Состояние

Управление составом открывается из меню администратора. Корневой экран показывает три числа и ведёт в три подэкрана: «Ожидают допуска», «Допущенные» и «Разрешённые ники»; списки листаются по восемь. «Ожидают допуска» — модерация по одному: один человек и кнопки «Допустить», «Закрыть», «Пропустить». Курсор очереди — идентификатор человека в кнопке, а не номер: «Допустить» несёт и того, кого допустить, и того, кого показать следом, а человек под курсором, которого уже нет в очереди, заменяется первым. «Пропустить» с последнего возвращает к первому, у очереди из одного её нет, пустая очередь несёт только возврат. «Закрыть» — и в очереди, и в списке допущенных — ведёт в подтверждение «Да, закрыть доступ» со стилем `danger`: закрытый человек уходит из списков, и вернуть его из бота нельзя. Кнопка экрана прошлого релиза, которая закрывала доступ сразу, теперь тоже спрашивает. Чем кончилось нажатие, говорит всплывающий ответ на него — «Человек допущен.», «Доступ закрыт.», «Ник убран.» или «Состояние уже было актуальным.», — а экран показывает следующего человека или ту же страницу. Несохранённое решение тоже называется всплывающим текстом, и на экране остаётся тот же человек: уйди очередь дальше, отказ выглядел бы допуском. Добавление ника задаёт вопрос с «Отменой»; ответ на него — сообщение, поэтому итог стоит строкой над списком ников. «Обновить» есть на корне и подэкранах: состав меняется без участия администратора. После любой команды бот заново читает экран из Identity. Это отрисовка на сегодняшнем Identity: одним вызовом `ListCommunityMembers` читается весь состав, листание и курсор живут в боте. Допуск, который действительно сменил состояние, бот сообщает и самому человеку — «Доступ открыт» с кнопкой «Ближайшие сходки»: тот ждёт на кадре ожидания и иначе о решении не узнаёт. Telegram id адресата бот спрашивает `ResolveTelegramUserId`. Сообщение — побочный результат: экран администратора уходит раньше, допуск уже сохранён, и отказ Identity или Telegram пишется в запись границы на `warn`. Получатель, которого нет, который заблокирован или сам заблокировал бота, — ожидаемый исход, как в доставке уведомлений, и сбоем не считается. Повтора нет: под отложенное сообщение у бота нет хранилища, а повторное «Допустить» состояния уже не меняет и молчит; человек и без сообщения попадает в продукт следующим `/start` ([PER-395](https://linear.app/anticnvm/issue/per-395)). Человек с ником показан по нику. Человек без ника показан кодом заявки — последними восемью символами идентификатора: голова UUIDv7 несёт время создания и у профилей одной минуты совпадает, а хвост случаен. Тот же код человек без ника видит в кадре ожидания P-14 и называет администратору; человеку с ником кадр ожидания кода не показывает и отсылает к нику, потому что в списке он стоит по нику. В тексте экрана у человека без ника ещё и упоминание по Telegram id. Откроет ли оно профиль, решает Telegram по настройкам приватности человека, поэтому опорой остаётся код. Подпись кнопки «Закрыть» в списке допущенных строится из того же кода ([PER-399](https://linear.app/anticnvm/issue/per-399)). Экран идёт в HTML-разметке, поэтому ники и подтверждение экранируются. Право не вычисляется по клавиатуре: на каждом действии бот разрешает личность и передаёт её вместе с ролями в Identity, который принимает решение. Роль в боте решает только, что показать до сервиса: вход в управление, как описано выше, и вопрос `ForceReply` о нике — его бот задаёт только администратору, иначе отказ пришёл бы уже после набора ответа. Отказ по праву человек видит без имени сервиса, который его принял.

Принято, но не реализовано ([ADR-060](../decisions/ADR-060-auction-access-premoderation.md)): у очереди появляются основное представление — карточка заявки «по одному» с кнопками «Допустить», «Отказать», «Профиль» и «Пропустить», подписью круга и источника и курсором пропуска в `callback_data` — и список отказанных с действием «Пересмотреть». Профиль открывается ссылкой `tg://user?id=…`, а если её не пускают настройки приватности — `t.me/<ник>`; фото не показываются. Очередь одна для заявок обеих поверхностей. Методы Identity под эти экраны — `ReadApplicationQueue`, `AdmitApplication`, `DeclineApplication`, `ListRefusedApplications` и `ReconsiderApplication` ([PER-436](https://linear.app/anticnvm/issue/per-436), [Identity gRPC](../architecture/integration.md#identity-grpc)).

**Своего хранилища у экранов нет.** Единственное хранилище компонента — журнал попыток доставки уведомлений ([ADR-052](../decisions/ADR-052-telegram-bot-delivery-journal-in-jetstream-kv.md)), и к экранам он не относится. Состояние экрана живёт в самом экране, остальное приходит в апдейте:

| Факт | Откуда берётся |
|---|---|
| кто обратился | `from` |
| что редактировать | сообщение внутри нажатия |
| что нажали | `callback_data` |
| на какой вопрос отвечают | `reply_to_message` |
| ключ команды создания | `callback_data` кнопки |

Шаг вопроса лежит в самом вопросе: под ним стоит кнопка «Отмена», и её `callback_data` называет, чего бот ждёт, — поле и сходку формы, момент публикации, источник материала с версией карточки, круг адресатов рассылки или ник. Клавиатура вопроса — inline-кнопка вместе с `force_reply`, и Telegram возвращает её в `reply_to_message.reply_markup` ответа. Бот разбирает шаг тем же `parseCallback`, что и нажатия, поэтому ответ на вопрос переживает рестарт: ответ формы создания сохраняется в то же поле и возвращает черновик, который цел в Meetups. Карта «идентификатор вопроса → ожидаемый ответ» в памяти процесса хранит каждый заданный вопрос, но нужна только двум: у вопроса рассылки она держит название сходки для подписи кадра подтверждения, и после рестарта кадр обходится без него, а шагом названия материала она владеет одна: источник, принятый на предыдущем шаге, в 64 байта кнопки не помещается, и после рестарта ответ на этот вопрос получает «Этот вопрос уже устарел. Прикрепи материал заново.» с возвратом в материалы. Принятый ответ снимает клавиатуру вопроса, и вопрос перестаёт быть вопросом; отказ зависимости по таймауту или недоступности оставляет его ждать того же ответа. «Отмена» ничего не пишет в сервисы: сообщение вопроса удаляется, а экран, с которого он задан, — карточка, черновик, статус, материалы, управление или состав сообщества — приходит новым сообщением. Если Telegram удалить сообщение не дал, вопрос правится в этот экран на месте, и поздний ответ на него получает «вопрос устарел». Вопрос о моменте публикации помнит, откуда задан: с черновика его шаг пишется `pd`, из «Статуса» — `pm`, и «Отмена» возвращает туда же. Брошенный вопрос бот убирает сам: команда или нажатие кнопки в другом сообщении удаляют открытые вопросы чата, которые есть в карте; ошибка удаления нажатию не мешает, а вопрос, заданный до рестарта, в карте не числится и остаётся. Ответ без текста — фото, стикер — на вопрос поля, ника или момента публикации значением не становится: вопрос задаётся заново с подсказкой «Нужен ответ текстом.» и тем же шагом, а прежний закрывается после отправки нового. Тот же порядок у любого повторного вопроса: сначала уходит новый, потом закрывается старый, и упавшая отправка шаг не теряет. Экран, с которого задан вопрос, теряет клавиатуру в момент нажатия, чтобы в чате не оставалось двух живых наборов кнопок. Черновик при любом исходе цел в Meetups, и путь к нему не зависит от карты: раздел «Скрытые сходки» (A-16) в «Управлении сходками» выбирает скрытые сходки из того же viewer-aware списка, что и «Ближайшие сходки», и открывает их обычной карточкой с «Изменить» и «Статус → Опубликовать» ([PER-353](https://linear.app/anticnvm/issue/per-353)). Отдельного запроса черновиков в контракте нет, поэтому раздел показывает и сходки, снятые с публикации. В «Ближайших сходках» скрытая сходка стоит с пометкой «скрыта», а черновик, брошенный до ввода названия, подписан «Без названия»: Telegram не принимает кнопку без текста. Постороннему раздел пуст по тому же правилу видимости ([ADR-022](../decisions/ADR-022-meetup-state-axes-and-visibility.md)). Подтверждение материала от карты не зависит: название и источник восстанавливаются из самого сообщения подтверждения и его клавиатуры или медиа. Подтверждение рассылки тоже: текст лежит в сообщении предпросмотра, на которое отвечает кадр подтверждения, и возвращается в `reply_to_message`.

Вопросы прошлого релиза несли шаг иначе: невидимый символ нулевой ширины в начале текста с сущностью `text_link` на `https://t.me/<бот>#v1:manage:field:<токен>:<поле>`, а у момента отложенной публикации — `v1:manage:publish-later:<токен>`. Новые вопросы такого маркера не получают, но читается он ещё один релиз: вопрос, заданный до обновления, принимает ответ в то же поле той же сходки. После этого релиза разбор маркера удаляется.

Черновик, атрибуты, расписание и видимость сходки в краю не копируются.

### Автор сходки

Выбор владельца ([PER-404](https://linear.app/anticnvm/issue/per-404)): карточка называет автора каждому, кто её видит. Строка стоит под статусом: автору — «Вы автор этой сходки», остальным — «Автор: @ник». Ник отдаёт Identity только для действующего администратора; нет ника, автор больше не администратор или Identity не ответил — строки нет, заглушки вместо неё тоже. Строка одна и та же во всех отрисовках карточки: при просмотре, после правки, публикации, назначения публикации и смены статуса, и в подменю статуса. Именует автора представление одной обёрткой над диспетчером: Identity зовёт представление, а не приложение, и сценарии про автора не знают. Новый вид результата, который рисуется карточкой, получает строку, когда его добавляют в список видов этой обёртки. В списках сходок автора нет: там он стоил бы вызова Identity на каждую строку.

### Материалы сходки

Карточка показывает одну упорядоченную коллекцию материалов из viewer-aware снимка Meetups. Материал-ссылка отображается названием и открывает исходное сообщение; материал-файл карточка только называет, а открывается он из экрана «Материалы» кнопкой, по которой бот заново читает доступную человеку сходку и отправляет Telegram `file_id` тем видом, каким он записан; второй вид остаётся запасным для файлов без записанного вида. Материалы-фото богатая карточка показывает постерами под своим текстом: одно фото — фотографией, несколько — каруселью, не больше десяти, в порядке коллекции ([PER-443](https://linear.app/anticnvm/issue/per-443)). Вид файла бот передаёт в Meetups при прикреплении и читает из снимка; фото, прикреплённые раньше, вида не несут и в постеры не попадают. Карточка с постерами остаётся богатым сообщением и правится на месте, как и без них. Если Telegram отвергает карточку с постерами — например, файл стал недоступен, — она приходит новым сообщением без них. При `TELEGRAM_BOT_PRESENTATION=plain` постеров нет, фото открывается из «Материалов». Под карточкой не больше пяти рядов кнопок ([дизайн-код](../design/bot/design-code.md#карточка-сходки)). Длинная коллекция не переполняет лимиты сообщения и клавиатуры: карточка показывает начало и число оставшихся материалов, а полный список доступен любому смотрящему постранично по восемь элементов. Кнопки изменения в этом списке получает только администратор. Если Telegram больше не может отправить файл, человек получает нейтральный отказ без раскрытия причины.

Управление материалами доступно с кадра сходки администратору. Добавление просит переслать сообщение канала или прислать документ/фото, затем ввести название длиной до 200 символов и явно подтвердить привязку. Для публичного канала собирается `t.me/<username>/<message_id>`, для приватного — `t.me/c/<chat_id>/<message_id>`; скрытый или иной источник получает отказ E-06 и в Meetups не отправляется. До подтверждения команда `AttachMaterial` не вызывается.

Удаление всегда проходит отдельный кадр подтверждения и прямо сообщает, что исчезнет только привязка, а исходное сообщение или файл останутся. После успешных `AttachMaterial` и `RemoveMaterial` бот показывает список материалов из возвращённого снимка. Подтверждение файла — сообщение с самим файлом, и экран в нём не живёт: после нажатия оно остаётся следом с подписью «Прикреплено: <название>» и без кнопок, а список приходит новым сообщением. Поверхность заранее скрывает управление от не-администратора, но окончательное решение о праве принимает Meetups на каждой команде.

### Ручные рассылки

Рассылка — единственное действие продукта, которое нельзя отменить: отзыва сообщения нет. Поэтому до отправки она проходит три шага: вопрос, предпросмотр и явное подтверждение ([PER-226](https://linear.app/anticnvm/issue/PER-226)). Поводов два, механизм у Notifications один ([notifications.md](notifications.md)):

- **сообщение подписчикам** — кнопка «Написать подписчикам» на карточке сходки, `BroadcastToMeetupSubscribers`. Кнопка есть и у отменённой сходки: сообщить подписчикам об отмене — законный повод, и Notifications жизненный цикл при рассылке не фильтрует;
- **объявление сообществу** — кнопка «Объявление сообществу» в «Управлении сходками», `BroadcastToCommunity`.

Вход видит только администратор: в MVP организатор сходки и есть администратор ([overview.md](../product/overview.md)), а Notifications подтверждает право на сходку отношением `COMMUNITY_ADMINISTRATOR`. Нажатие входа без роли, например из присланного вручную `callback_data`, получает отказ до вопроса: человек не набирает текст, который не уйдёт. Правило общее для всех входов, которые задают вопрос, — так же устроено добавление ника в управлении составом. Подтверждение, наоборот, роль не проверяет. Отказ по праву приходит от Notifications кадром E-01, и вызов мимо кадра отклоняется тем же путём, что нажатие в нём.

Вопрос задаётся с `ForceReply` и называет сходку. Ответ проверяется по правилам сервиса до предпросмотра ([integration.md](../architecture/integration.md)): пустой текст, текст длиннее 4096 UTF-16-единиц и символ NUL получают вопрос заново, а не отказ после «Отправить». Сходку читают один раз, при вопросе: исчезнувшая к нажатию входа отвечает E-03, а её название записывается рядом с вопросом как подпись для кадра подтверждения. На ответе сходку не перечитывают: сбой Meetups в этот момент стоил бы человеку набранного текста, а сходку, исчезнувшую за время набора, отклонит Notifications на отправке. Запись вопроса снимается только после того, как оба кадра ушли, поэтому упавшая отправка оставляет вопрос ждать того же ответа.

Предпросмотр — сам текст отдельным сообщением, без заголовка и разметки: ровно тот текст автора, что уйдёт получателям. Заголовок и кнопки канал добавляет при доставке ([«Доставка уведомлений»](#доставка-уведомлений)). Кадр подтверждения отвечает на него. Он называет круг адресатов словами — «подписчики сходки, у кого включены сообщения организатора» или «участники сообщества, у кого включены объявления» — и прямо говорит, что отменить отправку будет нельзя. Числа получателей в кадре нет: `BroadcastAccepted` подтверждает приём, а не доставку, и «отобрано 7» автор прочёл бы как «получили 7». Кнопки две: «Отправить» и «Не отправлять».

Текст рассылки в память процесса не попадает. «Отправить» читает его из `reply_to_message` кадра подтверждения и принимает только сообщение самого бота. Поэтому подтверждение переживает рестарт, а экран, у которого предпросмотра больше нет, получает «экран устарел» без вызова Notifications. Ключ рассылки — UUIDv7, рождённый в кнопке «Отправить», как ключ создания сходки. Двойное нажатие и повтор после сбоя несут один ключ, и Notifications отвечает `created = false` без второго разворота.

| Ответ Notifications | Кадр |
|---|---|
| принято | «принято к отправке» — приём, а не доставка |
| повтор того же ключа | E-09: уже принято раньше, второй раз не уйдёт |
| `PERMISSION_DENIED` | E-01: писать может только организатор, ничего не отправлено |
| `UNAVAILABLE`, истёк срок ответа | E-05 с «Повторить» на той же кнопке: принята ли рассылка, неизвестно, и повтор с тем же ключом это выяснит |
| `INVALID_ARGUMENT` | «Сообщение не принято», ничего не отправлено; код и текст отказа — в записи границы, а не человеку |
| `ALREADY_EXISTS` | с этой кнопки уже ушёл другой текст, рассылку начинают заново |

Доставка самих сообщений в этот срез не входит: канал пока снимает ручные рассылки с записью в лог (раздел «Доставка уведомлений»), и отрисовку добавит [PER-217](https://linear.app/anticnvm/issue/per-217).

### Архив сходок

Вход в архив (кадр P-08) стоит рядом со списком актуальных сходок — в стартовом ответе и на самом списке. Архив читает `ListArchivedMeetups`, показывает отменённые, состоявшиеся и планируемые, у которых прошла последняя названная дата, и различает их подписью статуса при каждой строке: архив — производное правило чтения ([meetups.md](meetups.md)), а не отдельная ось в контракте, поэтому «прошедшая» на крае — это `MEETUP_LIFECYCLE_PLANNED` внутри архивного ответа, и никакая другая. Порядок строк — тот, что отдаёт Meetups (новейшая дата первой, без даты — последними); край его не пересортировывает и не группирует, в отличие от списка актуальных. Карточка архивной сходки — та же карточка `GetMeetup`, что и у актуальной, с той же упорядоченной коллекцией материалов; отдельного read-only представления для архива не заведено.

### Прошедшая дата сходки

Дату раньше сегодняшнего дня сообщества бот не запрещает и молча не принимает: он спрашивает. Такая сходка законна: Meetups её примет, а архив — правило чтения, и она просто сразу окажется в нём. Но чаще такая дата — опечатка, а без вопроса сходка незаметно уходит мимо «Ближайших» ([PER-342](https://linear.app/anticnvm/issue/PER-342)). Правило одно для формы создания и точечной правки даты. Архивное чтение Meetups оно не меняет.

Граница — день, а не момент, и тот же, по которому Meetups уводит планируемую сходку в архив ([meetups.md](meetups.md)). Сегодняшняя дата в прошедший час вопроса не вызывает: сходка остаётся в «Ближайших». День сообщества бот считает поясом из `HUB_BOT_COMMUNITY_TIME_ZONE`, который AppHost раздаёт обоим сервисам из одной константы. Момент отложенной публикации это правило не затрагивает: его прошлое по-прежнему отсекает Meetups.

На прошедшую дату бот ничего не отправляет в Meetups и отвечает кадром подтверждения A-16. Кадр называет дату, говорит, что сходка сразу уйдёт в архив и не появится в «Ближайших сходках», и предлагает две кнопки. «Сохранить дату» проводит её через тот же шаг формы с пометкой «подтверждено», и форма идёт дальше. «Нет» открывает экран выбора даты той же формы — создания или правки, — правя кадр на месте. Дата и режим формы едут в `callback_data`, поэтому ответ от карты вопросов не зависит и переживает рестарт. Сама дата перед сохранением разбирается заново, как ответ текстом. Кадр одноразовый: «Да» снимает его клавиатуру, «Нет» правит его в экран выбора даты, иначе старое «Сохранить дату» позже откатило бы дату, введённую взамен.

Ответ после публикации и после правки даты не обещает видимость, которой нет. Если дата сходки раньше сегодняшнего дня, кадр A-07 говорит, что сходка сразу в архиве, а не «видна в списке». «Изменение сохранено» дополняется той же оговоркой.

### Отложенная публикация

Отложенность — свойство момента подачи команды, а не отдельный вид публикации ([ADR-024](../decisions/ADR-024-meetups-state-storage-with-domain-event-log.md)), поэтому отдельного сценария у неё нет: рядом с «Опубликовать» на черновике A-06 и в подменю статуса скрытой сходки A-10 стоит «Опубликовать позже». Кнопка открывает тот же экран выбора даты, что и поле «Дата и время»: заготовки дня и времени без режима ответа, «Другая дата» и «Отмена». «Другая дата» задаёт вопрос, и момент вводится в том же виде `ДД.ММ.ГГГГ ЧЧ:ММ`, что и расписание сходки, по времени сообщества. Кнопка черновика несёт источник (`:d`), поэтому и «Отмена» экрана, и «Отмена» вопроса возвращают на черновик, а не в «Статус». Бот передаёт его в `ScheduleMeetupPublication` местной парой «дата и время» и в мгновение не переводит: интерпретирует её Meetups ([integration.md](../architecture/integration.md)).

Назначенный момент карточка показывает строкой «Публикация назначена на …» под статусом, а после отмены или публикации строки нет: её источник — `scheduled_publish_at` в снимке, а не память бота. Meetups отдаёт мгновение UTC, и адаптер переводит его в местное время сообщества поясом из `HUB_BOT_COMMUNITY_TIME_ZONE`. Пояс обязателен при старте, как у Meetups, и локально оба сервиса получают его из одной константы AppHost: расхождение поясов показало бы момент, сдвинутый на их разницу. Пока момент назначен, подменю статуса называет кнопку «Перенести публикацию» и добавляет «Отменить отложенную публикацию», которая проходит отдельный кадр подтверждения, как отмена сходки. О самом срабатывании бот не сообщает: это уведомление принадлежит Notifications.

| Отказ | Кадр |
|---|---|
| ввод не разобран | E-02: вопрос повторяется с примером формата, Meetups не вызывается |
| `INVALID_ARGUMENT`: момент уже прошёл или не представим в поясе сообщества | E-02 со своим текстом: вопрос повторяется и просит время в будущем |
| `FAILED_PRECONDITION`: сходка опубликована или отменена | E-04: ответ по перечитанному снимку и текущая карточка, вопрос больше не задаётся |
| `ABORTED` | вопрос повторяется по перечитанному снимку с текстом конфликта версий |
| отмена, когда момента уже нет | повтор без эффекта (E-09): кадр подтверждения не рисуется, человек видит, что публикации уже нет |

Администратор отмечает сходку состоявшейся прямо с карточки (кнопка появляется только при `lifecycle: planned`, кадр A-07) через отдельное подтверждение (кадр A-15), не через подменю статуса: `MarkMeetupHeld` идемпотентен для уже состоявшейся, а отменённую перевести нельзя — Meetups отвечает `FailedPrecondition`, и человек видит кадр E-04 «действие сейчас недоступно», а не кадр недоступности и не текст сервиса.

### Формат `callback_data`

```
v<версия>:<домен>:<действие>[:<аргумент>]…
```

Кнопка под следом — уведомлением или сообщением «Доступ открыт» — несёт то же действие с пометкой `t` сразу после версии: `v1:t:view:<токен>`, `v1:t:nav:hub`, `v1:t:notify:global`, `v1:t:notify:settings:<токен>`. Разбирается она тем же разбором, а экран по ней приходит новым сообщением: след остаётся в истории как был ([дизайн-код](../design/bot/design-code.md#доставка)). Пометка стоит два байта, и самая длинная такая кнопка занимает 43. Уведомление прошлого релиза несёт `v1:view:` без пометки и по-прежнему правится в карточку.

Домены: `nav`, `meetup`, `manage`, `mm`, `notify`, `bc`. Домен `auc` принадлежит общему пакету `shared/typescript/auction-bot-ui` ([ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md)): его кнопки одинаковы в обоих ботах, пишет и разбирает их пакет, а не `parse-callback.ts`. Чужой домен пакет отклоняет ошибкой `AuctionCallbackError` с причиной `foreign`, неизвестную версию — с `outdated`, остальное — с `malformed`. Идентификаторы сходки и материала — UUIDv7 в base64url (22 символа). Публичный номер сходки в `callback_data` не используется: он не является ключом связи, перебираем и известен только после вставки ([ADR-023](../decisions/ADR-023-meetup-public-number.md)).

Правила:

- **версия обязательна и разбирается первой.** Неизвестная версия — не ошибка, а состояние: человек получает «этот экран устарел» и актуальную перерисовку;
- **кнопка несёт целевое состояние**, а не переворот: `…:changes:1`, а не `…:toggle:changes`;
- **в кнопке нет прав.** Ни роли, ни признака видимости: право проверяется на сервере при каждом нажатии;
- **`callback_data` не является доверенным входом:** клиент может прислать произвольную строку для видимого ему сообщения.

Категория уведомлений едет псевдонимом, а не именем из словаря контракта:
`NOTIFICATION_CATEGORY_COMMUNITY_ANNOUNCEMENT` рядом с токеном сходки в 64 байта
не помещается. Карта псевдонимов исчерпывающая и живёт в одном месте —
`src/presentation/parse-callback.ts` разбирает её, `src/notifications/client.ts`
переводит в enum:

| Псевдоним | Категория контракта | Область |
|---|---|---|
| `published` | `NOTIFICATION_CATEGORY_MEETUP_PUBLISHED` | только глобальная |
| `changes` | `NOTIFICATION_CATEGORY_MEETUP_CHANGED` | глобальная и сходки |
| `material` | `NOTIFICATION_CATEGORY_MEETUP_MATERIAL` | глобальная и сходки |
| `reminder` | `NOTIFICATION_CATEGORY_MEETUP_REMINDER` | глобальная и сходки |
| `organizer` | `NOTIFICATION_CATEGORY_ORGANIZER_MESSAGE` | глобальная и сходки |
| `announcement` | `NOTIFICATION_CATEGORY_COMMUNITY_ANNOUNCEMENT` | только глобальная |

Область — часть типа, а не проверка: домен `set` разбирает только четыре
категории сходки, поэтому кнопка с глобальной категорией у сходки не рисуется,
не разбирается и до `INVALID_ARGUMENT` от Notifications не доезжает.

Снятия переопределения в кадре сходки нет, потому что его нет на проводе:
«наследовать глобальное» в `SetMeetupCategoryPreference` не выражается
([integration.md](../architecture/integration.md)). Кадр называет следствие до
нажатия — переключение закрепляет значение за этой сходкой. Отметка
«отличается» считается сравнением снимка сходки с глобальным и говорит про
расхождение значений, а не про наличие переопределения: контракт намеренно не
сообщает, чем получено значение, поэтому совпадающее переопределение от
наследования неотличимо.

### Идемпотентность

| Класс повтора | Чем закрывается |
|---|---|
| тот же апдейт доставлен дважды | при polling редок; вредный случай покрыт ключом создания |
| человек нажал дважды | формой команды: целевое состояние вместо действия |
| команда прошла, ответ потерян | ключом создания на стороне Meetups |

Ключ создания генерируется в момент отрисовки клавиатуры и лежит в кнопке. Оба быстрых нажатия несут один ключ; перерисовка меню порождает новый, поэтому второе законное создание даёт новый черновик. Нажатие кнопки из старого сообщения открывает ранее созданный черновик — принятое следствие. Ключ старше правила перерисовки: сначала исполняется команда с ключом из нажатой кнопки, и только потом сообщение перерисовывается результатом этой команды. Сама перерисовка нового ключа не порождает и второго черновика не создаёт.

Требование к контракту Meetups ([PER-51](https://linear.app/anticnvm/issue/PER-51)): команда создания принимает ключ, атомарно связывает его с результатом и при повторе возвращает ранее созданный черновик; ключ уникален в пределах организатора.

| нажата кнопка | `answerCallbackQuery` уходит вместе с результатом: его отправляет первый видимый вызов Bot API этого update, а до него клиент сам крутит индикатор на кнопке ([дизайн-код](../design/bot/design-code.md#ожидание), [PER-444](https://linear.app/anticnvm/issue/per-444)). Результат или кадр E-05 приходит редактированием. Ответ по умолчанию без текста: всплывающее окно поверх экрана, который сейчас перерисуется, человек назвал навязчивым ([PER-400](https://linear.app/anticnvm/issue/per-400)). Текст несут три случая, где его смысла на экране нет: переключатель категории («Включено: новые сходки.», кадр P-08), экран, который после нажатия остался тем же («Без изменений.», E-09), и повтор после сбоя, который снова не удался («Пока не получилось.»); в двух последних сообщение не правится вовсе. Если ответ не ушёл за 8 с от начала обработки, его отправляет сторож; отказ самого ответа действие не отменяет и пишется в запись границы полем `reply_error`. Экран на время ожидания не правится. Нечитаемая кнопка подтверждается так же и соседей не зовёт ([PER-346](https://linear.app/anticnvm/issue/per-346)) |
| бот ждёт сервис дольше 1 с | `sendChatAction` с повтором каждые 4 с, пока не ушёл первый видимый вызов; так же после ответа на вопрос и команды. Update, на который бот не отвечает, индикатора не получает |
| сообщение не изменилось | считается успехом, человеку ничего не показывается |
| слишком часто | `retry_after` соблюдается, используется готовый механизм grammY |
| сообщение не редактируется | ответ отправляется новым сообщением |
| юзкейс успешен, Telegram ответ не принял | юзкейс не откатывается |
| нажатие в устаревшем сообщении | сначала исполняется действие из `callback_data`, включая ключ создания, затем это же сообщение перерисовывается по текущему состоянию; проактивной зачистки старых экранов нет |
| недоступен сосед | кадр E-05: сбой и пустой результат — разные экраны. У кадра два выхода — «Повторить» и «Меню»; повтор, который снова не удался, сообщение не правит, а отвечает на нажатие текстом «Пока не получилось.» |
| любой кадр отказа | первое предложение жирным вместо заголовка и выход последним рядом: «Повторить», возврат к ближайшему живому экрану или «Меню». Кадра без кнопки нет; исключение — кадры без доступа P-14 и P-17, за которыми экранов нет |

Текст отказа сервиса и код gRPC человеку не показываются ни в одном ответе:
текст на английском и описывает провод, а не ситуацию человека. Адаптер
кладёт отказ в `cause` целиком, строки для ответа у экрана нет, а запись
границы пишет `grpc_code` и текст в `error` ([PER-397](https://linear.app/anticnvm/issue/per-397)).

| Статус gRPC Meetups на команде | Кадр |
|---|---|
| `INVALID_ARGUMENT` на кнопке (статус, материал) | E-05: неверную команду собрал бот, это сбой на нашей стороне |
| `INVALID_ARGUMENT` на значении формы | шаг повторяется, как E-02, фразой «значение не подошло» без причины |
| `FAILED_PRECONDITION` | E-04: «действие сейчас недоступно» и путь к карточке. Код не говорит, что мешает — отмена, пока висел экран, или черновик без названия, — поэтому кадр не называет причину |

Отказ Notifications отвечает кадром из того же набора, что и отказ Meetups или
Identity: третий сосед новых кадров не заводит, потому что человеку важна
природа отказа, а не имя сервиса за ним.

| Статус gRPC Notifications | Кадр |
|---|---|
| `UNAVAILABLE`, `DEADLINE_EXCEEDED`, внутренняя ошибка | E-05: сбой на стороне продукта, пустой список категорий вместо него не показывается |
| `PERMISSION_DENIED` | E-01: отказ приходит от владельца ресурса, а не от проверки в боте |
| `INVALID_ARGUMENT` на глобальной категории у сходки | E-04: до человека не доходит — такая кнопка не рисуется и не разбирается; доехавший отказ означает устаревший экран и перерисовку |
| `ALREADY_EXISTS` | E-09: повтор не создаёт второго объекта, состояние то же |
| сходка исчезла между отрисовкой и нажатием | E-03: «не найдено», неотличимо от несуществующей |

Интервалы повторов Telegram и конкретные тексты решаются при следующих срезах. RPC к каждому соседу ограничен 3 с одним дедлайном транспорта Connect; он же отменяет вызов и даёт код отказа. Поверх него у одного update общий бюджет 5 с на все сервисы: вызов получает меньшее из своего дедлайна и остатка бюджета, а при исчерпанном бюджете не делается и отвечает тем же отказом по дедлайну. Бюджет едет в `RpcMetadata.deadlineAt` и на провод не попадает.

Отказ разрешения личности имеет два исхода, и различает их код gRPC. Недоступность зависимости, таймаут и внутренняя ошибка дают `{ kind: "unavailable" }`; нарушение контракта и рассинхрон схемы — `InvalidArgument`, `Unimplemented` и соседние коды — дают `{ kind: "rejected" }`. Человеку в обоих случаях уходит один и тот же fail-closed ответ кадра E-05 без кнопки «Повторить», потому что в этом срезе ещё нет экрана списка, который она повторяла бы. В записи границы код отображается в общий словарь `error_category`: отдельно видны `dependency_unavailable`, `timeout`, `authorization`, `invariant` и `unexpected`, а у отвергнутого RPC рядом остаётся `grpc_code`. Повтор лечит недоступность или таймаут и никогда не лечит нарушение инварианта, поэтому они не сливаются ([first-slice.md](../architecture/first-slice.md#наблюдаемость), [logging.md](../standards/observability/logging.md)).

```
Не получилось загрузить данные. Это на моей стороне.

Попробуй ещё раз через минуту.
```

### Доставка уведомлений

Второй вход компонента — адресные факты Notifications из шины ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md)). Бот читает их собственным durable `hub-bot-notifications-events` и ведёт журнал попыток в bucket `hub-bot-deliveries`. Оба объявляет топология AppHost ([integration.md](../architecture/integration.md#jetstream)); бот к ним только привязывается и без них не стартует. Адрес шины — переменная `HUB_BOT_NATS_URL`, её отдаёт Aspire. Хранилище и выбор «дубль, а не потеря» приняты в [ADR-052](../decisions/ADR-052-telegram-bot-delivery-journal-in-jetstream-kv.md), имена уточнены ADR-044 от 2026-10-03 без переноса прежних dev-данных. Код живёт в `src/delivery/`: юзкейс не знает ни JetStream, ни Telegram, а ответы Bot API раскладывает по классам отказа представление (`src/presentation/notification-message.ts`).

Порядок обработки одного сообщения:

1. **Журнал.** Запись «доставлено» или «отброшено» — сообщение подтверждается без похода в Telegram. Журнал недоступен — сообщение откладывается: отправка вслепую и есть дубль, от которого журнал защищает.
2. **Срок и тип.** Истёкший `not_after` и тип, который канал ещё не рисует, снимаются с записью в журнал и логом. Канал рисует `meetup_published`, `meetup_changed`, `meetup_material`, `meetup_unpublished`, `meetup_reminder`, `organizer_message` и `community_announcement` ([PER-394](https://linear.app/anticnvm/issue/PER-394)); тип, которого сборка не знает, снимается, а не копится в durable. Ручная рассылка с пустым телом, как и сообщение организатора без карточки сходки, — нарушение контракта и снимается без записи, как неразборное сообщение. Тело из одних пробелов контракт пропускает, и канал его тоже не отвергает: под заголовком его Telegram примет. Факт изменения с пустым списком аспектов или без состояния сходки — нарушение контракта и снимается без записи, как неразборное сообщение; аспект из схемы новее сборки канал называет «другими сведениями», а не отвергает.
3. **Получатель.** `IdentityService.ResolveTelegramUserId`: `NOT_FOUND` и `FAILED_PRECONDITION` снимают сообщение, недоступность Identity откладывает его.
4. **Отправка и отметка.** Отметка «доставлено» пишется после ответа Telegram, ack — после отметки. Падение между отправкой и отметкой повторит сообщение, но не потеряет его.

| Исход | Действие с сообщением | Запись журнала |
|---|---|---|
| отправлено | `ack` | `delivered` |
| уже доставлено или отброшено | `ack` | без изменений |
| 403 от Telegram: бот заблокирован, аккаунт удалён | `term` | `dropped`, `bot_blocked` |
| прочие 4xx от Telegram | `term` | `dropped`, `telegram_rejected` |
| 429 от Telegram | `nak` на большее из `retry_after` и задержки по удвоению | `retrying` |
| 5xx, сетевой сбой, таймаут, недоступность Identity или журнала | `nak` с удвоением задержки | `retrying` |
| попытки кончились | `term` | `dropped`, `attempts_exhausted` |
| сообщение не разбирается | `term` | без записи: нет надёжного ключа |

Числа: 20 попыток по счётчику доставок JetStream, задержка удваивается от 5 с до потолка в 10 мин — это около двух с половиной часов недоступности. Вызов Bot API ограничен 10 с отдельным клиентом grammY, а не общим с поллером, потому что обязан уложиться в `ack_wait` durable. Бот держит у себя одно сообщение: таймер `ack_wait` идёт с выдачи, и сообщение, ждущее в буфере за зависшими отправками, истекло бы до своей попытки, а счётчик доставок, по которому считаются попытки, вырос бы вхолостую. Недоступность NATS процесс не останавливает — клиент переподключается без предела, и доставка продолжается с позиции durable. Удалённый durable или стрим останавливают процесс с отказом.

Текст собирается по образцу кадра P-11. Заголовок «Новая сходка: <название>», строка «когда» в той форме, в какой расписание опубликовано, — предварительная дата, день без времени, интервал или «Дата пока не назначена», — и строка места, если оно задано. Кнопки: «Открыть сходку» и «Не присылать новые сходки». Первая — кнопка следа (`v1:t:view:`): карточка приходит новым сообщением, а уведомление остаётся в истории. Вторая выключает глобальную категорию `published` тем же вызовом `SetGlobalCategoryPreference`, что и кадр P-09. Результат дописывается строкой под уведомлением, кнопка отключения сменяется кнопкой «Настроить уведомления», а текст уведомления остаётся. Отказ Notifications приходит отдельным сообщением, чтобы не стереть то, о чём уведомляли. Своей кнопки повтора у него нет: повтор — та же кнопка в уведомлении, иначе успех дописался бы под текстом отказа.

Остальные типы собраны по тому же образцу: заголовок называет повод и сходку, одно сообщение на повод, карточка целиком не повторяется.

- **Изменение.** Старых значений контракт не несёт, поэтому текст говорит, что изменилось, и показывает, как стало: строка «Изменилось: место, дата и время» и текущие «когда» и «где». Описание и ссылка на календарь только называются, за ними ведёт «Открыть сходку». Смена состояния выносится в заголовок — «Сходка отменена», «Сходка состоялась», «Сходка снова опубликована»; у отменённой сходки дата и место не повторяются. Возврат в план показывается строкой «Статус: запланирована», новый вид сходки — строкой «Вид».
- **Материал.** Заголовок «Новый материал у сходки «<сходка>»» и строкой ниже название материала, если оно есть: материал бывает и файлом, а название сходки в кавычках не читается как название материала. Кнопки: «Открыть сходку» и «Не присылать материалы этой сходки». «Открыть сходку» ведёт в карточку, где материалы перечислены: вида источника в факте нет, и кнопку прямо на материал собрать не из чего.
- **Снятие с публикации.** «Сходка снята с публикации: <название>» и дата, чтобы её узнать. Клавиатуры нет: «Открыть сходку» упёрлась бы в скрытую карточку, а отключать уже нечего.
- **Напоминание.** «Напоминание: <название>», строки «когда» и «где» — как у новой сходки. Кнопки: «Открыть сходку» и «Не присылать напоминания».
- **Сообщение организатора.** «Сообщение организатора: <название>», пустая строка и текст автора дословно, без разметки: сообщение уходит без `parse_mode`, и символы автора Telegram не толкует. Имени отправителя нет — оно не едет в контракте ([notifications.md](notifications.md)). Кнопки: «Открыть сходку» и «Не присылать сообщения организатора» — «этой сходки» в подпись не помещается на экран телефона, а что категория выключена только у этой сходки, говорит ответ на нажатие.
- **Объявление сообщества.** «Объявление сообщества», пустая строка и текст автора дословно. Сходки у объявления нет, поэтому кнопка одна — «Не присылать объявления».

Тело рассылки ограничено тем же пределом в 4096 UTF-16-единиц, что и сообщение Telegram ([integration.md](../architecture/integration.md)), и заголовок над телом предельной длины получил бы отказ 400 — сообщение снялось бы без повтора. Поэтому заголовок ставится, только когда заголовок с телом помещаются в предел, а иначе уходит одно тело: текст автора не обрезается, а у сообщения организатора сходку по-прежнему называет кнопка «Открыть сходку». По той же причине подтверждение отключения под такой рассылкой не дописывается: текст остаётся как был, кнопка отключения сменяется кнопкой настроек, а заметка об отключении приходит отдельным сообщением.

Кнопка отключения в уведомлениях об изменении, о связанном сообщении и в сообщении организатора выключает категорию **у этой сходки** (`SetMeetupCategoryPreference`, `v1:notify:moff`), а не глобально: эти категории получают подписчики сходки, и настройка у сходки перекрывает общую, так что общий выключатель не остановил бы уведомления там, где категория включена явно. Результат дописывается под уведомлением так же, как у новой сходки, а кнопка отключения сменяется кнопкой «Уведомления сходки». Изменения и снятие с публикации идут по одной категории, и подтверждение говорит об этом прямо: после отключения изменений служебное сообщение о снятии этой сходки тоже не придёт. Сходка, исчезнувшая к нажатию, и отказ Notifications приходят отдельным сообщением. Настройка пишется раньше, чем читается карточка, поэтому ответ о скрытой сходке не обещает, что выключения не было, и говорит то, что верно в обоих случаях: пока сходку не вернут в публикацию, уведомлений по ней не будет.

Кнопка отключения в напоминании, наоборот, выключает **глобальную** категорию `reminder` (`v1:notify:off:reminder`) тем же путём, что у новой сходки. По сходке напоминание приходит один раз — второе бывает только после переноса, — поэтому выключатель у сходки остановил бы почти ничего, а человеку, который жмёт «хватит», нужна общая настройка. Настройка у сходки перекрывает общую, а снять переопределение контракт не даёт, поэтому подтверждение не обещает полной тишины: напоминания сходок, где категория включена отдельно, останутся, и выключают их в уведомлениях сходки.

Запись в лог — одна на сообщение: `operation` — subject факта, `use_case` отсутствует, потому что доставку не начинал человек ([logging.md](../standards/observability/logging.md)). Сверх каркаса пишутся `notification_id`, `notification_type`, `attempt` и `retry_delay_ms`, получатель — `identity_id`, а `request_id` приходит из факта. Ожидаемые отказы получателя — уровень `warn`; нарушение контракта, исчерпанные попытки и тип, который канал не рисует, — `error`: принятый Notifications, но не нарисованный тип значит, что автор видел «принято», а до получателя ничего не дошло. Счётчик `telegram_bot.notification.deliveries` делится по исходу.

### Наблюдаемость и privacy

Логи структурные, без bot token, `initData` и полного JSON апдейта. Telegram user id — персональные данные и не ключ поиска: после разрешения личности в лог пишутся `identity_id` и `request_id`. Норматив — [logging.md](../standards/observability/logging.md).

Оба обработчика update — сообщение и callback — заполняют каркас одной `writeBoundary`. `operation` называет обработчик, успех пишется уровнем `Info`, как у Identity и Meetups, отказ увеличивает `solguficky.failures` в том же месте, где рождается запись. Нечитаемый `callback_data` — `invariant` без stack; отказ Meetups по правам на публикации — `authorization`. Отказ по конфликту версий — `invariant` с `error: version_conflict`: человеку уходит текст решения [PER-78](https://linear.app/anticnvm/issue/per-78) и актуальный снимок, а не общий отказ зависимости. Отказ по допуску к хабу — тоже `authorization`, но `error` называет `hub_access_pending` или `hub_access_blocked`; скрытая или отсутствующая сходка — `visibility` с `meetup_not_visible`; недоступность Identity остаётся `dependency_unavailable` или `timeout`.

Трейсы уходят по OTLP по тому же адресу из окружения, что логи и метрики; без адреса трассировка no-op. Каждый update открывает корневой спан `telegram.update <тип>` вида Consumer с атрибутами `telegram.update.type` и `request_id` — тем же, что в записи границы. Вызовы Bot API внутри update — дочерние спаны `telegram.bot_api <метод>`: transformer ставится на `ctx.api` этого update, поэтому `getUpdates`, меню команд и доставка из NATS трейсов без корня не порождают. Исходящие вызовы Identity, Meetups и Notifications идут клиентскими спанами `<сервис>/<метод>` через interceptor Connect, который кладёт W3C `traceparent` в заголовки. Спан update доезжает до interceptor'а через `AsyncLocalStorage`, а не через типы запросов application-слоя. Провайдер, менеджер контекста и пропагатор передаются явно (`Tracing` в `src/tracing.ts`) и глобально не регистрируются, как у Identity. Текст, ник, Telegram id, chat id, payload и описание отказа Bot API в атрибуты не пишутся; отказ несёт только код (`telegram.bot_api.error_code`, `rpc.grpc.status_code`) и `error.type`. Доставка уведомлений из NATS идёт вне update и не трассируется.

### Общий код с мини-приложением

Речь не про `shared/typescript/auction-bot-ui` из [ADR-044](../decisions/ADR-044-two-telegram-bots-and-shared-auction-screens.md): тот пакет общий у двух ботов и относится к аукциону. Пакет с мини-приложением заранее не создаётся. Когда мини-приложение появится, разделяться могут DTO представления, presentation models, Telegram-идентификаторы, локализуемые тексты и типы UI-состояния без инвариантов. Общий package не становится источником правды для инвариантов Meetups, авторизации, переходов доменных состояний и проверки `initData`. Браузер на внутренний gRPC не ходит.

## Угловые случаи, обязательные в тестах

1. два быстрых нажатия «Создать сходку» дают один черновик;
2. повтор вызова Meetups с тем же ключом возвращает тот же черновик, а не ошибку и не второй объект;
3. нажатие «Создать сходку» после перерисовки меню даёт новый черновик;
4. нажатие в старом сообщении перерисовывает его по текущему состоянию;
5. `callback_data` неизвестной версии не роняет процесс, а отвечает «экран устарел»;
6. переключатель, нажатый дважды, оставляет то же состояние и сообщает об этом;
7. при двух открытых черновиках ответ на вопрос формы попадает в поле того черновика, к которому относится вопрос, а не в последний созданный;
8. ответ на вопрос формы создания и точечной правки после рестарта процесса восстанавливает шаг из сообщения, а ответ на вопрос названия материала получает понятный текст, а не тишину;
9. недоступность Meetups даёт кадр E-05, а не пустой список;
10. сценарий «создал и опубликовал» проходится без единой телеграмовской структуры;
11. правка одного поля не проходит форму заново и не теряет остальные поля;
12. снятие с публикации и отмена выполняются только из подтверждения, а отказ от подтверждения не отправляет команду;
13. кнопка из старого сообщения обрабатывается по текущему состоянию сходки: на уже отменённой человек получает понятный текст, а не кадр недоступности.
14. материалы карточки сохраняют порядок Meetups, ссылка открывает сообщение, а файл отправляется отдельной кнопкой;
15. привязка ссылки и файла достигает Meetups только после подтверждения, а скрытый источник получает E-06 без команды;
16. удаление привязки выполняется только после подтверждения и не обещает удалить исходный объект.
17. архив показывает отменённые, состоявшиеся и прошедшие без даты пересортировки, в порядке, который отдаёт Meetups;
18. отметка сходки состоявшейся выполняется только из подтверждения, а отменённую отметить нельзя;
19. дата раньше сегодняшнего дня сообщества сохраняется только после подтверждения, сегодняшняя дата в прошедший час вопроса не вызывает, а ответ о публикации такой сходки не обещает её в списке;
20. уведомление, доставленное до рестарта, после рестарта не уходит второй раз, даже если ack потерян, а накопленное до старта доставляется ровно один раз;
21. получатель, заблокировавший бота, получает одну попытку, а не бесконечные повторы; временный отказ Telegram повторяется до доставки;
22. тип уведомления, который канал ещё не рисует, снимается с записью в лог, а не доставляется молча и не копится в durable;
23. отключение категории из уведомления меняет глобальную настройку и оставляет текст уведомления на месте;
24. команда меню проходит политику поверхности, как `/start`, и открывает экран новым сообщением, а отказ `setMyCommands` не мешает старту polling;
25. рассылка уходит только после предпросмотра и подтверждения с предупреждением о необратимости; вход в неё не-администратор не видит, а подтверждение мимо кадра отклоняет Notifications кадром E-01;
26. повторное «Отправить» и «Повторить» после сбоя несут тот же ключ рассылки и второй раз её не рассылают;
27. ответ на нажатие уходит после ответа сервиса, а при зависшем сервисе — сторожем; его отказ действие не отменяет, а update без ответа бота не получает «печатает…».

Пункты 1–10 проверяются и на уровне L2, против настоящих Identity и Meetups, в наборе [tests/contour/bot-wire](../../tests/contour/bot-wire): 1–3 — `idempotency.test.ts`, 4 и 5 — `stale-screens.test.ts`, 7 и 8 — `drafts-and-restart.test.ts`, 9 — `meetups-unavailable.test.ts`, 10 — `create-and-publish.test.ts`. Там же лежат сценарий первого среза с отрицательной половиной (`first-slice.test.ts`), кадры E-01, E-03, E-04 и E-09 и материалы A-13 и A-14 (`materials.test.ts`): прикрепление и снятие через настоящий Meetups и кадр конфликта на подтверждении, собранном по карточке, которую изменили мимо бота. Идемпотентность набор считает по журналу Meetups, а не по экрану: двойное нажатие и успех снаружи неотличимы. Число записей выводится из суммы версий сходок автора, пока каждое событие поднимает версию. `journalOf` читает оба viewer-aware списка (`ListVisibleMeetups` и `ListArchivedMeetups`), затем снимки через `GetMeetup` и оставляет только сходки автора: автор видит и свои скрытые черновики без роли администратора. Прямой клиент предъявляет токен бота; служебный `ListMeetupStates` закрыт для всех по ADR-056 и набор его не вызывает. Два расхождения названы явно. Пункт 5 бот исполняет не буквально: на кнопку неизвестной версии он открывает актуальный список, а не отвечает «экран устарел», и набор проверяет именно это. Пункт 6 на L2 не покрыт: переключатели есть только у категорий уведомлений, а контур поднимает Identity и Meetups без Notifications.

На уровень L3, в живой контур [tests/telegram-live](../../tests/telegram-live) из [ADR-046](../decisions/ADR-046-telegram-test-contour.md), перенесены только края Telegram, которых L2 не видит (`error-frames.live.test.ts`, [PER-279](https://linear.app/anticnvm/issue/per-279)). E-03 проверяется отправкой `/start <payload>` с обеих сторон: опубликованная сходка открывает карточку, а скрытая и несуществующая дают один и тот же текст и одну и ту же клавиатуру. Пункт 4 и E-04 проверяются настоящим `callback_query` по кнопке старого сообщения: бот правит это же сообщение, а не присылает новое. Смену состояния между отрисовкой и нажатием держит L2: у драйвера нет доступа к Meetups мимо бота. Остальное на L3 не переносится. E-01 не воспроизводится: не-администратор кнопки административного действия не получает, а клиент Telegram нажимает только кнопки, которые есть под сообщением. Пункт 5 не переносится по той же причине. E-09 и пункты 1–3 считаются по журналу Meetups, которого драйвер не видит. Пункты 7, 8 и 10 — логика бота без края Telegram. Пункт 9 гасит зависимость и остаётся за [PER-174](https://linear.app/anticnvm/issue/per-174). Пункт 6 не переносится по решению владельца.

## Опыт предыдущей реализации

Rust/Teloxide-шлюз предыдущего поколения удалён из репозитория. Что из него взято и что признано ошибкой — в [архиве](../archive/services/auction-domain-and-lessons.md).

Переносится: обработчик возвращает действие, а отдельный executor вызывает Telegram API; UI builders и сценарная логика остаются чистыми функциями; transport и presentation тестируются раздельно.

Не переносится: дедупликация по `callback_query.id` (у каждого нажатия свой идентификатор, от двойного нажатия она не защищает), диалоговое состояние в памяти процесса, `BotAction` в типах Telegram и одновременное существование JSON- и Protobuf-путей на шине.

## Что решено и что осталось

Принято в [ADR-030](../decisions/ADR-030-telegram-bot.md): имя и граница компонента, стек, long polling, диспетчер приложения, состояние в сообщении, ключ создания внутри кнопки как требование к контракту Meetups. Имя пересмотрено уточнением ADR-044 от 2026-10-03: Hub Bot. Отсутствие собственного хранилища, принятое там же, дополнено [ADR-052](../decisions/ADR-052-telegram-bot-delivery-journal-in-jetstream-kv.md): журнал доставки уведомлений лежит в JetStream KV, а канал выбирает риск дубля, а не потери. Принято в [ADR-034](../decisions/ADR-034-telegram-bot-rich-presentation.md): продуктовая карточка по умолчанию — `sendRichMessage`; та же экранная модель собирает `sendMessage` при `HUB_BOT_PRESENTATION=plain`. Кодогенерация Protobuf — `protoc-gen-es` и Connect с транспортом gRPC, команда и место версий — раздел «Кодогенерация TypeScript» в [стандарте Protobuf](../standards/contracts/protobuf.md#кодогенерация-typescript). Принято в [PER-343](https://linear.app/anticnvm/issue/PER-343): [дизайн-код экранов](#дизайн-код-экранов) — дерево и возврат, доставка результата, вопрос с выходом, формат и правило ожидания с его числами; отдельного ADR у него нет, запись — [design-code.md](../design/bot/design-code.md).

Скелет в `apps/hub-bot` фиксирует toolchain первого TypeScript-компонента:

| Вопрос | Решение |
|---|---|
| Package manager | **npm**. Lockfile — `apps/hub-bot/package-lock.json`. Поле `packageManager` и CI/`just` вызывают только `npm ci`. Выбор уже стоял в [protobuf.md](../standards/contracts/protobuf.md#кодогенерация-typescript). |
| Module system | **ESM + `NodeNext`**. `"type": "module"` и `module`/`moduleResolution`: `NodeNext`. |
| Strictness | `strict` и явно: `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature`, `useUnknownInCatchVariables`. Для TypeScript 7 обязателен `"types": ["node"]`. |
| Linting и formatting | **Biome**. `npm run lint` → `biome check .`, `npm run format` → `biome format --write .`. Один инструмент, без TypeScript compiler API, который 7.0 не отдаёт. |
| Testing | **Vitest**, `vitest run` без watch. Coverage — `npm run coverage` без порога. |
| Type checking | отдельный `tsc --noEmit`; сборка — `tsc -p tsconfig.build.json`. |
| Zod | `^4.5.4`. Схемы в `src/presentation/schemas.ts`, типы через `z.infer`. |
| Coverage gate | команды без порога. |
| Dependency boundaries | на скелете component test диспетчера без grammY и review. Lint-rule на запрет импорта grammY в application не вводится. |
| TypeScript | **7.0.x**, нативный `tsc`. Совместимость с Zod 4.5 и grammY 1.46 проверена в контуре PER-92. |
| Aspire | `AddJavaScriptApp`, скрипт `start`. |

Осталось вне этого брифа:

- отрисовка ручных рассылок: Notifications их порождает ([PER-225](https://linear.app/anticnvm/issue/PER-225)), бот их подаёт (раздел «Ручные рассылки»), но канал пока снимает эти типы с записью в лог — отрисовку добавит [PER-217](https://linear.app/anticnvm/issue/per-217);
- что модуль отдаёт в карточку и форма экрана настроек — решения 3 и 4 [RFC-003](../rfcs/RFC-003-bot-presentation-rich-blocks.md);
- ревизия макета после выбора 1d — отдельное решение владельца.

Решается при реализации следующих задач, ADR не требуется: конкретные тексты и локализация, числа повторов Telegram. Числа ожидания заданы [дизайн-кодом](#дизайн-код-экранов) и живут константами в `src/presentation/waiting.ts`.
