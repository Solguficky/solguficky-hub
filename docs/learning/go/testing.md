# Тесты в Go

В Go тесты — часть языка и инструмента, а не отдельный фреймворк: нет ни атрибутов, ни ссылки на тестовый пакет, ни отдельного раннера. Файл объясняет, как это устроено и какие решения приняты в тестах Identity. Раскладка модуля — в [service-layout.md](service-layout.md), сам сервер — в [unary-server.md](../grpc/unary-server.md).

## Механика

### Где живёт тест и как он запускается

Тест — это файл `*_test.go` **рядом с тестируемым кодом**, в том же каталоге. Отдельного дерева `tests/` нет и быть не может: пакет — это каталог, а тест обязан быть в пакете. Конвенция имени — `foo_test.go` тестирует `foo.go`; она ничем не проверяется, но по ней ориентируются читатель и инструменты.

Тестом считается функция `func TestXxx(t *testing.T)` в таком файле. Никаких атрибутов: `go test` находит их по сигнатуре и имени. Ассертов в стандартной библиотеке тоже нет — есть `t.Fatalf`, и проверка пишется обычным `if`. Отсюда принятая форма сообщения `got X want Y`: она заменяет то, что в xUnit печатает сам ассерт.

`go test ./...` собирает и прогоняет всё дерево. Результат кешируется по содержимому входов, поэтому повторный прогон без правок печатает `(cached)`; `-count=1` кеш отключает.

### Два тестовых пакета: белый ящик и чёрный

В одном каталоге разрешены два пакета: `server` и `server_test`. Это уникальная для Go развилка, и она задаёт уровень доступа.

- `package server` — **белый ящик**: видны неэкспортируемые имена. Так тестируются `requestID`, `serverFault`, поле `srv.health`.
- `package server_test` — **чёрный ящик**: пакет импортируется снаружи, доступен только его публичный API. Так тестируется путь клиента через `bufconn`.

Практический смысл развилки: она не даёт тесту стать причиной расширения API. Константа `stubIdentityID` неэкспортируемая, потому что это деталь заглушки; её точное значение проверяет внутренний `resolve_test.go`, а внешний `server_test.go` проверяет наблюдаемое — что ответ непустой и повторяемый. Если бы такой развилки не было, константу пришлось бы экспортировать и она стала бы частью контракта пакета навсегда.

Файлы Identity разложены по этому правилу:

| Файл | Пакет | Что проверяет |
|---|---|---|
| `resolve_test.go` | `server` | заглушку и её значение |
| `interceptor_test.go` | `server` | цепочку интерцепторов и поля записи |
| `server_internal_test.go` | `server` | `GracefulStop` через неэкспортируемое поле `health` |
| `server_test.go` | `server_test` | путь клиента через `bufconn` |
| `apply_test.go` | `migrations_test` | ограничения схемы на живом PostgreSQL |

`GracefulStop` попал в белый ящик вынужденно: после остановки сервер соединений не принимает, и увидеть `NOT_SERVING` снаружи по сети уже невозможно.

Тесты миграций — чёрный ящик: они вызывают публичные `Apply`/`ApplyDSN` и дальше говорят с PostgreSQL SQL-ом. Схема и есть шов. Поднимать общий `identity` и чистить таблицы между тестами нельзя: `t.Parallel()` гоняет их одновременно. Поэтому каждый тест делает `CREATE DATABASE` с уникальным именем и в `t.Cleanup` — `DROP DATABASE ... WITH (FORCE)`. `FORCE` нужен, потому что к моменту cleanup соединение теста ещё может быть открыто; без него `DROP` завершился бы ошибкой из-за открытого подключения.

Если PostgreSQL недоступен и `IDENTITY_DATABASE_URL` не задан, тесты схемы пропускаются. В CI переменная задана, и отсутствие базы — ошибка, а не skip: иначе джоба была бы зелёной без проверки критериев приёмки.

### Табличные тесты и параллельность

Идиома вместо параметризованных тестов — таблица случаев и цикл с подтестом:

```go
for _, tc := range cases {
	t.Run(tc.name, func(t *testing.T) {
		t.Parallel()
		...
	})
}
```

`t.Run` заводит подтест с собственным именем в отчёте, `t.Parallel` отпускает его выполняться параллельно с другими помеченными. Линтер `paralleltest` следит, чтобы пометка не терялась.

`t.Context()` даёт контекст, который отменяется по завершении теста, `t.Cleanup` регистрирует освобождение ресурса — так в `newConn` закрываются listener, сервер и соединение. Линтер `usetesting` требует именно их вместо `context.Background()` и ручного `defer`.

### Подмена зависимостей без моков

Библиотек моков в стандартной библиотеке нет, и здесь они не понадобились: подмена делается тем же интерфейсом, который принимает production-код. Логгер проверяется своей реализацией `slog.Handler` из 4 методов, которая складывает записи в срез:

```go
type capture struct {
	mu      sync.Mutex
	records []slog.Record
}
```

Мьютекс не декоративный: подтесты идут параллельно, и `-race` поймал бы конкурентную запись в срез.

`bufconn` — та же идея на уровень ниже: `net.Listener` поверх памяти. Работает полный стек gRPC — кодек, HTTP/2, интерцепторы, — но порт не занимается.

### Детектор гонок

`go test -race` инструментирует обращения к памяти и печатает стек обеих сторон гонки. Он требует cgo и компилятора C, поэтому на машине разработчика под Windows без MinGW не запускается:

```
go: -race requires cgo
cgo: C compiler "gcc" not found
```

Отсюда решение: `-race` стоит отдельным шагом в CI на Linux, а `just identity-test` остаётся обычным прогоном.

## Урок

**Формулировка утверждения важнее покрытия строк.** Первая версия хелпера искала запись с нужным сообщением: она проходила и когда таких записей было две, поэтому двойное логирование паники жило в зелёных тестах. Замена на `sole`, который требует ровно одну запись, ловит регрессию. Покрытие у обеих версий одинаковое — разная сила утверждения.

**Тестировать надо собранную конструкцию, а не только детали.** Интерцепторы по отдельности вели себя правильно; дефект был в их композиции. Пока тесты проверяли каждый интерцептор изолированно, дефект был невидим — и появился он именно там, где никто не смотрел. Отсюда `chainUnary`/`chainStream`: собирают ту же пару и в том же порядке, что и `New`.

**Тест не должен расширять API ради удобства.** Экспортировать значение ради теста дёшево, а стоит дорого: оно навсегда становится контрактом пакета. Развилка «белый ящик — чёрный ящик» решает это без компромисса, и она есть в любом языке в виде InternalsVisibleTo или friend-сборок; в Go это просто два пакета в одном каталоге.

**Тест чужой библиотеки — не тест.** В срезе были три теста, гонявшие `proto.Marshal`/`Unmarshal` туда-обратно. Они проверяли `google.golang.org/protobuf`, а не наш код, и держали в корне модуля пакет без единого файла с кодом. Удалены: тот же путь сериализации проходит настоящий вызов через `bufconn`, и делает это на нашем коде.

**Мутация — единственная проверка того, что тест что-то ловит.** Зелёный тест не отличается от теста, который всегда зелёный. Проверяется одним движением: внесите дефект, ради которого тест написан, и убедитесь, что он красный. Именно так найдено, что первый вариант мутации ничего не доказывал — запись шла через `slog.Default()`, мимо инжектированного логгера, и тест её не видел.

## Почему так, а не иначе

| Вариант | Цена |
|---|---|
| Отдельный каталог `tests/` | невозможен: пакет — это каталог, и тест вне его теряет доступ к пакету |
| Только внешний тестовый пакет | `requestID`, `serverFault` и `srv.health` пришлось бы экспортировать ради теста |
| Только внутренний тестовый пакет | ничто не проверяет, что публичного API хватает клиенту; путь через кодек и HTTP/2 остаётся непокрытым |
| `testify` и его ассерты | зависимость ради синтаксиса; стандартных `if` + `t.Fatalf` на этом объёме достаточно |
| Хелпер ищет запись по сообщению | проходит при двух записях; регрессия двойного логирования остаётся зелёной |
| Тесты интерцепторов только по отдельности | дефект композиции невидим — именно так он и появился |
| `proto.Marshal` туда-обратно | тестирует библиотеку protobuf; тот же путь покрыт вызовом через `bufconn` |
| `-race` в `just identity-test` | на Windows без MinGW команда падает на cgo; локальный прогон перестал бы работать |
| Реальный TCP-порт в тестах | гонки за `:50051` и зависимость от файрвола |
| Общая тестовая база без изоляции | параллельные тесты ломают друг другу уникальный индекс и состав строк |
| `t.Skip` в CI при недоступной базе | джоба зелёная, критерии приёмки не проверялись |

## Проверь себя

- Два пакета в одном каталоге компилируются: `go test ./internal/server/` собирает `server` и `server_test` вместе. Проверено.
- Тест, ищущий запись по сообщению, пропускает вторую такую же: старая версия хелпера была зелёной на двойном логировании паники, новая падает с `records: got 2 ... want 1`. Проверено мутацией.
- Мутация через `slog.Default()` вместо инжектированного логгера тесты **не** валит. Проверено — отсюда явная граница у `sole`.
- `go test -race ./...` локально не запускается: `-race requires cgo`, `gcc` не найден. Проверено; в CI шаг отдельный.
- `go test -count=1 -v ./internal/migrations/` на доступном PostgreSQL: шесть тестов PASS, включая повторный `Apply`, параллельный `ApplyDSN` и отклонение второго профиля с тем же Telegram user id. Проверено.
