# Стиль документации

Документы пишутся для человека, который должен быстро понять текущее правило, устройство или контекст решения.

## Язык и формат

- Основной язык — русский; имена в коде, CLI и идентификаторы не переводятся.
- Архитектурные диаграммы пишутся в Mermaid и хранятся рядом с текстом.
- Ссылки внутри репозитория — относительные.
- Заголовок и первый абзац должны объяснять назначение документа без чтения остальных разделов.
- Часто меняющиеся данные хранятся в одном месте и переиспользуются ссылкой.
- Таблица используется для точных сопоставлений, а не вместо нескольких предложений.

## Стиль по слоям

| Слой | Вопрос | Стиль |
|---|---|---|
| `product/` | Что и для кого строим? | продуктовые формулировки без преждевременной реализации |
| `architecture/` | Как устроена система и почему? | устойчивый обзор, Mermaid, ссылки на ADR |
| `services/` | За что отвечает компонент? | границы, данные, зависимости, открытые вопросы |
| `standards/` | Как обязательно делать? | нормативные формулировки «используй», «не делай» |
| `rfcs/` | Что предлагается изменить? | проблема, варианты, последствия, открытые вопросы |
| `decisions/` | Что решили и почему? | неизменяемая история решения |
| `development/` | Как выполнять работу? | проверяемая последовательность действий |
| `learning/` | Почему незнакомый код выглядит так? | объяснение для читателя, дифф как источник, ссылки на первоисточники |
| `archive/` | Что было зафиксировано раньше? | исходный текст с явной исторической пометкой |

## Антипаттерны

- выдавать Future-направление за принятое решение;
- смешивать Current и MVP без подписей;
- хранить прогресс задачи в долговечном документе;
- копировать кодовые контракты в архитектурный обзор;
- дублировать standard целиком в `AGENTS.md` или skill;
- использовать архивный snapshot как источник актуальной архитектуры;
- писать «можно использовать X», если документ на самом деле требует X.

## Устаревание

- Заменённый ADR остаётся в истории и ссылается на замену.
- Заменённый standard получает ссылку на новый и затем удаляется, если больше не нужен для понимания.
- Устаревший architecture-документ либо получает `Superseded`, либо переносится в `archive/`.
- Выполненные task-документы удаляются: их история остаётся в Git и Linear.
