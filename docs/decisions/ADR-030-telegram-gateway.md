# ADR-030: Telegram Gateway — TypeScript, grammY и граница приложения

> **Дата:** 2026-08-23  
> **Статус:** Accepted

## Контекст

Новый Telegram-вход нужен первому вертикальному срезу: без него нет наблюдаемого ответа человеку. Текущий Rust + Teloxide шлюз обслуживает аукцион, хранит диалог и идемпотентность в памяти и не является фундаментом MVP. Стек TypeScript + grammY принят владельцем раньше этого ADR и уже стоит в [overview.md](../architecture/overview.md); не оформленными оставались устройство компонента и вопросы из [services/telegram-gateway.md](../services/telegram-gateway.md).

На решение действуют уже принятые границы:

- [ADR-026](ADR-026-identity-mvp-model-and-access.md) — Gateway устанавливает Telegram user id и на каждом продуктовом update синхронно вызывает Identity; кэша прав нет, недоступность — fail-closed;
- [ADR-028](ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md) — ответственность Notifications заканчивается публикацией адресного факта в шину; резолвинг, текст, retry и журнал попыток принадлежат каналу;
- [first-slice.md](../architecture/first-slice.md) — черновик сходки живёт в Meetups, диалог Gateway хранит только шаг; повтор кнопки не создаёт второй объект, и этого нельзя добиться одним подавлением повторов на краю;
- transport к Meetups и wire-контракты, судьба legacy-аукционных callback и migration gate в этот ADR не входят. Вызов Identity уже синхронный gRPC по [ADR-026](ADR-026-identity-mvp-model-and-access.md).

Компонент ещё не существует как код. Имя, стек, вход апдейтов, внутренняя граница и место операционного состояния нужно зафиксировать до реализации, иначе первый срез начнёт смешивать Telegram-типы с юзкейсами и прятать ключ создания в память процесса.

## Варианты

### Имя компонента

- **Telegram Gateway** / `telegram-gateway` — уже используется в документах, Aspire и Linear;
- Telegram Bot, Telegram Edge, Solguficky Bot — новые имена ценой переименования всех ссылок без новой границы.

### Стек

- **TypeScript + grammY** — принятое направление;
- оставить Rust + Teloxide и нарастить его под сходки;
- Go или Python с другой Telegram-библиотекой.

### Доставка апдейтов

- webhook везде, локально через туннель;
- long polling везде;
- **два режима одного процесса:** long polling в локальном Aspire, webhook в среде с публичным HTTPS.

### Граница приложения

- grammY-handlers содержат вызовы Identity, Meetups и сборку ответа;
- **презентационные адаптеры отделены от транспортных юзкейсов;** юзкейс вызывается диспетчером приложения;
- вынести юзкейсы в отдельный процесс или сервис.

### Диалоговое состояние и ключи

- память процесса, как в legacy;
- Redis;
- **собственная PostgreSQL-база Gateway;**
- хранить шаг и ключ создания в Meetups.

### Идемпотентность создания

- дедупликация только по `update_id` в Gateway;
- ключ только в Gateway без участия Meetups;
- **ключ живёт на обеих сторонах:** Gateway сохраняет его до первого вызова, Meetups атомарно связывает с результатом команды.

### Второй вход — уведомления

- отдельный деплой канала;
- **тот же процесс:** рядом с обработкой updates свой durable consumer, рендерер и журнал попыток;
- вернуть доставку в Notifications.

## Решение

| Ось | Решение |
|---|---|
| Имя | **Telegram Gateway**; каталог и процесс — `telegram-gateway` |
| Стек | **TypeScript, Node.js LTS, grammY** |
| Вход апдейтов | **long polling локально; webhook в среде с публичным HTTPS** |
| Граница | **презентационные адаптеры / диспетчер приложения / юзкейсы** |
| Операционное хранилище | **отдельная PostgreSQL-база** |
| Диалог | курсор шага и ссылка на черновик; атрибуты сходки в Meetups |
| Создание | ключ идемпотентности на обеих сторонах команды |
| Уведомления | свой durable consumer, рендерер, журнал попыток и retry в том же процессе |
| Mini App | общего backend-транспорта нет; допустим только будущий presentation package |
| Legacy | новая реализация с нуля; вывод Rust — отдельный migration gate |

### 1. Имя и место

Человекочитаемое имя компонента — **Telegram Gateway**. Идентификатор в репозитории, оркестрации и конфигурации — `telegram-gateway`. Реализация появится в `apps/telegram-gateway` вместе с первым коммитом кода, не раньше.

Это тот же Telegram edge, что уже описан в брифе: не владеет инвариантами Meetups, системными ролями и решениями авторизации.

### 2. Стек

Новый Gateway пишется на TypeScript и grammY, runtime — поддерживаемая Node.js LTS. Legacy Rust + Teloxide не наращивается под сходки и не разделяет процесс с новой реализацией.

Плагин grammY Conversations для продуктового диалога не используется: черновик принадлежит Meetups, а курсору шага не нужен replay функций. Конкретные версии Node, grammY и форма Aspire-хостинга (`AddJavaScriptApp`) — технический дизайн, меняется без нового ADR.

### 3. Доставка апдейтов

Один процесс поддерживает два режима входа, переключаемых конфигурацией:

- **локальный Aspire** — long polling. Публичный URL и туннель во inner loop не требуются;
- **среда с публичным HTTPS** — webhook. Вход проверяется secret token, как требует [ADR-026](ADR-026-identity-mvp-model-and-access.md).

Если выбранный hosting не даёт входящего HTTPS, тот же процесс остаётся на long polling. Это конфигурация, а не вторая архитектура. Площадка по-прежнему Open и этим ADR не выбирается.

В обоих режимах Gateway устанавливает Telegram user id из уже принятого update. Identity authentication material не видит. При polling доверенность входа — владение bot token; при webhook — secret token HTTP-входа.

### 4. Внутренняя граница и кто вызывает юзкейс

Компонент делится на три слоя.

**Презентационные адаптеры** знают Telegram и grammY: разбор update и deep link, `callback_data`, сборка текста, клавиатуры и `answerCallbackQuery`, вызов Bot API, ошибки и лимиты Telegram.

**Юзкейсы приложения** не принимают и не возвращают типы Telegram, grammY `Context` или `Bot`. На входе — уже установленная личность, намерение и ключ идемпотентности, если команда его требует. На выходе — результат или отказ, пригодный для любой презентации. Юзкейс ходит в Identity, Meetups и command plane Notifications; он не открывает Bot API.

**Диспетчер приложения** — единственная in-process точка, которая принимает транспортно-нейтральную команду и вызывает юзкейс. Его вызывают:

- адаптер Telegram-апдейтов — в рабочем составе;
- адаптер потребителя шины — для доставки уведомления;
- компонентный тест;
- диагностический CLI или тестовый адаптер.

Тест и CLI прогоняют юзкейс, не конструируя Telegram `Update`, grammY `Context` и `Bot`. Отдельного HTTP API для юзкейсов в MVP нет.

Адаптер апдейтов отвечает на `callback_query` в лимите Telegram даже тогда, когда юзкейс ещё не закончился: человеку уходит короткое подтверждение, результат дорисовывается редактированием сообщения.

### 5. Что хранит Gateway

У Gateway своя PostgreSQL-база, отдельная от Meetups, Identity и Notifications. В ней живут только операционные факты края:

- курсор диалога: шаг, ссылка на черновик в Meetups, ключ незавершённой команды создания, версия строки;
- дедупликация `update_id`;
- ключ идемпотентности команды, который Gateway выдал до первого вызова соседа;
- журнал попыток доставки уведомлений;
- при polling — offset `getUpdates`.

Черновик, атрибуты, расписание и видимость сходки в Gateway не копируются. Redis не вводится: эти записи обязаны пережить рестарт, а отдельный operational stack ради TTL не окупается.

### 6. Диалог и конкурентность

Курсор адресуется человеком после разрешения identity. Конкурирующие update одного человека не держат транзакцию базы на время сетевого вызова: версия строки курсора проверяется оптимистично, проигравший повторно читает курсор и решает, применимо ли его намерение.

`callback_data` несёт намерение, идентификатор ресурса и версию экрана, но не снимок атрибутов. Нажатие на старое сообщение перерисовывает текущее состояние, как требует кадр E-04. Точная укладка в 64 байта — технический дизайн.

### 7. Идемпотентность

Два разных повтора закрываются двумя механизмами.

**Повтор того же Telegram update** — уникальность `update_id` в базе Gateway. Telegram может прислать тот же update снова; второй раз юзкейс не выполняется.

**Повтор намерения создать черновик** — ключ команды. Двойное нажатие даёт два разных `update_id`, поэтому дедупликации update недостаточно. Gateway выдаёт ключ и записывает его в курсор **до** первого вызова Meetups. Повтор шага предъявляет тот же ключ. Meetups атомарно связывает ключ с результатом команды: повтор возвращает уже созданную сходку и не заводит вторую.

Формат ключа — [UUIDv7](ADR-020-uuidv7-identifiers.md). Требование к будущему контракту Meetups: команда создания принимает ключ и соблюдает эту ассоциацию. Transport команды этим ADR не выбирается.

### 8. Уведомления в том же процессе

Второй вход — собственный durable consumer шины, не общий с другими каналами. Поток обработки:

1. принять адресный факт Notifications;
2. разрешить внутренний идентификатор в Telegram id через Identity;
3. собрать текст, клавиатуру, deep link и кнопку категории из кода типа и данных;
4. отправить через тот же Bot API client, что и интерактивные ответы;
5. записать исход попытки.

Формулировки и раскладка клавиатуры живут в Gateway и версионируются вместе со словарём типов уведомлений, который остаётся межсервисным контрактом. Готовый текст из шины не читается.

Журнал попыток, retry и выбор между редким дублем и потерей принадлежат Gateway. Для MVP выбирается **редкий дубль вместо потери**: пропущенное напоминание о сходке хуже повторного сообщения. Человек, заблокировавший бота, получает терминальный отказ 403; повод Notifications при этом не гасится — обратных событий нет.

Один процесс, один bot token, один ограничитель Bot API. Интерактивный ответ не ставится в общую очередь позади веерной рассылки: лимит общий, но callback и reply имеют приоритет над фоновой доставкой. Точные интервалы retry и реакция на 429 — технический дизайн; правило одно: `retry_after` соблюдается, успешный юзкейс не откатывается из-за отказа Telegram отправить уже вычисленный ответ.

### 9. Общий код с Mini App и логирование

Mini App вне MVP, общего backend-транспорта нет. Браузер не ходит на внутренний gRPC. Когда Mini App появится, допустим общий package только для DTO представления, текстов, Telegram-идентификаторов и UI-состояния без инвариантов. Пакет не создаётся заранее.

Логи структурные. В них нет bot token, webhook secret, `initData`, полного JSON update и телефона. После разрешения identity в лог пишутся внутренний идентификатор и сквозной correlation id запроса. Telegram user id считается персональными данными и не является ключом поиска в логах.

### 10. Что этим ADR не решается

- transport операций Gateway → Meetups и точный wire-контракт command plane Notifications; вызов Identity остаётся синхронным gRPC по ADR-026;
- wire-контракты и имена subjects;
- физическая схема таблиц Gateway, кодировка `callback_data`, числа retry и timeout;
- судьба legacy-аукционных callback и удаление Rust-шлюза;
- исчезающие сообщения и Rich Messages — [PER-20](https://linear.app/anticnvm/issue/PER-20);
- контракт экранов будущих модулей сходки.

## Обоснование

**Имя не меняется.** Новое название не открывает новой границы и только расходится с уже принятыми документами.

**TypeScript + grammY остаётся.** Стек уже выбран владельцем для быстро меняющегося Telegram-края и будущего общего языка с Mini App. Rust на этом месте повторяет цену legacy без его аукционного смысла. Go и Python пригодны, но не дают принятого сочетания Telegram-экосистемы и типизированного представления. Conversations отвергнут, потому что replay обработчика конфликтует с правилом «черновик в Meetups, в Gateway только шаг».

**Два режима входа, а не один.** Webhook локально требует туннель и добавляет во inner loop чужой отказ. Polling в среде с HTTPS отказывается от повторной доставки со стороны Telegram и от проверки secret token, на которую опирается ADR-026. Режим без публичного входа оставляет polling, чтобы ADR не предписывал туннель до решения о hosting.

**Диспетчер приложения — названная граница, а не слой «на будущее».** Если юзкейс принимает `Context`, его нельзя прогнать без Telegram, и первый срез не докажет, что доменные правила живут не в Gateway. Отдельный процесс для юзкейсов удвоил бы деплой ради той же машины. Тест и CLI вызывают тот же диспетчер, что и адаптеры.

**Своя PostgreSQL, не Redis и не Meetups.** Курсор, ключ создания и журнал доставки обязаны пережить рестарт: иначе ломаются E-02, E-09 и доставка после рестарта канала. Redis был бы ещё одним стеком, из которого эти записи нельзя потерять. Класть шаг диалога и ключ создания в Meetups значит отдать краю чужой домен: Meetups начал бы знать про шаги формы бота.

**Ключ на обеих сторонах.** Дедупликация `update_id` закрывает повтор Telegram, но не двойное нажатие. Ключ только в Gateway закрывает повтор вызова, но не случай «команда прошла, ответ потерян»: сосед заведёт второй объект. Ассоциация в Meetups — то требование среза, которое нельзя выполнить на краю.

**Уведомления в том же процессе.** ADR-028 уже отдал каналу резолвинг, текст и журнал. Второй деплой ради десятков сообщений в день не окупается. Возврат доставки в Notifications вернул бы сервису Telegram API, от которого он отказался.

**Редкий дубль, не потеря.** Окно «отправили в Telegram, не записали исход» неустранимо. Для напоминания о сходке второе сообщение — видимый, но поправимый дефект; молчаливый пропуск — провал обещания MVP.

## Последствия

### Что становится проще

- юзкейс первого среза пишется и гоняется без Telegram-объектов;
- локальный запуск не зависит от публичного URL;
- черновик и шаг формы имеют по одному владельцу;
- повтор создания проверяется сквозным ключом, а не надеждой на один клик;
- канал уведомлений не требует отдельного сервиса и не конкурирует за чужой consumer;
- формулировки бота правятся без контракта Notifications.

### Что становится сложнее

- появляется четвёртая PostgreSQL-база и свой контур миграций;
- процесс обязан корректно работать в двух режимах входа;
- Meetups должен принять ключ идемпотентности в команде создания — это требование к ещё не спроектированному контракту;
- оптимистичная версия курсора не освобождает от гонки двух администраторов по самой сходке: её по-прежнему закрывает версия строки Meetups;
- диагностика «дошло ли уведомление» остаётся двухшаговой;
- общий Bot API limiter нужно проектировать так, чтобы рассылка не съедала лимит ответа на нажатие;
- presentation package с Mini App легко превратить в носитель доменных правил — это удерживается review, а не схемой.

## Предсказание и пересмотр

Ожидается, что курсора шага и ссылки на черновик хватит всем кадрам формы, что редкий дубль уведомления останется незаметным на масштабе одного сообщества, и что webhook понадобится только там, где уже есть публичный HTTPS.

Решение пересматривается, если:

- диалог начнёт хранить содержимое полей или ветвления, которым мало курсора — тогда отдельно решается более богатая модель, а не молчаливо включается Conversations;
- Meetups не сможет атомарно связать ключ с результатом — ломается E-09, и менять нужно контракт создания, а не только Gateway;
- hosting без входящего HTTPS станет постоянной средой, а Telegram перестанет отдавать пропущенные polling-апдейты за приемлемое окно — тогда нужен туннель или смена площадки;
- веерная рассылка начнёт вытеснять интерактивные ответы — выделяется отдельный процесс канала, а не меняется граница Notifications;
- появится Mini App с собственным backend-транспортом — этот ADR его не выбирает и не запрещает, кроме прямого доступа браузера к внутреннему gRPC.
