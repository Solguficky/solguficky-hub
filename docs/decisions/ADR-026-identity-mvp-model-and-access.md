# ADR-026: Модель Identity и проверка доступа в MVP

> **Дата:** 2026-08-20  
> **Статус:** Accepted

## Контекст

Identity должен разрешать Telegram user id во внутреннюю identity, хранить глобальную роль администратора и позволять вручную контролировать состав пользователей. Автоматическая проверка членства потребовала бы сделать бота администратором группы и дать ему доступ ко всей переписке независимо от Privacy Mode, что противоречит принципу минимальных привилегий.

У сервиса нет сложного домена, конкурирующих бизнес-команд или требования к истории. Однако параллельные Telegram updates могут одновременно попытаться создать профиль. Ник Telegram необязателен, изменяем и переиспользуем, поэтому не может быть ключом. Факты доступа и роли чувствительны к устареванию.

## Варианты

- текущее состояние в PostgreSQL и синхронное разрешение identity при каждом действии;
- кэш фактов доступа в Gateway с TTL;
- подписанный контекст-токен;
- события Identity и локальные проекции у потребителей;
- автоматическая проверка membership через Bot API.

Для служебных операций рассматривались Identity CLI, защищённый endpoint и прямое редактирование БД. Для исключения человека — блокировка с отзывом роли, блокировка с сохранением роли и удаление профиля.

## Решение

- PostgreSQL — единственный источник истины. Профили, статус доступа и глобальные роли хранятся текущим состоянием в строках; чтение и запись используют те же таблицы.
- Внутренний UUIDv7 — междоменный ключ. Telegram user id — уникальная внешняя привязка. `username` nullable, не уникален и не используется для связи или авторизации.
- Регистрация происходит только при `/start` и выполняется атомарным upsert по Telegram user id. Параллельный или повторный `/start` возвращает ту же identity. Последующие действия не создают отсутствующий профиль и обновляют ник существующего только при изменении.
- Membership сообщества в MVP не моделируется. Профиль означает факт регистрации через `/start`; контроль состава ручной и постфактум. Ранняя рабочая формулировка про хранение membership в строках этим решением отклонена. Allowlist ников с ручным путём для людей без ника остаётся отложенным усилением.
- Исключение блокирует доступ, сохраняет профиль и автоматически отзывает активные глобальные роли. Повторный допуск сохраняет identity, но не восстанавливает роли.
- Роли хранятся отдельными записями с identity, видом роли, временем и субъектом выдачи и временем отзыва.
- Maintainer использует защищённый служебный gRPC endpoint для идемпотентной выдачи и отзыва ролей, блокировки и повторного допуска. Прямой SQL и hardcoded Telegram user ids не являются штатным путём.
- Gateway вызывает Identity синхронно по gRPC на каждом Telegram update, которому требуется продуктовое действие. Кэша фактов доступа нет. При недоступности Identity операция завершается fail-closed.
- Authentication выполняет Telegram, а Gateway устанавливает Telegram identity после проверки secret token вебхука. Identity не проверяет authentication material. Meetups принимает доменные authorization-решения.
- Identity не публикует событий в MVP и не использует CQRS, Event Sourcing, акторов или отдельную read model.

Wire-контракт, service authentication, timeout и точная схема проектируются перед реализацией отдельным contract change.

## Обоснование

Текущее состояние отвечает всем MVP-запросам и сохраняет изменяемые персональные данные в единственном владельце. Upsert закрывает реальную техническую гонку дешевле версий строк или акторов. Условное обновление ника не превращает неизменившееся чтение в запись.

Синхронная проверка нужна для продолжения текущего пользовательского действия. Запрос по уникальному ключу несопоставимо дешевле Telegram round trip, а устаревший кэш разрешений равнозначен пропущенной проверке. Пересматривать его следует по измеренному p95, а не заранее.

Сохранение заблокированного профиля удерживает стабильные междоменные ссылки. Автоматический отзыв роли исключает неожиданное восстановление административных полномочий после повторного допуска.

Защищённый endpoint сохраняет application invariants и допускает автоматизацию. Его цена — обязательная service authentication; поэтому endpoint нельзя считать публичным или реализовать до проектирования защиты.

## Последствия

### Что становится проще

- одна модель чтения и записи без проекций и согласования событий;
- стабильные ссылки переживают блокировку и повторный допуск;
- отзыв доступа начинает действовать со следующего обращения;
- схема явно препятствует использованию ника как identity key.

### Что становится сложнее

- доступность Identity входит в критический путь каждого продуктового действия;
- служебный endpoint требует отдельной защиты и аудита;
- ручная сверка не предотвращает первое обращение постороннего человека;
- блокированные профили требуют принятой retention-политики.

## Предсказание и пересмотр

Ожидается, что индексный lookup не будет заметен на фоне Telegram API. Кэш или токен рассматривается только если наблюдаемый p95 Identity существенно влияет на UX. Membership пересматривается при реальной потребности в премодерации; автоматическая проверка через Bot API требует отдельного изменения privacy-принципа. Исходящие события вводятся только при появлении потребителя, которому недостаточна синхронная проверка.
