# ADR-034: Представление бота — Rich Messages по умолчанию и плоский текст за тоглом

> **Дополнение:** 2026-10-03 решение распространено на бота аукциона — карточка лота идёт rich-сообщением, второй рендерер и тогл процесса у бота аукциона вводит перевёрстка его экранов; разбор — в разделе [«Дополнение 2026-10-03»](#дополнение-2026-10-03-область--оба-бота).

> **Дата:** 2026-09-06  
> **Статус:** Accepted

## Контекст

Продуктовая карточка сходки, центр уведомлений и вклад модуля в карточку упираются в словарь, которым бот рисует сообщение. [ADR-030](ADR-030-telegram-bot.md) проводит границу представления, но форму сообщений не выбирает. Варианты и живой прогон собраны в [RFC-003](../rfcs/RFC-003-bot-presentation-rich-blocks.md).

Слой C показал, что обычный бот отправляет `sendRichMessage` с `reply_markup` и кнопками в документе, читатель без Premium видит карточку и свой шёпот, desktop и mobile рисуют блоки. Offline-доставка шёпота и эфемерная команда остаются наблюдательными хвостами и гейт механики не держат.

Откат без второго рендерера дорог: карточка, настройки и секции модулей пришлось бы заново собирать плоским текстом и отдельными экранами. Детект клиента Bot API не даёт.

## Варианты

**1a только.** Продуктовая карточка остаётся `sendMessage` плюс inline-клавиатура. Нулевой риск, иерархия рисуется переносами строк, постеры и настройки не закрываются одним механизмом.

**1d только.** Все продуктовые экраны идут `sendRichMessage`. Одна реализация; если клиент режет блоки, откат — переписывание представления.

**1d плюс детект клиента.** Бот угадывает возможности получателя и выбирает рендерер на каждое сообщение. Bot API этого не сообщает; цена — ложные срабатывания и две реализации без надёжного входа.

**1d по умолчанию, 1a за тоглом процесса.** Одна экранная модель, два рендерера. Оператор переключает процесс целиком. Дефолт — rich.

**Вариант D макета.** Отдельная навигация «назад» из богатого документа. RFC-003 его не вводит; этот ADR тоже.

## Решение

Продуктовая карточка по умолчанию отправляется **`sendRichMessage`**. Та же экранная модель собирает второй рендерер в **`sendMessage`**. Режим выбирает **тогл процесса**, не детект клиента и не настройка на человека.

| Ось | Решение |
|---|---|
| Дефолт | **1d**, `sendRichMessage` |
| Второй рендерер | **1a**, `sendMessage` плюс inline-клавиатура |
| Переключение | конфигурация процесса, `TELEGRAM_BOT_PRESENTATION=rich\|plain`, дефолт `rich` |
| Деградация | операторский тогл, не 5b |
| Состояние экрана | **2a** из ADR-030: логика не строится на том, раскрыта ли секция у клиента |
| Навигация | уже выбранный вариант B; вариант D не вводится |
| Контракт модуля | не выбирается: 3a / 3b / 3c остаются открытыми |
| Экран настроек | не выбирается: 4a / 4b / 4c остаются открытыми |
| Макет | ревизия storyboard — отдельное решение владельца |

Представление принимает экранную модель — заголовок, поля, секции, действия — и вызывает один из двух рендереров. Юзкейсы по-прежнему не видят типы Telegram.

Правило разделения кнопок из RFC-003 остаётся в силе: в блок — то, что читают; в клавиатуру — то, что одновременно список и действие над элементом. В режиме `plain` действие из блока, которому негде стоять в тексте, уезжает в `reply_markup`. Одно действие в оба слоя не дублируется.

Правка на месте: rich — `editMessageText` с `rich_message`; plain — тот же метод с `text`. Отдельного `editRichMessage` нет.

grammY 1.46 уже типизирует `sendRichMessage`, `reply_markup` и `ephemeral_message_parameters`. Raw Bot API для этих вызовов не нужен.

`.proto` этим ADR не меняется.

## Обоснование

**Живой прогон снял гейт механики.** Сервер принял карточку в личке и в группе, Premium читателю не нужен, callback приходит и с клавиатуры, и из документа. Оставаться на 1a после этого — платить иерархией из переносов строк за риск, который проверка не подтвердила.

**Тогл дешевле детекта и дешевле одной реализации.** Две реализации — названная цена RFC-003. Она окупается тем, что откат — перезапуск процесса, а не переписывание экранов. Детект клиента (5b) ту же цену платит и врёт: Bot API возможности получателя не отдаёт. Всегда слать минимум (5c) отменяет смысл выбора 1d.

**Тогл процесса, не человека.** Per-user режим удвоил бы состояние края и потребовал бы хранилища, которого у компонента нет. Операторский флаг совпадает с «один экземпляр на токен» из ADR-030: переключили процесс — переключили всех, кого он обслуживает.

**2a не пересматривается.** Сворачиваемые секции — содержимое. Решение бота не зависит от того, раскрыта секция или нет: это уже следует из состояния в `callback_data`.

**3 и 4 не закрываются заодно.** 1d разблокирует 3b и 4b, но не выбирает их. Контракт модуля попадает в `.proto`; экран настроек — отдельный продуктовый вопрос. Вариант D из макета по-прежнему не вводится.

## Последствия

### Что становится проще

- постеры, таблица полей и сворачиваемые секции закрываются одним методом;
- правка карточки на месте не меняет `message_id`;
- откат на плоский текст не требует нового ADR: меняется значение тогла;
- юзкейс и экранная модель пишутся один раз.

### Что становится сложнее

- два рендерера: каждое новое поле экрана собирается дважды;
- в `plain` пропадают стили кнопок документа и раскладка «кнопка у секции»; список-как-действие остаётся только в клавиатуре;
- место до сгиба и бюджет длины — общие ресурсы карточки и будущих секций модулей;
- ревизия макета не входит в это решение и до отдельного выбора владельца расходится с дефолтной механикой.

## Предсказание и пересмотр

Ожидается, что дефолтного rich хватит desktop и mobile без Premium, а тогл понадобится как операторский откат, а не как повседневный режим.

Решение пересматривается, если:

- клиент режет блоки или ломает клавиатуру на карточке — дефолт возвращается к 1a, rich остаётся за тоглом или снимается;
- тогл ни разу не понадобился после появления продуктовой карточки — второй рендерер можно удалить отдельным решением;
- понадобился разный режим разным людям в одном процессе — это уже не конфигурация, а хранилище, и упирается в ADR-030.

Offline-доставка шёпота и `BotCommand.is_ephemeral` сами по себе пересмотром не являются: это хвосты наблюдения, не гейт.

## Дополнение 2026-10-03: область — оба бота

Раздел дописан после принятия и текст выше не меняет: он называет, на какие боты решение действует. Выбор сделал владелец на чекпоинте плана [PER-450](https://linear.app/anticnvm/issue/per-450).

ADR принят, когда бот был один, и говорит о «продуктовой карточке» без имени бота. [ADR-044](ADR-044-two-telegram-bots-and-shared-auction-screens.md) завёл второй бот, а [дизайн-код](../design/bot/design-code.md#показ-фото-лота) выбрал для карточки лота rich-сообщение, в котором изображение стоит через `media`; лот без изображения — та же карточка без `media`. Отсюда вопрос, которого раньше не было: обязан ли бот аукциона вторым рендерером.

**Решение: правило одно на оба бота.** Карточка лота по умолчанию уходит `sendRichMessage`, та же экранная модель собирается вторым рендерером в `sendMessage`, режим выбирает тогл процесса бота аукциона. Тогл у каждого процесса свой: боты — разные процессы с разной конфигурацией, и откат одного не трогает другой. Имя переменной выбирает реализация; у бота хаба она сегодня называется `HUB_BOT_PRESENTATION`, а не `TELEGRAM_BOT_PRESENTATION` из таблицы решения.

**Срок.** Сегодня у бота аукциона нет ни rich-карточки, ни тогла: карточка лота — сообщение-фото с подписью. Второй рендерер и тогл вводит перевёрстка экранов аукциона ([PER-465](https://linear.app/anticnvm/issue/per-465)) вместе с самой rich-карточкой, а не раньше: тогл без rich-рендерера переключать нечего.

**Отвергнуто: бот аукциона только с rich.** Один рендерер дешевле, но возвращает цену, которую ADR уже назвал: откат при клиенте, который режет блоки, становится переписыванием экрана, а не перезапуском процесса. У карточки лота откат нужнее, чем у карточки сходки: она несёт цену и срок торгов.

**Что не меняется.** Остальные экраны обоих ботов — обычные сообщения с HTML-разметкой: rich остаётся формой карточки сходки и карточки лота, это сужение принадлежит дизайн-коду. Сигналы пересмотра прежние и читаются по каждому боту отдельно.
