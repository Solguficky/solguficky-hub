# ADR-021: .NET Aspire для локальной оркестрации

**Дата**: 18.07.2026

**Статус**: Принято

#### Контекст

Локальный запуск платформы сейчас держится на трёх независимых docker-compose файлах (корневой + `services/auction-service/docker-compose.yml` + `services/notifications-service/docker-compose.yml`), которые разошлись по портам, именам сетей и версиям образов NATS/PostgreSQL. Топология «что поднять для конкретной задачи» каждый раз собирается руками, нет единого дашборда логов/трейсов, а строки подключения копипастятся между compose-файлами и `appsettings.json`.

**Требования:**
- Один источник правды для локальной топологии.
- Гибкость: возможность поднять только инфраструктуру (NATS + PostgreSQL) и запускать сервисы руками из IDE, либо поднять весь стек одной командой.
- Единое место для логов/трейсов/health при полном запуске.
- Задел на генерацию артефактов для возможного будущего деплоя на k3s, без завязки на него сейчас; актуальная граница local / production-like / hosting описана в `docs/architecture/infrastructure.md`.

#### Рассмотренные варианты

**1. Статус-кво: докрутить docker-compose (единый файл + `.env`-профили)**
- ✅ Ничего нового не изучать, инструмент уже знаком.
- ✅ Не тянет дополнительный .NET AppHost-проект в репозиторий.
- ⚠️ Строки подключения и порты по-прежнему копипастятся вручную между compose и `appsettings`.
- ⚠️ Нет встроенного дашборда логов/трейсов — пришлось бы отдельно поднимать Loki/Grafana даже для лёгкой отладки.
- ⚠️ Топология «Local/Container/Off» на компонент через `.env`/profiles реализуема, но неудобно читается и легко рассинхронизируется вручную.

**2. Tilt**
- ✅ Популярен для смешанных (build from source + containers) топологий, live-reload.
- ⚠️ Ещё один язык конфигурации (Tiltfile на Python-подобном Starlark) поверх уже полиглотного стека.
- ⚠️ Не даёт нативного OTel-дашборда — трейсы всё равно нужно подключать отдельно.
- ⚠️ Не решает задачу «строки подключения сами прорастают в сервисы» — service discovery всё равно на compose/DNS.

**3. k3d (локальный k3s)**
- ✅ Ближе всего к целевой прод-топологии (k3s), меньше расхождений dev/prod.
- ⚠️ Избыточная сложность для ежедневной разработки пет-проекта (Helm/манифесты вместо одного `docker-compose up`).
- ⚠️ Решение о деплое ещё не принято (отдельный ADR «Хостинг»), рано жёстко привязываться к Kubernetes в dev-контуре.

**4. .NET Aspire (13.x)**
- ✅ Один AppHost-проект на C# — топология описывается кодом, а не YAML/DSL: `AddProject`, `AddExecutable`/`AddDockerfile` для Rust-gateway, контейнерные ресурсы для NATS/PostgreSQL.
- ✅ Service discovery и строки подключения инжектятся автоматически через `WithReference`, не копипастятся.
- ✅ Dashboard из коробки: логи, OTel-трейсы, health — закрывает то, ради чего сейчас поднимается отдельный Loki/Grafana для локальной отладки.
- ✅ `aspire publish` умеет генерировать docker-compose/Kubernetes-манифесты из той же топологии — задел на k3s-деплой без решения о нём сейчас.
- ✅ C# — родной язык для владельца проекта, минимальный порог входа по сравнению с Tilt/Starlark.
- ⚠️ Ещё одна версионируемая зависимость (Aspire CLI/SDK), которая заметно обновляется между минорными версиями.
- ⚠️ Полноценный OTel для Rust-шлюза Aspire не даёт «из коробки» — телеграм-гейтвей пока остаётся вне трассировки.

#### Решение

Используем **.NET Aspire** как единственный инструмент локальной оркестрации. AppHost-проект — в `infra/apphost/`. NATS и PostgreSQL — всегда контейнерные ресурсы Aspire; C#-сервисы и Rust-шлюз получают три режима на компонент (`Local`/`Container`/`Off`), управляемые параметрами AppHost без правки кода топологии. Текущее состояние режимов и профиль запуска описаны в `docs/development/local-development.md`.

Рукописные docker-compose файлы (`docker-compose.yml`, `services/auction-service/docker-compose.yml`, `services/notifications-service/docker-compose.yml`) удаляются по итогам миграции; при необходимости compose-файл генерируется через `aspire publish`.

#### Обоснование

1. **Устраняет копипасту, а не переносит её.** Три рукописных compose-файла с разными портами/сетями/версиями образов — сейчас источник рассинхронизации. Aspire даёт один AppHost-проект вместо трёх YAML.
2. **Dashboard закрывает наблюдаемость для dev-контура бесплатно.** Не нужно отдельно поднимать Loki/Grafana (`docker-compose.logging.yml`) ради просмотра логов при локальной отладке — это остаётся для прод/staging сценария.
3. **C# — родной язык владельца**, порог входа в AppHost-код ниже, чем в Tiltfile или Kubernetes-манифесты.
4. **Не привязывает к проду преждевременно.** `aspire publish` — генерируемый артефакт, а не решение о деплое; выбор k3s/другой платформы остаётся за отдельным ADR «Хостинг».
5. **Учебная ценность.** Событие/акторы уже изучаются через auction-service; Aspire — актуальный инструмент экосистемы .NET, знание которого пригодится и вне пет-проекта.

#### Последствия

**Позитивные:**
- ✅ Единая точка правды для топологии, меньше расхождений между окружениями разработчиков.
- ✅ Логи и трейсы C#-сервисов видны в одном дашборде без дополнительной настройки.
- ✅ Документы интеграции, ADR и сервисные `AGENTS.md` обновляются один раз, а не в трёх compose-файлах.

**Негативные:**
- ⚠️ Aspire CLI/SDK версионируется агрессивно (минорные релизы могут ломать API) — версия фиксируется явно в `infra/apphost/apphost.csproj` и обновляется осознанно, не автоматически.
- ⚠️ Windows-специфичные риски (интеграция `cargo`-исполняемого файла через `AddExecutable`) проверяются на итерации 2 плана, до полировки остального.
- ⚠️ Rust-шлюз не получает OTel-трейсы автоматически — остаётся в scope будущей работы, не блокирует текущую миграцию.

**Миграционный путь:** выполненные шаги и оставшийся проверочный gate поддерживаются в `docs/development/local-development.md`; задачи и приоритеты миграции ведутся в Linear.
