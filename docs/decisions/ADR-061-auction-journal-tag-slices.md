# ADR-061: Теги журнала лота Auction — четыре среза по номеру среза Pekko

> **Дата:** 2026-10-03  
> **Статус:** Accepted

## Контекст

[ADR-045](ADR-045-auction-scala-pekko-persistence-jdbc.md) выбрал Pekko Persistence JDBC. Глобальное чтение журнала у этого плагина строится только на тегах: read journal даёт `eventsByPersistenceId`, `eventsByTag` и `persistenceIds`, а запросы по срезам принадлежат другим плагинам. Тег пишется строкой `event_tag` в момент append. Поэтому схема тегов — часть формата журнала: её смена после первого production-события означает переписывание строк, а не правку конфигурации. [ADR-058](ADR-058-auction-journal-row-json-storage-model.md) оставил строку без тегов и отложил выбор до первой проекции.

Первая проекция — read model лота ([PER-324](https://linear.app/anticnvm/issue/per-324)): `GetLot` и `ListAuctionLots` читают её, а offset хранится в той же базе и обновляется одной транзакцией с read model (`JdbcProjection.exactlyOnce`). Следом журнал будут читать публикация фактов в шину ([PER-331](https://linear.app/anticnvm/issue/per-331)) и трансляция изменений лота ([PER-335](https://linear.app/anticnvm/issue/per-335)). Каждая из них держит свой offset на тег и читает те же теги.

Масштаб первого мероприятия — до 50–100 подключений к экрану на одном узле ([ADR-040](ADR-040-auction-screen-sse.md)), кластер одноузловой (ADR-045).

## Варианты

Общее допущение вариантов: проекция читает журнал через `eventsByTag` этого плагина. Чтение по `persistenceIds` с перебором лотов не рассматривается: оно не даёт одного offset на поток и требует своего учёта позиций по каждому лоту — ту работу, которую тег и offset проекции делают готовыми.

- **Т1. Один тег `lot`.** Одна проекция, одна строка offset, один опрос базы. Цена: каждая проекция журнала лотов навсегда остаётся одним потоком. Распараллелить её позже можно только перетегированием записанных строк и полным replay, а перестройка read model по команде вынесена в К2.
- **Т2. Фиксированные срезы `lot-0..lot-N-1`.** Лот попадает ровно в один срез, все его события — под одним тегом, поэтому порядок событий лота проекция видит в порядке журнала. На каждый тег — свой экземпляр проекции под `ShardedDaemonProcess`. Цена — N опросов базы и N строк offset на проекцию.
- **Т3. Тег на лот или на аукцион.** Даёт выборку одного лота или одного аукциона, но проекция по таким тегам требует экземпляра на тег, а число тегов растёт с данными. Для потока «все лоты» не годится.

## Решение

Принят **Т2** с N = 4. Владелец выбрал его 2026-10-03 на чекпоинте плана PER-324.

1. Тег лота — `lot-<slice % 4>`, где `slice` — номер среза, который Pekko сама считает по persistence id (`Persistence.sliceForPersistenceId`, 1024 среза). Своей хеш-функции у сервиса нет.
2. Тег ставит entity лота через `withTagger`. Он один на лот и не зависит от события.
3. Каждая проекция журнала лотов запускает по экземпляру на тег под `ShardedDaemonProcess`; `projection_key` её offset — тег.
4. События аукциона ([PER-325](https://linear.app/anticnvm/issue/per-325)) получат своё семейство тегов по тому же правилу, а не теги лотов: проекции выбирают типы агрегатов независимо, а порядка между агрегатами журнал всё равно не даёт.

## Обоснование

Цена ошибки в N несимметрична. Любая смена числа срезов переносит лоты в другие теги: записанные строки `event_tag` остаются со старыми тегами, а offset новых экземпляров начинается с нуля, так что смену сопровождает переписывание `event_tag`. Четыре среза на одном узле стоят четыре лёгких опроса базы на интервал чтения, а взамен каждая следующая проекция получает запас параллелизма без миграции журнала. Т1 дешевле сегодня, но фиксирует один поток навсегда для всех проекций, включая публикацию в шину. Т3 решает другую задачу — выборку по ключу, — и для неё есть read model.

Номер среза взят у Pekko, а не своей формулой: формула держит формат журнала, и её стабильность — забота библиотеки, которая обещает её для своих же запросов по срезам. Литерал тега для фиксированного лота держит L1-тест: он падает при любой смене формулы.

## Последствия

### Что становится проще

- Новая проекция журнала лотов — ещё один `ShardedDaemonProcess` на те же четыре тега, без правки журнала.
- Застрявший срез не останавливает остальные: экземпляры независимы и рестартуют по отдельности.
- Отставание видно по тегу: метрика `auction.projection.events_behind` несёт тег атрибутом.

### Что становится сложнее

- Порядок событий есть только внутри лота. Проекция, которой нужен порядок между лотами, должна получать его из данных, а не из потока.
- `eventsByTag` плагина отдаёт события по `ordering` и ждёт ещё не закоммиченные номера `max-tries × query-delay` (в сервисе — 50 × 200 мс, около десяти секунд). Транзакция журнала, закоммиченная позже этого окна, оставляет в потоке тега дыру, и событие из потока не придёт. Проекция лота это переживает: на пропуске номера обработчик дочитывает недостающие события лота из журнала по persistence id. Без этого одна такая дыра останавливала бы весь тег. Каждая следующая проекция журнала лотов обязана так же не верить потоку тега на пропуске номера.
- События, записанные до этого решения, тегов не несут. Лот, у которого такие события есть, попадает в проекцию со своим первым тегированным событием, а предыдущие обработчик дочитывает из журнала. Лот, у которого после решения нет ни одного события, в read model не появится. Production-событий до решения нет.

## Предсказание и пересмотр

Ожидаем, что четырёх срезов хватит на весь первый год: ни одна проекция не упрётся в один поток на одном узле.

Пересмотр — на одном из сигналов:

- отставание `events_behind` одного тега держится выше нуля под нормальной нагрузкой, и причина — пропускная способность обработчика, а не отказ;
- появится второй узел кластера и понадобится распределять срезы между узлами;
- переход на плагин с запросами по срезам (`eventsBySlices`) — тогда теги перестают быть единственным способом глобального чтения.
