# ADR-036: Временный bootstrap первого администратора из конфигурации

> **Дата:** 2026-09-09  
> **Статус:** Accepted

## Контекст

[ADR-026](ADR-026-identity-mvp-model-and-access.md) отдал выдачу глобальной роли администратора maintainer'у через защищённый служебный endpoint и запретил hardcoded-список Telegram user id «ни при каких условиях». Bootstrap через переменную окружения поэтому сняли в [PER-46](https://linear.app/anticnvm/issue/per-46). Служебный endpoint ждёт решения [PER-30](https://linear.app/anticnvm/issue/per-30) в milestone «MVP реализован и проверен локально». Миграция роль не выдаёт: `granted_by` ссылается на `profiles(id)`, а профиля maintainer'а в схеме нет.

В срезе не осталось пути получить первого администратора. Наблюдаемый результат [PER-40](https://linear.app/anticnvm/issue/per-40) — администратор заводит и публикует сходку — без этой роли не проверяется. Штатный механизм аутентификации endpoint здесь не выбирается: это [PER-30](https://linear.app/anticnvm/issue/per-30). Whitelist, инвайт-токены и премодерация остаются за [PER-76](https://linear.app/anticnvm/issue/per-76).

Выбор зафиксирован задачей реализации [PER-167](https://linear.app/anticnvm/issue/per-167), которую завёл владелец до этой записи.

## Варианты

### A. Поднять PER-30 и служебный endpoint в этот milestone

Закрыть [PER-30](https://linear.app/anticnvm/issue/per-30) здесь, затем реализовать endpoint и выдать роль штатным путём ADR-026.

| | |
|---|---|
| **Цена** | Сначала выбрать service authentication, затем спроектировать и реализовать endpoint, затем выдать роль. Срез ждёт весь этот контур. |
| **Что нарушает в ADR-026** | Ничего: это и есть принятый путь. |
| **Что не нарушает** | Запрет hardcoded-списка, запрет SQL как штатного пути, границу «роль выдаёт maintainer, а не бот». |
| **Негативный исход** | [PER-40](https://linear.app/anticnvm/issue/per-40) остаётся непроверенным до milestone 4. Если механизм выбрать под давлением среза, «удобно локально» станет дырой в проде — именно этот риск [PER-30](https://linear.app/anticnvm/issue/per-30) выносит отдельно. |

Это вариант, который выглядит очевидным: «сделать то, что уже решено». Он не разблокирует срез. Задача [PER-163](https://linear.app/anticnvm/issue/per-163) прямо говорит: если выбрать его, решение закрывается этим выводом, а механизм выбирает сама [PER-30](https://linear.app/anticnvm/issue/per-30). Наблюдаемый результат [PER-40](https://linear.app/anticnvm/issue/per-40) от этого не появляется.

### B. Временная maintainer-операция в процессе Identity

Необязательная `IDENTITY_ADMIN_TELEGRAM_USER_ID`. При `ResolveIdentity` совпавшего Telegram id атомарно создаётся первая активная роль `admin`. Операция снимается вместе с появлением штатного endpoint.

| | |
|---|---|
| **Цена** | `ResolveIdentity` на время среза становится путём выдачи роли. Telegram user id живёт в конфигурации процесса. `granted_by` указывает на тот же профиль: схема требует существующий `profiles.id`, а другого субъекта выдачи нет. |
| **Что нарушает в ADR-026** | Запрет hardcoded-списка Telegram user id «ни при каких условиях» — переменная окружения это список длины один. Утверждение, что `ResolveIdentity` роли не выдаёт. |
| **Что не нарушает** | Границу «роль выдаёт maintainer, а не администратор в боте». Запрет SQL как штатного пути. Запрет веб-админки. То, что роль после выдачи живёт строкой в `identity_roles`, а не списком в коде. |
| **Негативный исход** | Переменная, которую забыли снять после endpoint, остаётся чёрным входом: кто задаст id и перезапустит процесс, получит роль. Утечка значения — Aspire dashboard, `.env`, дамп процесса. Наивная реализация восстановит отозванную роль следующим `/start`. |

Разовая команда `just` / SQL после `/start` — соседний вид той же операции. Он не кладёт Telegram id в конфигурацию и не делает `ResolveIdentity` путём выдачи, но требует второй шаг после каждого сброса базы и не автоматизирует проверку среза через Aspire. `granted_by` упирается в ту же схему. Владелец этот вид отверг, заведя [PER-167](https://linear.app/anticnvm/issue/per-167) именно как переменную окружения.

### C. Разовое отступление на прямой SQL

Maintainer один раз вставляет строку в `identity_roles` после того, как человек нажал `/start`.

| | |
|---|---|
| **Цена** | Нулевая в коде. Знание живёт у того, кто выполнил запрос. |
| **Что нарушает в ADR-026** | «Прямой SQL не является штатным путём ни для одной из групп». |
| **Что не нарушает** | Запрет hardcoded-списка: id не хранится в репозитории и не читается процессом. `ResolveIdentity` роли не выдаёт. |
| **Негативный исход** | После `aspire run` с чистой базой роли нет. Проверка [PER-40](https://linear.app/anticnvm/issue/per-40) зависит от скрытого ручного шага, которого нет в репозитории. Следующая сессия или другой исполнитель срез не воспроизведут. |

### D. Проверять PER-40 на профиле с ролью, проставленной в локальной базе

Не вводить пути в продукт. Администратор среза — заранее подготовленная строка в чьей-то локальной базе.

| | |
|---|---|
| **Цена** | Нулевая в коде и в репозитории. |
| **Что нарушает в ADR-026** | Ничего в тексте: путь в продукт не появляется. Нарушает предусловие среза из [first-slice.md](../architecture/first-slice.md): роль выдана maintainer'ом как данные, которые можно получить, запустив срез. |
| **Что не нарушает** | Запрет hardcoded-списка, запрет SQL как штатного пути, границу выдачи ролей. |
| **Негативный исход** | Milestone «Первый вертикальный срез работает» нельзя подтвердить из чистого дерева. CI, чужой клон и свежий Aspire остаются без администратора. Это не путь, а отказ от пути. |

## Решение

До появления служебного endpoint первый администратор среза появляется **временным bootstrap из конфигурации**.

- Необязательная `IDENTITY_ADMIN_TELEGRAM_USER_ID`. Пустое или отсутствующее значение bootstrap выключает. Некорректное заданное значение останавливает процесс.
- При `ResolveIdentity` для совпавшего Telegram id атомарно создаётся первая активная запись роли `admin`. Повторные и параллельные вызовы идемпотентны.
- Отозванная роль следующим `ResolveIdentity` не восстанавливается.
- `granted_by` указывает на тот же профиль. Это названная цена схемы: колонка обязана ссылаться на `profiles(id)`, а профиля maintainer'а нет.
- Значение Telegram id в лог не идёт.
- Параметр передаётся через AppHost. Реализация — [PER-167](https://linear.app/anticnvm/issue/per-167).
- Bootstrap **удаляется** вместе с реализацией штатного endpoint. Выбор механизма аутентификации остаётся за [PER-30](https://linear.app/anticnvm/issue/per-30) в её milestone.

ADR-026 в силе для модели доступа, премодерации и штатной выдачи ролей. Это решение временно исключает только запрет hardcoded-списка и утверждение, что `ResolveIdentity` роли не выдаёт — и только для первой выдачи в срезе.

## Обоснование

Вариант A отвергнут, хотя он единственный ничего не нарушает. Он отвечает на другой вопрос: как защитить штатный endpoint. Срезу нужен администратор в этом milestone, а не выбранный механизм service authentication. Поднять [PER-30](https://linear.app/anticnvm/issue/per-30) сюда — значит либо задержать [PER-40](https://linear.app/anticnvm/issue/per-40), либо выбрать защиту под давлением проверки сходки.

Вариант D отвергнут, потому что это отказ от воспроизводимого среза. Вариант C отвергнут по той же причине в более мягкой форме: путь есть, но его нет в репозитории и он не переживает сброс базы.

Вариант B нарушает самый жёсткий запрет ADR-026. Он выбран потому, что среди путей, которые вообще появляются в свежем запуске, это единственный, который:

- оставляет роль данными в `identity_roles`, а не проверкой списка на каждом запросе;
- оставляет выдачу за maintainer'ом — он задаёт переменную, а не нажимает в боте;
- переживает сброс базы Aspire: после `/start` роль появляется снова, пока переменная задана и роль не отозвана;
- уже был спроектирован в [PER-46](https://linear.app/anticnvm/issue/per-46) и снят только из-за конфликта с ADR-026, а не потому что устройство не работало.

Цена нарушения названа и ограничена: один идентификатор в конфигурации, одна операция, снятие вместе с endpoint, запрет восстанавливать отозванное.

## Последствия

### Что становится проще

- свежий Aspire-запуск среза получает администратора после `/start` совпавшего Telegram id;
- [PER-40](https://linear.app/anticnvm/issue/per-40) проверяется без ручной правки базы и без ожидания [PER-30](https://linear.app/anticnvm/issue/per-30);
- роль после выдачи читается как обычная строка `identity_roles`; повторный `/start` вторую запись не создаёт.

### Что становится сложнее

- `ResolveIdentity` временно совмещает разрешение личности и выдачу роли;
- журнал выдачи врёт: `granted_by` указывает на получившего, а не на maintainer'а;
- переменная — секрет эксплуатации: её значение нельзя писать в лог и нельзя оставить после появления endpoint;
- забытое снятие bootstrap после [PER-30](https://linear.app/anticnvm/issue/per-30) превращает временное исключение в постоянный чёрный вход;
- продукт формально обещает роль без списка Telegram id, а срез до снятия переменной этот список длины один держит в конфигурации.

## Предсказание и пересмотр

Ожидается, что переменная будет задана только в локальном контуре владельца и в явном тестовом окружении, а в любой развёрнутой среде её не будет.

Решение снимается, когда появляется штатный endpoint из [PER-30](https://linear.app/anticnvm/issue/per-30): переменная, ветка выдачи в `ResolveIdentity` и документация запуска удаляются тем же изменением, что и endpoint. Пересмотр раньше — если переменная окажется заданной вне локального контура; если отозванная роль восстановится; если значение попадёт в лог.
