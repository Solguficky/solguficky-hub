# ADR-020: UUIDv7 вместо ULID для идентификаторов

**Дата**: 18.07.2026

**Статус**: Принято. Заменяет ADR-019 в части формата ID (разделение Meetup/Auction из ADR-019 остаётся в силе).

#### Контекст

ADR-019 выбрал ULID как формат ID аукционов (а в будущем — сходок): нужны локальная генерация без похода в БД и сортируемость по времени (локальность индекса, естественный порядок для Event Sourcing). ULID эти свойства даёт, но это нестандартный формат — в каждом языке нужна сторонняя библиотека. Проект полиглотный (сейчас C#, Rust, Python; в планах Go, Kotlin, Ruby, Elixir), и каждая новая интеграция тянет за собой поиск и поддержку ULID-библиотеки.

В мае 2024 вышел RFC 9562, стандартизовавший UUIDv7 — UUID с тем же устройством, что у ULID (48 бит unix-timestamp в мс + случайные биты), и той же сортируемостью по времени. Поддержка нативная почти везде: `Guid.CreateVersion7()` в .NET 9+, крейт `uuid` с фичей `v7` в Rust, `uuid.uuid7()` в Python 3.14+ (до этого — пакет `uuid6`), функция `uuidv7()` в PostgreSQL 18+.

Боевых данных нет, ID в контрактах — `string`, поэтому миграция сейчас дешёвая; с появлением реальных данных она станет заметно дороже.

#### Рассмотренные варианты

1. **Оставить ULID** — код уже работает; но нестандарт, сторонняя зависимость в каждом языке, вечный «налог» на полиглотность.
2. **UUIDv7** — те же свойства (локальная генерация, time-ordered), стандарт IETF, нативная поддержка в рантаймах и PostgreSQL 18+; минус — строка длиннее (36 символов против 26).
3. **UUIDv4** — нативен ещё шире, но не сортируется по времени: фрагментация индекса и потеря естественного порядка в ES — свойство, ради которого выбирали ULID, теряется.

#### Решение

Заменить ULID на **UUIDv7 (RFC 9562)** для всех генерируемых сервисами ID (аукционы, будущие сходки).

**Контрактный формат**: канонический строковый UUID — 36 символов, lowercase, с дефисами (`0198f2a4-7c1e-7d3a-9b21-4f8e12ab34cd`). В Protobuf ID остаётся `string`.

**Генерация**: только нативными средствами — `Guid.CreateVersion7()` (C#), `uuid::Uuid::now_v7()` (Rust), `uuid6.uuid7()` / `uuid.uuid7()` (Python).

**Парсинг на границах** (NATS/gRPC): `Guid.TryParse` + ответ с ошибкой вместо необработанного исключения.

**Хранение**: в PostgreSQL ID пока остаётся строкой; переход на нативный тип `uuid` — отдельный пункт техдолга (при появлении Meetups Service).

#### Обоснование

Ключевой аргумент — полиглотность: единственное преимущество ULID перед UUIDv7 (компактность строки) не окупает стороннюю зависимость в каждом из 4–7 языков стека. UUIDv7 даёт идентичные свойства (локальная генерация, монотонность по времени, distributed-safe, idempotency) из стандартной библиотеки. Бонус: PostgreSQL 18+ понимает `uuidv7()` нативно, что упростит будущий переход колонок на тип `uuid`.

Миграция сделана сейчас, потому что данных нет и контракт не меняется (`string` остаётся `string`) — фактически меняется только генерация и парсинг.

#### Последствия

**Позитивные:**
- Ноль сторонних ID-библиотек во всех текущих и будущих сервисах
- Стандарт IETF — совместимость с инструментами, БД, логами из коробки
- Путь к нативному типу `uuid` в PostgreSQL

**Негативные:**
- Строка ID длиннее: 36 символов против 26 у ULID
- Смешение старых ULID и новых UUID в dev-журнале — лечится очисткой dev-БД (данных нет)
- `Guid.CreateVersion7()` требует .NET 9+ → апгрейд C#-сервисов с net8.0 (выполнен в рамках этой же миграции)

#### Связанные решения

- **ADR-019**: Разделение Meetup и Auction, формат ID — ULID (заменён в части формата ID)
- **ADR-002**: Event Sourcing для stateful-сервисов
- **ADR-007**: Полиглотная модель
- **ADR-023**: Публичный номер сходки рядом с UUIDv7 — уточняет это решение для сходок, не заменяя его
