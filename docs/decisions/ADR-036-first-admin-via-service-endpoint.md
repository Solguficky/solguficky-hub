# ADR-036: Первый администратор среза появляется только через служебный endpoint

> **Дата:** 2026-09-09  
> **Статус:** Accepted

## Контекст

[ADR-026](ADR-026-identity-mvp-model-and-access.md) отдал выдачу глобальной роли администратора maintainer'у через защищённый служебный endpoint и запретил hardcoded-список Telegram user id «ни при каких условиях». Bootstrap через переменную окружения поэтому сняли в [PER-46](https://linear.app/anticnvm/issue/per-46): `ResolveIdentity` роли не выдаёт. Служебный endpoint ждал [PER-30](https://linear.app/anticnvm/issue/per-30) в milestone «MVP реализован и проверен локально». Миграция роль не выдаёт: `granted_by` ссылается на `profiles(id)`, а профиля maintainer'а в схеме нет.

В срезе не осталось пути получить первого администратора, и наблюдаемый результат [PER-40](https://linear.app/anticnvm/issue/per-40) без роли не проверяется. Предыдущая итерация записала временный bootstrap из конфигурации и завела [PER-167](https://linear.app/anticnvm/issue/per-167); владелец отменил эту задачу: bootstrap противоречит PER-46 и больше не является выбором.

Штатный механизм аутентификации endpoint здесь не выбирается — это [PER-30](https://linear.app/anticnvm/issue/per-30). Whitelist, инвайт-токены и премодерация остаются за [PER-76](https://linear.app/anticnvm/issue/per-76).

## Варианты

### A. Поднять PER-30 и служебный endpoint в этот milestone

Закрыть [PER-30](https://linear.app/anticnvm/issue/per-30) в milestone среза, затем реализовать endpoint и выдать роль штатным путём ADR-026.

| | |
|---|---|
| **Цена** | Сначала выбрать service authentication, затем спроектировать и реализовать endpoint, затем выдать роль. [PER-40](https://linear.app/anticnvm/issue/per-40) ждёт весь этот контур. |
| **Что нарушает в ADR-026** | Ничего: это и есть принятый путь. |
| **Что не нарушает** | Запрет hardcoded-списка, запрет SQL как штатного пути, границу «роль выдаёт maintainer, а не бот», решение PER-46 не класть выдачу в `ResolveIdentity`. |
| **Негативный исход** | Срез не проверяется, пока не закрыты PER-30 и реализация endpoint. Если механизм выбрать под давлением проверки сходки, «удобно локально» станет дырой в проде — риск, который PER-30 выносит отдельно. |

### B. Временная maintainer-операция в процессе Identity

Необязательная `IDENTITY_ADMIN_TELEGRAM_USER_ID`. При `ResolveIdentity` совпавшего Telegram id атомарно создаётся первая активная роль `admin`.

| | |
|---|---|
| **Цена** | `ResolveIdentity` становится путём выдачи. Telegram user id живёт в конфигурации процесса. `granted_by` указывает на тот же профиль. |
| **Что нарушает в ADR-026** | Запрет hardcoded-списка «ни при каких условиях». Утверждение, что `ResolveIdentity` роли не выдаёт. |
| **Что не нарушает** | Границу «роль выдаёт maintainer, а не администратор в боте». Запрет SQL как штатного пути. |
| **Негативный исход** | Перечёркивает PER-46: горячий путь разрешения личности снова выдаёт права. Забытая переменная после endpoint — чёрный вход. |

### C. Разовое отступление на прямой SQL

Maintainer один раз вставляет строку в `identity_roles` после `/start`.

| | |
|---|---|
| **Цена** | Нулевая в коде. Знание живёт у того, кто выполнил запрос. |
| **Что нарушает в ADR-026** | «Прямой SQL не является штатным путём ни для одной из групп». |
| **Что не нарушает** | Запрет hardcoded-списка. `ResolveIdentity` роли не выдаёт. |
| **Негативный исход** | После сброса базы роли нет. Проверка среза зависит от скрытого шага вне репозитория. |

### D. Проверять PER-40 на профиле с ролью в локальной базе

Не вводить пути в продукт.

| | |
|---|---|
| **Цена** | Нулевая в коде и в репозитории. |
| **Что нарушает в ADR-026** | Ничего в тексте. Нарушает предусловие [first-slice.md](../architecture/first-slice.md): роль можно получить, запустив срез. |
| **Что не нарушает** | Запрет hardcoded-списка, запрет SQL, границу выдачи ролей. |
| **Негативный исход** | Milestone «Первый вертикальный срез работает» нельзя подтвердить из чистого дерева. Это отказ от пути. |

## Решение

Первый администратор появляется **только через защищённый служебный endpoint** из ADR-026.

- `ResolveIdentity` роли не выдаёт и не восстанавливает. Повторный `/start` возвращает только активные записи.
- Hardcoded-список Telegram user id, переменная окружения с Telegram id и выдача из `ResolveIdentity` запрещены. [PER-167](https://linear.app/anticnvm/issue/per-167) отменена и не возвращается.
- Прямой SQL и заранее проставленная локальная роль не являются путём среза.
- Человек сначала регистрируется через `/start`, затем maintainer выдаёт роль по внутреннему идентификатору.
- [PER-30](https://linear.app/anticnvm/issue/per-30) поднимается в milestone «Первый вертикальный срез работает». Механизм аутентификации endpoint эта запись не выбирает — его выбирает сама PER-30.
- Реализация endpoint и вызов выдачи заводятся после PER-30. До закрытия PER-30 контракт служебных операций не пишется.

ADR-026 не исключается и не переписывается. Это решение применяет его к срезу и отвергает временные швы.

## Обоснование

Вариант B отвергнут владельцем: он противоречит PER-46 и самому жёсткому запрету ADR-026. Временный шов, который потом снимают вместе с endpoint, уже один раз породил пустой путь — когда bootstrap сняли, а endpoint ещё не подняли.

Варианты C и D отвергнуты по той же причине, что и B в мягкой форме: срез должен воспроизводиться из репозитория, а не из чьей-то базы, и временное отступление не должно становиться единственным путём.

Вариант A — единственный, который не создаёт второй механизм выдачи. Его цена названа: [PER-40](https://linear.app/anticnvm/issue/per-40) ждёт PER-30 и последующую реализацию. Эта цена принята сознательно. PER-30 при этом остаётся решением про authentication, а не про «секрет в env, чтобы завтра опубликовать сходку»: ослабленный endpoint под давлением среза запрещён тем же текстом PER-30, который выносит риск «удобно локально → дыра в проде».

## Последствия

### Что становится проще

- один путь выдачи на срез и на MVP: maintainer, служебный endpoint, роль как данные;
- `ResolveIdentity` остаётся разрешением личности, как зафиксировала PER-46;
- нечего снимать после появления endpoint — временного bootstrap в коде нет.

### Что становится сложнее

- наблюдаемый результат PER-40 нельзя проверить, пока не закрыты PER-30 и реализация endpoint;
- в milestone среза появляется задача из зонта [PER-76](https://linear.app/anticnvm/issue/per-76): endpoint нужен сходке, но принадлежит модели доступа;
- `granted_by` по-прежнему требует существующий профиль; чем endpoint назовёт субъекта выдачи — вопрос реализации после PER-30, не этой записи.

## Предсказание и пересмотр

Ожидается, что PER-30 закроется в том же milestone, что и срез, и реализация endpoint успеет до проверки PER-40.

Пересмотр — если PER-30 упрётся в инфраструктуру, которой в MVP нет, и endpoint нельзя защитить без нового контура; либо если проверка PER-40 понадобится раньше, чем появится вызываемый endpoint. Возврат к bootstrap из конфигурации этой записью не допускается: он уже отвергнут.
