# ADR-016: Архитектура RBAC для MVP + Action паттерн для тестируемости

> **Текущая применимость:** Legacy scope. Hardcoded-роли заменены [ADR-026](ADR-026-identity-mvp-model-and-access.md); остальные решения этого ADR относятся к legacy-аукционному Telegram Gateway.

*   **Дата:** 24.10.2025
*   **Статус:** Принято
*   **Контекст:**

При разработке Telegram Gateway возникла необходимость в системе ролей (RBAC) для разграничения доступа админов и обычных пользователей. Также критична была тестируемость FSM логики и UI билдеров. Наконец, нужно было определить четкие критерии, когда использовать синхронные gRPC вызовы, а когда асинхронные NATS команды.

**Требования MVP:**
- Админы должны иметь возможность создавать лоты через пошаговую форму (FSM)
- UI для админов и пользователей должен отличаться
- Вся логика (FSM, UI, хендлеры) должна быть легко тестируема без запуска бота

*   **Решение:**

**1. RBAC для MVP: Hardcoded список админов**

Для MVP система ролей реализована через конфигурацию:
- Список Telegram ID админов хранится в `configuration.yaml` (секция `auth.admins`)
- Модуль `app/auth` содержит `UserRole` enum (`Admin`, `User`)
- Функция `get_user_role(user_id, config)` определяет роль по ID
- `Dependencies` содержит helper-метод для проверки роли

**2. Модульная архитектура UI**

UI разделен на чистые функции, организованные по модулям:
```
src/app/ui/
├── common.rs          # Переиспользуемые кнопки
├── user/auction.rs    # UI для обычных пользователей
└── admin/
    ├── auction_management.rs  # Админская панель аукциона
    └── lot_creation.rs        # UI для создания лота
```

Все UI функции:
- Чистые (pure functions)
- Принимают DTO и возвращают `(String, InlineKeyboardMarkup)`
- Легко тестируются юнит-тестами

**3. Action паттерн для изоляции teloxide API**

Хендлеры не вызывают `teloxide::Bot` напрямую, а возвращают `BotAction` enum:
```rust
pub enum BotAction {
    SendMessage { chat_id, text, keyboard },
    EditMessage { chat_id, message_id, text, keyboard },
    AnswerCallback { callback_id, text },
    SendPhoto { chat_id, photo_url, caption, keyboard },
    Multiple(Vec<BotAction>),
}
```

Выполнение происходит через функцию `execute_action(&Bot, BotAction)` в модуле `helpers.rs`.

**4. FSM как чистые функции**

FSM логика изолирована в модуле `app/fsm/lot_creation.rs`:
```rust
pub struct FsmTransition {
    pub new_state: State,
    pub action: BotAction,
}

pub fn handle_title_input(chat_id, state, input) -> Result<FsmTransition, String>
```

Каждая функция:
- Валидирует ввод
- Обновляет draft
- Вычисляет новое состояние
- Вызывает UI билдер
- Возвращает `FsmTransition`

**5. Критерии выбора синхронный vs асинхронный**

**Основной критерий - природа операции:**

- **CRUD операции** (данные без состояния) → **синхронный** (gRPC/прямой вызов)
  - Простые запросы/модификации данных
  - Результат операции сразу известен
  - Примеры: `CreateLot`, `UpdateLot`, `GetAuction`, `GetUserProfile`

- **Команды к агрегатам** (stateful бизнес-логика) → **асинхронный** (NATS)
  - Требуют сложной валидации и изменения состояния
  - Event Sourcing / Actor model
  - Нужно оповестить других подписчиков
  - Примеры: `PlaceBid`, `StartAuction`, `ProcessFinalPhase`

**Дополнительные критерии:**

| Критерий | Синхронный | Асинхронный |
|----------|------------|-------------|
| **UX обратная связь** | Критична немедленная | Может быть отложена |
| **Частота** | Редкие (< 10/мин) | Частые (> 100/мин) |
| **Роль** | Админ (конфигурация) | Пользователь (действия) |
| **Broadcast** | Не нужно уведомлять | Нужно разослать события |

**Примеры классификации:**

✅ **Синхронные (CRUD):**
- `CreateLot` - просто данные, нужна валидация → прямой вызов MockAuctionService (MVP), gRPC в будущем
- `UpdateLot` - модификация данных → gRPC к Auction Service (будущее)
- `GetAuction` - query → прямой вызов (MVP), gRPC в будущем

**Важно:** CRUD операции с лотами НЕ должны идти через NATS команды. Для будущего нужен gRPC контракт `AuctionService` с методами `CreateLot`, `UpdateLot`, `DeleteLot`.

✅ **Асинхронные (Команды к агрегатам):**
- `PlaceBid` - команда к LotActor, Event Sourcing → NATS
- `StartAuction` - команда к AuctionSessionActor → NATS
- `ProcessFinalPhase` - команда к AuctionSessionActor → NATS

*   **Последствия:**

**Позитивные:**
- ✅ FSM логика легко тестируется (12 юнит-тестов реализовано)
- ✅ UI билдеры легко тестируются (8 юнит-тестов реализовано)
- ✅ Хендлеры изолированы от `teloxide` API
- ✅ Админы определяются через конфиг - быстро для MVP
- ✅ Четкие критерии для выбора sync/async
- ✅ CRUD операции не создают лишней сложности с NATS

**Негативные:**
- ⚠️ Hardcoded список админов не масштабируется
- ⚠️ При росте числа хендлеров нужно много wrapper-функций (~150 строк)
- ⚠️ Нужно помнить о различии CRUD vs команды при добавлении новых операций

**План миграции:**
- При появлении User Service заменить `get_user_role` на gRPC вызов
- Логика авторизации уже изолирована в модуле `auth` - миграция будет простой
- Структура хендлеров и FSM не потребует изменений
