# ADR-024: TypeScript для Aspire AppHost

> **Дата:** 2026-08-18  
> **Статус:** Accepted

## Контекст

ADR-021 выбрал Aspire для локальной оркестрации и C# для AppHost. После этого Aspire 13.2 получил TypeScript AppHost, а в 13.4 ATS API стали общедоступными. TypeScript SDK генерируется из той же host-side модели, поэтому смена языка не требует отказываться от .NET-проектов, контейнерных ресурсов или hosting-интеграций.

C# перестал быть универсальным языком репозитория: новые MVP-компоненты планируются без привязки к .NET, а TypeScript уже является общим языком для продуктового UI и планируемого Telegram gateway. Поддержка отдельного C#-проекта только ради описания топологии добавляет лишний toolchain и снижает доступность AppHost-кода.

## Варианты

1. Оставить C# AppHost: зрелая реализация и типизированные project references, но отдельный язык и проект сохраняются только ради orchestration-кода.
2. Перенести AppHost на TypeScript: одна и та же ресурсная модель Aspire остаётся доступна, а топология становится доступнее для большей части будущего стека.
3. Заменить Aspire на compose, Tilt или Kubernetes: не решает задачу смены языка и заново открывает уже принятое ADR-021 решение об инструменте.

Выбор между декларативной моделью профилей и прямым императивным описанием всей топологии этим ADR не фиксируется. Миграция сохраняет наблюдаемое поведение текущих профилей; упрощение модели требует отдельного решения после опыта живых запусков и первых MVP-сервисов.

## Решение

Aspire остаётся инструментом local orchestration, а канонический AppHost переносится с C# на **TypeScript** в `infra/apphost/apphost.mts`. Минимальные подтверждённые версии для этого репозитория — Aspire CLI 13.4 и Node.js 22.13; Node major фиксируется в `.nvmrc`, ограничение среды — в `package.json`.

На время gate TypeScript AppHost существует рядом с прежним C# AppHost. C#-файлы и `AppHost.csproj` удаляются только после успешного запуска инфраструктуры, проверки профилей и режимов компонентов. После gate два AppHost не должны оставаться параллельными источниками правды.

## Обоснование

TypeScript убирает специальный C#-слой, не меняя выбранную в ADR-021 runtime-модель Aspire. Это важнее краткосрочной стоимости миграции, потому что AppHost должен регулярно дополняться MVP-сервисами владельцем и агентами независимо от языка самих сервисов.

Сохранение старого AppHost до gate делает переход обратимым и следует уже принятому правилу: compose и проверенную реализацию нельзя удалять на основании одного только переноса кода.

## Последствия

### Что становится проще

- AppHost использует более универсальный для будущего MVP язык.
- Добавление TypeScript/JavaScript-сервисов не требует редактирования C#-проекта.
- Версии CLI и runtime явно отделены от версий .NET-сервисов.

### Что становится сложнее

- До завершения gate в каталоге временно находятся две реализации топологии.
- Обновления Aspire требуют проверки совместимости генерируемого TypeScript API и Node.js.
- Типы project references больше не генерируются MSBuild-проектом; пути к проектам нужно проверять smoke-тестом.

## Предсказание и пересмотр

Ожидается, что первые MVP-сервисы будут добавляться в AppHost без C#-специфичного orchestration-кода. Решение пересматривается, если TypeScript API не обеспечивает паритета для используемых ресурсов либо его эксплуатационная нестабильность регулярно блокирует обновления Aspire.

После двух живых сценариев — локального inner loop и e2e-запуска — следует отдельно оценить, нужны ли профили `Local`/`Container`/`Off`, или прямое императивное описание и явный выбор ресурсов проще.
