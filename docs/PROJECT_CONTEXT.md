# Solguficky Hub — контекст, состояние и направление проекта

> **Срез:** 06.08.2026  
> **Статус:** основной документ текущей архитектурной синхронизации  
> **Операционное планирование:** milestones, приоритеты, задачи и прогресс ведутся в Linear  
> **Ограничение:** документ фиксирует контекст и зрелость решений, но не заменяет ADR, сервисные требования и код

## 0. Как читать этот документ

Проект одновременно является продуктом для Telegram-сообщества и учебной площадкой для Event Sourcing, акторов и распределённых систем. Документ нужен, чтобы не смешивать:

- фактически существующий код;
- направление ближайшего продуктового цикла;
- принятые архитектурные решения;
- ещё не выбранные варианты;
- отложенные учебные гипотезы;
- legacy-прототипы.

Для этого у каждого значимого утверждения есть две независимые характеристики.

### 0.1 Временной слой

| Слой | Значение |
|---|---|
| **Current** | Фактически существует в текущем репозитории |
| **MVP** | Входит в ближайший продуктовый цикл: проведение первой живой сходки через бота |
| **Future** | Возможное направление после MVP без текущего обязательства реализации |
| **Legacy** | Существующий код или документ, который не входит в активное продуктовое направление |

### 0.2 Зрелость решения

| Статус | Значение |
|---|---|
| **Accepted** | Направление принято владельцем проекта; нетривиальное техническое решение должно быть закреплено ADR |
| **Proposed** | Есть предпочтительный вариант, но решение ещё нужно спроектировать или утвердить |
| **Open** | Варианты ещё исследуются; выбирать реализацию рано |
| **Superseded** | Решение больше не определяет целевую архитектуру, но может сохраняться как история |

Пример: Meetups имеет слой **MVP**, но язык реализации имеет статус **Open**. Scala/Pekko-аукцион имеет слой **Future** и является принятым стратегическим направлением, но его дизайн и реализация ещё не начаты.

### 0.3 Источники правды

При расхождении источников применяется следующий порядок:

1. код, конфигурация, тесты и миграции — для утверждений о фактическом состоянии;
2. действующие ADR с учётом более поздних заменяющих решений — для принятой архитектуры;
3. этот документ — для текущего направления, границ MVP, legacy и открытых вопросов;
4. профильные продуктовые, архитектурные и сервисные документы;
5. архивные документы — только как исторические материалы.

Linear является источником правды для порядка работ, milestones, задач и прогресса. Эти сведения не дублируются в репозитории отдельным roadmap.

### 0.4 Границы подтверждения

Срез основан на проверке дерева репозитория, кода сервисов, Protobuf-контрактов, Aspire AppHost, CI и действующих документов. При этом заново не подтверждались:

- полноценный `aspire run` всего стека;
- end-to-end сценарий через живого Telegram-бота;
- production deployment;
- восстановление аукциона из реального production Event Store;
- корректность всех фаз аукциона;
- фактическая доставка сообщений во время рестартов подписчиков.

Наличие кода означает только существование реализации, а не production readiness.

## 1. Продукт

### 1.1 Что строим

Solguficky Hub — Telegram-ориентированная платформа сообщества и единое место правды о живых сходках:

- узнать, какая сходка ближайшая, где и когда она проходит;
- зарегистрироваться и изменить решение об участии;
- помочь в подготовке;
- получить необходимые напоминания;
- сохранить полезные материалы и память о прошедшем событии.

Бот не должен создавать дополнительный шум в общем чате.

### 1.2 Цель MVP

Провести первую живую сходку через бота.

Минимальный наблюдаемый критерий успеха:

- участники узнают актуальные данные о сходке через бота;
- регистрация и изменение RSVP проходят через продукт;
- организатор может создать и изменить сходку штатным способом;
- базовые роли и полномочия работают без конфигурации `user_id` в файле;
- в день проведения не требуется вручную исправлять данные непосредственно в БД.

Точный набор UX-сценариев и экранов должен быть утверждён на этапе продуктового проектирования. Закреп, `/start`, глубина меню и способ обновления сообщений не являются заранее зафиксированными критериями MVP.

### 1.3 Основные роли

- **Участник сообщества** узнаёт о сходках, регистрируется и управляет собственным участием.
- **Организатор сходки** создаёт и ведёт конкретную сходку в пределах доменных полномочий.
- **Администратор сообщества** модерирует предложения и управляет общими правилами.
- **Owner** управляет системными полномочиями и аварийными административными действиями.

Это продуктовые роли, а не готовая RBAC-матрица. Дополнительные роли вроде редактора контента или модератора вводятся только из реального сценария. Права не должны определяться хардкодом Telegram `user_id`.

### 1.4 Двойное назначение

Проект имеет две цели:

1. принести реальную пользу сообществу;
2. дать владельцу практику проектирования, технического лидерства и эксплуатации распределённой системы.

При прямом конфликте выигрывает продукт. Учебная технология оправдана, когда для неё есть подходящая задача и её стоимость не ставит под угрозу проведение сходки.

## 2. Продуктовые принципы

### 2.1 Тишина и ненавязчивость

Бот не должен превращать общий чат в поток технических сообщений и команд.

Следствия определяются при проектировании сценариев. Допустимы разные механики:

- личные сообщения;
- Telegram-команды;
- silent messages;
- inline-взаимодействия;
- редактируемые сообщения;
- ограниченные публикации в общем чате;
- Mini App.

Ни одна из этих механик сама по себе не является продуктовым принципом. Автообновляемый закреп — возможное решение, а не обязательство.

### 2.2 Privacy by design и минимальные привилегии

Бот проектируется так, как если бы доступ к произвольным сообщениям общего чата ему не предоставлялся.

- Не анализировать переписку участников ради продуктовой аналитики или скрытой автоматизации.
- Не строить ключевые сценарии на чтении произвольного текста в группе.
- Запрашивать только необходимые Telegram updates и полномочия.
- Не отключать Privacy Mode без отдельного, явно обоснованного решения.
- Не считать клиентский JavaScript доверенной стороной.

Для Telegram Mini App исходный `initData` передаётся на backend, где проверяются подпись, `auth_date` и допустимое окно повторного использования. Клиентская проверка может улучшать UX, но не заменяет серверную авторизацию.

### 2.3 Минимизация и целевое использование данных

- Сохранять только данные, необходимые для заявленных сценариев.
- Для каждого чувствительного поля понимать цель, срок хранения и круг потребителей.
- Не собирать историю сообщений «на будущее».
- Не выводить приватные данные участника в общий чат без явного продуктового основания.
- Разделять Telegram identity, внутренний профиль и доменные роли.

### 2.4 Последствия для backlog

Любая будущая идея должна отвечать на вопросы:

- требует ли она чтения произвольных сообщений;
- можно ли реализовать её командой, явной пересылкой, кнопкой или формой;
- какие данные сохраняются и зачем;
- кто увидит результат;
- можно ли отказаться от функции без потери основного сценария сходки.

Например, цитатник допустим как явное действие пользователя над выбранным сообщением, но не как постоянный анализ всего чата.

## 3. Анти-скоуп

В MVP не входят:

- настоящие платежи, эквайринг, эскроу и депозиты;
- клиенты вне Telegram;
- публичный продукт за пределами сообщества;
- мультитенантность;
- аукцион;
- achievements;
- content feed как отдельный заранее спроектированный сервис;
- отдельный scheduler без подтверждённой потребности;
- выбор языков ради заполнения полиглотной матрицы.

Поведенческий анти-скоуп:

- не начинать новый интересный сервис вместо завершения продуктового среза;
- не строить сложную систему управления проектом вместо самого продукта;
- не переписывать работающие части только ради нового языка;
- не считать количество языков показателем архитектурного качества;
- не передавать агенту принятие решений, которые владелец хочет научиться принимать сам.

## 4. Фактическое состояние репозитория

### 4.1 Общая оценка

**Current:** репозиторий содержит преимущественно аукционный прототип и инфраструктурный задел. Продуктовое ядро сходок ещё не реализовано.

Meetups и Identity отсутствуют не только как исполняемые сервисы, но и как межсервисные контракты. Поэтому ближайшая работа — не развитие текущего аукциона, а проектирование и реализация первого вертикального среза вокруг сходок.

### 4.2 Карта компонентов

| Компонент | Current | Роль относительно MVP | Статус |
|---|---|---|---|
| `telegram-gateway` | Rust + Teloxide, UI старого аукциона | Будет заменён новой реализацией | Legacy → MVP replacement |
| `auction-service` | C# + Akka.NET, акторы, persistence, gRPC, NATS | Не входит | Legacy |
| `notifications-service` | C#, один аукционный `BidPlacedHandler` | Можно развить в reminder service | Current / MVP candidate |
| `websocket-gateway` | C# + SignalR, только `auction:live` | Не требуется текущим MVP | Legacy / frozen |
| `meetups` | Отсутствует | Владелец данных о сходках | MVP |
| `identity` | Отсутствует | Telegram identity, роли и membership | MVP |
| Mini App | Пустая заготовка | UX определяется после сценариев и макетов | MVP, scope open |
| `nats-tester` | Python CLI | Ручная проверка контрактов и subjects | Current tooling |
| Aspire AppHost | Реализация есть, полный запуск не подтверждён | Локальная оркестрация | Current, verification pending |

### 4.3 Telegram Gateway

Текущая Rust-реализация:

- ориентирована на аукционные сценарии;
- создаёт `MockAuctionService` в production composition root;
- хранит Telegram dialogue state в памяти;
- имеет полезное разделение handler → `BotAction` → executor;
- содержит как JSON-, так и Protobuf-пути обработки NATS-событий;
- хранит callback idempotency только в памяти;
- использует Teloxide-типы внутри `BotAction`, поэтому паттерн нельзя перенести механически как независимое доменное ядро.

Это не фундамент нового продукта. Полезны идеи чистых UI builders, действий как результата handler и разделения Telegram API от сценарной логики.

### 4.4 Auction Service

Текущий сервис действительно содержит:

- `AuctionActor` и `LotActor`;
- Event Sourcing/CQRS на Akka.Persistence;
- persistence в PostgreSQL;
- gRPC queries и CRUD лотов;
- NATS command handler;
- публикацию событий через persistence query.

Некоторые пункты прежнего техдолга уже не соответствуют коду:

- EF migration существует и применяется при старте;
- scoped `LotRepository` разрешается через создаваемый scope, а не напрямую удерживается singleton-handler.

Актуальные ограничения:

- runtime/e2e-поведение в production не подтверждалось;
- рефакторинг фаз не следует считать законченным;
- деньги представлены `double`, этот выбор нельзя переносить в новые контракты;
- существующая модель является источником опыта и гипотез, а не спецификацией auction v2.

### 4.5 Notifications Service

Сервис существует как каркас маршрутизации событий в уведомления, но его единственный содержательный сценарий связан с аукционом.

Текущий handler:

- обрабатывает `BidPlacedEvent`;
- формирует `SendMessageCommand`;
- временно предполагает `user_id == chat_id`;
- не реализует напоминания о сходках;
- не решает scheduling, durable delivery и дедупликацию side effects.

Каркас можно оставить на C#, но пригодность структуры должна подтверждаться первым реальным reminder-сценарием.

### 4.6 WebSocket Gateway

Сервис:

- подписан только на аукционный namespace;
- содержательно маппит только `bid_placed`;
- публикует сообщения в `auction:live` через SignalR.

Для MVP сходок он не требуется. Пока код остаётся в active tree, он должен продолжать собираться и явно маркироваться как frozen legacy. Исключать оставленный код из CI нельзя: это превратит заморозку в незаметное разрушение.

### 4.7 Контракты

`contracts/proto/` является текущим source control для NATS и gRPC контрактов. Кодогенерация выполняется потребителями при сборке.

Обнаруженные разрывы относятся прежде всего к legacy gateway:

- `SendMessageCommand` читается одним путём как JSON, хотя контракт Protobuf уже существует;
- `BidPlacedEvent` имеет одновременно JSON- и Protobuf-пути;
- поле `op_id` присутствует, но не обеспечивает идемпотентность без consumer-side проверки;
- новые Meetups и Identity контракты пока отсутствуют.

### 4.8 Aspire и локальная инфраструктура

В репозитории есть Aspire AppHost, ServiceDefaults и профили топологии. Однако полный `aspire run` не был подтверждён в среде, где код создавался.

Дополнительные факты:

- current `core` profile всё ещё поднимает Auction + Rust Gateway;
- gateway запускается через Cargo;
- AppHost/ServiceDefaults и C#-сервисы используют разные target framework поколения;
- рукописные compose-файлы пока остаются страховочной рабочей конфигурацией;
- NATS image закреплён на ветке 2.10, поэтому возможности более новых версий нельзя считать доступными без обновления.

Живой smoke test Aspire является prerequisite перед дальнейшим наращиванием AppHost.

### 4.9 CI

GitHub Actions присутствует, поэтому утверждение «CI нет» устарело. При этом конфигурацию нельзя считать полностью подтверждённой:

- workflow устанавливает .NET 8 для сервисов, переведённых на net10;
- не подтверждён успешный удалённый прогон после последних изменений;
- изменения `contracts/proto/` должны проверять всех потребителей, а не только сервисы, выбранные обычными path filters.

## 6. Telegram Gateway: целевое направление

### 6.1 Решение

**MVP / Accepted, ADR pending:** переписать Telegram Gateway с нуля на TypeScript и grammY.

Это одновременно:

- отказ от дорогой для данного сервиса Rust-разработки;
- отказ от необоснованного промежуточного назначения Go;
- смена продуктового назначения с UI аукциона на edge для сценариев сходок.

### 6.2 Почему не Rust

Rust не раскрывает свои сильные стороны на часто меняющемся Telegram IO glue, но увеличивает стоимость:

- освоения;
- компиляционного цикла;
- работы с async и библиотечными типами;
- быстрых продуктовых итераций;
- поддержки единственным владельцем.

Полезные паттерны существующего gateway сохраняются как знания, но не требуют сохранения языка.

### 6.3 Почему не Go

Go мог бы дать простую эксплуатацию и предсказуемый runtime, но в данном контексте уступает TypeScript:

- экосистема Telegram-ботов не даёт достаточного преимущества относительно grammY;
- новый язык не создаёт уникальной учебной ценности для этого edge-сервиса;
- исчезает возможность безопасно разделять часть presentation contracts с Mini App;
- TypeScript лучше соответствует скорости изменения Telegram UX.

Это не общий запрет Go. Язык остаётся в learning pool для будущей задачи, которой действительно соответствуют его свойства.

### 6.4 Почему не Python

Python также имеет зрелые Telegram-библиотеки и высокую скорость первой реализации. TypeScript выбран не потому, что Python непригоден, а из-за совокупности контекста:

- единый язык с будущим Mini App;
- возможность разделять ограниченный слой presentation contracts;
- сильная статическая проверка быстро меняющихся callback payload и UI-state;
- один package/tooling ecosystem для Telegram edge и браузерной части.

Если эти преимущества не подтвердятся на практике, выбор можно пересмотреть отдельным заменяющим ADR.

### 6.5 Что можно разделять с Mini App

Допустимый общий код:

- DTO и схемы валидации UI payload;
- presentation models;
- Telegram-facing identifiers;
- локализуемые тексты и форматирование;
- типы UI-состояний без backend-инвариантов.

Нельзя делать общий TypeScript package источником правды для:

- инвариантов Meetups;
- решений об авторизации;
- правил перехода доменных состояний;
- прав доступа;
- серверной проверки Telegram `initData`.

Общий язык gateway и Mini App также не устраняет browser transport boundary. Mini App не может произвольно обращаться к внутреннему gRPC endpoint. Понадобится явно выбранный HTTP/BFF/Connect/gRPC-Web boundary.

### 6.6 Что должен решить ADR

- long polling или webhook для первого deployment;
- граница между grammY handlers и application use cases;
- модель и persistence диалогового состояния;
- обработка callback retry и idempotency;
- concurrency model;
- Telegram API error handling и rate limits;
- допустимый общий package с Mini App;
- browser/backend transport;
- правила логирования без утечки персональных данных;
- стратегия переключения со старого Rust gateway.

Для Aspire 13 JavaScript-приложение следует подключать актуальным API `AddJavaScriptApp`; старый `AddNpmApp` не должен становиться основой нового решения.

## 7. Meetups: граница и выбор языка

### 7.1 Роль сервиса

**MVP / Accepted boundary:** Meetups владеет данными и правилами жизненного цикла сходки.

Предварительно сюда относятся:

- создание и изменение сходки;
- публикация/отмена;
- дата, место и состояние;
- RSVP;
- meetup-specific роли организаторов;
- правила допустимых изменений;
- события жизненного цикла сходки.

Граница уточняется human-led D0/D1. До этого нельзя окончательно выбирать язык, persistence pattern или транспорт каждой операции.

### 7.2 Критерии выбора языка

Сначала фиксируются требования сервиса:

- сложность инвариантов;
- конкурентные изменения RSVP и состояния;
- модель согласованности;
- транзакционные границы;
- потребность в Event Sourcing;
- скорость продуктовых итераций;
- зрелость PostgreSQL, gRPC, Protobuf, NATS и observability tooling;
- стоимость локальной разработки и deployment;
- знакомство владельца;
- учебная отдача именно на этом домене.

Только после этого сравниваются кандидаты.

### 7.3 Кандидаты

| Язык | Сильная сторона | Основной риск |
|---|---|---|
| F# + ASP.NET Core | Явные типы и инварианты, знакомая .NET-инфраструктура | Дополнительная сложность интеграционных границ и поддержки |
| C# + ASP.NET Core | Максимальная скорость и зрелая инфраструктура | Меньше принуждения к точному доменному моделированию |
| Kotlin | Богатая модель типов и новый JVM-опыт | Новый operational/tooling stack одновременно с новым ядром |
| Go | Простота runtime и deployment | Менее выразительная доменная модель; слабее соответствует текущей учебной задаче |

F# остаётся сильным кандидатом, но не назначается заранее.

### 7.4 Decision experiment

После D0/D1 выбрать один сквозной сценарий, например RSVP с конкурирующими изменениями, и для 2–3 кандидатов сравнить:

- доменную модель;
- API/contract boundary;
- persistence transaction;
- обработку ошибок;
- тестируемость;
- количество инфраструктурного glue;
- время реализации владельцем.

Результат фиксируется отдельным ADR, а не общей таблицей языковых предпочтений.

## 8. Identity как отдельный сервис

### 8.1 Принятое направление

**MVP / Accepted boundary:** Identity остаётся отдельным сервисом.

Это осознанное разделение, а не утверждение, что сервис уже спроектирован. Цена решения:

- отдельный deployment unit;
- отдельное хранилище и миграции;
- межсервисные контракты;
- отказоустойчивость и наблюдаемость;
- правила согласованности между identity и доменными полномочиями.

### 8.2 Предлагаемая ответственность

Identity отвечает за:

- сопоставление Telegram user с внутренним participant identity;
- membership в сообществе;
- системные роли вроде owner/admin;
- минимальные данные профиля, если они нужны нескольким сервисам;
- серверную проверку Telegram authentication material, если boundary будет назначен сюда.

Meetups отвечает за решения своего домена:

- кто является организатором конкретной сходки;
- кто может изменить или отменить конкретную сходку;
- кто может модерировать предложение;
- какие действия разрешены текущим состоянием сходки.

Identity сообщает факты и общие роли; доменный сервис принимает доменное решение.

### 8.3 Открытые вопросы

- Что считается участником сообщества?
- Нужна ли предварительная регистрация до первого RSVP?
- Кто создаёт identity при первом входе?
- Какие Telegram-данные сохраняются?
- Как отзывается роль?
- Что происходит при недоступности Identity?
- Нужна ли синхронная проверка на каждом действии?
- Как разделить authentication и authorization?

Язык Identity выбирается после ответов. C#, F#, Kotlin и Go остаются кандидатами, но для MVP действует общий runtime-language budget: TypeScript на edge и по умолчанию один backend stack, если отдельный ADR не оправдает усложнение.

## 9. Notifications и scheduling

### 9.1 MVP-сценарий

**MVP / Open design:** напоминания участникам, подтвердившим RSVP, являются первым непридуманным сценарием Notifications.

Точные интервалы, opt-in, quiet hours, отмена и изменение времени сходки должны быть определены требованиями. Значения «24 часа» и «2 часа» являются хорошей стартовой гипотезой, но не архитектурным принципом.

### 9.2 Scheduler пока не является сервисом

Сначала нужно определить механику:

- кто создаёт расписание;
- где хранится pending reminder;
- что происходит при переносе/отмене сходки;
- как переживается restart;
- какая задержка допустима;
- как исключается повторная отправка.

Только после этого выбирается placement:

1. scheduling внутри Notifications;
2. scheduling внутри Meetups;
3. отдельный Scheduler.

Для MVP предпочтительным кандидатом является scheduling внутри Notifications, если именно Notifications владеет жизненным циклом доставки. Отдельный сервис оправдан только при появлении нескольких независимых потребителей общей scheduling capability.

### 9.3 Три разных задачи

Нельзя объединять словом JetStream:

1. **Scheduling** — когда сообщение становится готовым к обработке.
2. **Durable delivery** — переживает ли готовое сообщение restart потребителя.
3. **Exactly-once user-visible side effect** — не получит ли пользователь два Telegram-сообщения.

JetStream может помочь со вторым пунктом и в новых версиях имеет scheduling-возможности, но не отменяет:

- durable consumer configuration;
- idempotency key;
- consumer-side deduplication;
- outbox/inbox или эквивалентную модель;
- обработку Telegram API retry.

Текущий NATS 2.10 не даёт права проектировать решение на возможностях более новой версии без отдельного upgrade decision.

## 10. Mini App

**MVP / Open:** продуктовый scope и стек Mini App выбираются после сценариев и первых утверждённых макетов.

До выбора framework необходимо определить:

- какие действия действительно неудобны в интерфейсе бота;
- кто пользователь каждого экрана;
- какие состояния загрузки, ошибки и отсутствия данных нужны;
- какие операции требуют elevated permissions;
- какие данные доступны браузеру;
- какой backend boundary обслуживает Mini App.

TypeScript является естественным языком клиента. Из этого не следует автоматический выбор React/Vue/Svelte и не следует прямой доступ браузера к внутренним сервисам.

## 11. Аукцион и WebSocket legacy

### 11.1 Позиция

- Аукцион не входит в MVP.
- Текущий C#/Akka.NET сервис не является основой, которую обязательно мигрировать.
- Auction v2 в будущем проектируется с нуля на Scala + Apache Pekko.
- WebSocket Gateway пока остаётся frozen legacy.

Pekko предпочтителен стратегически как Apache-проект и открытая actor ecosystem после изменения лицензирования новых версий Akka. Это направление должно получить собственный ADR перед началом проектирования v2.

### 11.2 Что сохранить из текущего аукциона

- карту агрегатов и actor hierarchy;
- команды, события и состояния;
- найденные инварианты;
- модели concurrency и ordering;
- recovery assumptions;
- удачные тестовые сценарии;
- ошибки реализации и выводы;
- гипотезы, которые не были проверены production-нагрузкой;
- границы gRPC, NATS и read model;
- ретро «что в Akka.NET реализации оказалось удачным и неудачным».

### 11.3 Что не переносить автоматически

- текущие proto как вечный публичный контракт;
- `double` для денег;
- незавершённую FSM фаз;
- actor topology без нового D0–D4;
- persistence schema;
- допущение, что работающий unit test подтверждает live auction behavior;
- связь WebSocket Gateway с будущей topology.

### 11.4 Gate удаления

До удаления кода:

1. зафиксировать текущее фактическое состояние;
2. извлечь domain/actor/event артефакты;
3. отметить проверенное и непроверенное;
4. сохранить полезные тест-кейсы или их описание;
5. определить судьбу auction proto и зависимых consumers;
6. удалить код, topology, CI paths и активные инструкции одним согласованным изменением.

Пока gate не пройден, сервис остаётся в репозитории, собирается в CI и не развивается без явного запроса.

## 12. Инфраструктура и hosting

### 12.1 Три контура

#### Daily local development

Aspire является принятой точкой локальной оркестрации:

- запуск инфраструктуры и нужных сервисов;
- service discovery и конфигурация;
- единый dashboard;
- логи, health и traces;
- возможность отключить компонент и запустить его из IDE.

Первый следующий инфраструктурный шаг — подтвердить `aspire run` smoke test и только затем адаптировать topology под новый TypeScript gateway и MVP-сервисы.

#### Production-like integration

k3s нужен для практики контейнерной оркестрации и проверки production-like deployment. Он не заменяет удобный inner loop Aspire.

#### Production hosting

Приоритетом является собственно управляемая инфраструктура, но площадка остаётся открытым решением:

- домашний мини-ПК;
- VPS;
- Railway как fallback или быстрый временный deployment.

Выбор площадки и deployability — разные решения. Даже без мини-ПК сервис должен иметь воспроизводимый build, configuration model, migrations, secrets boundary, health checks, backup/restore и deployment artifact.

### 12.2 Порядок работ

Production deployment не обязан быть первым milestone. Текущий порядок приоритетов хранится в Linear. Однако эксплуатационные требования нельзя откладывать до последней недели перед сходкой: они формулируются вместе с сервисами, даже если сама инфраструктура поднимается позже.

ADR-006 с безусловным Railway больше не выражает целевую позицию и должен быть заменён решением, разделяющим:

- требования к hosting;
- критерии выбора площадки;
- deployment model;
- learning goals;
- fallback strategy.

## 13. Контракты и межсервисное взаимодействие

### 13.1 Базовое правило

- Protobuf остаётся форматом межсервисных NATS и gRPC контрактов.
- JSON в NATS между сервисами не является допустимым целевым форматом.
- Subjects именуются `<commands|events>.<domain>.<action>` в snake_case.
- Многоуровневая подписка использует `>`; `*` совпадает только с одним токеном.
- Изменение `contracts/proto/` требует проверки и пересборки всех потребителей.

### 13.2 Sync и async

Текущее правило «команды к stateful агрегатам через NATS, CRUD и queries через gRPC» остаётся рабочей отправной точкой, но ADR-016 смешивает слишком много решений и не должен применяться механически к ещё не спроектированным сервисам.

Для каждой операции нужно ответить:

- требуется ли немедленный ответ пользователю;
- кто владеет состоянием;
- допустима ли eventual consistency;
- что происходит при timeout;
- как клиент узнаёт итог асинхронной команды;
- нужна ли durable delivery;
- как обеспечивается idempotency.

### 13.3 Schema Registry — не один вопрос

Нужно раздельно решить:

| Задача | Ближайший разумный уровень |
|---|---|
| Source control схем | Git остаётся источником |
| Breaking-change detection | Добавить compatibility check в CI, например Buf |
| Code generation | Унифицировать команды и версии генераторов |
| Distribution/discovery | Оценивать после появления независимых lifecycle/repositories |
| Runtime schema resolution | Не вводить без сценария, которому он нужен |
| Учебная эксплуатация Registry | Возможна отдельной итерацией после product slice |

Отказ от Apicurio из-за прежнего дедлайна не является вечным запретом. Возврат Schema Registry — **Open**, а не принятое решение. Сначала нужно определить, какую конкретную проблему он решает.

### 13.4 Contract governance до первого нового proto

До добавления Meetups/Identity контрактов нужно решить минимум:

- правила совместимости;
- package/version naming;
- ownership;
- codegen matrix для TypeScript и выбранного backend stack;
- CI breaking checks;
- правила удаления legacy auction контрактов;
- отдельность контрактного изменения от реализационного, когда оно затрагивает несколько потребителей.

### 13.5 Сквозная надёжность и observability

**Current:** сервисы используют core NATS-семантику без подтверждённых durable consumers. При рестарте подписчика сообщение может быть потеряно. Наличие JetStream на сервере не означает, что приложения используют его гарантии.

Перед тем как надёжная доставка станет частью продуктового потока, одновременно проектируются:

- stream и retention policy;
- durable consumer;
- ack/retry policy;
- idempotency key и проверка `op_id`;
- consumer inbox/dedup storage;
- идемпотентность внешнего Telegram side effect;
- dead-letter или операционный способ разбирать необрабатываемые сообщения;
- метрики lag, redelivery и failed delivery.

Read model вводится не как обязательный CQRS-ритуал, а когда query-нагрузка, пользовательский UX или изоляция stateful aggregate делает прямые ask/query обращения неудобными.

Минимальный observability baseline для MVP:

- структурные логи без персональных и Telegram authentication данных;
- correlation/operation id через межсервисный путь;
- health и readiness checks;
- метрики ошибок, latency и delivery attempts;
- трасса первого вертикального среза Gateway → Identity → Meetups;
- понятный оператору способ увидеть и повторить неуспешное действие без ручной правки БД.

Loki/Grafana-конфигурация и Aspire dashboard являются заделом, но наличие конфигурационных файлов не подтверждает работающую наблюдаемость.

## 14. Выбор языков и technology pool

Язык назначается существующей задаче, а не наоборот.

### 14.1 Матрица решения

Для сервиса фиксируются:

- доменная сложность;
- владение данными;
- consistency/concurrency требования;
- latency и throughput;
- интеграции;
- persistence;
- observability;
- maturity библиотек;
- deployment footprint;
- скорость разработки владельца;
- учебная отдача;
- стоимость добавления ещё одного runtime в MVP.

Затем кандидаты сравниваются по одинаковой шкале. Обязательные ограничения применяются до субъективного интереса к языку.

### 14.2 Текущий technology pool

| Технология | Статус |
|---|---|
| TypeScript + grammY | Accepted для нового Telegram Gateway |
| F#, C#, Kotlin, Go | Кандидаты для Meetups/Identity после требований |
| Scala + Pekko | Future direction для auction v2 |
| Kotlin | Интересен, но не закреплён за Content Feed |
| Go | Интересен, но не закреплён за Scheduler |
| Ruby | Интересен, но отдельная админка не обоснована |
| C# + Orleans | Future hypothesis для Achievements |

Для списка интересов ADR не нужен. ADR нужен, когда реальный сервис, требования и последствия дают выбору архитектурный вес.

### 14.3 Runtime-language budget MVP

Базовое ограничение:

- TypeScript на Telegram edge;
- один backend runtime по умолчанию;
- второй backend runtime допускается только при явном преимуществе, зафиксированном ADR.

Это не запрет полиглотности, а защита product cycle от одновременного освоения нескольких operational stacks.

## 15. Процесс проектирования

### 15.1 Цель процесса

Процесс должен развивать владельца как архитектора/техлида, а не превращать проектирование в генерацию документов агентом.

Исходный D0–D8 полезен как перечень вопросов, но слишком формален как обязательный pipeline для каждого сервиса.

### 15.2 Human-owned design loop

#### A. Сформулировать

Владелец формулирует:

- проблему;
- затронутые роли;
- границы;
- наблюдаемый результат;
- первичные сценарии;
- исходную гипотезу.

Агент может помогать искать факты и выявлять пропуски, но не подменяет исходную постановку.

#### B. Оспорить

Агент:

- ищет контрпримеры;
- расширяет список вариантов;
- проверяет технологические факты;
- показывает скрытую стоимость;
- проверяет privacy, failure modes и evolvability;
- находит противоречия с кодом и ADR.

#### C. Решить и нарезать

Владелец:

- выбирает вариант;
- объясняет, почему отвергнуты альтернативы;
- принимает компромиссы;
- утверждает вертикальные срезы.

Агент может оформить ADR и задачи после того, как решение принято.

#### D. Реализовать и проверить

Агент может:

- реализовать утверждённый срез;
- написать тесты;
- обновить связанные документы;
- проверить отклонения от дизайна;
- подготовить факты для ретро.

Существенное отклонение от принятого дизайна возвращается на checkpoint, а не маскируется как мелкая реализационная деталь.

### 15.3 D0–D8 как библиотека вопросов

| Шаг | Сохраняемая ценность |
|---|---|
| D0 | Проблема, роли, границы, успех, anti-scope |
| D1 | Основные, ошибочные, пограничные и административные сценарии |
| D2 | События, команды, состояния, инварианты, глоссарий — только если есть домен |
| D3 | Проверяемые функциональные и НФ-требования |
| D4 | Альтернативы, последствия и ADR |
| D5 | Контракты до зависимых реализаций, когда они действительно межсервисные |
| D6 | Вертикальные срезы, каждый с демонстрируемым результатом |
| D7 | Реализация с фиксацией существенных отклонений |
| D8 | Сверка прогнозов с фактом после реального использования |

Не каждый шаг обязан порождать отдельный файл.

### 15.4 Глубина по риску

Вместо постоянных тиров используются risk triggers. Углублённое проектирование требуется, если присутствует хотя бы один фактор:

- сервис владеет важными данными;
- есть бизнес-инварианты;
- есть конкурентные команды;
- затрагиваются деньги или права;
- меняется публичный контракт;
- несколько потребителей;
- сложное восстановление после отказа;
- новая для владельца технология с operational cost;
- ошибка потребует миграции данных или координации сервисов.

Если ни одного фактора нет, достаточно короткого problem/design brief и задачи в Linear.

### 15.5 Артефакты и Linear

В репозитории живут долговечные знания:

- проблема и границы сервиса;
- сценарии и требования;
- доменная модель;
- контракты;
- ADR;
- design retro.

В Linear живут:

- initiatives и milestones;
- приоритеты;
- задачи;
- зависимости исполнения;
- оценки;
- статус и прогресс.

Агент может механически подготовить Linear issues после утверждения срезов, но scope и порядок утверждает владелец.

### 15.6 Исполняемая граница роли агента

Краткое правило должно находиться в `AGENTS.md`:

- продуктовые и архитектурные решения принимает владелец;
- агент исследует, оппонирует и проверяет;
- агент не создаёт новый сервис, ADR или межсервисный контракт без явного запроса;
- реализация начинается после утверждения границ и среза;
- документация обновляется вместе с кодом.

## 16. Реестр направлений

### 16.1 Accepted

| Направление | Что именно принято | Что ещё требуется |
|---|---|---|
| Product MVP | Первая живая сходка через бота, без аукциона | D0/D1 и точные acceptance criteria |
| Product principles | Тишина, ненавязчивость, privacy, least privilege, data minimization | Применить к сценариям и backlog |
| Telegram Gateway | Новая реализация TypeScript + grammY | ADR и migration slice |
| Meetups | Отдельный владелец данных сходок | Граница, язык, модель и контракты |
| Identity | Отдельный сервис | Ответственность, failure model, язык и контракты |
| Notifications | Существующий C# каркас пока сохраняется | Спроектировать reminders |
| Auction MVP scope | Аукцион исключён из MVP | Извлечение знаний и вывод legacy |
| Auction v2 | Будущее направление Scala + Pekko | Полный design cycle после MVP |
| Local orchestration | Aspire | Подтвердить живым запуском |
| Planning | Linear — источник приоритетов и прогресса | Не дублировать roadmap в Git |

### 16.2 Open

- точный набор сценариев и границы MVP;
- язык и persistence Meetups;
- язык и failure model Identity;
- placement и механизм scheduling;
- transport boundary Mini App;
- stack Mini App после макетов;
- contract compatibility tooling;
- необходимость и роль Schema Registry;
- момент включения JetStream durable consumers;
- production hosting: мини-ПК, VPS или Railway;
- точный момент удаления auction-service;
- дальнейшая судьба websocket-gateway;
- общий backend runtime budget после выбора Meetups и Identity.

### 16.3 Superseded или более не определяет направление

- Rust как целевой стек Telegram Gateway;
- Go как целевой стек Telegram Gateway;
- F# как уже выбранный язык Meetups;
- Identity как модуль внутри Meetups;
- Railway как безусловно выбранный hosting;
- Kotlin как заранее выбранный стек Content Feed;
- Go как заранее выбранный стек Scheduler;
- Ruby как заранее выбранный стек админки;
- deployment как обязательный первый milestone;
- закреп, `/start` и edit-message как продуктовые принципы;
- Scala как исключённый из проекта язык;
- аукцион как часть MVP.

### 16.4 Состояние существующих ADR

| ADR | Позиция при синхронизации |
|---|---|
| ADR-006 | Безусловный Railway больше не выражает направление; требуется заменяющий ADR о hosting criteria |
| ADR-007 | Смешивает несколько назначений сервисов и языков; не использовать как актуальную матрицу стеков |
| ADR-008 | Исторически заменён ADR-014, статус в журнале нужно сделать явным |
| ADR-013 | Полезное правило «решение до кода» сохраняется, но инициатива и окончательный выбор принадлежат владельцу; процесс требует отдельного пересмотра |
| ADR-014 | Protobuf-in-Git остаётся Current; запрет Registry не считать вечным без нового рассмотрения |
| ADR-016 | Критерий sync/async полезен, но документ перегружен RBAC, UI, FSM и gateway-specific решениями; применять по частям и затем заменить более узкими ADR |

Этот документ не меняет статусы ADR задним числом. Обновление журнала решений выполняется отдельным согласованным изменением: один ADR — одно решение, старые записи сохраняют историю и получают явную ссылку на замену.

## 17. Ближайшая последовательность по зависимостям

Этот раздел не задаёт приоритеты вместо Linear. Он показывает логические зависимости.

### A. Синхронизация контекста

Основной контекст и инструкции агентам переключены на модель Current / MVP / Future / Legacy, отдельный Git-roadmap удалён, а каталоги документации приведены к семантической структуре. Оставшаяся работа:

1. В отдельном подходе разнести устойчивые части этого переходного документа по `docs/product/`, `docs/architecture/` и `docs/services/`, не создавая дублирующих источников правды.
2. Обновить статусы и при необходимости добавить заменяющие ADR отдельными решениями.
3. Подтвердить живой запуск Aspire или зафиксировать конкретный blocker.

### B. Human-led проектирование ядра

1. D0/D1 продукта MVP.
2. D0/D1 Meetups.
3. D0/D1 Identity.
4. Первый список проверяемых privacy и reliability требований.
5. Определение первого пользовательского вертикального среза.

### C. Решения до контрактов

1. ADR Telegram Gateway.
2. ADR о границе Identity/Meetups, если текущей фиксации недостаточно для реализации.
3. Decision experiment и ADR языка Meetups.
4. Решение о backend runtime Identity.
5. Contract governance и CI compatibility check.

### D. Первый вертикальный срез

Предпочтительный кандидат:

```text
Telegram user
→ новый TypeScript Gateway
→ Identity
→ Meetups
→ просмотр опубликованной сходки или RSVP
→ наблюдаемый ответ пользователю
```

Срез должен проверить реальные границы сервисов, authentication/authorization, синхронный или асинхронный transport, persistence, ошибки и локальную оркестрацию.

### E. Следующие срезы

- управление сходкой организатором;
- изменение/отмена и реакция RSVP;
- reminders через Notifications;
- Mini App только для сценариев, где интерфейса бота недостаточно;
- production-like deployment;
- production hosting;
- legacy extraction/removal вне критического пути продукта.

## 18. Модель документации

| Информация | Источник правды |
|---|---|
| Цель, принципы, scope | `docs/product/` после смысловой декомпозиции этого документа |
| Текущий общий контекст перехода | `docs/PROJECT_CONTEXT.md` |
| Current/target architecture | `docs/architecture/` после смысловой декомпозиции этого документа |
| Принятые технические решения | отдельные ADR в `docs/decisions/` |
| Сервисные требования и дизайн | `docs/services/<service>/`, когда такой документ нужен |
| Машиночитаемые контракты | `contracts/proto/` |
| Каталог интеграций и эксплуатационные детали контрактов | `docs/architecture/integration.md` |
| Локальная разработка и технические руководства | `docs/development/` |
| Неприоритизированные идеи | `docs/product/ideas.md` |
| Приоритеты, milestones, задачи, прогресс | Linear |
| Инструкции агентам | `AGENTS.md` и вложенные `AGENTS.md` |
| Нормативные инженерные соглашения | `docs/standards/` |
| Исторические материалы | `docs/archive/` |

Отдельный `ROADMAP.md` не используется. Репозиторий хранит причины, решения, требования и устойчивые ограничения; Linear хранит изменчивый порядок исполнения.

После переноса принятых частей в профильные документы `PROJECT_CONTEXT.md` должен либо стать компактным обзором и навигатором, либо быть архивирован. Он не должен навсегда дублировать продуктовые документы и ADR.
