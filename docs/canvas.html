Архитектура: шина посередине

Всё асинхронное идёт через NATS одним контрактом (Protobuf), всё синхронное — мимо шины, по gRPC. Это не стилистика, а критерий выбора из ADR-016: команды к stateful-агрегатам и события — в шину; CRUD и queries — в gRPC.

gRPC, в обход шины telegram-gateway → auction-service (queries, CRUD лотов) · → meetups-service (P1). Сейчас гейтвей ходит не в gRPC, а в MockAuctionService — это P1-долг.

Только Protobuf

JSON в шине запрещён (ADR-012). Контракты живут в contracts/proto/ и генерятся при сборке каждого сервиса — без Schema Registry (ADR-014).

Хореография, не оркестрация

Сервисы не знают друг о друге — только о темах. Имена: <commands|events>.<домен>.<действие>, snake_case.

ES — точечно

Event Sourcing только там, где нужна история и конкурентные изменения (аукцион). Сходки, роли, лента — обычный CRUD на EF Core.

UUIDv7 в контрактах

ID генерит сервис, сортируется по времени, нативен во всех языках (ADR-020, заменил ULID). Строка 36 символов, lowercase.

Открытые вопросы

Где это будет жить

Railway дорожает и прячет инфраструктурную практику. Кандидаты: дешёвый VPS или домашний сервер — бот на long polling работает за NAT без белого IP, для Mini App добавится туннель. План в два шага: сначала деплой compose из Actions, потом k3s как учебный этап (манифесты генерирует Aspire).

Проверить Aspire живьём

До прогона aspire run весь AppHost — непроверенный фундамент. Наращивать поверх него нельзя.

Стек Mini App

TypeScript плюс фреймворк — решается ADR после первых утверждённых макетов, не раньше.

Когда включать JetStream

Сейчас теряем сообщения при рестарте подписчика. Хорошее упражнение по надёжности — но требует durable consumers и идемпотентности разом.

Обещание пользователю

Бот — единое место правды о сходках: узнать что и когда, поучаствовать в подготовке, сохранить память о прошедшем. И не создавать шума в общем чате.

  • Тихий в чате — вся интерактивность в личке, в общем чате только обновляемый закреп
  • Одна кнопка до главного — /start и сразу ближайшая сходка
  • Редактирование вместо новых сообщений

MVP ядра

P1

Карточка сходки, календарь, RSVP «Пойду», авто-саммари в закрепе, создание и предложение сходки с модерацией, базовые роли.

  • Роли: солегуфик · организатор · солеадмин и owner
  • Полная матрица из семи ролей — только если сообщество вырастет

Топ идей из бэклога

  • Голосование за дату — крошечное, бьёт в главный блокер «когда всем удобно»
  • Витрина «кто придёт» — час работы поверх RSVP
  • Фото-альбом и ретро-опрос — закрывают память о сходке
  • «Год в соли» — лучший retention-ход и лучшая витрина Event Sourcing
  • Квизмейстер — второй модуль, проверка модульности платформы

Анти-скоуп

То, что решено не делать — чтобы пет-проект не утонул:

  • Настоящие платежи, эскроу, депозиты — только «вариант Б» со счётом и ручным подтверждением
  • Клиенты вне Telegram
  • Schema Registry
  • Публичность за пределами сообщества
