# Domain docs

Как скиллы читают доменную документацию этого репозитория перед работой с кодом.

## Перед исследованием прочитай

- **`CONTEXT.md`** в корне репозитория, если он есть.
- **`docs/decisions/`** — ADR, затрагивающие область работы. Индекс — [README.md](../decisions/README.md). Файлы называются `ADR-NNN-<slug>.md`; каталога `docs/adr/` в репозитории нет.
- Словарь домена Meetups и форма доменного события — [ADR-031](../decisions/ADR-031-meetups-domain-vocabulary-and-event-form.md).

Если файла нет — **продолжай молча**. Не сообщай об отсутствии и не предлагай создать заранее. `/domain-modeling` создаёт их лениво, когда термин или решение действительно закрывается.

## Структура

Репозиторий single-context: `CONTEXT-MAP.md` нет и не заводится, пока не появится несколько независимых доменных контекстов.

```
/
├── CONTEXT.md            ← пока не создан
├── docs/decisions/       ← ADR-001 … ADR-032
└── apps/, shared/, contracts/
```

## Используй словарь домена

Называя доменное понятие — в заголовке задачи, гипотезе, имени теста — бери термин из `CONTEXT.md` и ADR-031, а не синоним. Понятия нет в словаре — это сигнал: либо изобретается язык, которого в проекте нет, либо есть настоящий пробел; отметь его для `/domain-modeling`.

## Сообщай о конфликте с ADR

Если вывод противоречит принятому ADR, скажи это явно, а не переопределяй молча:

> _Противоречит [ADR-024](../decisions/ADR-024-meetups-state-storage-with-domain-event-log.md), но стоит переоткрыть, потому что…_

Новый ADR оформляется только скиллом `sgh-record-decision` и только после явного решения владельца.
