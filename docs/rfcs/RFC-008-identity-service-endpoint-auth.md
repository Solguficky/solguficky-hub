# RFC-008: Аутентификация служебного endpoint Identity

> **Статус:** In Review  
> **Автор:** исследование по [PER-30](https://linear.app/anticnvm/issue/per-30); решение принимает владелец  
> **Дата:** 2026-09-10

## Кратко

Служебный endpoint выдачи роли администратора — единственная точка, из которой можно выдать себе роль ([ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), [ADR-036](../decisions/ADR-036-first-admin-via-service-endpoint.md)). Чем вызывающий доказывает право на этот вызов, ещё не выбрано.

Документ отвечает на пять вопросов PER-30 фактами текущего контура и сравнивает четыре механизма. Рекомендация: **один общий секрет в metadata gRPC, один и тот же локально и в развёрнутом контуре, без обхода.** Выбор делает владелец. После выбора — короткий ADR: цена здесь в отвергнутых ослаблениях, а не в сложности самого механизма.

## Проблема и границы

### Что вынуждает решать сейчас

Первый администратор среза появляется только этим endpoint. Реализация выдачи заводится после выбора. Под давлением проверки сходки «удобно локально» прямо запрещён текстом PER-30 и ADR-036.

### Что в границах

- чем вызывающий доказывает право на maintainer-операцию;
- один механизм или разные для локальной разработки и развёрнутого контура;
- проверка права на операцию, а не только на подключение;
- аудит вызова относительно журнала доступа ADR-026;
- отношение к [ADR-005](../decisions/ADR-005-grpc-synchronous-communication.md) и инфраструктуре, которой в MVP нет.

### Что вне границ

- контракт и реализация выдачи/отзыва роли — заводятся Feature после выбора;
- чем запись роли назовёт `granted_by`: колонка сейчас `NOT NULL REFERENCES profiles(id)`, профиля maintainer'а нет. Это схема Feature, не authentication;
- service authentication вызова бота `ResolveIdentity` — отдельный открытый пункт [integration.md](../architecture/integration.md);
- админка maintainer'а — [PER-33](https://linear.app/anticnvm/issue/per-33), вне MVP; пока интерфейс — `grpcurl`;
- площадка hosting: [ADR-006](../decisions/ADR-006-railway-hosting.md) в `Needs review`, целевая площадка Open ([infrastructure.md](../architecture/infrastructure.md)).

### Кто вызывает

Не сервис сетки, а maintainer с ноутбука. PER-33 уже зафиксировал `grpcurl` как достаточный интерфейс, пока операций единицы. Механизм, который нельзя предъявить из `grpcurl`, тянет CLI, CA или VPN — инфраструктуру, которой в MVP нет.

## Факты, которые ограничивают выбор

| Факт | Источник | Следствие |
|---|---|---|
| Служебных RPC нет: только `ResolveIdentity`, health и reflection | `identity_service.proto`, `server.go` | Auth вешается на будущие maintainer-методы того же gRPC-сервера; отдельного listener нет |
| Транспорт — plaintext h2c, TLS нет | Aspire `scheme: http`, README: `grpcurl -plaintext` | Секрет в metadata едет открытым текстом по тому пути, которым идёт RPC |
| Интерцепторы уже есть: лог и recovery, auth нет | `interceptor.go` | Цепочка unary interceptor — существующий шов, не новый runtime |
| Identity endpoint публикуется на хост Aspire | `IdentitySetup.cs`, dashboard / `aspire describe` | «Слушает localhost контейнера» локально не является изоляцией от того, кто сидит за dashboard |
| Площадка production не зафиксирована | ADR-006 `Needs review`, infrastructure.md | Нельзя принять «нас спасет приватная сеть Railway» как единственную защиту |
| Публичный HTTP-прокси Railway ломает gRPC; публичный gRPC — это TCP Proxy в интернет | [документация Railway](https://docs.railway.com/networking/tcp-proxy), [разбор сотрудника](https://station.railway.com/questions/nest-js-g-rpc-request-not-working-6d81108e) | Сеть без auth превращается в дыру в тот момент, когда порт публикуют «чтобы дёрнуть grpcurl» |
| Приватная сеть Railway шифрует трафик WireGuard и не ограничивает протокол | [private networking](https://docs.railway.com/networking/private-networking) | Это защита транзита между сервисами одной среды, не доказательство, что вызывающий — maintainer |
| Журнал ADR-026 пишет смену статуса допуска, не выдачу роли | ADR-026, бриф Identity | Он не аудитит этот endpoint |
| Строка роли несёт `granted_at`, `granted_by`, `revoked_at` | миграция `00001_identity_schema.sql` | Долговечный след выдачи уже спроектирован; субъект для maintainer'а — дыра схемы, не дыра auth |
| Успешный RPC пишется на `Debug` | README Identity, `logging.md` | Выдача роли — редкая операция вне горячего цикла; её успех на границе должен быть виден без debug |

## Сценарии и требования

| Сценарий | Наблюдаемый исход |
|---|---|
| Maintainer с секретом выдаёт роль зарегистрированному профилю | успех; роль видна следующим `ResolveIdentity` |
| Вызов без секрета, с пустым секретом или с неверным | `Unauthenticated`; роль не меняется |
| Секрет не задан в процессе | maintainer-методы не исполняются; обхода «пока не задали» нет |
| Тот же процесс, `ResolveIdentity` / health | работают как сейчас, секрет не требуют |
| Локальный Aspire и развёрнутый контур | одна проверка, один заголовок, один отказ |
| Повторная выдача той же роли | идемпотентный успех (уже принято ADR-026); auth на это не влияет |
| Скомпрометирован процесс бота | без секрета выдать роль нельзя: поверхности разделены |

Требования, которые отсекают варианты до сравнения цены:

1. Доказательство права живёт в вызове, а не в том, с какого адреса пришли.
2. Локальный контур не слабее развёрнутого: нет флага «auth выключена», нет «на loopback можно без секрета».
3. Право проверяется на maintainer-методе. Подключение к порту и успешный health этого права не дают.
4. Механизм предъявляется `grpcurl` без нового бинарника и без PKI.
5. Не появляется runtime, которого нет в MVP: CA, mesh, IdP, VPN, второй listener.

## Варианты

«Ничего не менять» не содержателен: endpoint ещё не существует, а без выбранной защиты его нельзя реализовать.

### A. Общий секрет в metadata gRPC

Переменная процесса, например `IDENTITY_MAINTAINER_TOKEN`. Maintainer-методы читают `authorization: Bearer <token>` (или выделенный metadata-ключ) и сравнивают с секретом за постоянное время. Нет секрета или несовпадение — `Unauthenticated`. `ResolveIdentity`, health и reflection секрет не требуют.

Локально секрет задаёт Aspire / env, в развёрнутом контуре — секрет хостинга. Ротация — замена значения и рестарт. Клиент — `grpcurl -H`.

| | |
|---|---|
| **Цена** | Утечка секрета равна полному праву выдачи. Один секрет не различает maintainer'ов. По plaintext h2c секрет виден на пути RPC. |
| **Что не тянет** | CA, TLS, второй порт, CLI, IdP. |
| **Негативный исход** | Короткий или залогированный секрет. Лечится длиной, запретом писать значение ([logging.md](../standards/observability/logging.md)) и отсутствием обхода. |
| **Откат** | Смена interceptor'а. Данных и контракта потребителей не касается. |

Это вариант, который выглядит очевидным. Его слабость реальна: секрет статичен и не именует человека. Для одного maintainer'а и редкой операции это та цена, которую платят, чтобы не строить PKI. Опасная форма того же варианта — «секрет только в проде, локально не проверяем». Она отвергается требованиями выше, а не самим секретом.

### B. mTLS (клиентский сертификат)

Сервер требует клиентский сертификат. `grpcurl` умеет `-cert`/`-key`. Доказательство — владение ключом.

| | |
|---|---|
| **Цена** | CA или самоподписанная пара, раздача ключа, ротация, TLS вместо нынешнего h2c. Aspire и Railway mesh не предоставляют. Railway на публичном gRPC и так требует сами себе сертификаты на TCP Proxy. |
| **Что не тянет** | IdP и пользовательские сессии. |
| **Негативный исход** | PER-30 упирается в инфраструктуру, которой в MVP нет — сигнал пересмотра ADR-036. Срез снова встаёт. |
| **Откат** | Смена транспорта процесса, не только interceptor'а. |

mTLS решает чужую задачу: взаимное доверие сервисов сетки. Вызывающий здесь — человек с `grpcurl`.

### C. Подписанный токен (JWT или аналог)

Короткоживущий токен с подписью. Секрет подписи всё равно нужен.

| | |
|---|---|
| **Цена** | Выпуск токена до каждого `grpcurl`, часы, алгоритмы, срок жизни. Для операции «выдать первого администратора» истечение ничего не закрывает: вызов разовый. |
| **Что не тянет** | Полноценный IdP, если ключ локальный. |
| **Негативный исход** | Обход через вечный токен «чтобы не мучиться» — тот же общий секрет в другой обёртке, плюс поверхность ошибок подписи. |
| **Откат** | Средний: меняется формат заголовка и способ выпуска. |

Срок жизни окупается, когда вызовов много и вызывающих несколько. Сейчас ни того ни другого нет. PER-33 как раз сторожит момент, когда операции станут регулярными.

### D. Сетевая изоляция без аутентификации

Порт не опубликован, значит вызвать может только «свой». Локально — loopback, в проде — приватная сеть.

| | |
|---|---|
| **Цена** | Нулевая в коде. Вся защита — в том, как опубликован listener. |
| **Что нарушает** | Требование 1 и 2. Aspire отдаёт endpoint на хост. Публикация TCP Proxy на Railway — штатный способ «дёрнуть gRPC с ноутбука» и одновременно вход из интернета. Hosting не зафиксирован, приватной сети может не быть. |
| **Негативный исход** | Ровно дыра PER-30: локально «и так никто не увидит», в проде порт открыли для удобства. |
| **Откат** | Поздний: дыру замечают после того, как роль уже выдана. |

Изоляция сети остаётся полезным слоем *рядом* с доказательством права, а не вместо него. Бот и maintainer делят один сервер: закрыть порт для посторонних значит закрыть его и для бота либо завести второй listener — это уже вариант E.

### E. Второй listener / unix-сокет «только для maintainer»

Отдельный адрес для выдачи роли. На нём можно не требовать секрет, если он «недоступен».

| | |
|---|---|
| **Цена** | Второй bind, второй endpoint Aspire, отдельный способ достучаться в развёрнутом контуре (SSH, sidecar, ещё один TCP Proxy). |
| **Что не закрывает** | Кто именно вызвал. Доступ к сокету на машине разработчика шире, чем владение секретом. |
| **Негативный исход** | Локально сокет, в проде «пока опубликуем порт» — снова два механизма. |
| **Откат** | Топология процесса, не конфигурация. |

Имеет смысл, если появится регулярный CLI и нужно отделить нагрузку. Для первого вызова — лишний operational-контур.

## Предложение

Вариант **A**: общий секрет в metadata, одна проверка во всех контурах.

- Секрет задан — процесс слушает как сейчас. Не задан или пустой — maintainer-методы не исполняются; флага обхода нет.
- Проверка висит на конкретных RPC выдачи и отзыва, не на канале. Health, reflection и `ResolveIdentity` не становятся «входом в роль».
- Право на операцию в MVP совпадает с правом вызова: maintainer-операций две, и обе принадлежат одному секрету. Раздельные scope появятся, когда появится второй вызывающий или админка (PER-33).
- Локальный и развёрнутый контур отличаются только тем, *откуда* берётся значение секрета, а не тем, *проверяется* ли оно.
- Сеть и TLS не заменяют секрет и не откладываются этим выбором: plaintext h2c остаётся как сейчас; если listener станет доступен из интернета, это дефект публикации, и секрет всё ещё обязателен.
- Клиент — `grpcurl`. Отдельный CLI и PKI не вводятся.

Почему не B и не C: оба требуют контура, которого нет, и не дают выигрыша для одного человека с разовым вызовом. Почему не D и не E: они и есть «удобно локально»; ADR-036 уже назвал этот риск.

Оппонирование самому A. Статический секрет не атрибутирует человека и живёт, пока его не сменят. Это приемлемо, пока maintainer один и вызов редкий. Сигнал пересмотра — второй человек с правом выдачи, регулярные операции (PER-33) или публикация Identity в интернет как штатный вход.

## Аудит

Отдельная таблица аудита endpoint не нужна.

Журнал ADR-026 отвечает на вопрос «кто изменил допуск в сообщество». Выдача роли — другой вопрос, и след у него уже есть: строка `identity_roles`. Дополнить её на границе записью успеха maintainer-RPC на уровне `Info` (не `Debug`): `operation`, `result`, `identity_id` цели, `request_id`. Значение секрета не пишется.

Чего этого следа не хватает: `granted_by` не умеет назвать maintainer'а без профиля. Это закрывает Feature реализации, не этот RFC. Кандидаты там — nullable `granted_by` или явный системный субъект вне `profiles`. На выбор authentication это не влияет.

## Отношение к ADR-005

Решение остаётся на том же синхронном gRPC. Новый транспорт, отдельный HTTP-фасад и JSON не появляются. Меняется только interceptor будущих методов. Service authentication бота к `ResolveIdentity` этим не закрывается и не должна закрываться тем же секретом: иначе бот получает право выдавать роли.

## Что станет сложнее

- Aspire и ручной `identity-run` обязаны нести секрет, иначе выдачу нельзя проверить;
- ротация секрета — рестарт процесса; окна из двух секретов в MVP нет;
- plaintext h2c остаётся принятым риском локально и внутри частной сети; закрывается публикацией порта, а не этим RFC;
- один секрет = один maintainer с точки зрения доказательства права.

## Открытые вопросы

Владелец выбирает вариант. Рекомендация — A, плюс короткий ADR.

1. Принять A или другой вариант из раздела «Варианты»?
2. Согласен ли, что это ADR, а не только запись в брифе? Критерий: откат *механизма* дешёвый, откат *ослабления* (D/E, локальный обход) — дыра в модели доступа. ADR здесь сторожит отвергнутое, как ADR-036 сторожит отвергнутый bootstrap.
3. Имя секрета `IDENTITY_MAINTAINER_TOKEN` — ок или другое?

Не спрашивается в этом RFC и уходит в Feature после выбора: форма RPC, `granted_by`, контракт в `contracts/proto/`.

## Результирующие артефакты

- **ADR:** нужен, если принят любой вариант кроме «только бриф». Фиксирует механизм, запрет локального обхода и отвергнутые B–E.
- **Standard:** не нужен. Правило «не логировать секрет» уже есть в `logging.md`.
- **Бриф Identity:** после принятия убрать вопрос из «Открытых вопросов» и описать выбранный механизм.
- **Задачи Linear:** Feature на контракт и реализацию выдачи — после принятия, не сейчас. PER-33 не двигается.
