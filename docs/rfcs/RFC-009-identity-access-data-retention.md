# RFC-009: Retention и жизненный цикл данных доступа Identity

> **Статус:** Accepted, [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md)  
> **Автор:** исследование по [PER-29](https://linear.app/anticnvm/issue/per-29); решение владельца — смешанный пакет  
> **Дата:** 2026-09-10

## Кратко

ADR-026 ввёл четыре набора данных о людях и ни у одного не назвал срок жизни. Владелец 2026-09-10 принял для хаба: whitelist гасится **пометкой без TTL**; закрытый человек — `blocked`; **пригласительные ссылки откладываются** — два пути: общая ссылка на бота и whitelist, плюс `pending` с ручным `allowed`; журнал **вечен независимо от профиля** и называет людей внутренним `identity_id`. Решение записано в [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md).

Второй вход — бот аукциона с более широкой аудиторией и shared-ссылкой — не получает ни второго Identity, ни своей авторизации внутри бота. Текущий `pending` / `allowed` / `blocked` — это допуск к хабу, а не «в продукт вообще». Области и роли аукциона остаются [PER-146](https://linear.app/anticnvm/issue/per-146); этот RFC только запрещает схеме MVP сделать их невозможными.

«Хранить всё вечно» здесь не дефолт, а отдельный ответ с обоснованием: для допуска к хабу оно принимается только для профиля и журнала, потому что удаление ломает уже принятые инварианты. На посетителей аукциона по shared-ссылке это обоснование не переносится.

## Проблема и границы

### Что вынуждает решать сейчас

Схема whitelist и журнала ещё не заведена; инвайт-токены в этом срезе не появляются. Срок жизни — свойство записи, а не поздняя уборка: без политики Feature премодерации либо хранит PII без цели, либо удаляет строку, от которой зависит дыра в допуске. Листья [PER-76](https://linear.app/anticnvm/issue/per-76) это кодируют; этот RFC выбирает политику до схемы.

### Что в границах

- список разрешённых ников: что значит «гасится», сколько живёт непогашенная запись;
- инвайт-токены хаба: в этом срезе не заводятся; TTL не выбирается;
- профиль закрытого человека: удаление, `blocked` навсегда или архив;
- журнал доступа: свой срок, отличный от профиля, или нет;
- какой допуск кодируют эти наборы, если платформа имеет два входа.

### Что вне границ

- формат payload инвайт-токена рядом с `m_<uuid>` — не в этом срезе: приглашения отложены;
- точная схема таблиц, джоб уборки и команд бота — Feature после выбора;
- retention прикладных логов Loki — [logging.md](../standards/observability/logging.md) его в MVP не проектирует;
- исходящие события Identity и ретеншен стрима JetStream — контракт событий ещё Open;
- строки `identity_roles` с `revoked_at` — история роли уже принята ADR-026 и этим вопросом не пересматривается;
- **области доступа хаб / аукцион, роли аукциона (администратор, ведущий, помощник), что делает `/start` в боте аукциона** — [PER-146](https://linear.app/anticnvm/issue/per-146). PER-146 прямо не пересматривает механику премодерации хаба;
- **второй бот, два токена, где живёт проверка области** — [PER-147](https://linear.app/anticnvm/issue/per-147);
- запрос человека «забудьте меня» и юридический режим 152-ФЗ — не продукт MVP; сигнал пересмотра, не вариант сейчас.

### Что уже решено и этим RFC не переоткрывается

- блокировка сохраняет профиль и внутренний идентификатор ([ADR-026](../decisions/ADR-026-identity-mvp-model-and-access.md), состав MVP в [overview.md](../product/overview.md));
- повторный допуск возвращает ту же identity, роли не восстанавливает;
- подписки Notifications переживают блок и возврат, потому что identity стабильна ([ADR-028](../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md));
- whitelist применяется один раз при регистрации, а не на каждом действии; обещание «у списка есть срок жизни» владелец ослабляет: TTL нет, гашение пометкой;
- одноразовая инвайт-ссылка из ADR-026 в этом срезе **не реализуется** — владелец отложил, пока нет наблюдаемой потребности;
- журнал не источник истины и не участвует в проверке доступа;
- второй бот, если появится, — отдельный компонент с отдельным токеном: два поллера на одном токене конфликтуют ([ADR-030](../decisions/ADR-030-telegram-bot.md));
- Identity отвечает «кто это», «что можно» — владелец ресурса: Meetups для сходок, аукцион для ставок (бриф Identity).

## Факты, которые ограничивают выбор

| Факт | Источник | Следствие |
|---|---|---|
| Ник — PII людей, которые к боту ещё не обращались | [overview.md](../product/overview.md) | Непогашенный whitelist — самое чувствительное из четырёх хранилищ; «вечный список» превращает его в реестр, который продукт запретил |
| Ник переиспользуем | ADR-026 | Помеченная использованной строка с уникальностью по нику закрывает ник новому человеку; удаление погашенной строки это не ломает |
| После регистрации ник живёт кэшем профиля | бриф Identity | Погашенная строка whitelist — вторая копия той же PII без своей цели |
| Токен до погашения — предъявительский секрет | ADR-026 | Срок жизни — окно утечки, не уборка. Пересланная ссылка работает у того, кто нажал первым |
| Payload `/start` — до 64 символов `A-Za-z0-9_-` | [Deep Linking](https://core.telegram.org/bots/features#deep-linking) | Энтропия токена ограничена форматом; окно жизни нельзя раздувать «потому что токен длинный» |
| Сырой payload и сам токен в лог не пишутся | [logging.md](../standards/observability/logging.md) | Утечка токена — база, бэкап и пересылка ссылки, не журнал приложения |
| Журнал пишет, кто кого допустил | ADR-026 | «Чужое погашение обнаруживается» — это журнал, а не вечное хранение самого токена |
| `blocked` сохраняет identity | ADR-026 | Удаление профиля = новый `/start` → новый id в `pending` |
| Подписки не гасятся блокировкой | бриф Notifications | Удаление профиля либо уничтожает настройки, либо требует tombstone и перепривязку — отдельного решения на это нет |
| Meetups хранит `author UUID` в своей базе | миграция Meetups | Межбазовой FK нет, но стабильный id — обещание ссылок; новый id после удаления — чужой автор |
| Схема whitelist и журнала не заведена; инвайт-токенов в срезе нет | миграции Identity: `profiles`, `identity_roles` | Политика должна быть свойством будущей строки (пометка погашения, уникальность только среди непогашенных), а не поздним CRON, от которого зависит допуск |
| Объём сообщества хаба — десятки-сотни людей, не миллионы | продукт | Для *хаба* цена хранения ничтожна; аргумент «вечно, потому что дёшево» не проходит критерий минимизации |
| Аудитория аукциона шире аудитории чата: торговать пускаем чужих, сходки им не открываем | [PER-146](https://linear.app/anticnvm/issue/per-146), [RFC-007](RFC-007-auction-scope-and-format-options.md) | Один статус «допущен к продукту» не умеет этого. Посетитель по shared-ссылке не должен оказаться в очереди хаба |
| Ссылку на аукцион будут широко пересылать | [PER-147](https://linear.app/anticnvm/issue/per-147) | Shared-ссылка аукциона — не одноразовый инвайт хаба. Срок 7 дней и погашение «кто первый нажал» к ней неприменимы |
| `ResolveIdentity` создаёт профиль в `pending` при первом обращении | код Identity, ADR-026 | Если бот аукциона вызовет тот же RPC до областей доступа, каждый посетитель станет кандидатом в сообщество сходок |
| Бот не содержит доменных правил допуска | бриф Identity | Второй бот тоже не заводит свою авторизацию: он предъявляет Telegram user id и применяет ответ Identity |

Строки про токен и payload относятся к отложенному инвайту: в схеме этого среза их нет; если инвайт вернут, TTL выбирается заново.

## Сценарии и требования

| Сценарий | Наблюдаемый исход |
|---|---|
| Человек из whitelist нажал `/start` с этим ником | профиль `allowed`; строка списка больше никого не допускает |
| Тот же ник позже занял другой человек, его добавили в список | новый человек допускается своей записью; старая погашенная ему не мешает |
| Ник в списке, человек так и не пришёл | запись остаётся непогашенной, пока администратор не удалит; в проверке после чужой регистрации не участвует |
| Нет в whitelist или нет ника, открыл общую ссылку бота хаба | профиль `pending`; отказ без данных сходок; допуск только ручным `allowed` |
| Администратор перевёл `pending` в `allowed` | тот же `identity_id`, сходки видны |
| Человека закрыли, он снова жмёт `/start` | тот же `identity_id`, статус `blocked`, отказ без данных сходок |
| Закрытого вернули | та же identity, `allowed`, роли не вернулись, подписки Notifications на месте |
| Закрытого удалили бы из `profiles` | новый `/start` создаёт новый id в `pending`; совпадение с живым whitelist — автодопуск |
| Администратор спрашивает, кто закрыл человека | ответ в журнале, пока действует сам статус |
| Человек из whitelist открыл бота хаба | допуск к хабу `allowed`; сходки видны |
| Тот же человек, не из списка, открыл бота аукциона по shared-ссылке | тот же `identity_id`, если профиль уже есть, или новый профиль; **хаб не становится `pending` и не становится `allowed`**; сходки закрыты |
| Человек только с аукциона написал боту хаба | отказ без данных сходок; не очередь «ждёт допуска в сообщество», пока его туда явно не взяли |
| Закрыли доступ к хабу | сходки больше не видны; доступ к аукциону этим RFC не отзывается — это [PER-146](https://linear.app/anticnvm/issue/per-146) |

Требования, которые отсекают варианты до сравнения цены:

1. У каждого чувствительного поля есть цель и срок. Срок «пока продукт жив» допустим, только если цель действует столько же.
2. Источник истины допуска к хабу — статус профиля хаба. Срок жизни whitelist не может зависеть от того, успел ли отработать janitor. Если инвайт вернут, то же правило для токена.
3. Удаление не создаёт путь в допуск к хабу в обход явного решения администратора.
4. Погашенная запись не держит ник как занятый ключ: ник переиспользуем.
5. Не появляется четвёртое состояние доступа к хабу («архив») без своего ответа человеку: `pending` и `blocked` уже различаются текстами, третьего кадра для «архива» нет.
6. Четыре набора PER-29 описывают **хаб**. Посетитель аукциона по shared-ссылке не наследует ни очередь `pending`, ни «навсегда» журнала и блока хаба. Второй Identity и локальная авторизация в боте аукциона не появляются.

## Два входа, один Identity

Владелец уточнил ограничение: бот аукциона будет отдельным, потому что аудитория шире; второго Identity и авторизации внутри нового бота быть не должно; люди из whitelist — это те, кому открыт основной бот, остальные заходят в аукцион по shared-ссылке.

Это уже названо в backlog, не с нуля. [PER-146](https://linear.app/anticnvm/issue/per-146) вводит раздельный допуск к хабу и к аукциону. [PER-147](https://linear.app/anticnvm/issue/per-147) отделяет вход: ссылку на аукцион будут широко пересылать, два поллера на одном токене конфликтуют. ADR-026 при этом знает **один** допуск к продукту. Пока схема MVP пишет этот один допуск как «весь продукт», PER-146 потом либо мигрирует всех посетителей аукциона из очереди хаба, либо мирится с дырой «чужой видит сходки / чужой висит в pending».

### Что из этого следует для PER-29, а что нет

PER-29 не проектирует области и роли аукциона. Он обязан не заложить одну калитку.

| Слой | Где живёт | Чего здесь не делать |
|---|---|---|
| Личность | один Identity, один `identity_id` на Telegram-аккаунт | не заводить Identity-2 и не резолвить личность внутри бота аукциона |
| Допуск к хабу | `pending` / `allowed` / `blocked` + whitelist + журнал; одноразовый инвайт отложен | не называть это «ролью» и не открывать им аукцион «за компанию» |
| Допуск к аукциону | область доступа, [PER-146](https://linear.app/anticnvm/issue/per-146) | не кодировать shared-ссылку одноразовым инвайтом хаба |
| Ставка, лот, ведущий | аукцион как владелец ресурса | не складывать это в `identity_roles` рядом с `admin` |
| Проверка на входе | бот вызывает Identity и fail-closed, если его поверхности нет в ответе | не держать второй список ников / пароль / «если этот бот — пускаем» в composition root аукциона |

«Роль людей из белого списка» в словаре репозитория — это не `identity_roles`. Роль сейчас одна: администратор хаба. Whitelist выдаёт **допуск к поверхности хаба**. Если записать membership хаба ролью `community`, роль и допуск смешаются, а «что можно на сходке» опять окажется в Identity — прямо против границы сервиса. Аукционные роли (ведущий, помощник зала) — тоже PER-146, и они не про вход по shared-ссылке.

Shared-ссылка аукциона — другой объект. Одноразовый инвайт хаба в этом срезе не реализуется; даже если его вернут, он предъявительский и погашается первым нажатием. Ссылку аукциона как раз **нужно** пересылать; «кто первый нажал» и TTL 7 дней там были бы поломкой входа. Общая ссылка бота хаба (`t.me/bot`) уже публична и тоже не секрет: калитка — whitelist и очередь `pending`, не хвост `/start`.

### Как бот аукциона не заводит свою авторизацию

Тот же контракт, что у хаба: бот устанавливает Telegram user id, Identity отвечает внутренним идентификатором и фактами допуска. Бот аукциона не хранит состав, не сверяет ники и не выдаёт доступ. Он только отказывается, если в ответе нет допуска к *его* поверхности. Где именно стоит эта проверка, чтобы её нельзя было забыть в одном из двух входов, решает PER-147; здесь фиксируется, что проверяемый факт принадлежит Identity.

Опасный путь без областей: `ResolveIdentity` как сейчас создаёт `pending` на любое первое обращение. Бот аукциона, подключённый к этому RPC, наполняет очередь модерации хаба посторонними. Для MVP это ещё не грозит — второго бота нет. Для схемы премодерации грозит имя и смысл колонки: статус надо считать **допуском к хабу**. Feature [PER-76](https://linear.app/anticnvm/issue/per-76) не должна писать в бриф и в комментарии к схеме «допуск к продукту».

### Цена для retention

Обоснование «закрытый профиль и журнал навсегда» держится на цели «этому аккаунту нельзя в сообщество сходок, и решение объяснимо». У человека, который только открыл shared-ссылку аукциона, этой цели нет. Если на него перенести пакет B, Identity станет реестром широкой аудитории события — ровно то, что минимизация запрещает, а PER-29 просил обосновать. Срок жизни посетителя аукциона, переживает ли допуск само событие, и блок хаба vs блок аукциона — критерии приёмки PER-146, не числа этого RFC.

Пока областей нет, пакет B безопасен только если единственный вызывающий `ResolveIdentity` — бот хаба. Это операционный инвариант MVP, не модель навсегда.

## Варианты по вопросам среза

«Ничего не менять» не содержателен: записей ещё нет, а Feature без чисел либо не пишет срок, либо выбирает его молча в миграции.

### 1. Список разрешённых ников

**Гашение при регистрации**

| | Удалить строку в той же транзакции, что допуск | Пометить использованной и оставить |
|---|---|---|
| **Цель после погашения** | нет: ник уже кэш профиля, факт допуска — в журнале | повторно увидеть «этот ник уже заходил» без журнала |
| **Переиспользование ника** | новый человек добавляется новой строкой | уникальность по нику мешает; частичный уникальный индекс на непогашенных это чинит ценой второй копии PII |
| **Минимизация** | вторая копия PII не живёт | живёт без своей цели, пока строку не уберут отдельно |
| **Откат** | удаление необратимо; журнал остаётся | строку можно вернуть в непогашенные — и это снова реестр |

Владелец выбрал **пометку**: список остаётся мини-реестром одноразового допуска, после регистрации к нему не обращаются. Уникальность — только среди непогашенных, иначе переиспользованный ник нельзя добавить. Удаление отвергнуто как менее наблюдаемое.

**Непогашенная запись**

| | A. 14 дней | B. 30 дней | C. Без срока, удаляет администратор |
|---|---|---|---|
| **Цель** | список — разовый пропуск к ближайшей сходке, не абонемент | тот же пропуск с запасом на человека, который открыл бота не сразу | постоянный черновик состава |
| **Риск** | администратор перезаливает список чаще | произвольное круглое число | список становится реестром людей, которые о продукте могут не знать |
| **Сигнал пересмотра** | жалобы «не успел» | то же, либо растущий хвост неиспользованных | сам факт, что никто не чистит |

Владелец выбрал **без TTL**. Цена — ники людей, которые так и не пришли, живут пока их не удалят руками. Это ослабляет обещание overview, что у списка есть срок жизни; принимается только явно.

### 2. Инвайт-токены хаба — откладываются

Владелец: приглашения пока необязательны, возможно решается проблема, которой нет. В этом срезе **два пути** допуска в хаб:

1. **Общая ссылка на бота хаба** (`t.me/bot`, уже публична) + **whitelist**. Совпал непогашенный ник на `/start` → `allowed`.
2. Нет в списке или нет ника → профиль **`pending`** → администратор **вручную** переводит в `allowed`.

Одноразовая персональная ссылка из ADR-026 в схему, контракт и команды бота этого среза **не входит**. Это не shared-ссылка аукциона ([PER-146](https://linear.app/anticnvm/issue/per-146), [PER-147](https://linear.app/anticnvm/issue/per-147)). Кадр [PER-32](https://linear.app/anticnvm/issue/per-32) «вход по приглашению» откладывается вместе с токенами.

Цена известна и принимается явно: человек **без ника** не может попасть в `allowed` первым `/start`. Он всегда видит отказ и ждёт ручного допуска. Whitelist бессилен без ника; без инвайта это не дыра, а очередь.

Сигнал вернуть инвайт: онбординг людей без ника упирается в экран отказа чаще, чем приемлемо. Тогда TTL, хэш токена и кадр PER-32 выбираются заново — строки про токен в таблице фактов выше к тому моменту остаются в силе. Сейчас число TTL не спрашивается.

### 3. Профиль закрытого человека

| | Удалить | `blocked` навсегда | Четвёртое состояние «архив» |
|---|---|---|---|
| **Повторный `/start`** | новый id, `pending`; живой whitelist с тем же ником — автодопуск | тот же id, отказ, пока администратор явно не вернёт | тот же id, если архив отвечает как `blocked`; иначе это удаление под другим именем |
| **Подписки Notifications** | надо tombstone и решать, что делать с настройками | переживают блок, как уже принято | то же, плюс новое состояние в реплике |
| **Ссылки Meetups `author`** | висячий UUID без человека | стабильны | стабильны |
| **Сверка состава** | закрытый исчезает из списка; администратор может допустить «нового» того же Telegram-аккаунта | виден как закрытый, ник-кэш узнаваем | нужен кадр, которого нет |
| **Минимизация** | PII уходит | Telegram user id, ник и статус живут, пока живёт решение «этому аккаунту нельзя» | те же данные плюс словарь |

Удаление — дыра, которую PER-29 прямо называет. Она не гипотетическая: whitelist как раз и срабатывает на `/start` нового профиля. Архив без своего ответа человеку — четвёртое состояние в нарушение требования 5.

Рекомендация: **остаётся `blocked` навсегда как допуск к хабу**, включая ник-кэш и Telegram user id. Это как раз случай «хранить вечно», и обоснование не «мало данных», а действующая цель: не пустить этот аккаунт в сходки без явного допуска и не порвать identity, на которую уже опираются Notifications и Meetups. Отзыв аукциона этим не утверждается.

Срок «пока хаб жив» пересматривается, если появится отдельное продуктовое «забудьте этого человека» с tombstone во все реплики. В MVP такого сценария нет. Пересмотр «блок хаба = блок аукциона» — [PER-146](https://linear.app/anticnvm/issue/per-146).

Профили, которые так и остались в `pending`, PER-29 не спрашивает. Они — очередь администратора, не закрытый доступ. Автоудаление `pending` тем же TTL, что whitelist, смешает «не пришёл по списку» и «нажал `/start` и ждёт». Автоудаление `pending` в этом срезе не входит: остаются, пока администратор не допустит или не закроет.

### 4. Журнал доступа

Журнал объясняет текущий статус. Пока статус действует, цель журнала действует.

| | Короткий TTL (12 месяцев), профиль живёт | Пока живёт профиль | Вечно независимо от профиля |
|---|---|---|---|
| **«Кто закрыл» через год** | неотвечаемо, блок ещё действует | отвечаемо | отвечаемо даже после удаления профиля, которого в B нет |
| **Минимизация** | старые переходы `pending → allowed` уходят | история человека живёт с ним; объём — единицы строк на человека | журнал переживает профиль и становится вторым реестром |
| **Проверка доступа** | не затрагивается ни одним вариантом | то же | то же |

Рекомендация RFC была: журнал живёт столько же, сколько профиль. Владелец выбрал **вечно, независимо от профиля**: это история решений, не реестр людей; TTL при необходимости выставится позже. Строка называет subject и actor внутренним `identity_id`, не Telegram user id и не ником.

## Пакеты

Whitelist, закрытый профиль и журнал связаны: удаление профиля обессмысливает короткий журнал, а пометка whitelist спорит с переиспользованием ника. Инвайт из сравнения выпал — владелец отложил его. Ниже пакеты — цена отвергнутых сочетаний по оставшимся вопросам, не меню TTL токена.

### A. Минимизация

14 дней на непогашенный ник, гашение удалением. `blocked` всё равно навсегда: иначе дыра. Журнал — 12 месяцев.

| | |
|---|---|
| **Цена** | Частые перезаливки списка. Годовалый блок необъясним. |
| **Что выигрывает** | Наименьший хвост PII людей, которые так и не пришли. |
| **Негативный исход** | Администратор расширяет сроки «чтобы не мешало» — и пакет тихо становится C без решения. |
| **Откат** | Уже удалённые строки не вернуть. |

### B. Целостность модели ADR-026 без инвайта в срезе

Гашение whitelist удалением; непогашенное — 30 дней. `blocked` навсегда. Журнал — с профилем. Одноразовый токен ADR-026 в срез не входит.

| | |
|---|---|
| **Цена** | TTL и janitor, который не является источником истины. Закрытые люди и журнал накапливаются. |
| **Что выигрывает** | Список не реестр, identity стабильна, допуск объясним, пока действует. |
| **Негативный исход** | 30 — круглое число. Лечится сигналом: перезаливка тех же ников каждую сходку → длиннее. |
| **Откат** | Удлинить TTL — правка константы. Укоротить — не возвращает уже удалённые ники. Удалить `blocked` позже — новое решение с tombstone. |

«Навсегда» для закрытых — исключение из минимизации. Оно принято не по лени, а потому что альтернатива — дыра и слом реплики.

### C. Эксплуатационный запас

Гашение — пометка; непогашенное без TTL, чистит администратор. `blocked` навсегда. Журнал вечен независимо от профиля.

| | |
|---|---|
| **Цена** | Список становится реестром. Помеченный ник спорит с переиспользованием, пока уникальность не вынесут на частичный индекс. |
| **Что выигрывает** | Отладка и «кто уже заходил» без похода в журнал. |
| **Негативный исход** | Ровно то, что продукт запретил: постоянный реестр людей, которые могли не знать о боте. |
| **Откат** | Поздний: данные уже собраны, удаление — отдельная зачистка. |

## Предложение

Смешанный пакет принят владельцем 2026-09-10 и записан в [ADR-038](../decisions/ADR-038-identity-hub-access-retention.md).

- **Whitelist хаба.** Гашение — **пометка использованной и оставить**, не удаление. TTL нет: непогашенное живёт, пока администратор не удалит. Список — предварительный шаг регистрации, после `/start` к нему не обращаются. Уникальность только среди непогашенных: иначе занятый другим человеком ник нельзя добавить снова. Список не выдаёт доступ к аукциону.
- **Инвайт хаба.** В этом срезе **нет**. Два пути: общая ссылка на бота хаба + whitelist; иначе `pending` и ручной `allowed`. Третий путь ADR-026 (одноразовая персональная ссылка) не реализуется, пока онбординг без ника не упрётся в экран отказа. Shared-ссылка аукциона — другой объект ([PER-146](https://linear.app/anticnvm/issue/per-146), [PER-147](https://linear.app/anticnvm/issue/per-147)).
- **Закрытый человек хаба.** `blocked` навсегда, identity сохраняется. Удаление и архив отвергнуты владельцем. Повторный допуск — то же `identity_id`, роли не возвращаются.
- **Журнал.** Append-only след «кто сменил чей допуск к хабу, когда, из какого статуса в какой». Не источник истины, в проверке доступа не участвует. Срок — **вечно, независимо от профиля**. Людей называет `identity_id`: subject — чей допуск, actor — кто сменил (`NULL` на системный переход whitelist). Telegram user id и ник в журнал не пишутся.
- **Имя в схеме.** Допуск к хабу, не «к продукту». Бот аукциона не зовёт сегодняшний `ResolveIdentity` до PER-146.

Оппонирование whitelist без TTL. Запрет реестра в [overview.md](../product/overview.md) относится не к диску, а к никам людей, которые к боту не обращались и могут не знать о продукте. Погашенная строка — вторая копия ника, который уже кэш профиля; её цена мала, если на ней нет уникальности. Непогашенная без срока — стоячий список таких людей. «Не будут чистить» здесь не про объём, а про отсутствие цели, когда человек так и не пришёл. Владелец принял эту цену явно. Частичный уникальный индекс на непогашенных обязателен.

Оппонирование отложенному инвайту. Люди без ника всегда идут через `pending`. Это дешевле, чем заводить предъявительский секрет «на всякий случай». Цена не в схеме, а в очереди модерации и в кадре отказа. Если очередь без-ников станет основной массой — инвайт возвращается отдельным решением, не молча в Feature.

## Что такое журнал

Это не лог приложения и не Event Sourcing. У профиля есть текущий статус — его читает проверка доступа. Журнал рядом пишет факты смены этого статуса в той же транзакции: администратор А перевёл identity X из `pending` в `allowed` в момент T. По нему отвечают «кто пустил / кто закрыл», не «можно ли сейчас пускать». Роли администратора в него не входят: у роли свой след в `identity_roles`.

Людей в строке называет внутренний `identity_id`, не Telegram user id. Actor — администратор, который сменил статус; `NULL`, если переход сделала система (whitelist на `/start`). Ник и Telegram user id живут на профиле; журнал к ним не join'ится в горячем пути и не копирует их. Владелец принял срок «вечно, независимо от профиля»: это история UUID, не второй список аккаунтов.

Без журнала остаётся только текущая строка профиля: видно, что человек `blocked`, не видно, кто и когда. Сворачивать статус из журнала на каждом Telegram update ADR-026 отверг: проверка fail-closed не должна читать историю.

## Сценарии блока — не архив и не удаление

Владелец: архив не нужен, полное удаление не нравится, скорее `blocked`. Identity хранит **Telegram-аккаунт**, не человека в жизни.

| Юзкейс | Что делает продукт | Чего нельзя ждать |
|---|---|---|
| Был `allowed`, вышел из аудитории хаба | `blocked`, тот же id; повторный `/start` — отказ без сходок | Автовозврат, если снова появился в чате: членство чата продукт не видит |
| Был `pending`, не дали `allowed` | остаётся `pending` — очередь, не блок. Блок pending — отдельное «этого не хотим даже в очереди» | Что `pending` сам истечёт |
| Вернулся после отъезда | повторный допуск того же id в `allowed`; роли не восстанавливаются | Что блок «протухнет» сам |
| За нарушения | тот же `blocked`; возврат только явным допуском | Отдельный статус «бан» vs «уехал»: одного `blocked` достаточно |
| Временно не писал боту | ничего; следующий апдейт резолвит ту же identity | Блокировать «за тишину» |
| Потерял Telegram-аккаунт, зашёл с нового | новый `telegram_user_id` → **новая** identity в `pending`. Старая строка жива | Склейка людей |
| Несколько аккаунтов одного человека | несколько identity. Ник в один момент принадлежит одному аккаунту; второй путь — ручной допуск | Один профиль на человека |

Склейка аккаунтов в PER-29 не входит: для этого нет сигнала в Telegram, кроме совпадения ника в узком окне, а ник нельзя делать ключом.

## Инвайт хаба откладывается

ADR-026 выбрал третий путь — одноразовую персональную ссылку — для людей **без ника**, чтобы первый `/start` сразу был `allowed`. Владелец отложил его: наблюдаемой потребности нет, общая ссылка бота уже публична.

| Вопрос | Ответ этого среза |
|---|---|
| Для какой аудитории был бы инвайт? | Хаб. Человек сообщества без ника, или кого нет в whitelist, но пустить надо сразу |
| Реализуется сейчас? | Нет. Схема, команды и кадр PER-32 не заводятся |
| Чем заменяется? | Общая ссылка на бота хаба + whitelist; иначе `pending` и ручной `allowed` |
| Для внешней аудитории? | Нет. Внешние — бот аукциона и его shared-ссылка |
| Есть в whitelist → сразу `allowed`? | Да, на `/start` бота хаба |
| Нет в whitelist / нет ника? | Профиль создаётся в `pending`. Ссылка на бота хаба публична |
| Единственный вход в бота хаба? | Нет. Два пути плюс голый `/start` без payload |
| Вход в бота аукциона? | Нет, и не вход вовсе |

Цена: первый контакт человека без ника — всегда отказ и ожидание. Сигнал вернуть инвайт — эта очередь становится основной массой онбординга, а не запасным путём.

## Что станет сложнее

- люди без ника всегда видят `pending`, пока администратор не допустит вручную;
- whitelist без TTL копит ники людей, которые так и не пришли; чистка только ручная;
- закрытые профили хаба накапливаются, список состава обязан уметь фильтр по статусу;
- колонка допуска в MVP уже должна называться так, чтобы PER-146 добавлял область, а не переименовывал «весь продукт»;
- потерянный Telegram-аккаунт не сливается со старым профилем;
- вернуть инвайт позже — отдельное решение: TTL, хэш, кадр PER-32 и обещание overview про персональные приглашения.

## Открытые вопросы

Принято целиком: гашение whitelist пометкой без TTL; закрытый человек — `blocked`; инвайт хаба в этом срезе не реализуется; журнал вечен независимо от профиля и оперирует `identity_id`.

Формат payload, схема таблиц, команды бота, области аукциона, склейка аккаунтов, возврат инвайта этим выбором не закрываются.
