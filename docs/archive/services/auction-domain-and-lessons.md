# Аукцион: доменная модель и уроки реализации

> **Историческое.** Извлечено из кода четырёх сервисов предыдущего поколения — C#/Akka.NET Auction Service, Rust/Teloxide Telegram Gateway, C# Notifications Service и C#/SignalR WebSocket Gateway — перед их удалением из репозитория 2026-08-24.
>
> Документ фиксирует **то, что было реализовано**, а не то, что задумывалось. Замысел лежит в соседних ТЗ: [auction-service-akka-design.md](auction-service-akka-design.md), [telegram-gateway-rust-design.md](telegram-gateway-rust-design.md), [notifications-auction-design.md](notifications-auction-design.md), [websocket-gateway-auction-design.md](websocket-gateway-auction-design.md). Продуктовая спецификация будущего аукциона — [product/future/auction.md](../../product/future/auction.md).

## Зачем этот документ

Удаляемый код был единственным местом, где доменные правила аукциона существовали в исполнимой форме. ТЗ описывают намерение и расходятся с реализацией в важных местах: часть механик не написана вовсе, часть работает не так, как записано. Ниже — срез фактического поведения, набор дефектов и список гипотез, которые код так и не проверил.

Каталог дефектов (§5) ценнее доменной модели: модель будет спроектирована заново, а перечисленные ошибки повторяются в любой реализации торгов.

## 1. Доменная модель как она была реализована

### 1.1. Сущности

| Сущность | Идентификатор | Где жила |
|---|---|---|
| Аукцион | `Guid`, строка длиной 36 в контрактах | Актор `auction-{guid}`, журнал событий |
| Лот | `int`, автоинкремент PostgreSQL | Строка таблицы (атрибуты) + актор `lot-{id}` (торги) |
| Ставка | не адресуется | Событие `BidPlaced` в журнале лота |
| Прокси-ставка | ключ — `user_id` | `ImmutableDictionary<long, double>` в состоянии лота |

Атрибуты лота, заведённые через бота: название (≤100 символов при вводе, ≤500 в БД), описание (≤5000), стартовая цена, минимальный шаг, ссылка на изображение (необязательная), порядок отображения.

Разделение показательное: **статические атрибуты лота хранились строкой в БД, а торговое состояние — событиями в журнале актора**. Два хранилища на одну сущность связывались только числовым `lot_id`.

### 1.2. Фазы аукциона

```
NotStarted ──StartAuction──▶ OpenBidding ──EndOpenBidding──▶ Idle
                                                              │
                                                     StartFinalPhase
                                                              ▼
   Finished ◀────────FinishAuction──────────────────────── Final
```

`StartAuction` персистит **два** события подряд: `AuctionStarted`, затем сразу `OpenBiddingStarted`. Отдельного состояния «аукцион создан, торги не начаты» не существовало.

Переходы проверялись строго: `EndOpenBidding` принималась только из `OpenBidding`, `StartFinalPhase` — только из `Idle`. `FinishAuction` принималась из любой фазы кроме `Finished`.

Событие `FinalPhaseEnded` объявлено и применяется при восстановлении, но **не персистится ни одной командой**. Переход `Final → Finished` возможен только через `FinishAuction`.

### 1.3. Правило приёма ставки

Единственное доменное правило, доведённое до конца:

```
minRequired = (CurrentPrice ?? StartingPrice) + MinBidStep

if IsFinished           → BidRejected("Auction for this lot has finished.")
if Amount < minRequired → BidRejected("Minimum bid required: {minRequired}")
else                    → BidPlaced(UserId, Amount, PreviousLeaderId, ts)
```

Ставка выше минимума принималась любая — верхней границы и проверки кратности шагу не было. Ставка лидера поверх собственной ставки не запрещалась.

### 1.4. Алгоритм прокси-ставок

Запускался после каждой принятой ставки и рекурсивно после каждой автоставки:

```
currentPrice = CurrentPrice ?? StartingPrice

contender = прокси-ставка с максимальным MaxAmount
            среди тех, где user ≠ CurrentLeaderId и MaxAmount > currentPrice
            при равенстве максимумов — меньший user_id
если contender нет → стоп

если у текущего лидера есть прокси-ставка L:
    nextBid = min(contender.Max, L + MinBidStep)
иначе:
    nextBid = currentPrice + MinBidStep

nextBid = min(nextBid, contender.Max)

если nextBid > currentPrice:
    персистить BidPlaced(contender, nextBid, предыдущий лидер)
    повторить
```

Свойства, которые стоит осознанно подтвердить или изменить в новой реализации:

- **против ручного лидера** прокси перебивает ровно на один шаг — классическое поведение;
- **против другого прокси** ставка сразу прыгает к `min(свой максимум, чужой максимум + шаг)`, то есть война двух прокси сходится за одну итерацию, а не серией шагов;
- **при равных максимумах** выигрывает меньший `user_id`, а не тот, кто поставил раньше: время установки прокси-ставки в состоянии не хранилось;
- **каждая автоставка — отдельное персистируемое событие**, публикуемое наружу. Серия автоставок порождает серию уведомлений «вашу ставку перебили», а не одно итоговое.

## 2. Actor/event-логика

### 2.1. Иерархия

```
AuctionRegistry (ReceiveActor, без персистентности)
└── auction-{guid}   AuctionActor (ReceivePersistentActor)
    └── lot-{id}     LotActor     (ReceivePersistentActor)
```

Реестр создавал аукцион по требованию (`Context.Child` → `IsNobody()` → `ActorOf`), аукцион создавал акторы лотов при старте торгов. Маршрутизация — двумя конвертами: `ForwardToAuction` и `ForwardToLot`.

`PersistenceId` — `auction-{guid}` и `lot-{id}`. Идентификатор лота глобальный, а не составной: **два аукциона не могли содержать лот с одним номером**, хотя иерархия акторов это допускала.

### 2.2. Публикация событий наружу

Наружу события уходили не из акторов, а из отдельной проекции. Механизм:

1. `AuctionEventTagger` (`IWriteEventAdapter`) помечал **каждое** записываемое событие тегом `auction`;
2. `AkkaPersistenceQueryListener` читал `EventsByTag("auction", Offset.NoOffset())` через Akka.Persistence.Query;
3. доменное событие отображалось в Protobuf-сообщение и публиковалось в NATS.

Это рабочая и переиспользуемая идея: **актор ничего не знает о шине, наружу публикует проекция журнала**. Именно на неё ссылается [ADR-024](../../decisions/ADR-024-meetups-state-storage-with-domain-event-log.md), когда говорит, что события уже публиковались через persistence query. Её дефекты — в §5, пункты 5.5 и 5.6.

### 2.3. Что домен так и не получил

- **Лот никогда не продавался.** `LotSold` объявлено и применяется при восстановлении, но не персистится ни одним обработчиком. Победитель не определялся нигде.
- **Время не участвовало.** `EndTime` в состоянии лота всегда `null`; таймеров, дедлайнов и анти-снайпа не было.
- **Фаза `Final` ничего не меняла для лотов.** Приём ставок в ней не отличался от `OpenBidding`.
- **Снятие и изменение прокси-ставки** не предусмотрено: словарь только пополнялся.
- **Отмена ставки, снятие лота, пауза торгов** отсутствовали.

## 3. Контрактный след

Subjects, которыми пользовалась ветка. Схемы удалены вместе с аукционом и восстанавливаются из истории Git:

| Subject | Producer | Consumer |
|---|---|---|
| `commands.auction.start` | ручной publisher | Auction Service |
| `commands.auction.place_bid` | Telegram Gateway | Auction Service |
| `commands.auction.set_proxy_bid` | ручной publisher | Auction Service |
| `commands.auction.end_open_bidding` | ручной publisher | Auction Service |
| `commands.auction.start_final_phase` | ручной publisher | Auction Service |
| `events.auction.started` | Auction Service | — |
| `events.auction.bid_placed` | Auction Service | Notifications, WebSocket Gateway, Telegram Gateway |
| `events.auction.phase_transitioned` | Auction Service | — |
| `commands.telegram.send_message` | Notifications | Telegram Gateway |

gRPC-поверхность Auction Service обслуживала только чтение каталога лотов: `GetAllLots`, `GetLot`. Торги через gRPC не шли.

## 4. Что подтвердилось и стоит переиспользовать

**Чистая функция перехода на краю.** FSM создания лота в Rust-гейтвее была написана как `(состояние, ввод) → Result<(новое состояние, действие)>` без обращения к сети и без побочных эффектов. Это дало быстрые детерминированные тесты на весь диалог, включая полный проход мастера. Идею забрал [ADR-030](../../decisions/ADR-030-telegram-bot.md).

**Но граница была проведена не до конца.** Возвращаемое `BotAction` содержало `ChatId`, `MessageId` и `InlineKeyboardMarkup`, то есть типы teloxide. Юзкейс нельзя было прогнать без Telegram-структур, и свойство «домена на краю нет» доказано не было. Ровно это ADR-030 называет «прошла половину пути».

**Тег плюс проекция журнала** как способ вынести события наружу (§2.2).

**Разделение «атрибуты в таблице, торги в журнале»** оказалось удобным: каталог лотов читался обычным SQL, без восстановления акторов.

## 5. Каталог дефектов

Самая ценная часть. Каждый пункт — ошибка, воспроизводимая в любой новой реализации торгов.

### 5.1. Деньги в `double`

Цены, шаги и максимумы прокси-ставок — `double` на всех уровнях: состояние актора, колонки PostgreSQL, поля Protobuf, DTO. Сравнение `Amount < minRequired` и накопление `currentPrice + MinBidStep` выполнялись в плавающей точке.

### 5.2. `Sender` внутри callback-а `Persist`

```csharp
Persist(evt, e => {
    ApplyBidPlaced(e);
    Sender.Tell(new BidAccepted(cmd.Amount), Self);   // ← Sender читается позже
});
```

`Sender` — свойство актора, меняющееся с каждым обработанным сообщением. Callback `Persist` выполняется после записи в журнал, когда актор мог начать обрабатывать следующее сообщение. Ответ уходит не тому. Классическая ошибка Akka: отправителя нужно захватить в локальную переменную **до** `Persist`. Та же ошибка во всех обработчиках `AuctionActor`.

### 5.3. Событие не содержит данных, нужных для восстановления

`AuctionStarted` несёт только список `LotIds`. Стартовые цены и шаги лежали в `_lotConfigs` — обычном поле актора, заполняемом из команды. После рестарта журнал восстанавливал фазы и список лотов, но не конфигурацию торгов.

Правило, которое из этого следует: **событие обязано содержать всё, что нужно для восстановления состояния**, иначе журнал перестаёт быть источником правды.

### 5.4. Дочерние акторы не пересоздавались при восстановлении

`CreateLotActors()` вызывался только в обработчике команды `StartAuction`, но не после `Recover`. После рестарта процесса аукцион восстанавливал фазу `OpenBidding`, но не имел ни одного актора лота, и любая ставка получала `Lot {id} not found`. В сочетании с 5.3 сервис не переживал перезапуск.

### 5.5. Проекция без хранения offset

`EventsByTag("auction", Offset.NoOffset())` — чтение всегда с начала журнала. При каждом старте процесса **вся история событий заново публиковалась в NATS**. Consumers не были идемпотентны, поэтому это означало повторные уведомления и повторные push в WebSocket.

Offset проекции обязан храниться и восстанавливаться вместе с ней.

### 5.6. Идентификатор аукциона — изменяемое поле проекции

`_currentAuctionId` в `AkkaPersistenceQueryListener` присваивался при обработке `AuctionStarted` и подставлялся во все последующие события лотов. Проекция одна на процесс, поэтому при двух активных аукционах события лота приписывались тому, который стартовал последним. `lot_id` восстанавливался регуляркой из `PersistenceId` — то есть связь «лот → аукцион» в событии отсутствовала и достраивалась догадкой.

### 5.7. Явное присутствие поля, взведённое нулём

```csharp
PreviousLeaderId = evt.PreviousLeaderId ?? 0
```

Поле объявлено в Protobuf как `optional`. Присваивание значения — даже нуля — взводит признак присутствия, поэтому `HasPreviousLeaderId` был **истинным всегда**, включая первую ставку на лот. Notifications использовал ровно этот признак как условие отправки:

```csharp
return _cachedEvent.HasPreviousLeaderId;   // всегда true
```

Итог: на первую ставку по лоту формировалось уведомление «вашу ставку перебили» пользователю с id 0.

Правило: отсутствие значения кодируется отсутствием поля, а не нулём. Написать `?? 0` перед записью в `optional` — значит уничтожить семантику отсутствия.

### 5.8. Контракт требовал полей, которых у продюсера не было

`BidPlacedEvent` содержал `LotTitle` и `PreviousAmount`. Актор лота не знал названия (оно в таблице) и не хранил предыдущую цену, поэтому продюсер писал `""` и `0`. Шаблон уведомления подставлял их буквально:

> ❗ Ваша ставка в 0 рублей на лот '' была перебита.

Дефект межсервисный: каждый сервис по отдельности «работал». Ни один тест не проходил цепочку целиком.

### 5.9. JSON на шине

Notifications публиковал `commands.telegram.send_message` как Protobuf (`message.ToByteArray()`). Telegram Gateway читал тот же subject как JSON (`serde_json::from_slice::<SendMessageCommand>`). **Сценарий уведомления о перебитой ставке не работал вообще** — ни одно сообщение не разбиралось.

Это же нарушение [ADR-012](../../decisions/ADR-012-protobuf-from-start.md). Оно прожило в коде незамеченным, потому что путь никогда не проверялся сквозь.

### 5.10. `op_id` генерировался, но не проверялся

Gateway генерировал `op_id` как UUIDv7 на каждую команду и клал в Protobuf. Auction Service читал команду, но `op_id` не смотрел. Наличие поля создавало иллюзию идемпотентности при её полном отсутствии на стороне обработчика.

### 5.11. Идемпотентность на краю: четыре ошибки в тридцати строках

`IdempotencyCache` в гейтвее:

- элемент множества — кортеж `(String, Instant)`, поэтому хеш зависел от времени и **множество никогда не дедуплицировало по идентификатору**;
- из-за этого проверка шла линейным перебором `iter().any(...)` — O(n) на каждый запрос;
- `check_and_insert` не атомарна: между проверкой и вставкой проходит время, два одновременных запроса проходят оба;
- поле `ttl` сохранялось в структуре, но `cleanup` использовал жёстко зашитые 3600 секунд, игнорируя его.

Плюс общее: кэш в памяти процесса терялся при рестарте. [ADR-030](../../decisions/ADR-030-telegram-bot.md) отказался от дедупликации на краю в пользу целевых команд и ключа создания, разрешаемого доменом.

### 5.12. Состояние сообщения в поле singleton-обработчика

`BidPlacedHandler` разбирал сообщение в `CanHandle` и складывал результат в поле `_cachedEvent`, чтобы переиспользовать в `HandleAsync`. Обработчик — один экземпляр на процесс, вызовы приходят из подписки NATS без сериализации. Два сообщения подряд перетирали поле друг друга.

### 5.13. Прочее

- `PhaseTransitionedEvent` публиковался с захардкоженными строками `FromPhase`/`ToPhase`, не выведенными из состояния;
- Notifications подставлял `ChatId = evt.PreviousLeaderId`, то есть считал Telegram user id равным chat id. [ADR-028](../../decisions/ADR-028-notifications-subscriptions-replica-and-delivery-boundary.md) впоследствии вынес готовый текст и `chat_id` из контракта уведомлений;
- роли администраторов — список id в конфигурации, проверяемый на краю. Заменено [ADR-026](../../decisions/ADR-026-identity-mvp-model-and-access.md);
- WebSocket Gateway при неизвестном subject публиковал клиентам событие типа `unknown` с телом `{subject}` вместо того, чтобы его игнорировать.

## 6. Тест-кейсы, которые стоит перенести

Из `LotActorTests` (Akka.TestKit, in-memory journal):

- ставка выше минимума принимается, ответ содержит сумму;
- ставка ниже минимума отклоняется с причиной;
- статус после ставки отдаёт новую цену и лидера;
- прокси-ставка автоматически перебивает ручную: при `start=100`, `step=10`, прокси на 200 и ручной ставке 110 цена становится 120, лидер — владелец прокси.

Из `fsm_lot_creation_tests` (чистая функция, без Telegram): успешный ввод названия, пустое название, название длиннее 100 символов, ввод описания, корректная цена, нечисловая цена, нулевая цена, минимальный шаг, ссылка на изображение, пропуск изображения, отмена, полный проход мастера.

Кейсы, которых не было и которые обязаны появиться: одновременные равные ставки, повтор одной команды, восстановление актора после рестарта, война двух прокси-ставок, ставка после завершения лота, прокси-ставка ниже текущей цены.

## 7. Непроверенные гипотезы

Механики из [продуктовой спецификации](../../product/future/auction.md), для которых кода не существовало вовсе:

- анти-снайп с продлением по последней ставке — `EndTime` не заполнялся никогда;
- Buy-Now, Best & Final (Vickrey), Dutch, слотовый режим;
- смысл фазы `Final` как отдельного режима торгов;
- несколько аукционов на одну сходку ([ADR-019](../../decisions/ADR-019-meetup-auction-separation-and-ulid.md)): реестр акторов это поддерживал, проекция (§5.6) — нет;
- Big Screen как отдельный клиент: WebSocket Gateway доставлял только `bid_placed`.

Ни одна из них не подтверждена ни нагрузкой, ни живым мероприятием.
