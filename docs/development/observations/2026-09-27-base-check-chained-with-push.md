# 2026-09-27 — Сверка базы шла одной цепочкой с коммитом и push

- **Контекст:** PER-285, дерево `.claude/worktrees/per-285-task-7fd1d5`, [PR #242](https://github.com/Solguficky/solguficky-hub/pull/242), правка после сдачи; [`proj-deliver-task`](../../../.skillshare/skills/proj/proj-deliver-task/SKILL.md), шаг 3, абзац про сверку базы.
- **Наблюдение:** правку по решению владельца агент опубликовал одной командой: `git fetch`, `git log --oneline HEAD..origin/develop`, `git commit`, `git push`. Сверка напечатала `321cac7 [PER-271] …` — `develop` ушёл вперёд, — но следующие команды цепочки выполнились независимо от её вывода, и ветка ушла в PR на старой базе. Rebase, сделанный уже после push, прошёл чисто, но для публикации требовал `push --force` — пункт ручного гейта; агент откатил его `git reset --hard origin/feature/PER-285`. Скилл при этом велит «вывод непуст — сначала закоммить срез и сделай rebase … потом гейт» и не различает, опубликована ли ветка: до первого push rebase бесплатен, после — нет.
- **Последствие:** ветка PR осталась на базе без PER-271; мержу это не помешало (`CLEAN`), но сверка, ради которой шаг существует, не сработала, а исправление упёрлось в необратимое действие и откат.
- **Адресат:** Скилл — `proj-deliver-task`, шаг сверки базы: сверка — отдельный вызов, вывод которого читается до коммита и push, а для уже опубликованной ветки назван путь без `push --force`. Верхние адресаты не подходят: команда сверки существует, ошибка в порядке шагов и в том, что её вывод никто не прочитал до следующей команды, а события инструмента для хука нет.
- **Повторение:** два случая, второй описан в конце поля. Записи от 2026-09-24 и 2026-09-25 про ушедший `develop` — другой механизм: там сверку не делали вовсе и ревью и `buf breaking` сравнивали против сдвинувшейся ветки, здесь сверку сделали, но её вывод не управлял следующими шагами. Второй случай — PER-387, дерево `.claude/worktrees/per-220-project-task-7303dc`, [PR #251](https://github.com/Solguficky/solguficky-hub/pull/251), 2026-09-27, тот же шаг 3 `proj-deliver-task`. Первый `just verify-changed` шёл одной командой со сверкой: `git fetch && git log HEAD..origin/develop; echo ---; just verify-changed …`. Сверка напечатала `ee827a7 [PER-253] …`, но гейт отработал на старой базе; rebase сделан позже, перед коммитом. Необратимого действия не было: PER-253 трогал только `docs/observations/`, вердикт не изменился, цена — первый из двух прогонов по бюджету гейта. Механизм тот же — вывод сверки не управлял следующим шагом, — а буква «следующего сигнала» совпала не полностью; засчитывать ли случай вторым, решает владелец. Третий случай — PER-279, дерево `.claude/worktrees/per-279-task-5a4e98`, [PR #258](https://github.com/Solguficky/solguficky-hub/pull/258), 2026-09-28, тот же шаг 3. Форма дословно как во втором: `git fetch -q && git log --oneline HEAD..origin/develop; git status --short; just verify-changed …`. К этому моменту `develop` ушёл на `a1e7a5a [PER-273]`, и гейт пошёл на старой базе. Это заметили при сборке диффа для ревью; прогон, упёршийся в предел Bash в 600 с, остановили вручную. Необратимого действия снова не было, так что буква «следующего сигнала» совпала так же неполно, как во втором случае. Цена — потраченный прогон гейта и превышение бюджета.
- **Следующий сигнал:** проверка, чей вывод должен решать следующий шаг, стоит в одной цепочке с этим шагом, и её сигнал обнаруживается уже после необратимого действия.
- **Правило из двух случаев:** сверка базы — отдельный вызов, и её вывод читается до следующего шага; в одну цепочку с коммитом, push или гейтом она не ставится.
- **Статус:** вынесено на обсуждение
