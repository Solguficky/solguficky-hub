# 2026-09-22 — Новая проверка гейта брала домены из реестра и не видела домен без записей

- **Контекст:** PER-207, [PR #174](https://github.com/Solguficky/solguficky-hub/pull/174), ветка `feature/PER-207`; две новые проверки в [gate.py](../../../tools/nats-tester/nats_tester/gate.py) — subjects против веток `oneof occasion` и форма конверта события; шаг ревью контура, ось логической корректности.
- **Наблюдение:** первая версия проверки собирала сообщения с веткой `occasion` функцией `_occasion_messages()` из записей реестра subjects. Домен, у которого в реестре нет ни одной записи, в проверку не попадал вовсе, и гейт оставался зелёным — хотя поймать схему, забытую в реестре, было одной из двух целей проверки. Автор прогнал проверку мутациями до ревью: переименованный subject, чужой тип поля конверта, пять сломанных форм конверта. Всё ловилось, и проверку сочли закрытой. Дыру нашла ось ревью: ревьюер удалил из реестра все записи Identity и получил зелёный гейт. Мутации автор выбирал из тех же гипотез, по которым писал код. Мутации «предмета проверки нет совсем» среди них не было. Исправление строит список из самих схем (`_bus_event_descriptors()` обходит `bus_schema_files()`); после него та же мутация выдаёт все пять пропущенных subjects.
- **Последствие:** до коммита не дошло, но только потому, что на шаге ревью ось корректности читала код, а не отчёт о мутациях. Без неё гейт объявил бы проверенным контракт, который проверка не видела. Проверка, созданная ради этого случая, на нём молчала бы.
- **Адресат:** Автоматическая проверка — self-test гейта в `tools/nats-tester/` на заведомо сломанных входах, включая пустой реестр домена. Второй адресат — скилл `proj-review-change`: к мутациям «предмет испорчен» добавить мутацию «предмета нет совсем», когда в изменении есть новая проверка.
- **Повторение:** второй независимый случай механизма из [2026-09-19](2026-09-19-number-check-missed-new-document.md): там `check-document-numbers.sh` брал файлы из `git ls-files` и не видел неотслеживаемый RFC, созданный этой же правкой. Другая задача, другая сессия, другая проверка. Общее у двух случаев одно: список предметов проверка получает из производного источника — индекса git, реестра — и не видит предмет, которого там ещё нет. А это ровно тот предмет, ради которого её запускают в этот момент. Здесь есть и новое: мутационный прогон автора этого не поймал, потому что пустой вход совпадает с «всё в порядке».
- **Правило из двух случаев:** проверка, которая перебирает множество предметов, строит его из источника правды — файлов рабочего дерева, самих схем, — а не из производного списка, который надо дописывать отдельно. Её self-test или мутационный прогон включает вход «предмета нет совсем», а не только «предмет испорчен». Правило действует для проверок в `tools/` и рецептов `justfile`, входящих в `just verify`.
- **Следующий сигнал:** сигнал подтверждён дважды; дальше — формулировка правила, а не ожидание третьего случая.
- **Статус:** вынесено на обсуждение
