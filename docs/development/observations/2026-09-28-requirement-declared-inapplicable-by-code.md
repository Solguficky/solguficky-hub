# 2026-09-28 — Пункт задачи объявлен неприменимым по коду, мимо решённых кадров раскадровки

- **Контекст:** PER-400, ветка `feature/PER-400`, [PR #257](https://github.com/Solguficky/solguficky-hub/pull/257); `.work/PER-400/recon.md`, шаги 5–6 [`proj-start-task`](../../../.skillshare/skills/proj/proj-start-task/SKILL.md); [docs/services/telegram-bot.md](../../services/telegram-bot.md), [docs/design/bot/storyboard.html](../../design/bot/storyboard.html).
- **Наблюдение:** второй пункт задачи — «оставить всплывающий текст только там, где он несёт смысл, которого нет на экране». Разведка нашла в коде единственный ack с текстом и заключила, что места для такого текста нет. Кадры раскадровки с осмысленным тостом попали в вывод поиска, но были отброшены как «не реализованы», и решённые P-08, E-04 и E-09 с этим пунктом не сверялись. Чекпоинт плана пропущен с формулировкой «развилки нет», а в бриф ушло правило шире задачи: текст запрещён у любой кнопки. Ось спецификации подтвердила это как требование «с пустым множеством применения»; противоречие с решёнными кадрами нашла только ось корректности, до коммита.
- **Последствие:** бриф едва не закрепил запрет, который противоречит трём решённым кадрам и самой задаче; формулировку пришлось переписывать посреди гейта. Реальная развилка — такие кадры не реализовать, пока ack уходит до соседей, — всплыла только на ревью, а не на чекпоинте плана, где её решает владелец.
- **Адресат:** Скилл — `proj-start-task`, шаг 5 или 6: пункт задачи, признанный неприменимым, сверяется с дизайн-документами среза (раскадровка, бриф) до решения «развилки нет». Второй адресат — роль `proj-review-spec`: требование, объявленное неприменимым, проверяется по тем же документам, а не принимается по коду.
- **Повторение:** первое наблюдение. Запись [о выводе шире прогона](2026-09-22-claim-generalized-beyond-its-run.md) описывает другой механизм: там формулировка обобщила прогон, здесь требование сочтено пустым по неполному источнику.
- **Следующий сигнал:** пункт «Что сделать» задачи признан неприменимым или выполненным пустым множеством, а ревью или владелец находят для него случай в дизайн-документе среза.
- **Второй случай (2026-09-30):** PER-423, [PR #284](https://github.com/Solguficky/solguficky-hub/pull/284). Критерий приёмки требовал, чтобы `grep session docs/decisions` не находил слово в значении агрегата, а [docs/decisions/README.md](../../decisions/README.md) запрещает переписывать тексты ADR задним числом. Оба планировщика шага 6 независимо приняли правило README за ограничение и предложили дописку вместо правки, то есть сузили критерий. Источником неполноты здесь был норматив документации, а не код, но механизм тот же: пункт задачи сочтён невыполнимым по одному источнику. Развилку вынес на чекпоинт основной исполнитель при сведении планов. Владелец выбрал выполнить критерий и переписать тела ADR по месту.
- **Правило из двух случаев:** пункт задачи, который противоречит правилу репозитория или по прочитанному источнику выглядит неприменимым, не сужается и не объявляется пустым молча: на шаге 5 или 6 `proj-start-task` он выносится на чекпоинт развилкой «выполнить пункт или правило» с обоими источниками.
- **Статус:** вынесено на обсуждение
