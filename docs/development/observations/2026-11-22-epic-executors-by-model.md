# 2026-11-22 — Исполнители эпика по моделям: OpenCode deepseek сдал листья, Codex дал лучшее ревью, но не исполнение

- **Контекст:** эпик [PER-908](https://linear.app/anticnvm/issue/per-908), 21–22.11.2026, Orca 1.4.266, Run `run_c222d9c370b6`. Десять листьев, приёмка каждого — Sonnet 5.5 по [чеклисту](../../../.skillshare/skills/proj/proj-run-epic/references/acceptance.md). Модели исполнителей выбирал владелец, чтобы экономить лимит Claude: сначала OpenCode Go, затем порядок «OpenCode Go → Codex luna/terra → Sonnet». Таблица ролей по пулам — [agent-execution-cost.md](../agent-execution-cost.md), раздел «Маршрутизация по харнессу и пулу лимитов».
- **Наблюдение:** что показали исполнители по листьям.
  - **`opencode-go/deepseek-v4.1-flash`.** Сдал 7 листьев: PER-909, PER-907, PER-923, PER-929, PER-930, PER-931, PER-913. Шесть приняты с первой попытки. PER-907 вернули один раз: красный `contour` исполнитель принял за среду, а это был дефект. Чекпоинты он подавал по форме норматива и находил развилки сам:
    - предел `callback_data` в 64 байта (PER-913);
    - противоречие словаря подписей и раздела дизайн-кода (PER-931);
    - точную причину красного гейта — CRLF в `apps/achievements` (PER-930);
    - порядок выкладки «бот раньше сервиса» (PER-930).

    Повторяющиеся слабости, которые ловили постановка и приёмка:
    - заканчивал ход в ожидании фоновой задачи (PER-909);
    - правил файлы Python-скриптом и оставлял `console.log("DEBUG")` (PER-907);
    - не перепрогонял три оси после последних правок (PER-923, PER-929, PER-931);
    - не дублировал строку наблюдателей в Linear (PER-930).
  - **`opencode-go/hy4-flash-free`.** PER-912 прошёл контур без единого вмешательства, PER-911 сдан с первой попытки. Исполнитель PER-911 вставил токен `gho_` открытым текстом в эскалацию оркестратору. Наутро бесплатная модель под Orca не стартовала (`ServiceUnavailableError`).
  - **Codex (OpenAI) как внешний ревьюер и второе мнение.** Находил дефекты, которые пропустили три оси:
    - три находки в PER-909;
    - устаревшие `breaking.ignore` в PER-930;
    - отказ без `origin` в PER-913.

    Второе мнение `gpt-6.2-astra` дало вариант раскладки экрана «Управление», который выбрал владелец (Q-7). Ограничения: видит только 32 КБ корневого `AGENTS.md`, и лимит OpenAI кончился к вечеру.
  - **Codex `gpt-6.1-terra` как исполнитель PER-923.** Вопросы его чекпоинта были самыми точными в эпике:
    - дыра в решении оркестратора: состав альбома до «Да» негде держать;
    - нет сигнала конца альбома в Bot API;
    - у старых материалов нет `file_unique_id`.

    Но лист он не сдал. В его песочнице не было WSL и сети. `just` не находил `npm`, код 127, и понадобились решения оркестратора R-6 (тулинг поставил оркестратор) и R-7 (рецепты через Git Bash `-lc`). Примерно через четыре часа он упёрся в лимит OpenAI посреди листа, и лист доделал OpenCode deepseek по контексту продолжения.
  - **Claude Sonnet 5.5 как исполнитель Decision-листа PER-910.** Стартовал сразу, принят с первой попытки, чекпоинт с макетами и черновики листьев подал по форме.
- **Последствие:** на исполнителе Codex лист PER-923 потерял около полудня: среда, два обхода оркестратора, лимит и смена исполнителя. Тот же лимит оставил PER-913 без повторного внешнего ревью. Сдачу эпика обеспечил дешёвый deepseek при жёсткой постановке и приёмке Sonnet. Почти все потери на OpenCode шли от инфраструктуры: старт под Orca, роли подагентов, баланс Sonnet в пуле OpenCode, `npm`. От модели их не было.
- **Адресат:** Норматив — [agent-execution-cost.md](../agent-execution-cost.md), раздел «Маршрутизация по харнессу и пулу лимитов». Строка для исполнителей листов эпика под Orca: исполнитель — OpenCode Go `deepseek-v4.1-flash`, запасной — Claude Sonnet. Codex — внешнее ревью и второе мнение, не исполнитель: его пул один с ревью, а среда Windows ему мешает. Второй адресат — шаг 5 [proj-run-epic](../../../.skillshare/skills/proj/proj-run-epic/SKILL.md): он говорит «Исполнитель листа — всегда Claude» (`--agent claude`), а на деле исполнители шли на OpenCode по слову владельца. Шаг 3 при этом должен называть порядок исполнителей в плане эпика.
- **Повторение:** второй независимый случай для части про Codex-исполнителя. Первый — оркестрация PER-812…817, 2026-10-29, другой эпик и сессия: Orca трижды из четырёх отчиталась `input_accepted`, а Codex задания не получал, и один Codex молча вышел посреди реализации PER-817. Тогда владелец велел ставить Codex только на ревью, а в журнал случай не попал. Часть про OpenCode-исполнителей продолжает эпик [PER-917](https://linear.app/anticnvm/issue/per-917): записи [о ходе в ожидании](2026-11-20-opencode-worker-ended-turn-on-background-wait.md) и [об общем лимите](2026-11-11-parallel-workers-hit-shared-usage-limit.md). Там OpenCode-модели glm-5.3 и hy4 пропускали шаги контура чаще, чем deepseek здесь.
- **Правило из двух случаев:** исполнитель листа эпика под Orca — не Codex. Codex занимает внешнее ревью и второе мнение. Исполнитель берётся из пула, который не делит лимит с ревью: OpenCode Go `deepseek-v4.1-flash`, при его отказе Claude Sonnet.
- **Следующий сигнал:** в другом эпике исполнитель на Codex не доводит лист до сдачи из-за среды или лимита, или исполнитель на OpenCode deepseek требует больше одного возврата на лист.
- **Статус:** вынесено на обсуждение
