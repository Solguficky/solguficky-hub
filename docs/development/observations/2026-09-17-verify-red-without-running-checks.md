# 2026-09-17 — `just verify` вернул красный, не запустив ни одной проверки над правкой

- **Контекст:** сессия правки норматива 2026-09-17, текущий клон, команда `just verify`; `tools/skillshare/check-frontmatter.sh:37`.
- **Наблюдение:** `just verify` упал на первом рецепте, `check-agent-tools`, и вернул 1, не оценив изменение. `check-frontmatter.sh` собирает файлы циклом `for skill_file in $(find "$root" -name SKILL.md | sort)`: в PowerShell `find` резолвится в `C:\Windows\system32\find.exe`, тот печатает три ошибки использования и не находит ничего, поэтому список пуст, `$#` остаётся нулём и скрипт печатает `No SKILL.md found under .skillshare/skills, .claude/skills or .agents/skills`. `just` при этом установлен, `sh` — из Git, а правка не трогала `.skillshare/` вовсе. Диагноз подтверждён `Get-Command find` → `find.exe` из `system32`. Тот же корень у второго рецепта: `npm` лежит bash-скриптом с `#!/usr/bin/env bash`, `env` находит WSL-`bash`, и `just telegram-bot-tools` падает с `wsl: Failed to start the systemd user session`; оба отказа уходят после того, как `C:\Program Files\Git\usr\bin` поставлен впереди PATH.
- **Последствие:** гейт вернул красный, который читается как дефект правки, тогда как ни одна проверка над правкой не запускалась: `check-agent-tools` стоит первым в `verify`, остальные рецепты не пошли. Потрачены вызовы на доказательство «красный по окружению», и менее внимательный отчёт назвал бы гейт красным или собрал бы проверки руками.
- **Адресат:** Автоматическая проверка — `tools/skillshare/check-frontmatter.sh`: зависимость от неквалифицированного `find` делает вердикт недетерминированным по среде, а чинится это правкой скрипта и суждения не требует. Второй адресат — `AGENTS.md`: «гейт красный» и «гейт не оценил изменение» должны читаться по-разному.
- **Повторение:** второй независимый случай — PER-191, дерево `../solguficky-wt/PER-191`, другая задача и сессия: тот же `No SKILL.md found` на месте живой записи и падение `npm` на WSL-`bash`, гейт вернулся к работе только после `C:\Program Files\Git\usr\bin` в PATH. Родственные записи 2026-09-14: «`just` нет в среде агента» — там гейт не запускался вовсе и адресат другой, «Пайп съел код возврата» — там код возврата читался не у той команды. Другая задача, другая сессия, другой способ создания дерева, механизм дословно тот же. Четвёртый случай, после переноса, — PER-365, 2026-09-26, дерево `.claude/worktrees/per-365-project-task-0295bf`, созданное приложением: `just tools`, запущенный из PowerShell харнесса на шаге 2 контура, упал на `telegram-bot-tools` с `/bin/bash: C:/Program Files/nodejs/npm: No such file or directory` и кодом 127, хотя файл `npm` в этом каталоге лежит; тот же `just tools` из Bash-инструмента харнесса завершился с `EXIT=0`. Это ветка `npm` из первого случая, которую перенесённое правило не закрыло: оно исправило только `find` в `check-frontmatter.sh`.
- **Правило из двух случаев:** вердикт проверки не зависит от того, какой бинарь среды разрешится первым: `tools/skillshare/check-frontmatter.sh` находит `SKILL.md` и там, где неквалифицированный `find` — Windows-бинарь, либо `check-agent-tools` различает «ни один файл не найден» и «frontmatter сломан». Второй адресат той же записи — `AGENTS.md`, где «гейт красный» и «гейт не оценил изменение» читаются по-разному.
- **Следующий сигнал:** `just verify` или `just check-agent-tools` завершается ненулевым кодом до первой проверки, потому что инструмент из скрипта разрешился в чужой бинарь среды, а не в POSIX-инструмент.
- **Перенесено:** [check-frontmatter.sh](../../../tools/skillshare/check-frontmatter.sh) обходит каталоги глобами оболочки, а не `find`: с `system32` первым в PATH старая версия давала `No SKILL.md found` и код 1, новая — «valid in 94 files». Второй адресат — критические правила [AGENTS.md](../../../AGENTS.md), различие «гейт красный» и «гейт не оценил изменение».
- **Статус:** переведено в правило для ветки `find`; ветка `npm` вынесена на обсуждение — её правило из случаев: рецепты `just` в Windows-среде агента запускаются из POSIX-оболочки Git, а не из PowerShell, либо рецепт `telegram-bot-tools` вызывает `npm` так, чтобы тот не зависел от оболочки, в которой запущен `just`.
