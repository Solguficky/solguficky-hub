# 2026-09-21 — Дерево задачи приезжает на ветке в нижнем регистре

- **Контекст:** PER-221, рабочее дерево `C:/Users/anticnvm/orca/workspaces/solguficky-hub/per-221` создано приложением, ветка `feature/per-221`; [branching.md](../../standards/git/branching.md) — «Имя ветки — `feature/PER-N`… идентификатор пишется в верхнем регистре»; скилл `proj-start-task`, шаг «Заведи ветку или дерево».
- **Наблюдение:** дерево приехало на `feature/per-221`. Шаг скилла «текущее дерево уже на `feature/PER-N` той же задачи — ветку не создавай» читается как выполненный, хотя регистр идентификатора не совпадает с нормативом, а проверка норматива (`git branch --show-current` возвращает `feature/PER-N` с идентификатором в верхнем регистре) на этом имени красная. Переименование `git branch -m feature/PER-221` упало с `fatal: a branch named 'feature/PER-221' already exists` — файловая система Windows не различает регистр, — и прошло только с `-M`.
- **Последствие:** без переименования задача идёт под нестандартным именем: `git branch --show-current` не совпадает с `feature/PER-N`, поиск деревьев по этому имени даёт ложный результат, голова pull request отличается от нормативной. Цена обнаружения — упавшая команда и выбор между `-m` и `-M`.
- **Адресат:** Скилл — `proj-start-task`, шаг ветки или дерева: имя текущей ветки сверяется с `feature/PER-N` посимвольно, регистр приводится к верхнему (на Windows — `git branch -M`). Верхние адресаты не подходят: имя ветки задаёт харнесс, создающий дерево, а он вне репозитория.
- **Повторение:** второй независимый случай — PER-200, дерево `C:/Users/anticnvm/orca/workspaces/solguficky-hub/per-200`, та же дата, другая задача и сессия: дерево приехало на `feature/per-200`, шаг скилла про существующую ветку снова прочитался как выполненный, а переименование упало тем же `already exists`; обойдено двухшаговым `git branch -m` через промежуточное имя, `-M` в той сессии не пробовался. Имя ветки совпало с полем `gitBranchName` задачи дословно, а standard называет это поле запрещённым источником. Тот же симптом виден ещё в трёх задачах вне журнала — [PR #26](https://github.com/Solguficky/solguficky-hub/pull/26), [PR #27](https://github.com/Solguficky/solguficky-hub/pull/27) и [PR #123](https://github.com/Solguficky/solguficky-hub/pull/123) шли с веток `feature/per-81`, `feature/per-82` и `feature/per-132`, совпадающих со своими `gitBranchName` дословно, — но механизм имени в тех сессиях не проверялся: совпадение с полем ожидаемо и тогда, когда имя собирают из идентификатора вручную. Родственная запись 2026-09-17 «Расположение дерева передано харнессу…» — о свойствах дерева, которые задаёт харнесс вместо норматива.
- **Следующий сигнал:** рабочее дерево задачи приезжает на ветке `feature/per-N` в нижнем регистре, и контур открывается без переименования.
- **Правило из двух случаев:** имя ветки дерева сверяется с `feature/PER-N` посимвольно и приводится к нормативному при открытии контура; на регистронезависимой файловой системе Windows смена только регистра не проходит через `git branch -m` (`already exists`) и делается `-M` либо двухшаговым переименованием через промежуточное имя. Имя, которое дерево получает от харнесса, совпадает с полем `gitBranchName` Linear, а standard называет это поле запрещённым источником имени.
