# 2026-09-18 — Разведка читает сгенерированный код в чужом рабочем дереве

- **Контекст:** PER-254, рабочее дерево задачи, шаг чтения контекста `proj-start-task`; генераты в свежем дереве отсутствуют — `apps/identity/gen`, `apps/telegram-bot/gen` и `apps/meetups/Meetups.Contracts/obj` в Git не лежат и до сборки на диске их нет.
- **Наблюдение:** подагент разведки, которому поручили форму сгенерированных типов, взял её из соседнего рабочего дерева задачи PER-149: `apps/identity/gen/identity/v1/roles.pb.go`, `apps/meetups/Meetups.Contracts/obj/Debug/net10.0/identity/v1/Roles.cs` и `apps/telegram-bot/gen/identity/v1/roles_pb.ts`. В своём дереве генераты не были собраны, а свежесть чужой сборки неизвестна; владелец заметил это вопросом «зачем тебе читать сессию 149», и часть подтверждений пришлось переделывать в своём дереве через `just identity-proto`, `just telegram-bot-proto` и `dotnet build`.
- **Последствие:** форма сгенерированного кода на время стала «доказательством» из артефакта чужой задачи. Ошибка не проявилась только потому, что на момент разведки схема ещё не менялась; после правки контракта чужой `gen/` разошёлся бы с этим деревом, и вывод о потребителях оказался бы ложным.
- **Адресат:** Скилл — `proj-start-task`, шаг чтения контекста (и `proj-change-contract`): сгенерированный код читается только из своего дерева и только после местной кодогенерации; чужое рабочее дерево источником не является. Верхние адресаты не подходят: это порядок работы, командой он не проверяется.
- **Повторение:** первое наблюдение. Родственная запись 2026-09-17 про `just verify` в свежем дереве описывает тот же пробел подготовки, но другой сигнал: там гейт краснел, здесь чужой артефакт молча попал в вывод разведки.
- **Следующий сигнал:** в выводе разведки, ревью или отчёта появляется путь вне текущего рабочего дерева — соседний worktree, чужой `gen/` или `obj/`.
- **Статус:** наблюдение
