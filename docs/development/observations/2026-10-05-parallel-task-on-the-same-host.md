# 2026-10-05 — Две задачи взялись за один живой хост, и сигналы захвата этого не показали

- **Контекст:** PER-371 «Установить k3s на хост», [PR #363](https://github.com/Solguficky/solguficky-hub/pull/363), шаг захвата в [контуре исполнения](../agent-execution-loop.md#захват-задачи) и в скилле `proj-start-task`; связанная PER-311 «Поднять stage хаба с аукционом на VPS».
- **Наблюдение:** PER-311 перешла в In Progress в 14:24, PER-371 захвачена в 14:25. У PER-311 было своё рабочее дерево `per-311-stage-vps`. Её первый пункт «Что сделать» — «Установить k3s на хост одной закреплённой версией, API только на localhost»: тот же VPS, но без Ansible и с другим адресом API. Захват PER-371 прошёл чисто: delegate пуст, статус Todo, открытого PR нет. Все три сигнала читают только свою задачу, а связь двух задач в Linear — `relatedTo`, а не `blockedBy`. Пересечение нашлось при чтении связанных задач в разведке. До плана владелец решил, что k3s ставит PER-371, а PER-311 ждёт.
- **Последствие:** до живого шага потери не случилось: развязку нашла разведка, а боевые прогоны в обеих задачах запускает владелец. Без неё две сессии поставили бы k3s на один хост с разными флагами, и вторая наткнулась бы на чужую установку посреди работы на живой машине.
- **Адресат:** Скилл — `proj-start-task`, шаг захвата: кроме сигналов своей задачи, прочитать started-задачи из `relatedTo` и тех, что трогают тот же внешний ресурс (хост, кластер, общий файл). Пересечение — вопрос владельцу до ветки. Второй адресат — [linear.md](../../standards/backlog/linear.md), раздел «Зависимости»: две задачи, меняющие один живой хост, связываются `blockedBy`, а не `relatedTo`. Автоматическая проверка не подходит: «трогает тот же ресурс» выводится из текста задач, а не из полей трекера.
- **Повторение:** первое наблюдение. Родственная запись [2026-09-26](2026-09-26-plan-built-on-a-stale-premise.md): там вывод плана противоречил незакоммиченной правке соседней PER-162, и её адресат уже называет сверку с задачами в работе над теми же файлами. Сигнал той записи другой — устаревшая рамка задачи, найденная на чекпоинте плана, а не пересечение двух захватов одного ресурса. Если владелец сочтёт механизм общим, это второй случай её адресата, а не её сигнала.
