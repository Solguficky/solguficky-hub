# 2026-10-03 — sbt упал на нехватке памяти машины, и потолок heap пришлось задавать руками

- **Контекст:** PER-331, дерево `orca/workspaces/solguficky-hub/per-331`, Windows 11 с 14 ГБ памяти; `sbt compile` в `apps/auction`, затем рецепты `auction-*` и `just verify-changed`.
- **Наблюдение:** первый `sbt -batch compile` упал до компиляции кода: «There is insufficient memory for the Java Runtime Environment to continue. Native memory allocation (malloc) failed», рядом отказ cygwin `fork: Resource temporarily unavailable`. JVM оставила в `apps/auction` файлы `hs_err_pid*.log` и `replay_pid*.log`. Свободной физической памяти было около 1 ГБ из 14, её держали процессы соседних рабочих деревьев. Повтор с `-J-Xmx1g -J-Xss4m` прошёл. Дальше каждый вызов sbt запускался с этими флагами руками, а гейт — с `SBT_OPTS="-Xmx1g -Xss4m"`. В `apps/auction` нет ни `.jvmopts`, ни `.sbtopts`, и рецепты `auction-*` heap не ограничивают, так что умолчание JVM берёт долю от всей памяти машины, а не от свободной.
- **Последствие:** один упавший прогон и ручная обёртка у каждого следующего вызова sbt. Рецепты `just` в исходном виде на этой машине в этот момент не работали. Гейт, запущенный без обёртки, стал бы красным по окружению.
- **Адресат:** Автоматическая проверка — потолок heap в `apps/auction/.jvmopts` или в рецептах `auction-*` `justfile`, чтобы sbt не зависел от того, сколько памяти сейчас свободно. Плюс строка в [local-development.md](../local-development.md) о памяти при нескольких деревьях. Ниже спускаться не нужно: сигнал снимается конфигурацией, без суждения.
- **Повторение:** первое наблюдение.
- **Следующий сигнал:** sbt или другая JVM сборки падает с «insufficient memory» либо `malloc failed` при нескольких открытых деревьях, а повтор с явным `-Xmx` проходит.
- **Статус:** наблюдение
