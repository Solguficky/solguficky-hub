# 2026-09-14 — Пайп съел код возврата, и отвергнутый хуком коммит уехал в соседний

- **Контекст:** PER-245, ветка `feature/PER-245`, команды `just verify 2>&1 | tail -60` и `git commit -q -m ... 2>&1 | tail -1 && git add ... && git commit ...`.
- **Наблюдение:** дважды за одну сессию код возврата был прочитан у `tail`, а не у команды перед ним. Первый раз гейт остановился на рецепте `telegram-bot-proto` из-за отсутствующего `protoc-gen-es`, `tail` вернул 0, и сессия отчиталась о зелёном `just verify`. Второй раз хук `commit-msg` отверг заголовок длиной 77 символов при лимите 72; `tail` снова вернул 0, цепочка `&&` продолжилась, и следующий коммит забрал файлы несостоявшегося вместе со своими. Ни один из двух отказов не был виден в выводе: `tail -1` показывает последнюю строку хука, а она у lefthook успешная.
- **Последствие:** владельцу отправлен отчёт о зелёном гейте, которого не было, и потребовалась поправка. Два коммита пришлось разобрать `git reset --soft HEAD~2` и собрать заново с правильными заголовками. Оба раза расхождение нашлось не по коду возврата, а по сверке `git log` и лога гейта со списком ожидаемого.
- **Адресат:** Скилл — `proj-deliver-task` и `proj-write-commit`: оба предписывают шаг, результат которого нужно подтвердить, и оба не говорят, чем именно он подтверждается. Автоматическая проверка не подходит: команду составляет агент в момент запуска, и заранее проверять нечего. Второй адресат — правило в `AGENTS.md`, если окажется, что запрет читать код возврата через пайп нужен шире двух этих шагов.
- **Повторение:** второй независимый случай — PER-146, дерево `.claude/worktrees/per-146-project-task-784e10`, команда `just verify 2>&1 | tail -40`. Другая задача, другая сессия, другое дерево, механизм тот же и отказ тот же: гейт встал на `telegram-bot-proto` из-за отсутствующего `protoc-gen-es`, `tail` вернул 0, и владельцу отправлен отчёт о зелёном гейте. Внутри той же сессии сигнал сработал третий раз уже после исправления: запуск, обёрнутый в `just verify > log 2>&1; echo "VERIFY_EXIT=$?"; tail`, вернул 0 наружу как код `tail`, и красный гейт на `community-site-api-typecheck` был виден только в явно напечатанном `VERIFY_EXIT=1`. Два случая PER-245 по-прежнему независимыми друг другу не считаются. Четвёртый случай той же формы — сессия RFC-013 2026-09-21: фоновый запуск `just verify > log 2>&1; echo "EXIT=$?" >> log; tail log` завершился с кодом 0 от `tail`, харнесс доложил «completed (exit code 0)», а внутри лога стояло `EXIT=1` от `telegram-bot-proto`; красный прочитан только по явной строке. Пятый случай той же формы — PER-284 2026-09-21, дерево `.claude/worktrees/per-284-task-3f7dbb`: фоновый `just verify 2>&1 | tail -60`, харнесс доложил «completed (exit code 0)», гейт стоял на `telegram-bot-proto` из-за отсутствующего `node_modules`, и владельцу снова отправлен отчёт о зелёном гейте — поправленный в той же сессии. Подтверждения этот случай не добавляет: он показывает цену ожидания. Правило сформулировано после второго случая и с тех пор не принято, а ошибка повторилась в другой задаче, другом дереве и у другого исполнителя. Шестой случай — 2026-09-22, дерево `.claude/worktrees/multiple-tasks-conflicts-895f3a`, разложение журнала наблюдений по файлам, [PR #155](https://github.com/Solguficky/solguficky-hub/pull/155): фоновый `just verify 2>&1 | tail -40; echo "=== VERIFY EXIT: $? ==="`, харнесс доложил «completed (exit code 0)», и напечатанная строка `VERIFY EXIT: 0` была кодом `tail`. Здесь он отличается от пяти предыдущих: гейт был по-настоящему зелёным, поэтому ложный отчёт не состоялся, и неверно прочитанный код не проявился бы ничем. То есть пайп обесценивает проверку независимо от вердикта, а заметен становится только на красном; вердикт пришлось подтверждать обходом — `grep` по всему логу на отказы и отдельный прогон последнего рецепта `just meetups-format-check` без пайпа, до которого `just` доходит, только пройдя предыдущие. Случай добавляет довод за второй адресат записи: гейт прогонялся вне контура задачи, шага `proj-deliver-task` в сессии не было вовсе, и правило, которое живёт только в двух скиллах сдачи, здесь бы не сработало. Седьмой случай — PER-142 2026-09-22, дерево `.claude/worktrees/auction-per-142-483601`: фоновый `just verify > log 2>&1; echo "exit=$?"; tail log`, харнесс доложил «completed (exit code 0)», а внутри лога гейт стоял красным на `identity-lint` с кодом 3. Форма та же, что в третьем случае, и ошибка та же: `$?` печатался, но наружу уходил код `tail`, и именно его прочитал харнесс. Случай усиливает довод за второй адресат с другой стороны, чем шестой. Там гейт шёл вне контура; здесь он шёл **внутри** контура, но на шаге «Механический гейт», а не на шаге сдачи, и команду исполнитель составлял по ходу. Правило, записанное в `proj-deliver-task` и `proj-write-commit`, до этого шага не доходит: оба скилла запускаются позже, когда неверный вердикт уже прочитан и попал в отчёт. Восьмой случай — PER-207 2026-09-22, [PR #174](https://github.com/Solguficky/solguficky-hub/pull/174): на шаге «Механический гейт» внутри контура запущен `just verify 2>&1 | tail -60`. Харнесс доложил код 0, а гейт стоял красным на `identity-test`: рецепт без PostgreSQL падает, а не пропускается. Отказ прочитан по телу лога. Следующий прогон уже шёл без пайпа: `just verify > log; echo "VERIFY EXIT: $?"`. Подтверждения случай не добавляет: форма та же, что в пятом и седьмом, и шаг тот же, что в седьмом. Он показывает, что правило, вынесенное после второго случая, всё ещё не принято.
- **Следующий сигнал:** сигнал подтверждён дважды; дальше — формулировка правила, а не ожидание третьего случая.
- **Правило из двух случаев:** результат шага подтверждается кодом возврата самой команды, а не последней строкой её вывода. Практически: не ставить проверяемую команду перед пайпом, а когда вывод нужно сократить — печатать `$?` отдельной строкой сразу после неё и читать именно её, а не код обёртки. Область применимости — шаги, чей успех идёт в отчёт владельцу или служит условием следующего шага: гейт, коммит, push, кодогенерация. Оба случая про долгий вывод, поэтому правило нужно там, где вывод сокращают, а не везде.

Правило вынесено в `AGENTS.md`, а не только в скиллы сдачи, потому что случаи 6–8 произошли вне шага сдачи.
