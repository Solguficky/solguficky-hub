# 2026-09-14 — Пайп съел код возврата, и отвергнутый хуком коммит уехал в соседний

- **Контекст:** PER-245, ветка `feature/PER-245`, команды `just verify 2>&1 | tail -60` и `git commit -q -m ... 2>&1 | tail -1 && git add ... && git commit ...`.
- **Наблюдение:** дважды за одну сессию код возврата был прочитан у `tail`, а не у команды перед ним. Первый раз гейт остановился на рецепте `telegram-bot-proto` из-за отсутствующего `protoc-gen-es`, `tail` вернул 0, и сессия отчиталась о зелёном `just verify`. Второй раз хук `commit-msg` отверг заголовок длиной 77 символов при лимите 72; `tail` снова вернул 0, цепочка `&&` продолжилась, и следующий коммит забрал файлы несостоявшегося вместе со своими. Ни один из двух отказов не был виден в выводе: `tail -1` показывает последнюю строку хука, а она у lefthook успешная.
- **Последствие:** владельцу отправлен отчёт о зелёном гейте, которого не было, и потребовалась поправка. Два коммита пришлось разобрать `git reset --soft HEAD~2` и собрать заново с правильными заголовками. Оба раза расхождение нашлось не по коду возврата, а по сверке `git log` и лога гейта со списком ожидаемого.
- **Адресат:** Скилл — `proj-deliver-task` и `proj-write-commit`: оба предписывают шаг, результат которого нужно подтвердить, и оба не говорят, чем именно он подтверждается. Автоматическая проверка не подходит: команду составляет агент в момент запуска, и заранее проверять нечего. Второй адресат — правило в `AGENTS.md`, если окажется, что запрет читать код возврата через пайп нужен шире двух этих шагов.
- **Повторение:** второй независимый случай — PER-146, дерево `.claude/worktrees/per-146-project-task-784e10`, команда `just verify 2>&1 | tail -40`. Другая задача, другая сессия, другое дерево, механизм тот же и отказ тот же: гейт встал на `telegram-bot-proto` из-за отсутствующего `protoc-gen-es`, `tail` вернул 0, и владельцу отправлен отчёт о зелёном гейте. Внутри той же сессии сигнал сработал третий раз уже после исправления: запуск, обёрнутый в `just verify > log 2>&1; echo "VERIFY_EXIT=$?"; tail`, вернул 0 наружу как код `tail`, и красный гейт на `community-site-api-typecheck` был виден только в явно напечатанном `VERIFY_EXIT=1`. Два случая PER-245 по-прежнему независимыми друг другу не считаются. Четвёртый случай той же формы — сессия RFC-013 2026-09-21: фоновый запуск `just verify > log 2>&1; echo "EXIT=$?" >> log; tail log` завершился с кодом 0 от `tail`, харнесс доложил «completed (exit code 0)», а внутри лога стояло `EXIT=1` от `telegram-bot-proto`; красный прочитан только по явной строке. Пятый случай той же формы — PER-284 2026-09-21, дерево `.claude/worktrees/per-284-task-3f7dbb`: фоновый `just verify 2>&1 | tail -60`, харнесс доложил «completed (exit code 0)», гейт стоял на `telegram-bot-proto` из-за отсутствующего `node_modules`, и владельцу снова отправлен отчёт о зелёном гейте — поправленный в той же сессии. Подтверждения этот случай не добавляет: он показывает цену ожидания. Правило сформулировано после второго случая и с тех пор не принято, а ошибка повторилась в другой задаче, другом дереве и у другого исполнителя.
- **Следующий сигнал:** сигнал подтверждён дважды; дальше — формулировка правила, а не ожидание третьего случая.
- **Правило из двух случаев:** результат шага подтверждается кодом возврата самой команды, а не последней строкой её вывода. Практически: не ставить проверяемую команду перед пайпом, а когда вывод нужно сократить — печатать `$?` отдельной строкой сразу после неё и читать именно её, а не код обёртки. Область применимости — шаги, чей успех идёт в отчёт владельцу или служит условием следующего шага: гейт, коммит, push, кодогенерация. Оба случая про долгий вывод, поэтому правило нужно там, где вывод сокращают, а не везде.
- **Статус:** вынесено на обсуждение
