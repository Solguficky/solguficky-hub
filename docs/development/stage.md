# Stage хаба на VPS

Stage — хаб с аукционом и три бота в namespace `test` k3s на VPS ([PER-311](https://linear.app/anticnvm/issue/per-311), [PER-454](https://linear.app/anticnvm/issue/per-454), [PER-624](https://linear.app/anticnvm/issue/per-624)): семь сервисов чарта из AppHost, PostgreSQL на CloudNativePG и NATS JetStream. Раз в сутки ветка `stage` догоняет `develop`, и новые образы и чарт из неё stage выкатывает сам. Рантайм и правила кластера — [ADR-055](../decisions/ADR-055-k3s-runtime-from-aspire-chart.md), решения про stage — его дополнения 2026-10-06, 2026-10-07 и 2026-10-18. Боевой токен, бэкапы, Flux и SOPS в stage не входят: это листья [PER-80](https://linear.app/anticnvm/issue/per-80) и [PER-383](https://linear.app/anticnvm/issue/per-383).

Описание stage живёт в приватном ops-репозитории `solguficky-ops`, а не здесь: values с digest образов, манифесты PostgreSQL и NATS, сетевые разрешения и скрипты выкладки. Публичный репозиторий топологию среды не раскрывает (ADR-055, «Обоснование»). Этот файл — устойчивые правила работы со stage; команды и раскладка файлов — README ops-репозитория.

## Из чего состоит

| Что | Где | Кто применяет |
|---|---|---|
| namespace `test`: квота 1424Mi памяти, LimitRange, Pod Security `restricted`, NetworkPolicy, учётка выкатки | ops, `cluster/` | `ansible-playbook site.yml -K --tags cluster`, под sudo владельца |
| оператор CNPG, metrics-server, helm на хосте | ops, `cluster/`, `tasks/` | тот же playbook, теги `cluster` и `k3s` |
| таймер автовыкладки, клон ops-репозитория под `ops` и его read-only deploy key | ops, `tasks/autodeploy.yml` | тот же playbook, тег `autodeploy` |
| PostgreSQL 16 — кластер CNPG `hub-pg`, роль и база на сервис, роль `ops_readonly` | ops, `stage/test/postgres.yaml` | выкладка |
| NATS 2.12 с JetStream на томе | ops, `stage/test/nats.yaml` | выкладка |
| streams, durables, KV | чарт, Job `jetstream-topology` | Helm-hook при каждой выкладке |
| семь сервисов, из них три бота | чарт из AppHost, версия — ops `stage/test/release.yaml`, digest'ы — `stage/test/values.yaml` | выкладка |

Выкладка — одна и та же: её запускает таймер на хосте после нового коммита в ops-репозитории или человек командой `bin/stage deploy`.

Тома PostgreSQL и NATS — `local-path` на LV `/srv/state` хоста: они переживают рестарт пода и хоста.

## Секреты

Секреты лежат в файле `~/.config/solguficky/test.env` на хосте, права 0600, владелец `ops`. В Git и в values их нет. `bin/stage init` создаёт файл и генерирует сервисные токены и пароли ролей. Токены трёх тестовых ботов, `HUB_BOT_TOKEN`, `AUCTION_BOT_TOKEN` и `SUPPORT_BOT_TOKEN`, вписываются руками. Повторный `init` дописывает только новые переменные и прежних значений не меняет.

При выкладке из файла собираются Secret'ы ролей PostgreSQL и values секретов чарта. Последние передаются helm временным файлом в tmpfs и удаляются после установки. Каждый секрет чарта берётся из переменной с его именем в верхнем регистре (`secrets.auction.auction_db_user` — `AUCTION_DB_USER`). Секрет, которого в файле нет, роняет выкладку, а не уезжает пустой строкой.

Боты stage — три отдельных тестовых бота продакшн-среды Telegram, по одному на бот хаба, бот аукциона и бот поддержки. Два поллера на одном боте получают `409 Conflict` по очереди, и не работает ни один. Поэтому выкладка сравнивает id ботов каждой пары — часть токена до двоеточия — и при совпадении отказывает до первого изменения кластера, без значения токена в выводе (дополнение ADR-055 от 2026-10-07). Тот же токен нельзя одновременно держать в локальном `aspire run`: этого выкладка не видит, и второй поллер получит `409 Conflict`.

Бот поддержки ([ADR-068](../decisions/ADR-068-support-bot-with-operator-topics.md)) кладёт темы в тестовую супергруппу операторов, и он в ней администратор с правом управлять темами. Её id и ник бота поддержки — не секреты, а values среды: `config.support_bot.support_bot_group_id` и `config.hub_bot.support_bot_username` с `config.auction_bot.support_bot_username` — генератор чарта заводит ключ имени под каждым ботом, который его читает. Без id группы бот поддержки не стартует. Пустой ник выкладка не ловит, а «Задать вопрос ↗» бота аукциона тогда ведёт на `https://t.me/?start=auction`: ник в values — часть заведения бота, а не необязательная настройка.

Сводка «Что нового» на stage включена тем, кто переключатель не трогал ([ADR-069](../decisions/ADR-069-release-notes-as-environment-data.md), п. 5): values stage ставят `config.notifications.notifications_release_notes_enabled_by_default: "true"`. В чарте значение `false`: среда без ключа шлёт сводку только тем, кто включил категорию сам, а остальным сводки видны лишь в «Что нового». Иное значение, кроме `true` и `false`, роняет старт Notifications.

## Автовыкладка

Мерж в `develop`, который меняет образ сервиса или чарт, доезжает до stage следующей ночью без ручных шагов (дополнения ADR-055 от 2026-10-07 и 2026-10-18):

1. `stage-sync.yml` в 03:07 по Москве (`7 0 * * *` UTC) переносит ветку `stage` на `develop` fast-forward'ом. Push идёт deploy key'ем `STAGE_SYNC_KEY` из environment `stage-sync`, допущенного только для `main`: push под `GITHUB_TOKEN` не запустил бы публикации. Если в `stage` есть коммит, которого нет в `develop`, джоба красная, а ветка остаётся как была.
2. CI публикует изменённые этим переносом образы и чарт в GHCR (`image-*.yml`, `chart-publish.yml` на push в `stage`, по своим фильтрам путей).
3. Джоба `stage` того же workflow (`stage-bump.yml`) коммитит digest в `stage/test/values.yaml` или версию чарта в `stage/test/release.yaml` прямо в `main` ops-репозитория. Ключ записи — секрет `OPS_DEPLOY_KEY` в environment `stage` этого репозитория, допущенном только для ветки `stage`.
4. Таймер `solguficky-stage-autodeploy` на хосте раз в две минуты тянет клон ops-репозитория своим read-only deploy key и выкатывает новый коммит.

Образ у трёх ботов один — `hub-bot`, и ключ digest'а в `values.yaml` у них один: `parameters.hub_bot.hub_bot_image`. Новый digest перекатывает все три бота, а откатить образ одного бота отдельно нельзя. Ключ `parameters.auction_bot.auction_bot_image` новый чарт не читает, а CI его больше не двигает ([PER-538](https://linear.app/anticnvm/issue/per-538)). Из `values.yaml` он не удаляется: его читают версии чарта до PER-538. Откат `release.yaml` на такую версию ставит бот аукциона на последний записанный туда digest. Без ключа старый чарт взял бы свою заглушку `auction-bot:latest`, и выкладка отказала бы на проверке digest.

Входящего доступа к хосту у CI нет, API k3s по-прежнему закрыт. Публикации одного мержа приходят разными коммитами и выкатываются по очереди. Если чарт с новым сервисом пришёл раньше digest'а его образа, выкладка отказывает до изменения кластера, а коммит с digest'ом её чинит.

Таймер отмечает коммит попыткой до выкладки. Упавшая выкладка остаётся упавшей ревизией helm: по кругу она не повторяется и сама не откатывается. Следующий коммит в ops-репозитории выкатывается заново, а откат — решение человека, как и раньше. Исключение — выкладка, которая не прочитала чарт из GHCR: кластер она не тронула, и тот же коммит повторяется следующим тиком.

```bash
bin/stage autolog --since=today   # журнал таймера: коммит, версия чарта, digest каждого образа, итог
bin/stage status                  # образы подов по digest, история релиза, последняя автовыкладка
bin/stage pause                   # остановить автовыкладку; идущую выкладку пауза не прерывает
bin/stage resume                  # вернуть; следующий тик выкатит main, даже если новых коммитов нет
```

Журнал — `journalctl -u solguficky-stage-autodeploy` на хосте, `bin/stage autolog` читает его с control node. Таймер — системный юнит под `ops` и после перезагрузки хоста работает сам. Проверка — `ansible-playbook verify.yml -K --tags autodeploy`: таймер включён и после загрузки уже срабатывал.

### Первая установка

Пошаговый runbook с командами — README ops-репозитория, раздел «Автовыкладка: первая установка». Здесь — что должно быть верно, чтобы цепочка заработала, и в каком порядке. Порядок сложился на живой установке 2026-10-07, и каждый пропуск в нём стоил круга.

- **Deploy keys включены в организации** (Settings → Member privileges → Deploy keys). Это политика всей организации, на репозиторий её не включить. Пока она выключена, GitHub отвечает на добавление ключа `Deploy keys are disabled for this repository`.
- **Ключей два, у каждого своя роль.** Ключ хоста — только чтение, создаётся на хосте playbook'ом, в GitHub попадает только его публичная часть. Ключ CI — с правом записи, его закрытая часть живёт только в секрете `OPS_DEPLOY_KEY`.
- **Environment `stage` этого репозитория ограничен веткой `stage`**, и в нём лежит `OPS_DEPLOY_KEY`. Секрет нужен до переноса, который меняет образы: публикации без секрета проходят, а их джобы `stage` падают с «нет секрета», и digest'ы до ops не доходят — их приходится публиковать заново.
- **Синхронизации ветки нужны три вещи** (дополнение ADR-055 от 2026-10-18). Первая — deploy key этого репозитория с правом записи, закрытая часть которого лежит только в секрете `STAGE_SYNC_KEY` environment `stage-sync`, а environment допущен только для `main`. Вторая — ruleset ветки `stage`: запрет force push и удаления, обновление только с bypass для deploy key'ев. Третья — `stage-sync.yml` на `main`: cron и `workflow_dispatch` GitHub берёт только с default branch, поэтому до релиза в `main` ночного переноса нет.
- **Токены всех ботов в файле секретов хоста до `--tags autodeploy`.** На работающем хосте таймер срабатывает сразу при включении и выкатывает `main` ops. Без токена любого из ботов выкладка откажет на проверке и отметит коммит; после того как токен вписан, нужен `bin/stage resume`.

### Выкатить заново из CI

Отдельной кнопки выкладки нет: выкладка — это коммит в ops, и в него ведут обычные пути.

| Нужно | Как | Что произойдёт |
|---|---|---|
| довезти `develop` до stage, не дожидаясь ночи | `gh workflow run stage-sync.yml --ref main` | fast-forward `stage`, публикации изменённого, выкладка |
| пересобрать образ сервиса и выкатить | `gh workflow run image-<сервис>.yml --ref stage` | публикация, коммит digest в ops, выкладка таймером за ≤2 минуты |
| переопубликовать чарт и выкатить | `gh workflow run chart-publish.yml --ref stage` | новая версия `0.1.<N>` в `release.yaml`, выкладка |
| выкатить то, что уже записано в ops | `bin/stage resume` | следующий тик выкатывает `main` ops без сборки |
| то же сразу, не дожидаясь таймера | `bin/stage deploy` | ручная выкладка из `release.yaml` и `values.yaml` |
| вернуть образ на прежний digest | правка `stage/test/values.yaml` коммитом в `main` ops | таймер выкатит этот коммит |

Ручной запуск с другой ветки на stage не попадёт: публикация идёт только на ветке `stage`, и environment `stage` отдаёт секрет только ей. Чарт ветки ставится руками — раздел «Ручная выкладка».

## Ручная выкладка

Команды запускаются с control node (WSL) из корня ops-репозитория. kubeconfig среды хост не покидает, поэтому `bin/stage` копирует `stage/` на хост и запускает там helm и kubectl учёткой выкатки. Ручная выкладка и таймер берут один lock и идут по очереди. CI пишет в `origin/main` ops-репозитория, поэтому копия на control node отстаёт сама: `bin/stage deploy` отказывает, пока в ней нет `origin/main`, — иначе он выкатил бы старые digest'ы, а таймер, у которого этот коммит уже отмечен, их бы не вернул.

```bash
bin/stage deploy                                 # чарт и версия из stage/test/release.yaml — то же, что делает таймер
bin/stage deploy ./solguficky-hub-<версия>.tgz   # чарт ветки до публикации
```

Чарт ветки ставится только при остановленной автовыкладке: `bin/stage pause` до, `bin/stage resume` после. Иначе следующий коммит из ветки `stage` выкатит опубликованный чарт поверх ветки.

Порядок внутри выкладки: сначала проверки, которые могут отказать по входу, — секреты, токены ботов, digest каждого образа чарта. Затем Secret'ы ролей, PostgreSQL и NATS с ожиданием готовности, затем `helm upgrade --install` с `--wait`. Отказ проверки оставляет stage таким, каким он был. Pre-hook чарта применяет топологию JetStream до сервисов. Без `--atomic`: упавшая выкладка остаётся упавшей ревизией, и решение об откате принимает человек (ADR-055).

Правка values перекатывает поды сама: шаблон пода несёт контрольные суммы своих ConfigMap и Secret. Все сервисы — `Recreate`, поэтому каждая выкладка, меняющая под, даёт простой этого сервиса.

Чарт ставится с публичного GHCR без pull secret: пакеты образов и чарта открыты. Пакет нового образа GHCR создаёт приватным при первой публикации, и его открывают руками в настройках пакета.

## Остановка одного бота

Боты — разные процессы со своими токенами, и под одного не трогает другой.

```bash
bin/stage pause                 # иначе следующая выкладка вернёт под
bin/stage stop auction-bot      # бот аукциона перестаёт отвечать, бот хаба работает
bin/stage start auction-bot
bin/stage resume
```

Так же останавливается любой сервис чарта. Чарт задаёт одну реплику, и выкладка во время остановки может вернуть под, поэтому на это время автовыкладка стоит на паузе, а под возвращает явный `start`.

## Откат

```bash
bin/stage status            # номер ревизии в истории
bin/stage rollback <ревизия>
```

Откат возвращает образы, values и Secret'ы сервисов выбранной ревизии и перекатывает поды. Базу он не трогает.

Топологию JetStream откат тоже не трогает. Job топологии — hook на `pre-install,pre-upgrade`, а `helm rollback` запускает только `pre-rollback`, поэтому в NATS остаются streams и durables новейшей выкладки. Пока версии топологию только дополняют, старой версии сервисов это не мешает. Откат через изменённый stream или durable — решение человека, как и откат через миграцию. Старый образ поднимается на схеме новой версии: Flyway Auction пропускает неизвестные ему будущие миграции, а миграции остальных сервисов на это не проверены. Откат через миграцию, которую старый код не понимает, — решение человека, а не команды.

Проверено 2026-10-06: ревизия, менявшая шаблон пода бота, откатилась без правки базы, бот пересоздавался дважды, `409 Conflict` в его логе нет. Счётчики сходок, аукционов и журнала Auction до и после совпали.

Проверено 2026-10-06: после перезагрузки хоста все поды готовы примерно через три минуты, сходка, её события, аукцион и профиль на месте. Сервисы перезапускались два-три раза: они стартуют раньше PostgreSQL, и в кластере их никто не придерживает до готовности базы. Лотов на stage ещё нет (последний пункт раздела «Что известно»).

## Сброс данных

Данные stage не ценны, и иногда их проще завести заново, чем переносить: так решено для перевода реплики людей Notifications на права ([PER-529](https://linear.app/anticnvm/issue/per-529)), где миграция `022_identity_replica_rights` сбрасывает строки прежней формы. Сброс — это всё состояние среды разом, а не одна база:

- **Четыре базы сервисов — `identity`, `meetups`, `notifications`, `auction` — очищаются вместе.** Сервисы ссылаются друг на друга идентификаторами без ссылочной целостности: подписки и реплики Notifications держат `identity_id` и `meetup_id`, аукцион — сходку. Сброшенная по одной база оставляет в соседних ссылки на то, чего больше нет.
- **Состояние JetStream очищается вместе с базами** — streams, durables и KV журналов доставки ботов. Старый stream рядом с пустыми базами перечитали бы новые durables и заново разослали бы уведомления. Пустая шина рядом со старыми базами оставила бы реплики Notifications без событий, которые их поправили бы.
- **Роли, пароли и секреты не трогаются.** Пустые базы с прежними владельцами и паролями из файла секретов хоста — всё, что нужно сервисам. Схему каждый сервис применяет сам на старте, а топологию JetStream — Job чарта при выкладке.

Порядок:

1. `bin/stage pause`: иначе тик таймера поднимет сервисы посреди сброса.
2. Остановить все шесть сервисов (`bin/stage stop <сервис>`), чтобы ни один не писал в базу и не подтверждал сообщения во время очистки.
3. Очистить четыре базы и состояние JetStream.
4. `bin/stage deploy`: Job топологии заводит streams, durables и KV заново, сервисы стартуют и применяют миграции с нуля.
5. `bin/stage resume`.
6. Заново выдать набор `maintainer` — раздел «Администратор». Профили людей появятся заново с их первым `/start`.

Шаг 3 — очистку четырёх баз и состояния JetStream — выполняет команда ops-репозитория `bin/stage reset [--yes]`. Как очищать базы CNPG и том NATS, решает раскладка ops, и команда сброса — его, а не этого репозитория (ADR-055, «Обоснование»). Локальный сброс — `just local-data-reset` ([local-development.md](local-development.md)).

## Логи, метрики и база

```bash
bin/stage logs <сервис> [-f] [--since=1h] [--previous]   # identity, meetups, notifications, hub-bot, auction, auction-bot, nats, postgres
bin/stage top                                            # память и CPU подов
bin/stage db <база>                                      # туннель на localhost:15432 ролью ops_readonly, до Ctrl-C
```

Логи подов хранятся на хосте 14 дней (дополнение ADR-055 от 2026-10-05), но только для живых подов: лог пересозданного пода уходит вместе с ним, `--previous` даёт только прошлый рестарт контейнера.

Поиск по логам, метрики и трейсы stage — в своём источнике Better Stack, отдельном от прода (дополнение 2026-10-08 к [ADR-053](../decisions/ADR-053-production-observability-otlp-better-stack.md), [PER-378](https://linear.app/anticnvm/issue/per-378)). Источник видит не всё: логи туда идут от `Warning`, трейсы — выборкой 10 %, а хранятся 3 дня. Остальное — `bin/stage logs` в пределах тех же 14 дней на хосте.

`bin/stage db` печатает строку подключения для psql или DBeaver. Роль `ops_readonly` состоит в `pg_read_all_data`: читает все таблицы всех четырёх баз и ничего не пишет. Пароль — в файле секретов на хосте.

## Администратор

Набор `maintainer` на stage выдаёт служебный `GrantPreset` Identity с `"preset": "PRESET_MAINTAINER"`, снимает — `RevokePreset` ([ADR-065](../decisions/ADR-065-circle-presets-and-verb-rights.md)). Вызывающего сервиса у этих методов нет: право доказывает общий секрет `IDENTITY_MAINTAINER_TOKEN` в заголовке `authorization: Bearer`, и его утечка равна праву выдавать наборы ([ADR-037](../decisions/ADR-037-identity-maintainer-shared-secret.md)). Человеку без круга `member` выдача даёт его той же операцией. Тем же путём выдаётся и `PRESET_ADMIN`, но обычный путь другой: мейнтейнер назначает администратором себя и других экраном «Управление → Администраторы» в боте хаба, без секрета ([PER-521](https://linear.app/anticnvm/issue/per-521)): бот зовёт `AppointAdministrator` от его имени. Служебным endpoint'ом выдаётся только `maintainer`.

```bash
bin/stage grant <ник>     # выдать maintainer; ник Telegram с @ или без
bin/stage revoke <ник>    # снять
bin/stage presets         # активные наборы: ник и набор
```

1. Человек шлёт `/start` боту хаба на stage: так появляется его профиль. Без профиля, как и на нике у двух профилей, `grant` отказывает до вызова Identity.
2. Вызов идёт с хоста, а не с control node: секрет лежит в файле секретов хоста и его не покидает, как и kubeconfig среды (ADR-055). `bin/stage` копирует скрипты на хост, а там `identity_id` находится по нику в базе `identity`, `kubectl port-forward` к Service `identity-service` живёт один вызов, и секрет приходит в `grpcurl` окружением, а не аргументом. Прежний ручной путь — туннель с control node и `grpcurl` на нём — увозил секрет с хоста при каждой выдаче.
3. Повторная выдача отвечает `{"changed": false}`, второго сообщения о назначении в хаб не приходит.

Команды и раскладка — README ops-репозитория, раздел «Администратор».

### Разовая выкладка ADR-065

Переход на круг, наборы и права с глаголом ([ADR-065](../decisions/ADR-065-circle-presets-and-verb-rights.md)) меняет контракты пяти сервисов без обратной совместимости, поэтому выкатывается один раз, целиком и в таком порядке. Сброс данных не нужен: миграции Identity 017 и Notifications 024 переносят состояние, а мейнтейнер stage получает наборы `maintainer` и `admin` и назначать себя заново ему не нужно.

1. **До мержа — `bin/stage pause`.** Автовыкладка катит каждую публикацию мержа отдельным коммитом ops раз в две минуты. Без паузы новый образ одного сервиса встанет рядом со старыми соседями, а Identity применит миграцию раньше, чем остановлены боты.
2. **Мерж и публикации.** Мержится pull request, а ветка `stage` догоняет `develop` ночью или по `gh workflow run stage-sync.yml --ref main`; CI публикует образы `identity`, `meetups`, `notifications`, `auction`, `hub-bot` и чарт. Дождаться, пока все джобы `stage` этих публикаций зелёные (`gh run list --branch stage`), и `git pull` в копии ops: в `stage/test/values.yaml` новые digest'ы пяти образов, в `release.yaml` новая версия чарта.
3. **Остановить ботов** — `bin/stage stop hub-bot`, `bin/stage stop auction-bot`. Без них Identity не пишет новых событий, а Notifications дочитывает старые.
4. **Проверки до выкладки** в `bin/stage db identity`:
   - `SELECT count(*) FROM identity_outbox WHERE published_at IS NULL;` — 0. Иначе подождать: релей старого Identity ещё работает. Миграция 017 помечает неопубликованные строки прежней формы опубликованными — в новой форме их не закодировать, и событие пропало бы.
   - `SELECT count(*) FROM identity_roles r JOIN profiles p ON p.id = r.identity_id WHERE p.blocked AND r.revoked_at IS NULL;` — 0. Иначе миграция 017 откажет на старте с `a blocked profile holds an active role`.
5. **Дождаться, пока Notifications дочитал события Identity** — у durable `notifications-identity-events` стрима `IDENTITY_EVENTS` нет ни ожидающих, ни неподтверждённых сообщений (`nats consumer info IDENTITY_EVENTS notifications-identity-events`: `Unprocessed Messages: 0`, `Outstanding Acks: 0`). Готовой команды в `bin/stage` для этого нет. Событие прежней формы, прочитанное Notifications после его миграции 024, легло бы в реплику без круга и до следующего события человека уводило бы доставку не в тот бот.
6. **Выкладка** — `bin/stage deploy` (или `bin/stage resume`, и таймер выкатит `main` ops). Одна выкладка меняет все сервисы разом; боты возвращаются ею же. В логах Identity и Notifications (`bin/stage logs identity`, `bin/stage logs notifications`) — применённые миграции 017 и 024 без ошибок.
7. **Проверка результата.** В `bin/stage db identity`: `SELECT preset, count(*) FROM identity_presets WHERE revoked_at IS NULL GROUP BY preset;` — у мейнтейнера `maintainer` и `admin`. С телефона: в боте хаба есть «Управление», в аукционе сходки — «Добавить лот», и лот добавляется. Гость в боте аукциона по-прежнему торгует.
8. **`bin/stage resume`**, если на шаге 6 выкладка шла командой `deploy`.

Откат этой выкладки — не `bin/stage rollback`: старые образы не понимают схему после 017 и 024, а `goose down` выкладка не запускает. Если выкладка упала и не чинится вперёд, путь назад — сброс данных (раздел «Сброс данных») и повторная выкладка новой версии с bootstrap мейнтейнера.

## Наполнение аукциона

Свежий аукцион с лотами на сессию тестовой группы заводит `just auction-seed <каталог>` ([PER-613](https://linear.app/anticnvm/issue/per-613)), а не форма бота: аукцион после недели и финала заново не используется, а десять лотов формой — полчаса. Команда публикует сходку, включает у неё аукцион и заводит лоты с фото, стартовой ценой и шагом тем же путём, что форма сходки и форма лота бота хаба: клиентами бота, с токеном вызывающего бота хаба и от имени администратора, которого `ResolveIdentity` находит по Telegram id. Право на каждую команду решают Meetups и Auction, поэтому администратор должен уже держать набор `admin` (раздел «Администратор»). В базы команда не пишет: данные Auction — журнал Pekko Persistence, и путь к ним только через gRPC.

Каталог — JSON: сходка (`title`, `description`, `venue`, `startsAt` вида «31.10.2026 19:00» во времени сообщества) и лоты (`title`, `description`, путь `image` относительно файла каталога, `startingPrice` и `step` целыми рублями). Образец с фото — `tools/auction-seed/example/catalog.json`. Каталог проверяется целиком до первого вызова, и отказ перечисляет все ошибки с номерами лотов. Отказ сервиса посреди наполнения называет лот и шаг; то, что уже заведено, остаётся, и следующий запуск заводит новую сходку — каждый запуск новый.

Сроки недели, «Счастливые часы», розыгрыш и открытие недели команда не задаёт: это пульт администратора в боте хаба.

Переменные — без умолчаний: `IDENTITY_GRPC_URL`, `MEETUPS_GRPC_URL`, `AUCTION_GRPC_URL`, `HUB_BOT_SERVICE_TOKEN`, `AUCTION_SEED_ADMIN_TELEGRAM_ID`, `BOT_COMMUNITY_TIME_ZONE`. Адреса и токен — те же имена, что отдаёт `Contour.Host --with-auction`, поэтому команда без переименований идёт и против контура. Для stage значения берутся из файла секретов хоста (токен вызывающего бота хаба), а адреса — туннелем с control node к Service'ам Identity, Meetups и Auction: порты подов снаружи закрыты. Команды туннеля — README ops-репозитория.

## Если что-то не так

| Симптом | Причина | Что делать |
|---|---|---|
| джоба `stage` красная: `нет секрета OPS_DEPLOY_KEY` | секрета нет в environment `stage` или вызов не передал его по имени | положить секрет, затем `gh workflow run` нужной публикации на `stage` |
| джоба `stage-sync` красная: fast-forward невозможен | в ветке `stage` есть коммит, которого нет в `develop` | разобрать коммит: нужный довезти в `develop` pull request'ом, затем вернуть `stage` на предка `develop` (ruleset пустит только владельца в обход) |
| джоба `stage-sync` красная: `нет секрета STAGE_SYNC_KEY` | секрета нет в environment `stage-sync` или запуск не с `main` | положить секрет, запустить `stage-sync.yml` с `main` |
| ночью `stage-sync` не запустился | `stage-sync.yml` ещё не на `main`, или GitHub выключил расписание после 60 дней без активности в репозитории | релиз в `main`; включить workflow в Actions |
| джоба `stage` красная: push отвергнут пять раз | гонка записей одного мержа не разошлась повторами | перезапустить эту публикацию; повторится — сигнал пересмотра в дополнении ADR-055 |
| в `bin/stage autolog` `Permission denied (publickey)` | ключа хоста нет в Deploy keys ops-репозитория или deploy keys выключены в организации | добавить ключ (текст печатает `--tags autodeploy`) |
| `autolog` молчит, новый коммит в ops лежит | автовыкладка на паузе или таймер не включён | `bin/stage status` (строка «на паузе»), `bin/stage resume`; `verify.yml --tags autodeploy` |
| выкладка `упала, код N` | см. вывод helm в `autolog` | починить и закоммитить в ops или `bin/stage rollback`; тот же коммит сам не повторится |
| выкладка отказала до кластера: `нет digest образа` | чарт с новым сервисом пришёл раньше его образа | ничего: коммит с digest'ом выкатится следующим тиком |
| `bin/stage deploy`: «копия отстала от origin/main» | CI писал в ops после последнего `git pull` | `git pull` в копии ops на control node |
| `bin/stage grant`: `нет grpcurl на хосте` | хост собран до задачи `grpcurl` в `site.yml` ops | `ansible-playbook site.yml -K --tags grpcurl` |
| под Identity перезапустился с `connection refused` до `hub-pg-rw` | первое подключение нового пода к базе | ничего: рестарт снимает (пункт «Что известно») |

## Что известно

- **Простой PostgreSQL на обновлении оператора CNPG.** Инстанс один, и смена образа оператора пересоздаёт его: около трёх минут сервисы получают `connection refused`, а бот отвечает ошибкой зависимости. Так было 2026-10-06 после закрепления образа оператора по digest.
- **Первое подключение нового пода к базе бывает отвергнуто.** Identity однажды перезапустился на старте с `connection refused` до `hub-pg-rw`, хотя PostgreSQL работал. Похоже на задержку, с которой NetworkPolicy k3s узнаёт адрес нового пода; рестарт её снимает. Повторилось 2026-10-07 на автовыкладке нового образа Identity: один рестарт, код 1, `connection refused`.
- **NATS на stage новее локального.** Stage работает на nats-server 2.12, AppHost локально — на `nats:2.10-alpine`. Топология и сервисы на 2.12 работают, но опираться на возможности 2.12 нельзя, пока версии не выровнены решением об обновлении.
- **Память урезана.** Лимиты сервисов stage в сумме 944Mi против формы чарта 2048Mi. На 2026-10-07 в простое Auction занимает 295Mi из 320Mi, бот хаба — 84Mi из 112Mi, Identity — 14Mi из 48Mi. OOMKilled — сигнал поднять квоту `test`, а не снять лимиты (дополнения ADR-055 от 2026-10-06 и 2026-10-07).
