# Пульты бота: cookbook

> **Статус:** Draft, 2026-10-02. Пульт провода прошёл экраны бота против поднятого контура ([PER-343](https://linear.app/anticnvm/issue/per-343)); живой пульт проверен только L0-тестами и smoke-прогоном на подменах и против настоящей тестовой среды Telegram не запускался: войти в неё не удалось, чем проверять вместо неё — раздел [«Живая проверка»](#живая-проверка). Живой пульт даёт агенту доступ к тестовой среде Telegram, а [ADR-046](../decisions/ADR-046-telegram-test-contour.md) такого доступа пока не предусматривает: поправка к решению за владельцем.

Документ собирает готовые приёмы работы с двумя пультами, через которые человек или агент ведёт разговор с ботом по шагу: пишет, жмёт кнопки по подписи, читает экраны и выбирает следующий шаг по увиденному. Сценарии `tests/contour/bot-wire/` и живой прогон `just telegram-live-test` пишутся заранее и проверяют известное. Пульт нужен для прохода, в котором путь заранее неизвестен: исследовать новый экран, воспроизвести жалобу, проверить правку глазами пользователя до того, как закреплять её сценарием.

## Какой пульт брать

| | Пульт провода (L2) | Живой пульт (L3) |
|---|---|---|
| Рецепт | `just contour-bot-console` | `just telegram-live-console` |
| Клиент | `tests/contour/bot-wire/console/send.sh` | `tests/telegram-live/console/send.sh` |
| Порт | 7357, `BOT_CONSOLE_PORT` | 7358, `LIVE_CONSOLE_PORT` |
| Telegram | не участвует: экран — то, что бот отправил в Bot API | настоящий, тестовая среда |
| Бот | собирается в процессе пульта | поднимает владелец: `aspire run -- --profile hub --telegram-environment test` |
| Люди | сколько угодно, с ролями `admin`, `member`, `guest` | один синтетический аккаунт, роль — какая выдана в Identity |
| Ответ бота | готов к концу команды | асинхронный: пульт ждёт тишины |
| Лог бота в ответе | warn и error за действие | нет, бот в другом процессе |
| Нужно | Docker, .NET, Go, buf, Node | секреты `TelegramLive:*`, поднятый `hub`, доступ к DC Telegram |
| Журнал обмена | `.work/bot-console/*.jsonl` | `.work/bot-console-live/*.jsonl` |

По умолчанию бери L2. Там детерминированная среда, любые роли, видны ошибки бота, и не нужны ни секреты, ни Telegram. L3 нужен, когда вопрос именно про край Telegram: как доставляется сообщение, реальный `callback_query`, правка сообщения, всплывающее уведомление, уведомление, пришедшее само, или разметка карточки на стороне Telegram.

Ни один пульт не входит в `verify`, `test-all` и CI. Пульт — инструмент прохода, а не проверка: найденное в нём закрепляется сценарием (рецепт [«Закрепить находку»](#закрепить-находку-сценарием)).

## Общее для обоих

### Запуск и остановка

Пульт живёт, пока его не остановят командой `quit` или Ctrl+C. Готовность — строка `ready on http://127.0.0.1:<порт>/` в выводе рецепта или успешный ответ клиента без аргументов, который заодно печатает справку.

Агент запускает пульт фоновой командой, а готовности ждёт циклом на клиенте. Подъём контура занимает минуты, и ждать строки в выводе ненадёжно:

```bash
mkdir -p .work && just contour-bot-console > .work/bot-console.log 2>&1 &
until sh tests/contour/bot-wire/console/send.sh > /dev/null 2>&1; do sleep 3; done
```

`quit` останавливает только пульт. На L2 после него сам уходит и контур, потому что его держит `Contour.Host` ровно на время жизни пульта. На L3 бот продолжает работать: его поднимал владелец.

### Команда и ответ

Клиент склеивает аргументы в одну строку и отправляет её POST-ом. Кавычки не нужны: текст и подпись кнопки после действия берутся как есть, с пробелами и знаками. Код выхода клиента означает:

- `0` — команда исполнена;
- `22` — пульт отверг команду (400: нет такой кнопки, человек не заведён, опечатка) или не смог её исполнить (500: отказ сервиса или Telegram). Тело ответа всё равно напечатано;
- `7` — пульт не слушает.

Ответ — JSON. Главные поля:

- `changed` — экраны, которые действие отправило (`"change": "new"`) или отредактировало (`"change": "edit"`), по порядку;
- `last` — последний изменённый экран чата: то, что человек видит внизу;
- `pressable` — подписи кнопок, которые сейчас можно нажать на любом экране чата, начиная с последнего;
- `awaitsReply` у экрана — бот ждёт ответа на это сообщение: вопрос с режимом ответа и «Отменой» под ним.

Экран на L2 несёт ещё три поля — то, что бот отдал в Bot API, а не то, что нарисует клиент:

- `rows` — клавиатура по рядам; у кнопки `kind` — `callback` или `url` (её открывает клиент, нажать её нельзя), `target` — её `callback_data` либо адрес, и `style`, если бот задал цвет;
- `format` — `rich` (богатое сообщение, ADR-034), `html` или `plain`;
- `media` — `document` или `photo`: сообщение несёт файл, и `text` — его подпись.

И четыре поля у самого ответа на действие:

- `api` — методы Bot API, которые бот вызвал, по порядку. По ним видно, ушёл ли ответ на нажатие раньше правки экрана и был ли `sendChatAction`; вызов в чужой чат помечен `→ другому`;
- `ack` — ответ на нажатие: `{}` — без текста, `{"text": …}` — со всплывающим текстом, `null` — бот на нажатие не ответил. У действия без нажатия поля нет;
- `tookMs` — сколько бот обрабатывал действие;
- `lint` — нарушения [дизайн-кода](../design/bot/design-code.md#исполнение-правил) в экранах этого действия: запись каталога, правило и что именно не так. Поля нет — экраны чистые.

Если есть `jq`, ответ удобно сокращать до нужного:

```bash
send() { sh tests/contour/bot-wire/console/send.sh "$@" | jq -c '{last: .last.text, pressable, log}'; }
send alice say /start
```

### Кнопки по подписи

`press` нажимает кнопку с этой подписью на последнем изменённом экране, где она есть. Так поступает человек, который листает чат вверх до ближайшей подходящей кнопки. Если подписи нет, отказ перечисляет, что нажать можно. Кнопку-ссылку пульт не нажимает, её открывает клиент Telegram. На L3 отказ называет её URL.

## Пульт провода (L2)

### Заведение людей

```bash
S=tests/contour/bot-wire/console/send.sh
sh $S new alice admin      # роль admin выдаётся настоящим GrantAdminRole
sh $S new bob member       # ник попадает в whitelist первого admin, роль — на первом /start
sh $S new carol guest      # ник вне whitelist
sh $S people
```

`member` нельзя завести раньше первого `admin`: вносить ник в whitelist некому. Имена — латиница в нижнем регистре, у каждого свой Telegram id на запуск. База контура живёт столько же, сколько пульт, поэтому при следующем запуске все начинают с нуля.

### Создать и опубликовать сходку

```bash
sh $S alice say /start
sh $S alice press Управление
sh $S alice press Создать сходку
sh $S alice say Настолки у Алисы         # название — единственный вопрос формы
sh $S alice press Дата и время           # дальше поля заполняются с черновика
sh $S alice press Другая дата            # экран заготовок: день, затем время; текстом — через эту кнопку
sh $S alice say 12.06.2027 19:00
sh $S alice press Место
sh $S alice say Циферблат
sh $S alice press Описание
sh $S alice say Берём свои игры
sh $S alice press Опубликовать
```

Пока висит вопрос (`awaitsReply: true` у последнего экрана), `say` отвечает на него цитатой, как это делает клиент Telegram, а кнопки экрана, с которого вопрос задан, уже сняты: нажать можно только «Отмена» под вопросом — она удаляет вопрос и присылает экран заново. Дата открывается не вопросом, а экраном заготовок (`awaitsReply: false`): кнопки дня (`сб 10`), после нажатия — времени (`19:00`) и «Другой день»; кнопка времени сохраняет дату целиком, «Другая дата» задаёт вопрос для ввода текстом. Результат публикации — карточка сходки с заметкой и «Ссылкой для чата», и в ответе у этого экрана появится `meetupId`.

### Что видит участник

```bash
sh $S bob say /start
sh $S bob press Ближайшие сходки
sh $S bob press Настолки у Алисы         # подпись кнопки сходки — её название
sh $S bob link <meetupId>                # как переход по ссылке из чата сообщества
```

Отрицательный путь проходится так же: до `Опубликовать` сходки нет ни в списке у `bob`, ни по `link`. Ответ на скрытую сходку совпадает с ответом на несуществующую, а её `meetupId` берётся из `journalOf` в сценарии или из экрана автора.

### Ответ на старый вопрос формы

```bash
sh $S alice press Управление
sh $S alice press Создать сходку
sh $S alice say /menu                    # команда вместо ответа: вопрос остаётся висеть
sh $S alice press Управление
sh $S alice press Создать сходку
sh $S alice answer 1 Первый черновик     # ответ на первый вопрос в чате, а не на последний
```

`answer <n>` отвечает на n-й по счёту вопрос бота в этом чате, считая и уже закрытые. Так в клиенте выбирают «Ответить» на старом сообщении. Вопрос, на который ответ принят или под которым нажали «Отмена», больше не ждёт, и ответ на него получает «вопрос устарел».

### Материалы сходки

```bash
sh $S alice press Материалы (0)
sh $S alice press Прикрепить материал
sh $S alice forward solguficky_contour 77   # пересланный пост публичного канала
sh $S alice say Программа вечера            # название материала
sh $S alice press Прикрепить
sh $S alice press Прикрепить материал
sh $S alice document Карта проезда.pdf      # файл; фотография — alice photo
sh $S alice say Карта проезда
sh $S alice press Прикрепить
```

`forward`, `document` и `photo` отвечают на висящий вопрос, как `say`. Подтверждение файла — сообщение с файлом и подписью (`media` у экрана), и бот правит его подпись, а не текст.

### Медленный сервис

```bash
sh $S slow meetups 1500             # запросы бота к Meetups доходят на 1,5 с позже
sh $S bob press Ближайшие сходки    # tookMs ≈ 1500, в api — sendChatAction, затем ответ на нажатие и правка
sh $S slow meetups 4000             # дольше дедлайна RPC: бот получает таймаут сам
sh $S bob press ‹ Меню              # меню сервис не зовёт и приходит сразу
sh $S bob press Ближайшие сходки    # tookMs ≈ 3000, экран — кадр отказа с «Повторить»
sh $S slow meetups 0                # снять задержку
```

Ответ на нажатие уходит вместе с результатом, поэтому в `api` он стоит перед правкой экрана, а не первым вызовом; `sendChatAction` появляется, когда сервис отвечает дольше секунды. Личность разрешается на каждом действии, и задержка Identity складывается с задержкой экрана, который тоже читает Identity: состав сообщества при `slow identity 1500` приходит через три секунды.

Бот ходит к Identity и Meetups через TCP-прокси пульта, поэтому задержка настоящая: клиент и дедлайн — продакшн-код, и таймаут срабатывает в нём, а не изображается. Задерживаются только запросы бота; заведение людей и прямые клиенты идут мимо прокси. Задержка держится до `slow <сервис> 0`. Запрос, который бот бросил по таймауту, до сервиса всё равно дойдёт — как и в жизни.

### Рестарт бота посреди разговора

```bash
sh $S alice press Управление
sh $S alice press Создать сходку
sh $S restart                            # процесс бота новый, память о вопросах потеряна
sh $S alice say Название после рестарта  # ответ принят: шаг едет в кнопке «Отмена» под вопросом
```

Рестарт не переживает один вопрос — название материала: его шаг живёт в памяти процесса, и ответ получает «Этот вопрос уже устарел. Прикрепи материал заново.».

`restart` меняет только процесс бота. История сообщений у людей и данные в Meetups остаются.

### Устаревший экран

Кнопку на экране, который с тех пор переписан, нажать нельзя, как и в Telegram: правка без клавиатуры клавиатуру снимает. Чтобы проверить реакцию бота на кнопку, которая уже не соответствует состоянию, нажми кнопку на экране, отрисованном до изменения:

```bash
sh $S bob press Ближайшие сходки         # список со сходкой
# alice снимает сходку с публикации своим путём
sh $S bob press Настолки у Алисы         # кнопка из старого списка
```

### Ошибки бота

Поле `log` в ответе собирает записи уровня `warn` и `error`, которые бот записал за это действие, с полями `use_case`, `error_category` и `request_id`. Пустой `log` при странном экране значит, что бот считает ответ штатным. Непустой `log` при нормальном экране — кандидат в находку.

## Живой пульт (L3)

### Подготовка

Секреты и бот — те же, что у `just telegram-live-test` ([local-development.md](local-development.md#живой-прогон-start)): `TelegramLive:ApiId`, `ApiHash`, `BotUsername`, строка сессии от `just telegram-live-login 99966XYYYY` и `hub`, поднятый с `--telegram-environment test`. Роль синтетического аккаунта задаёт владелец в Identity. Пульт её не меняет, поэтому проход за администратора требует, чтобы аккаунт им был.

```bash
aspire run -- --profile hub --telegram-environment test   # отдельное окно
just telegram-live-console
L=tests/telegram-live/console/send.sh
sh $L say /start
```

Отказы соединения называют причину первым словом, как у живого прогона: `session-invalid`, `not-test-environment`, `flood-wait`, `telegram-unreachable`.

### Как читать ответ

Бот в Telegram отвечает асинхронно. Поэтому ответ пульта — всё, что бот прислал или отредактировал от начала действия до тишины: первое событие пульт ждёт до 15 секунд, дальше — пока бот молчит полторы секунды. Отсюда три поля, которых нет на L2:

- `silent: true` — бот не ответил ничем. Это не ошибка пульта: бот может молчать правильно. Если ответ ожидался, первым делом проверь, что `hub` поднят именно с тестовой средой;
- `meanwhile` — что пришло между прошлой командой и этой: уведомления и запоздалые правки. Уведомление о сходке приходит сюда, а не в `changed`;
- `toast` — всплывающее уведомление на нажатие. Текст `(бот не ответил на нажатие)` означает, что callback остался без ответа; правка экрана при этом могла прийти и есть в `changed`.

Номер экрана здесь — настоящий `message_id` в чате. Пульт при старте читает последние 30 сообщений бота, поэтому кнопки старых сообщений тоже нажимаются.

### Проход по меню

```bash
sh $L say /start
sh $L press Ближайшие сходки
sh $L press ‹ Меню
sh $L look                               # перечитать чат из Telegram, ничего не делая
```

`look` берёт состояние из Telegram, а не из памяти пульта. Им проверяют, что Telegram действительно показывает то, что пульт собрал из событий.

### Форма и ответ цитатой

`say` отвечает цитатой, только если вопрос — последний экран чата. Если после вопроса бот прислал что-то ещё, отвечай явно по номеру:

```bash
sh $L reply 4312 Новое место             # 4312 — message у экрана с awaitsReply: true
```

### Сходка по ссылке

Диплинки `t.me/<бот>?start=…` из тестовой среды ведут в продакшн. Поэтому ссылка открывается командой `link`, которая отправляет `/start <payload>`. Брать можно целую «Ссылку для чата» или готовый `startPayload` из ответа:

```bash
sh $L link https://t.me/solguficky_test_bot?start=m_AZLzpFtsfY6fASNFZ4mrzQ
sh $L link m_AZLzpFtsfY6fASNFZ4mrzQ
```

Сходки под этот рецепт владелец готовит так же, как для кадра E-03 ([local-development.md](local-development.md#живой-прогон-start)).

### Уведомления

Уведомления бот присылает сам, без действия со стороны аккаунта. Чтобы увидеть их, подпиши аккаунт через бота, вызови событие со стороны организатора в другом клиенте или через L2 на той же базе, а затем выполни любую команду, например `look`. Всё пришедшее окажется в `meanwhile`.

### Флуд-лимиты

Флуд-лимиты тестовой среды строже, чем в продакшне. Пульт их не пережидает: отказ `flood-wait` называет срок, и повтор раньше срока его продлевает. Длинные проходы разбивай паузами, а ради проверки логики не гоняй L3 там, где хватает L2.

## Живая проверка

Живой пульт требует входа в тестовую среду Telegram, а войти в неё 2 октября 2026 года не удалось ([PER-343](https://linear.app/anticnvm/issue/per-343)). Пока решение по [PER-422](https://linear.app/anticnvm/issue/per-422) не принято и нового факта нет, попытку не повторяют: она стоит времени и упирается в те же места.

| Что пробовали | Где остановилось |
|---|---|
| Telegram Web `web.telegram.org/k/?test=1`, синтетический номер `99966XYYYY` | форма приняла номер и дошла до шага кода — среда действительно тестовая, — но отвергла код, собранный из цифры дата-центра: «Invalid code». Проверен один номер второго дата-центра |
| регистрация драйвером mtcute 0.32.2, на котором стоит `just telegram-live-login` | не запускалась: библиотека на ответ «нужна регистрация» сама бросает отказ — неофициальным клиентам Telegram её закрыл. Драйвер умеет войти только в уже заведённый аккаунт |
| Telegram Desktop в тестовом режиме | по словам владельца, аккаунт завести не получилось |

Секретов `TelegramLive:*` и токена тестового BotFather на машине нет, и рецепты `just telegram-live-*` не запускались.

Вопрос про край Telegram — как клиент рисует кнопку, что принимает Bot API, сколько ждёт ответа на нажатие — проверяется двумя способами в продакшн-среде, и оба идут через бот-зонд:

- **Web K через Chrome.** Владелец сам входит в `web.telegram.org/k/` отдельным аккаунтом, агент ведёт чат с dev-ботом расширением браузера и читает экран. Агент не вводит ни номер, ни код, ни пароль и не открывает другие чаты аккаунта.
- **Руками владельца на Desktop и мобильном.** Владелец шлёт зонду команды и говорит, что видит; лог зонда даёт вторую половину — что дошло до бота.

Бот-зонд — одноразовый скрипт, который опрашивает Bot API токеном локального dev-бота и на каждую команду отвечает сообщением с одной проверяемой механикой: кнопки со стилями, вопрос с кнопкой, задержанный ответ на нажатие. В репозитории его нет: он пишется под вопрос и живёт в `.work/`. Что нужно соблюсти:

- токен читается из user-secrets AppHost (`Parameters:hub-bot-token`) внутри скрипта и не попадает ни в вывод, ни в текст ошибки. Токен бота сообщества зондом не является;
- пока зонд опрашивает Bot API, `aspire run` с ботом на том же токене не запускают: второй поллер получает `409 Conflict`;
- долгий опрос и остальные вызовы идут разными соединениями. На общем соединении ответ на нажатие встаёт в очередь за `getUpdates`, и замер задержки негоден;
- на старте зонд пропускает накопившиеся апдейты, иначе команда остановки из прошлого запуска гасит его сразу.

Web K опорным клиентом не является ([дизайн-код](../design/bot/design-code.md#опорные-клиенты)): он не рисует индикатор на кнопке и «печатает…» и не открывает режим ответа у вопроса с кнопкой. Его проход подтверждает то, что решает сервер, — принят ли вызов, какой лимит, что пришло в апдейте. Вид и поведение на Desktop и мобильном подтверждает только ручная проверка.

## Закрепить находку сценарием

Журнал обмена — готовый черновик сценария. Каждая строка `.work/bot-console*/…jsonl` несёт команду, код ответа и ответ. Находку с L2 переписывают в тест `tests/contour/bot-wire/` почти построчно:

| Пульт | Сценарий L2 |
|---|---|
| `new alice admin` | `organizerAtStart(wire, direct)` из `steps.ts` |
| `new bob member` | `memberAllowedBy(wire, direct, adminId)` |
| `alice say …` | `person.says("…")` |
| `alice answer 2 …` | `person.answers(2, "…")` |
| `alice press …` | `person.presses("…")` |
| `bob link <uuid>` | `person.opensLink(meetupId)` |
| `alice forward <канал> <пост>` | `person.forwardsChannelPost(channel, postId)` |
| `alice document <имя>`, `alice photo` | `person.sendsDocument(fileName)`, `person.sendsPhoto()` |
| `restart` | `wire.restart()` |
| `last.text`, `pressable` | `person.sees()`, `person.pressable()` |

Проверку итога бери из прямых клиентов (`direct.readAsAdmin`, `direct.journalOf`), а не только с экрана: иначе провод проверяет сам себя. Находка, которую видно только на L3, становится кадром в `tests/telegram-live/*.live.test.ts`, если её можно выразить через `sendStart` и `press` драйвера, а иначе — задачей на расширение драйвера.

## Ограничения

- L2 не видит Telegram: реальную доставку и правки проверяет только L3. `format`, `rows` и `style` — то, что бот отправил, а не то, что показал клиент.
- L2 принимает любой вызов Bot API. Правку, которую Telegram отверг бы, — например, `editMessageText` у сообщения с файлом — пульт покажет состоявшейся, хотя живой бот ушёл бы в запасной путь с новым сообщением. Экран с `media` и `format: "rich"` — как раз такой случай.
- На L2 нет Notifications: контур поднимает только Identity и Meetups. Настройки уведомлений, подписка и отправка рассылки отвечают кадром E-05, а сами уведомления не приходят.
- `slow` задерживает только Identity и Meetups и только в пульте: сценарии `tests/contour/bot-wire/` идут без прокси.
- На L3 один аккаунт и одна роль. Сценарии за нескольких людей проходятся на L2.
- Картинки экрана нет ни на одном уровне: экран — это текст и подписи кнопок. У сообщения без текста, например у богатой карточки, на L3 будет поле `media` с типом.
- Язык команд живёт в шапках `tests/contour/bot-wire/console/commands.ts` и `tests/telegram-live/console/commands.ts`. При расхождении с этим документом прав код.
