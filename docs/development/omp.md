# OMP как исполнитель контура

> **Статус:** Research, 2026-09-15. Документ разбирает харнесс OMP и фиксирует его настройку для [контура исполнения](agent-execution-loop.md). Он не переводит контур на OMP и не назначает роли моделей.

Разбор отвечает на два вопроса: что OMP умеет сверх текущего стека и как им пользоваться, не переносив вслепую привычки Claude Code. Проверялась версия `omp/18.1.17` на Windows 11. Роли моделей и подключение ключей остаются за [PER-263](https://linear.app/anticnvm/issue/per-263), раскладка скиллов — за [PER-250](https://linear.app/anticnvm/issue/per-250), перенос хуков и команд — за [PER-251](https://linear.app/anticnvm/issue/per-251); здесь только названы механизмы, которыми OMP их принимает.

Границы прогона: учётки не заводились и не обновлялись, `omp token` без `--list` не запускался, `auth-broker` не поднимался. Ни один вывод с реальным значением ключа в документ не попал.

Каждое утверждение ниже помечено: **прогнано 2026-09-15** — проверено командой на этой машине в этом репозитории; **не прогнано** — взято из [документации OMP](https://omp.sh/docs) и требует проверки.

## OMP против шагов контура

| Шаг контура | Чем закрывает OMP | Вердикт | Проверка |
|---|---|---|---|
| 1. Захват | чтение Linear только через MCP, своего знания о трекере нет | не заменяет | не прогнано |
| 2. Дерево | `omp worktree` и перехват `git worktree add` в bash | **расходится с нормативом**, чинится конфигом | `omp worktree list` прогнан; сам перехват — нет |
| 3. Чтение | `read`, `grep`, `glob`, `lsp`; скиллы репозитория видны | дублирует | прогнано частично |
| 4. Чекпоинт плана | `/plan`, отдельный ход планирования | дублирует | не прогнано |
| 5. Реализация | `edit`, `write`, `bash` под выбранным режимом | дублирует | прогнан только слой одобрения bash |
| 6. Гейт | `just verify` через bash; альтернатива — `cleanse` | дублирует; `cleanse` не проверен | прогнано 2026-09-15 |
| 7. Ревью | `omp review`, `omp security` | не проверялось | не прогнано |
| 8. Коммит | `omp commit` стейджит всё дерево и пишет своё сообщение | **не использовать**, см. ниже | прогнано 2026-09-15 |
| 9. Pull request | инструмент `github` выключен по умолчанию, нужен `gh` | не заменяет | не прогнано |
| 10. Рефлексия | скилл читается, `disable-model-invocation` понимается | дублирует | не прогнано |
| 11. Отчёт | комментарий в Linear только через MCP | не заменяет | не прогнано |

Единственная строка, где OMP **заменяет** текущий шаг, лежит не в контуре, а в его обслуживании: `omp usage` одной командой показывает остаток лимита по каждому аккаунту каждого провайдера. Сейчас это ручная проверка в интерфейсе каждого сервиса по отдельности, и именно её отсутствие делает исчерпанный лимит внезапным — то есть ровно задачу эпика [PER-248](https://linear.app/anticnvm/issue/per-248).

## Режимы одобрения

Режим называет высший ярус вызовов, который проходит без вопроса. Ярусов три: **read** (чтение), **write** (запись в рабочее дерево), **exec** (`bash`, `eval`, `browser`, `task`).

| Режим | Проходит сразу | Спрашивает |
|---|---|---|
| `always-ask` | только read | write и exec |
| `write` | read и write | exec |
| `yolo` | всё | ничего по ярусу |

Встроенное значение — `yolo`, и цена этого не очевидна из названия. У `bash` есть проверка на узкий набор критических форм: рекурсивное удаление абсолютного пути, «скачать и выполнить», выключение хоста, запись в файлы аккаунта. В режимах `always-ask` и `write` эта проверка принудительно вызывает вопрос, но документация называет её *bare override*, а `yolo` пропускает такие override. Под `yolo` страховка на `rm -rf /абсолютный/путь` выключена, и абсолютной границу делает только явный `deny`.

Выбран `write`. Аргумент нормативный: [agent-execution-loop.md](agent-execution-loop.md) различает «внутри контура», где агент коммитит и пушит без отдельного разрешения, и «вне контура», где он обязан остановиться перед коммитом. `yolo` это различие стирает и держит его только текстом. Под `write` вызов `git commit` упирается в вопрос, и граница становится механизмом, а не обещанием.

Цена `write` названа прямо: в headless-режиме (`-p`, подагенты, ACP без UI) вопрос задать некому, и вызов падает. Поэтому команды, которые контур обязан выполнять сам, вынесены в allow-лист, а не оставлены на усмотрение режима.

### Что проверено прогоном

Гипотеза, с которой разбор начинался, оказалась ложной, и это важнее, чем если бы она подтвердилась. Ожидалось, что allow-лист будет систематически промахиваться: `bash.allowCompoundCommands` выключен, а `allow` по документации обязан совпасть с полной несоставной командой, тогда как рецепты репозитория полны конструкций `cd apps/identity && go build ./...`.

Промаха нет. `verify` — список зависимостей из других рецептов, а составные команды живут **внутри тел рецептов** и исполняются самим `just`, мимо слоя одобрения OMP. Харнесс видит одну несоставную строку `just verify`.

| Проба | Команда | Ожидалось | Результат |
|---|---|---|---|
| 1 | `just check-document-numbers` в allow-листе, режим `write`, headless | выполнится | выполнилась, код `0` |
| 2 | `git status --short` вне allow-листа, те же условия | откажет | `Tool "bash" requires approval but no interactive UI available` |

Вторая проба нужна не меньше первой: без неё первая доказывала бы только то, что всё подряд проходит.

## Ловушка слоёв конфигурации

Слои складываются так: встроенные умолчания < глобальный `~/.omp/agent/config.yml` < проектный `<cwd>/.omp/config.yml` < оверлеи `--config` < флаги запуска. Проектный слой ищется **строго в каталоге запуска**, без обхода предков.

Отображения сливаются глубоко, **массивы заменяются целиком**. Разница между этими двумя правилами и есть ловушка, потому что в одном файле рядом лежат обе структуры:

- `tools.approval` — запись (mapping). Глобальные запреты переживут проектный слой.
- `bash.patterns` — массив. Проектный список **затирает глобальный целиком**.

Проверено прогоном 2026-09-15: нижний слой запрещал `echo SENTINEL*`, верхний объявлял единственное несвязанное правило `just *`. Команда `echo SENTINEL-TEST` **выполнилась** — запрет исчез молча, без предупреждения.

Отсюда раскладка: запреты на капабилити живут глобально, а `bash.patterns` обязан быть самодостаточным в том слое, где объявлен. Проектный [`.omp/config.yml`](../../.omp/config.yml) повторяет запреты не по небрежности, а потому что иначе он их снимает.

## Что изменено в конфигурации и почему

Глобальный `~/.omp/agent/config.yml`, построчно:

| Строка | Почему |
|---|---|
| `tools.approvalMode: write` | норматив различает «внутри контура» и «вне контура»; `yolo` это различие стирает и выключает встроенную проверку критических форм bash |
| `tools.approval.computer: deny` | управление десктопом не нужно ни на одном шаге контура; `deny` выигрывает в любом режиме и переживает его смену |
| `tools.approval.eval: deny` | `bash.patterns` управляют только инструментом `bash`; шелл, поднятый через `eval`, они не покрывают, и без этого запрета любой деньлист обходится |
| `worktree.clone: false` | перехваченный `git worktree add` иначе делает CoW-клон, невидимый в `git worktree list` |

Везде `deny`, а не `prompt`, по двум независимым причинам: `deny` действует во всех режимах, а `prompt` внутри подагента ответить некому, и он превращается в отказ.

Проектный `.omp/config.yml` несёт `worktree.clone: false` (чтобы норматив [branching.md](../standards/git/branching.md) защищался у любого, кто откроет репозиторий в OMP, а не только на этой машине) и самодостаточный `bash.patterns`: запреты первыми, затем `just *` под гейт и чтение состояния git. Порядок значим — выигрывает первое совпавшее правило.

Что **не** менялось и почему:

- `symbolPreset`, `composer.shape`, `theme` — косметика онбординг-мастера, к работе отношения не имеет.
- `modelRoles` — PER-263. Отдельно зафиксирован разрыв: `cycleOrder` по умолчанию ссылается на роль `slow`, а её в `modelRoles` нет.
- `providers.webSearchOrder: []` — выглядит недонастройкой, но пустой список означает порядок по умолчанию, а не отсутствие провайдера. Прогнано 2026-09-15: `omp search` отработал, выбрал OpenAI, вернул 16 источников.
- `advisor.enabled`, `prewalk.enabled`, `plan.autosave`, `memory.backend`, `security.enabled` — оставлены выключенными сознательно. Первые два тянут вторую модель, а роли — PER-263. `plan.autosave` при включении пишет планы в `<project>/.omp/plans/`, то есть в репозиторий.
- `omp setup` не запускался. Необязательных компонентов ровно два, и оба опрошены через `--check`: `python` не нужен (в системе настоящий Python 3.11.9), `speech` не нужен (parakeet и kokoro обслуживают `omp say`, в контуре не участвует). Сам мастер — онбординг, а не установщик: `setupVersion: 2` означает, что он уже прошёл и записал косметические ключи, поэтому повторный запуск перезаписал бы осознанные решения мастерскими умолчаниями.

## Где живут учётки

Хранилище — `~/.omp/agent/agent.db`, обычный SQLite **без шифрования**. Проверено прямым чтением схемы 2026-09-15: таблица `auth_credentials`, четыре записи, колонки `provider`, `credential_type`, `data`. Рядом лежат `agent.db-wal` и `agent.db-shm`, поэтому защищать нужно каталог целиком, а не один файл; любой бэкап или синхронизация каталога выносят учётки. На POSIX OMP ставит `0700`/`0600`, на Windows защита сводится к ACL аккаунта.

Порядок выбора источника: `--api-key` → `providers.<name>.apiKey` в `models.yml` → сохранённый OAuth-логин → ключ, сохранённый `/login` → переменная окружения провайдера → прочий сохранённый ключ → fallback кастомного провайдера. Практическое следствие, которое ломает интуицию: **экспорт переменной окружения не перебивает сохранённый `/login`**. Чтобы переменная подействовала, учётку сначала снимают через `/logout`.

`auth-broker` не настроен (`No auth-broker configured`). Он даёт общий пул учёток на несколько машин с refresh-токенами на одном хосте; при одной машине смысла не несёт и относится к ферме из [PER-248](https://linear.app/anticnvm/issue/per-248), а не к этой задаче.

## Показывает ли `omp usage` остаток

Показывает, и это ответ полями, а не пересказом. В JSON у каждого лимита есть `amount.used`, `amount.limit`, `amount.remaining`, `amount.usedFraction`, `amount.remainingFraction`, `window.resetsAt` и `metadata.limitReached`; сверху лежит агрегат `capacity.<провайдер>[]` с `usedAccounts` и `remainingAccounts`. Прогнано 2026-09-15 через `omp usage --json --redact`.

Оговорка, без которой ответ был бы неверным: **покрытие неполное**. В базе четыре учётки, в выводе две. Опущены `openrouter` и `together` — оба на api_key без квотных окон, то есть лимита, который можно исчерпать, у них нет. Но в предназначенный для этого массив `accountsWithoutUsage` они тоже не попали: он пуст. Команда не отличает «лимита нет» от «не проверял», и полагаться на её молчание как на «всё в порядке» нельзя.

Идентификаторы аккаунтов OMP печатает открыто, поэтому в любую запись и в любой скриншот вывод идёт только с `--redact`.

## Механизмы приёма скиллов, хуков и правил

Раздел — вход для PER-250 и PER-251, а не их решение.

**Скиллы.** Единица — каталог со `SKILL.md`, поиск на один уровень вглубь. Проектные источники, которые OMP читает по умолчанию: `.omp/skills/`, `.agent/skills/`, `.agents/skills/`, `.claude/skills/`, `.codex/skills/`, `.opencode/skills/`, `.github/skills/`. Ключ `skills.enableClaudeProject` включён по умолчанию, а `.claude/skills/` входит в список проектных источников, поэтому **OMP должен видеть скиллы этого репозитория** — те самые 52 каталога, которые раскладывает `skillshare sync -p` по [ADR-041](../decisions/ADR-041-skillshare-targets-not-committed.md), без отдельного таргета для OMP. Утверждение держится на значении ключа и списке источников из документации: подтвердить его прогоном не удалось, `omp -p '/extensions'` в print-режиме списка не печатает. Проверка остаётся входным условием PER-250, а не выводом этого разбора. Фильтры: `--skills '<glob>'`, `--no-skills`, ключи `skills.includeSkills`, `skills.ignoredSkills`, `skills.customDirectories`, отключение одного скилла через `disabledExtensions: [skill:<имя>]`. Одноимённые скиллы не сливаются — выживает провайдер с высшим приоритетом. Поле `disable-model-invocation` понимается и означает то же, что `hide`: скилл исчезает из автоматического подбора, но остаётся доступен явным `/skill:<имя>`.

**Хуки.** Здесь прямой трансляции нет, и это главный факт для PER-251. Хук OMP — доверенный модуль TypeScript, который подписывается на события (`tool_call`, `tool_result`, `context`, `session_start` и другие) и возвращает решение вроде `{ block: true, reason }`. Автопоиск идёт в `.omp/hooks/pre/` и `.omp/hooks/post/` проекта и в тех же каталогах профиля, нерекурсивно; разовая загрузка — `--hook <путь>` или `-e <путь>`, постоянная — массив `extensions` в конфиге. Хуки же в `.claude/settings.json` этого репозитория устроены иначе: матчер плюс shell-команда в JSON. Формы несовместимы, и перенос будет переписыванием, а не конвертацией. В обратную сторону OMP сильнее: `tool_call` умеет заблокировать вызов до исполнения, чего PostToolUse не может по определению.

**Правила и контекст.** `AGENTS.md` в корне подхватывается автоматически, вложенные `AGENTS.md` компонуются по уровням каталогов. Отсюда следствие для этого репозитория: однострочные `CLAUDE.md` рядом с каждым вложенным `AGENTS.md` нужны Claude Code и **в OMP избыточны** — он читает `AGENTS.md` напрямую. Отдельные файлы: `.omp/RULES.md` (липкие правила), `.omp/APPEND_SYSTEM.md` (дополнение системной инструкции), `.omp/SYSTEM.md` (замена — использовать только для сознательно другой персоны). Выключение — `--no-rules`.

Ловушка, которую стоит знать до того, как она сработает: при одинаковой глубине выживает **один** провайдер контекста, приоритет `native` > `claude` > `agents` > `codex` > `gemini` > `opencode` > `github` > `agents-md`. Файл `.omp/AGENTS.md` в корне **затенит** корневой `AGENTS.md`, а не дополнит его. Заводить его в этом репозитории нельзя.

**Плагины и MCP.** `omp plugin install|link --scope user|project`, каталоги через `omp plugin discover`. MCP-серверы подключаются отдельно; проектный конфиг MCP включён по умолчанию.

## Карта: сверх, дублирует, нет

**Сверх текущего стека.** `omp usage` по всем аккаунтам разом (единственное проверенное «заменяет»); `auth-broker` как общий пул учёток на ферму; `--profile` как изолированный набор auth, сессий, настроек и кеша; `--from-claude` и `--from-codex` — импорт чужой сессии, то есть прямой ответ на цель эпика; `prewalk` и `plan-yolo` как удешевление одной сессии сменой модели на полпути; `advisor` как второй голос внутри хода; `cleanse` как параллельная правка диагностик file-disjoint подагентами; встроенный LSP и DAP.

**Дублирует.** Скиллы, plan mode, MCP, подагенты, worktree, commit, git-UI, веб-поиск, чтение и правку файлов.

**Чего нет.** Знания о Linear иначе как через MCP. Норматива контура и его стоп-триггеров. Гейта `just`. Механики pull request репозитория (инструмент `github` выключен по умолчанию и требует `gh`). Раскладки скиллов по чужим харнессам: OMP **читает** чужие каталоги, но не синхронизирует их, поэтому skillshare он не заменяет, а потребляет его результат.

## Рецепты запуска

Каждый флаг объяснён; строка без пометки о прогоне не проверялась.

Разведка и чтение, шаг 3 контура. `always-ask` оставляет свободным только чтение, поэтому случайная правка исключена механизмом, а не намерением. Не прогнано.

```powershell
omp --approval-mode always-ask --thinking high
```

Работа внутри контура, шаги 5 и 6. Режим берётся из конфига, allow-лист пропускает гейт, всё остальное спрашивает. Прогнано 2026-09-15 в headless-варианте.

```powershell
omp
```

Неинтерактивный прогон. `-p` печатает и выходит, `--no-session` не сохраняет сессию, `--max-time` ограничивает время. **Обязательно перенаправить stdin**, иначе запуск повиснет — см. журнал ниже. Прогнано 2026-09-15.

```powershell
omp --no-session --max-time 30m -p "задача" < /dev/null
```

Проектирование до кода, шаг 4 контура. Отдельный ход планирования, который не трогает файлы, пока план не принят. Не прогнано.

```powershell
omp
# в сессии: /plan
```

Ревью среза, шаг 7 контура. `omp review` разбирает изменения, `omp security` гонит отдельный проход по уязвимостям; оба не заменяют три оси ревью норматива, а дают четвёртый независимый голос. Не прогнано.

```powershell
omp review
omp security
```

Фоновый неинтерактивный прогон, где вопрос задать некому. Режим `yolo` берётся **из оверлея, а не из глобального конфига**, и сопровождается запретами: под `yolo` `prompt` бесполезен, а `deny` продолжает действовать. Рецепт из документации, не прогнано.

```powershell
omp --config ./ci-approvals.yml -p "задача" < /dev/null
```

## `omp commit` использовать нельзя

Команда разобрана отдельно, потому что её поведение расходится с обещанием справки и с нормативом сразу по трём осям. Проверено контролируемым повтором 2026-09-15: до запуска в дереве 3 изменённых пути, после `omp commit --dry-run` — 314, после `git reset` — снова 3.

**Стейджит всё дерево, несмотря на `--dry-run`.** Флаг описан как «Preview without committing», и коммита он действительно не делает, но перед генерацией сообщения выполняет эквивалент `git add -A`. На Windows с `core.autocrlf=true` это добавляет к индексу 308 файлов, отличающихся только переводом строк: содержательных изменений среди них нет вовсе. Дерево при этом не портится, лечится одним `git reset`, но `git status` до сброса не отвечает на вопрос «что я изменил».

**Собственный инструмент упирается в выбранный режим.** Под `write` без интерактивного UI вызов `propose_commit` отклоняется: `requires approval, but no interactive approval UI is available`. Команда не падает, а молча переходит на запасной путь с предупреждением `Commit generated using fallback due to agent failure` и кодом выхода `1`.

**Сообщение запасного пути нарушает норматив по трём пунктам разом.** Сгенерировано: `refactor: refactored proj-draft-commit-message.md and 313 others`, следом список строк `- Updated ...`. [commit-messages.md](../standards/git/commit-messages.md) требует повелительного наклонения (здесь прошедшее), запрещает имя файла в роли темы и прямо говорит «тела у коммита нет».

Вывод: коммит остаётся за `proj-write-commit` и хуком `commit-msg`. `omp commit` в этом репозитории не применяется, и это ограничение стоит держать в голове ещё и потому, что команда меняет индекс до того, как покажет результат.

## Журнал негативного пути

| Команда | Что ожидалось | Что произошло | Обход |
|---|---|---|---|
| `omp setup --check --json` | снимок состояния всех необязательных компонентов | `error: setup --check/--json requires a COMPONENT (python\|speech)` | опрашивать покомпонентно: `omp setup python --check --json` |
| `omp -p '...'` из неинтерактивной оболочки | отработает и выйдет | прогресса нет 163 секунды, фаза не меняется: `Still starting after 160s — phase: readPipedInput`. Маркер печатается в обычный вывод, `PI_DEBUG_STARTUP=1` нужен только для потоковых маркеров | перенаправить stdin: `< /dev/null`. Без этого OMP ждёт закрытия пайпа, которого не будет; с перенаправлением отработали все последующие пробы |
| `timeout 240 omp ... \| tail` в Git Bash | команда отработает за отведённое время | на 120-й секунде оболочка агента перенесла команду в фон; нативный процесс `omp` продолжил жить в фоне | снят вручную: `Stop-Process -Name omp -Force`. Снял бы его сам `timeout` — **не проверено**: процесс убит на 163-й секунде, за 77 секунд до срока |
| `git status --short` под `write` headless | выполнится | `Tool "bash" requires approval but no interactive UI available` | ожидаемое поведение, не дефект: добавить команду в `bash.patterns` либо работать интерактивно |
| нижний слой `deny`, верхний слой с другим `bash.patterns` | запрет переживёт | запрещённая команда **выполнилась** | объявлять `bash.patterns` самодостаточным списком в каждом слое |
| `omp search` при `providers.webSearchOrder: []` | откажет, провайдер не задан | отработал, выбрал OpenAI, 16 источников | гипотеза оказалась ложной, обход не нужен |
| `omp commit --dry-run` | покажет предложение, дерева не тронет | застейджил 314 путей вместо 3, код выхода `1`, сообщение собрано запасным путём | `git reset`; команду не использовать |
| `omp -p '/extensions'` | напечатает список скиллов и хуков | вывел только `Working...`, списка нет | слеш-команды смотреть в интерактивной сессии |

Отдельной строкой то, что проверить не удалось: **у `omp cleanse` нет режима предпросмотра**. Команда детектирует и сразу правит, флага `--dry-run` у неё нет. Прогонять её в дереве с незакоммиченной работой значит смешать её правки со своими, поэтому кандидат на замену шага «Гейт» остаётся непроверенным. Это цена самой команды, а не пропуск в разборе.

## Рекомендация владельцу

Оставить OMP на выбранном `write` с текущими запретами и вернуться к трём вопросам отдельными задачами.

Первый — `omp cleanse` против `just verify`. Проверять его нужно в отдельном чистом дереве, потому что предпросмотра у команды нет.

Второй — `worktree.base`. Глобальное умолчание `~/.omp/wt` уводит деревья из `.claude/worktrees/`, и `omp worktree list` подтверждает это прямо: он смотрит только в свой каталог и деревьев репозитория не видит. Починить проектным конфигом нельзя — ключ принимает только абсолютный или `~`-относительный путь, а такой путь непереносим между машинами. Либо это личная глобальная настройка, либо командой `omp worktree` в этом репозитории не пользуются вовсе, и тогда правило должно быть записано, а не подразумеваться.

Третий — строка OMP в таблице «Механика сред» [agent-execution-loop.md](agent-execution-loop.md). Сейчас её добавлять рано: четвёртая колонка требует прогнанного `just verify` из-под OMP на живой задаче, а этого ещё не было. Правка норматива без такого прогона закрепила бы обязательство, которое ничем не подтверждено.

Follow-up задачи этим разбором не создаются: по границе PER-264 они появляются после выбора владельца.
