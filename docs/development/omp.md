# OMP как исполнитель контура

> **Статус:** Research, 2026-09-15, обновлён 2026-10-20. Документ разбирает харнесс OMP, фиксирует его настройку для [контура исполнения](agent-execution-loop.md) и назначение ролей моделей. Он не переводит контур на OMP.

Разбор отвечает на два вопроса: что OMP умеет сверх текущего стека и как им пользоваться, не переносив вслепую привычки Claude Code. Проверялась версия `omp/18.1.17` на Windows 11; обновление 2026-10-20 — режим одобрения через классификатор, роли без цепочек подмены и веб-интерфейс — проверялось на `omp/18.12.2`. Раскладка скиллов остаётся за [PER-250](https://linear.app/anticnvm/issue/per-250), перенос хуков и команд — за [PER-251](https://linear.app/anticnvm/issue/per-251); здесь только названы механизмы, которыми OMP их принимает. Роли моделей и их лимиты назначены [PER-263](https://linear.app/anticnvm/issue/per-263) и описаны отдельным разделом ниже.

Границы прогона: учётки не заводились и не обновлялись, `omp token` без `--list` не запускался, `auth-broker` не поднимался. Ни один вывод с реальным значением ключа в документ не попал.

Каждое утверждение ниже помечено: **прогнано 2026-09-15** или **прогнано 2026-10-20** — проверено командой на этой машине в этом репозитории; **не прогнано** — взято из [документации OMP](https://omp.sh/docs) и требует проверки.

## OMP против шагов контура

| Шаг контура | Чем закрывает OMP | Вердикт | Проверка |
|---|---|---|---|
| 1. Захват | чтение Linear только через MCP, своего знания о трекере нет | не заменяет | не прогнано |
| 2. Дерево | `omp worktree` и перехват `git worktree add` в bash | нормативу важна видимость дерева в `git worktree list`; перехват закрыт конфигом, команда `omp worktree` не проверена | `omp worktree list` прогнан; сам перехват — нет |
| 3. Чтение | `read`, `grep`, `glob`, `lsp`; скиллы репозитория видны | дублирует | прогнано частично |
| 4. Чекпоинт плана | `/plan`, отдельный ход планирования | дублирует | не прогнано |
| 5. Реализация | `edit`, `write`, `bash` под выбранным режимом | дублирует | прогнан только слой одобрения bash |
| 6. Гейт | `just verify` через bash; альтернатива — `cleanse` | дублирует; `cleanse` не проверен | прогнано 2026-09-15 |
| 7. Ревью | `omp review`, `omp security` | не проверялось | не прогнано |
| 8. Коммит | `omp commit` стейджит всё дерево и пишет своё сообщение | **не использовать**, см. ниже | прогнано 2026-09-15 |
| 9. Pull request | инструмент `github` выключен по умолчанию, нужен `gh` | не заменяет | не прогнано |
| 10. Рефлексия | скилл читается, `disable-model-invocation` понимается | дублирует | не прогнано |
| 11. Отчёт | комментарий в Linear только через MCP | не заменяет | не прогнано |

Единственная строка, где OMP **заменяет** текущий шаг, лежит не в контуре, а в его обслуживании: `omp usage` одной командой показывает остаток лимита по каждому аккаунту каждого провайдера. Сейчас это ручная проверка в интерфейсе каждого сервиса по отдельности, и именно её отсутствие делает исчерпанный лимит внезапным — то есть ровно задачу эпика [PER-248](https://linear.app/anticnvm/issue/per-248).

## Режимы одобрения

Режим называет высший ярус вызовов, который проходит без вопроса. Ярусов три: **read** (чтение), **write** (запись в рабочее дерево), **exec** (`bash`, `eval`, `browser`, `task`).

| Режим | Проходит сразу | Спрашивает |
|---|---|---|
| `always-ask` | только read | write и exec |
| `write` | read и write | exec |
| `yolo` | всё | ничего по ярусу |

Встроенное значение — `yolo`, и цена этого не очевидна из названия. У `bash` есть проверка на узкий набор критических форм: рекурсивное удаление абсолютного пути, «скачать и выполнить», выключение хоста, запись в файлы аккаунта. В режимах `always-ask` и `write` эта проверка принудительно вызывает вопрос, но документация называет её *bare override*, а `yolo` пропускает такие override. Под `yolo` страховка на `rm -rf /абсолютный/путь` выключена, и абсолютной границу делает только явный `deny`.

С 2026-09-15 по 2026-10-20 стоял `write`. Аргумент был нормативный: [agent-execution-loop.md](agent-execution-loop.md) различает «внутри контура», где агент коммитит и пушит без отдельного разрешения, и «вне контура», где он обязан остановиться перед коммитом. Под `write` вызов `git commit` упирался в вопрос, и граница была механизмом, а не обещанием. Цена `write` — вопрос на каждую команду вне allow-листа, а в headless-режиме (`-p`, подагенты, ACP без UI) вопрос задать некому, и вызов падает.

С 2026-10-20 по решению владельца глобальный режим — `yolo`, а решение о каждом вызове принимает классификатор, см. «Auto mode через pi-automode». Что из этого следует для границы контура, названо прямо: вопрос перед `git commit` больше не механизм OMP. Её держат текст норматива и правило классификатора про коммит на `develop` и `main`, то есть модель, а не детерминированная проверка.

Режим живёт в глобальном конфиге владельца, а не в проектном: у того, кто откроет репозиторий в OMP со своим конфигом, действует его режим. Поэтому allow-лист проектного `.omp/config.yml` не удалён — под `write` и `always-ask` он по-прежнему нужен.

### Auto mode через pi-automode

Своего режима с классификатором у OMP нет: `tools.approvalMode` принимает только `always-ask`, `write` и `yolo` (прогнано 2026-10-20, `omp config list`). Классификатор даёт стороннее расширение [`@czottmann/pi-automode`](https://pi.dev/packages/@czottmann/pi-automode), которое поддерживает и pi, и OMP 18. Установлено `omp install npm:@czottmann/pi-automode@1.17.0`; исходник перед установкой прочитан: сеть расширение использует только через completion API самого харнесса, процессов не запускает, пишет только свой конфиг и журнал решений.

Расширение подписано на `tool_call` и решает по порядку: запреты `permissions.deny`, детерминированные жёсткие запреты (удаление системных путей, запись в профили шелла, `authorized_keys`, автозапуск, ослабление TLS), `permissions.allow`, затем модель-классификатор. Чтение (`read`, `grep`, `find`, `ls`) классификатор не видит. Отказ модели, сбой провайдера и неразобранный bash блокируют вызов — расширение fail-closed. Пользовательские `!`-команды оно не охраняет и песочницей не является.

Зачем вместе с ним `yolo`: нативный вопрос OMP работает независимо от расширения. Расширение умеет только заблокировать вызов или пропустить его дальше, а под `write` OMP после этого всё равно спросит про любую команду вне allow-листа — получается двойная проверка, а не auto mode.

Конфиг расширения один на pi и OMP: путь `~/.pi/agent/extensions/pi-automode/config.json` зашит в код, рядом в `logs/` лежит журнал решений. В конфиге владельца: классификатор `opencode-go/claude-haiku-5-5` с `classifierReasoningLevel: low`, правка внутри рабочего каталога без классификатора, `deniedPaths` на `.env`, `~/.ssh` и хранилища ключей трёх харнессов, `permissions.allow` на `just *` и чтение состояния git, `permissions.deny` на `git push --force`, `git push -f`, `git reset --hard`, `git clean -fdx`, и правило `soft_deny` против коммита, push и pull request на `develop` и `main`. Конфиг описывает машину владельца и в репозиторий не выносится.

Прогнано 2026-10-20: в сессии веб-интерфейса на этом репозитории `node --version` выполнилась без вопроса, расширение показало `a:1 d:0 ca:1 cd:0` — одно разрешение решением классификатора. Тот же вызов из pi записал в журнал `outcome: allow`, `Fast classifier found no policy-relevant risk.`; классификатор потратил на него 2,4 тыс. токенов и $0,0003, почти всё — запись промпта в кэш. Блокирующий путь — `deny`, жёсткий запрет и отказ классификатора — **не прогнан**: пробы `git push --force` и `curl | sh` остановил классификатор Claude Code, из-под которого шла настройка.

### Что проверено прогоном

Гипотеза, с которой разбор начинался, оказалась ложной, и это важнее, чем если бы она подтвердилась. Ожидалось, что allow-лист будет систематически промахиваться: `bash.allowCompoundCommands` выключен, а `allow` по документации обязан совпасть с полной несоставной командой, тогда как рецепты репозитория полны конструкций `cd apps/identity && go build ./...`.

Промаха нет. `verify` — список зависимостей из других рецептов, а составные команды живут **внутри тел рецептов** и исполняются самим `just`, мимо слоя одобрения OMP. Харнесс видит одну несоставную строку `just verify`.

| Проба | Команда | Ожидалось | Результат |
|---|---|---|---|
| 1 | `just check-document-numbers` в allow-листе, режим `write`, headless | выполнится | выполнилась, код `0` |
| 2 | `git status --short` вне allow-листа, те же условия | откажет | `Tool "bash" requires approval but no interactive UI available` |

Вторая проба нужна не меньше первой: без неё первая доказывала бы только то, что всё подряд проходит.

## Ловушка слоёв конфигурации

Слои складываются так: встроенные умолчания < глобальный `~/.omp/agent/config.yml` < проектный `<cwd>/.omp/config.yml` < оверлеи `--config` < флаги запуска. Проектный слой ищется **строго в каталоге запуска**, без обхода предков.

Отображения сливаются глубоко, **массивы заменяются целиком**. Разница между этими двумя правилами и есть ловушка, потому что в одном файле рядом лежат обе структуры:

- `tools.approval` — запись (mapping). Глобальные запреты переживут проектный слой.
- `bash.patterns` — массив. Проектный список **затирает глобальный целиком**.

Проверено прогоном 2026-09-15: нижний слой запрещал `echo SENTINEL*`, верхний объявлял единственное несвязанное правило `just *`. Команда `echo SENTINEL-TEST` **выполнилась** — запрет исчез молча, без предупреждения.

Отсюда раскладка: запреты на капабилити живут глобально, а `bash.patterns` обязан быть самодостаточным в том слое, где объявлен. Проектный [`.omp/config.yml`](../../.omp/config.yml) повторяет запреты не по небрежности, а потому что иначе он их снимает.

## Что изменено в конфигурации и почему

Глобальный `~/.omp/agent/config.yml`, построчно:

| Строка | Почему |
|---|---|
| `tools.approvalMode: yolo` (до 2026-10-20 — `write`) | решает классификатор pi-automode; нативный вопрос OMP под `write` шёл бы вторым слоем поверх него, см. «Режимы одобрения» |
| `tools.approval.computer: deny` | управление десктопом не нужно ни на одном шаге контура; `deny` выигрывает в любом режиме и переживает его смену |
| `tools.approval.eval: deny` | `bash.patterns` управляют только инструментом `bash`; шелл, поднятый через `eval`, они не покрывают, и без этого запрета любой деньлист обходится |
| `worktree.clone: false` | перехваченный `git worktree add` иначе делает CoW-клон, невидимый в `git worktree list` |
| `modelRoles` — шесть ролей | назначены PER-263, пересмотрены владельцем 2026-10-20; раскладка и цена каждой роли — в разделе «Роли моделей и чьи лимиты они расходуют» |
| `retry.usageAwareFallback: true`, `retry.fallbackChains` сняты 2026-10-20 | цепочки подмены убраны решением владельца; что осталось от механики подмены — там же |
| `advisor.enabled: false` при назначенной роли `advisor` | модель для второго голоса выбрана, но постоянно включённый советник — вторая модель на каждом ходу; включается флагом `--advisor` |
| `externalThinking: false` | справка флага `--external-thinking` предупреждает дословно: *providers have flagged this request shape as abuse*; на OAuth-учётке ChatGPT это риск блокировки аккаунта |

Везде `deny`, а не `prompt`, по двум независимым причинам: `deny` действует во всех режимах, а `prompt` внутри подагента ответить некому, и он превращается в отказ.

Проектный `.omp/config.yml` несёт `worktree.clone: false` (чтобы норматив [branching.md](../standards/git/branching.md) защищался у любого, кто откроет репозиторий в OMP, а не только на этой машине) и самодостаточный `bash.patterns`: запреты первыми, затем allow-лист. Порядок значим — выигрывает первое совпавшее правило.

Под глобальным `yolo` владельца allow-лист молчит: пропускать без вопроса нечего, а запреты из `bash.patterns` и `tools.approval` действуют в любом режиме. Абзацы ниже описывают его смысл под `write`.

Allow-лист расширен 2026-09-15 с `just *` и чтения состояния git до чтения дерева, стеков репозитория и GitHub на чтение. Причина не в удобстве: режим `write` спрашивает про весь ярус exec, а у вопроса в нативном TUI ровно две кнопки, Approve и Deny. Опция «always allow» в OMP есть, но живёт в ACP-мосте — в обычном запуске её нет, поэтому allow-лист нельзя набрать по ходу работы, его пишут в конфиг заранее. Механизм, который делает расширение достаточным: правило `allow` возвращает ярус `write`, то есть команда проходит молча, и `approvalMode` менять не нужно. Прогнано 2026-09-15: `go version` выполнилась headless без вопроса, `cd apps/identity && go version` вернула `requires approval` — составная команда разбирается по частям только при `bash.allowCompoundCommands: true`, а он выключен. Сработает ли разбор на этой машине, **не прогнано**: он требует POSIX-шелла, а `shellPath` не задан и шелл резолвится поиском по PATH.

Запись в историю (`git commit`, `git push`, `gh pr create`) в allow-лист сознательно не входит. Это та же граница, ради которой выбран режим `write`: вопрос перед коммитом остаётся механизмом, а не обещанием.

Что **не** менялось и почему:

- `symbolPreset`, `composer.shape`, `theme` — косметика онбординг-мастера, к работе отношения не имеет.
- `providers.webSearchOrder: []` — выглядит недонастройкой, но пустой список означает порядок по умолчанию, а не отсутствие провайдера. Прогнано 2026-09-15: `omp search` отработал, выбрал OpenAI, вернул 16 источников.
- `prewalk.enabled`, `plan.autosave`, `memory.backend`, `security.enabled` — оставлены выключенными сознательно. `prewalk` тянет вторую модель на полпути сессии, и включать его имеет смысл после того, как станет понятна цена ролей на живых задачах. `plan.autosave` при включении пишет планы в `<project>/.omp/plans/`, то есть в репозиторий.
- `omp setup` не запускался. Необязательных компонентов ровно два, и оба опрошены через `--check`: `python` не нужен (в системе настоящий Python 3.11.9), `speech` не нужен (parakeet и kokoro обслуживают `omp say`, в контуре не участвует). Сам мастер — онбординг, а не установщик: `setupVersion: 2` означает, что он уже прошёл и записал косметические ключи, поэтому повторный запуск перезаписал бы осознанные решения мастерскими умолчаниями.

## Роли моделей и чьи лимиты они расходуют

Назначение живёт в глобальном `~/.omp/agent/config.yml`. `modelRoleStorage` уже стоял в `global`, менять его не пришлось; в репозиторий роли не выносятся сознательно — они описывают аккаунты владельца, а не свойство проекта.

Раскладка на 2026-10-20:

| Роль | Модель | Чей лимит | Когда тратится |
|---|---|---|---|
| `default` | `opencode-go/deepseek-v4.1-flash:high` | план OpenCode Go | каждый ход сессии |
| `smol` | `opencode-go/glm-5.3-flash:high` | план OpenCode Go | заголовки, `prewalk`, `plan-yolo`, починка сломанного правкой AST, извлечение памяти |
| `slow` | `openai-codex/gpt-6.1-sol:high` | **подписка Codex Plus** | только по явному вызову: `--slow` и цикл `cycleOrder` |
| `plan` | `openai-codex/gpt-6.1-sol:high` | **подписка Codex Plus** | режим планирования |
| `vision` | `openai-codex/gpt-6-luna:medium` | **подписка Codex Plus** | разбор изображений |
| `advisor` | `opencode-go/glm-5.3-flash:xhigh` | план OpenCode Go | только под флагом `--advisor`: `advisor.enabled` оставлен `false` |

Роль `default` в сентябре фактически тратила `openrouter`, а не план, — см. «Что показала проба». Прогнано 2026-10-20: та же модель отвечает с самого плана, расшифровка сессии называет провайдером `opencode-go`.

Роль `commit` снята 2026-10-20. `omp commit` этим разбором запрещён, но через роль шла и генерация заголовков сессий, а `opencode-go/hy4-preview` стоит $0,83 / $2,50 за миллион токенов — в разы дороже `smol` на задаче в пять слов. Без неё цепочка заголовков `tiny` → `commit` → `smol` разрешается в `smol`.

**Бесплатные модели OpenCode Zen в OMP не работают.** Модели с суффиксом `-free` у провайдера `opencode-zen` есть в каталоге OMP, но провайдер отвечает `403 OpenCode's free tier can only be used from within OpenCode` (`FreeTierError`). Прогнано 2026-10-20: роли `default` и `smol` на `deepseek-v4.1-flash-free` и `glm-5.3-flash-free` роняли каждый ход, и тот же ответ дал прямой запрос к API Zen на `jev-1.13-free`. Каталог OMP отказа не предсказывает: выбор такой модели проходит, а падает первый же запрос.

Назначением закрыт разрыв, который этот разбор зафиксировал отдельно: `cycleOrder` по умолчанию ссылается на роль `slow`, а её в `modelRoles` не было — цикл переключения моделей указывал в пустоту.

Раскладка отвечает цели [PER-248](https://linear.app/anticnvm/issue/per-248): поток идёт на план OpenCode Go, у которого на момент назначения нулевой расход по всем трём окнам, а подписка Codex остаётся под то, что вызывается руками и редко. Обратная раскладка — рассуждающие роли на потоке — выжигала бы недельное окно Codex фоном, то есть воспроизводила бы ровно ту зависимость, от которой эпик уходит.

Две оговорки по самому назначению:

- `smol` идёт на уровне `high`. Для роли, обслуживающей заголовки и мелкую рутину, это дороже необходимого, и сужение до `:low` — очевидный следующий шаг, если прогон покажет лишний расход. **Не прогнано.**
- `advisor` не входит в четыре роли CLI. Ключ `modelRoles.advisor` существует, и сверх него в конфиге живут ещё `commit` и `tiny`: цепочка генерации заголовков идёт `tiny` → `commit` → `smol`. Ни `commit`, ни `tiny` не назначены — `omp commit` этим разбором запрещён к использованию, а `tiny` разрешается в `smol` сам.
- `modelRoles.<роль>` не адресуется `omp config set`: команда отвечает `Unknown setting`, ключ принимает только запись целиком. Прогнано 2026-10-20; одну роль правят в самом `config.yml`.

### Подмена при исчерпанном лимите

**Цепочки `retry.fallbackChains` сняты владельцем 2026-10-20.** `retry.usageAwareFallback` и включённый по умолчанию `retry.modelFallback` остались, но подменять модель роли им больше не на что; что они делают без цепочек — переключают ли аккаунт того же провайдера или только повторяют запрос — **не прогнано**. Следствие для роли на временно бесплатной или превью-модели: её исчезновение у провайдера роняет роль, а не уводит её на запасную модель.

Ниже — устройство на 2026-09-15, оставленное как разбор механики и как контекст пробы.

Правило было записано конфигом, а не прозой: прозаическое правило не срабатывает у фонового агента ночью.

```yaml
retry:
  usageAwareFallback: true
  fallbackChains:
    default: ["opencode-go/gpt-5.6-luna", "openrouter/deepseek/deepseek-v4.1-flash"]
    smol:    ["opencode-go/qwen3.8-flash", "openrouter/z-ai/glm-5.3-flash"]
    slow:    ["opencode-go/deepseek-v4-pro", "openrouter/moonshotai/kimi-k3"]
    plan:    ["opencode-go/minimax-m3", "openrouter/openai/gpt-5.6-luna"]
```

Цепочка ведёт сначала на другую модель того же плана, потом к метрическому провайдеру. Различие между двумя механизмами подмены важнее самих цепочек:

- `retry.modelFallback` (включён по умолчанию) переключает модель **после отказа**: лимит упирается в стену, ход теряется, и только потом происходит подмена.
- `retry.usageAwareFallback` (включён этой задачей) смотрит на остаток квоты **до** запроса. Его описание добавляет оговорку — *Ordinary configured API keys are excluded*. То есть `openrouter` и `together` в упреждающую логику не попадают вовсе: квотного окна у них нет, и это ровно та причина, по которой их не показывает `omp usage`. Они работают запасным аэродромом после отказа, а не выбором по остатку.

`fallbackRevertPolicy` оставлен в `cooldown-expiry`: роль возвращается на основную модель, когда окно остынет.

Присутствие каждой модели цепочки у своего провайдера проверено через `omp models find` — **прогнано 2026-09-15**. Само срабатывание подмены на живом исчерпанном лимите — **не прогнано**: для этого нужно выбрать лимит, а на момент назначения он был нулевым.

### Расхождение с принятым решением

Решение «Распределение моделей по ролям» (принято 2026-08-31, волт владельца) ставит модели на собственных ключах **только на дешёвую рутину** и помечает их непроверенными кандидатами; имплементацию оно отдаёт Composer, ревью — Opus. Назначение выше создаёт это расхождение сознательно: PER-263 требует роль уровня имплементации на собственном ключе, проверенную задачей, а не приветственным ответом.

Отдельная причина, по которой решение вообще не переносится в OMP один к одному: подписка Anthropic в стороннем клиенте запрещена условиями использования (решение «Спавн официального CLI вместо SDK на подписке»), поэтому роли Opus внутри OMP быть не может ни в одной раскладке. Ревью уровня Opus остаётся за Claude Code.

Заметка волта этой задачей не правится: она живёт в личном контуре владельца.

### Что показала проба

Роль `default` проверена задачей уровня имплементации, а не приветственным ответом: написать проверку пар `AGENTS.md`/`CLAUDE.md`, завести рецепт и джобу CI. Прогон шёл в отдельном одноразовом дереве, с разовым оверлеем `bash.patterns` и запретом на `git add` и `git commit`, чтобы дифф остался несобранным и его можно было оценить. Результат в репозиторий не вливался: задача PER-263 назначает роли, а не заводит проверку.

**Уровень.** Скрипт прошёл все три критерия: зелёный на чистом дереве, красный с точным путём при удалённом и при испорченном `CLAUDE.md`, внешние скиллы под `.skillshare/skills/` не ломают проверку. Набор файлов взят из `git ls-files` — то есть tracked-клоны отсекаются механизмом, а не списком исключений. Сверх задания модель повторила соглашения репозитория: отдельный файл фикстур рядом с проверкой, английская шапка при русских комментариях внутри, финальная строка того же вида, что у соседнего скрипта, джоба CI по образцу `document-numbers` вместе с `persist-credentials: false`, и правка `AGENTS.md` в трёх местах сразу — карта `tools/`, список команд и правило про `just verify`. Претензий к уровню нет.

**Чей лимит израсходован — не тот, что назначен.** Это главный результат прогона. Расшифровка сессии показывает цепочку за 0,7 секунды до первого хода:

```
opencode-go/deepseek-v4.1-flash  → 403
opencode-go/gpt-5.6-luna         → шаг цепочки, не обслужил
openrouter/deepseek/deepseek-v4.1-flash → обслужил все 38 ходов
```

Причина первого отказа названа провайдером дословно: `403 The latest version of this model is only available hosted in China and requires explicit opt in`. Опт-ин делается в рабочем пространстве OpenCode и агентом не выполняется.

Поведение воспроизводится: тривиальный запрос на роли `default` идёт тем же путём и обслуживается с `openrouter`. То есть **на сегодня каждая сессия OMP на роли по умолчанию тратит метрический ключ, а не оплаченный план**. Цена измерена: проба стоила **$0,1583** за 1,18 млн токенов и 20 тарифицированных ходов.

Почему цепочка не остановилась на первом шаге, расшифровка не объясняет: событие смены модели на `opencode-go/gpt-5.6-luna` записано, отказа по нему — нет. Отдельной проверкой подтверждено, что сама модель жива: `gpt-5.6-luna`, `kimi-k3` и `glm-5.3-flash` на плане OpenCode Go отвечают. Значит дефект не в модели и не в учётке. **Не прогнано:** почему шаг цепочки пропускается.

**Что из этого следует.** Механизм подмены проверен живым прогоном, а не только конфигом: цепочка сработала, задача не упала, работа доехала до конца. Оговорка та же, что и у `omp usage`: молчание механизма не означает, что всё идёт по плану — падение на метрический ключ выглядит как успех и обнаруживается только в расшифровке сессии либо в счёте.

**Побочно прогнано 2026-09-15:** корневой `AGENTS.md` подхватывается автоматически — он лежит первым сообщением сессии ещё до первого хода модели. Раньше это утверждение держалось на документации.

**Негативный путь прогона.** `omp -p` в print-режиме не печатает ничего до конца сессии, а по `--max-time` выводит только `Deadline exceeded`: ни итогового сообщения, ни следа рассуждений. Ход работы восстанавливается только из `~/.omp/agent/sessions/<путь>/<сессия>.jsonl`. Для фонового запуска это значит, что наблюдать за агентом по стандартному выводу нельзя — смотреть надо расшифровку.

## Где живут учётки

Хранилище — `~/.omp/agent/agent.db`, обычный SQLite **без шифрования**. Проверено прямым чтением схемы 2026-09-15: таблица `auth_credentials`, четыре записи, колонки `provider`, `credential_type`, `data`. Рядом лежат `agent.db-wal` и `agent.db-shm`, поэтому защищать нужно каталог целиком, а не один файл; любой бэкап или синхронизация каталога выносят учётки. На POSIX OMP ставит `0700`/`0600`, на Windows защита сводится к ACL аккаунта.

Порядок выбора источника: `--api-key` → `providers.<name>.apiKey` в `models.yml` → сохранённый OAuth-логин → ключ, сохранённый `/login` → переменная окружения провайдера → прочий сохранённый ключ → fallback кастомного провайдера. Практическое следствие, которое ломает интуицию: **экспорт переменной окружения не перебивает сохранённый `/login`**. Чтобы переменная подействовала, учётку сначала снимают через `/logout`.

У одного провайдера бывает несколько записей, и OMP ведёт их как отдельные аккаунты: веб-интерфейс подписывает их `Account 2` и дальше. Прогнано 2026-10-20: после смены просроченных ключей через `/logout` и `/login` у `openrouter`, `together` и `opencode-go` в таблице осталось по две записи — просроченная, отвечавшая `401`, и новая. Выбирает ли OMP между ними и тратит ли ход на мёртвую запись, **не прогнано**; просроченные записи удалены из таблицы напрямую. После смены ключа таблицу стоит проверять по `provider`, а не верить, что `/logout` её очистил.

`auth-broker` не настроен (`No auth-broker configured`). Он даёт общий пул учёток на несколько машин с refresh-токенами на одном хосте; при одной машине смысла не несёт и относится к ферме из [PER-248](https://linear.app/anticnvm/issue/per-248), а не к этой задаче.

## Показывает ли `omp usage` остаток

Показывает, и это ответ полями, а не пересказом. В JSON у каждого лимита есть `amount.used`, `amount.limit`, `amount.remaining`, `amount.usedFraction`, `amount.remainingFraction`, `window.resetsAt` и `metadata.limitReached`; сверху лежит агрегат `capacity.<провайдер>[]` с `usedAccounts` и `remainingAccounts`. Прогнано 2026-09-15 через `omp usage --json --redact`.

Оговорка, без которой ответ был бы неверным: **покрытие неполное**. В базе четыре учётки, в выводе две. Опущены `openrouter` и `together` — оба на api_key без квотных окон, то есть лимита, который можно исчерпать, у них нет. Но в предназначенный для этого массив `accountsWithoutUsage` они тоже не попали: он пуст. Команда не отличает «лимита нет» от «не проверял», и полагаться на её молчание как на «всё в порядке» нельзя.

Идентификаторы аккаунтов OMP печатает открыто, поэтому в любую запись и в любой скриншот вывод идёт только с `--redact`.

## Веб-интерфейс ompweb

Своего веб-интерфейса у OMP нет; его даёт сторонний [`@kahme247/ompweb`](https://github.com/kahme247/ompweb). Он запускает тот же `omp` в режиме `rpc` и читает сессии из `~/.omp/agent`, поэтому учётки, роли, проектный `.omp/config.yml` и pi-automode у него те же, что в терминале, — отдельной настройки нет. Слушает `127.0.0.1:30177`; без хэша пароля вход открыт, и это допустимо только на loopback — привязка к другому адресу требует `OMP_WEB_PASSWORD_HASH`.

Прогнано 2026-10-20 на версии 0.5.1: сессия на этом репозитории открылась, ход на роли `default` ушёл в план Go, вызов bash прошёл через классификатор. Там же видна панель остатка лимитов по аккаунтам — то, что в терминале даёт `omp usage`.

Слеш-команду расширения нельзя посылать первым сообщением новой сессии. Сессия, начатая с `/automode status`, не получила файла: каждое следующее сообщение отвечало `Failed to send message: HTTP 404`, а вывода самой команды веб не показал. Состояние auto mode веб показывает плашкой над ответом.

## Перехват TLS на машине владельца

Kaspersky на машине владельца вскрывает HTTPS части доменов, подставляя свой корень `Kaspersky Anti-Virus Personal Root Certificate`. Прогнано 2026-10-20: `openrouter.ai`, `chatgpt.com` и `cursor.com` перехватываются, `opencode.ai` — нет. Node по умолчанию корню не доверяет (`SELF_SIGNED_CERT_IN_CHAIN`), и pi на openrouter падал с `Connection error`; `NODE_USE_SYSTEM_CA=1` берёт корень из хранилища Windows и лечит Node. OMP собран на Bun, и после той же переменной его журнал продолжает писать `self signed certificate in certificate chain` на запросах остатка лимитов `openai-codex` и `cursor`. Действует ли на Bun `NODE_EXTRA_CA_CERTS` с выгруженным корнем — **не прогнано**; надёжный путь — исключение домена в «Проверке защищённых соединений» Kaspersky.

## Механизмы приёма скиллов, хуков и правил

Раздел — вход для PER-250 и PER-251, а не их решение.

**Скиллы.** Единица — каталог со `SKILL.md`, поиск на один уровень вглубь. Проектные источники, которые OMP читает по умолчанию: `.omp/skills/`, `.agent/skills/`, `.agents/skills/`, `.claude/skills/`, `.codex/skills/`, `.opencode/skills/`, `.github/skills/`. Ключ `skills.enableClaudeProject` включён по умолчанию, а `.claude/skills/` входит в список проектных источников, поэтому **OMP должен видеть скиллы этого репозитория** — те самые 52 каталога, которые раскладывает `skillshare sync -p` по [ADR-041](../decisions/ADR-041-skillshare-targets-not-committed.md), без отдельного таргета для OMP. Утверждение держится на значении ключа и списке источников из документации: подтвердить его прогоном не удалось, `omp -p '/extensions'` в print-режиме списка не печатает. Проверка остаётся входным условием PER-250, а не выводом этого разбора. Фильтры: `--skills '<glob>'`, `--no-skills`, ключи `skills.includeSkills`, `skills.ignoredSkills`, `skills.customDirectories`, отключение одного скилла через `disabledExtensions: [skill:<имя>]`. Одноимённые скиллы не сливаются — выживает провайдер с высшим приоритетом. Поле `disable-model-invocation` понимается и означает то же, что `hide`: скилл исчезает из автоматического подбора, но остаётся доступен явным `/skill:<имя>`.

**Хуки.** Здесь прямой трансляции нет, и это главный факт для PER-251. Хук OMP — доверенный модуль TypeScript, который подписывается на события (`tool_call`, `tool_result`, `context`, `session_start` и другие) и возвращает решение вроде `{ block: true, reason }`. Автопоиск идёт в `.omp/hooks/pre/` и `.omp/hooks/post/` проекта и в тех же каталогах профиля, нерекурсивно; разовая загрузка — `--hook <путь>` или `-e <путь>`, постоянная — массив `extensions` в конфиге. Хуки же в `.claude/settings.json` этого репозитория устроены иначе: матчер плюс shell-команда в JSON. Формы несовместимы, и перенос будет переписыванием, а не конвертацией. В обратную сторону OMP сильнее: `tool_call` умеет заблокировать вызов до исполнения, чего PostToolUse не может по определению.

**Правила и контекст.** `AGENTS.md` в корне подхватывается автоматически, вложенные `AGENTS.md` компонуются по уровням каталогов. Отсюда следствие для этого репозитория: однострочные `CLAUDE.md` рядом с каждым вложенным `AGENTS.md` нужны Claude Code и **в OMP избыточны** — он читает `AGENTS.md` напрямую. Отдельные файлы: `.omp/RULES.md` (липкие правила), `.omp/APPEND_SYSTEM.md` (дополнение системной инструкции), `.omp/SYSTEM.md` (замена — использовать только для сознательно другой персоны). Выключение — `--no-rules`.

Ловушка, которую стоит знать до того, как она сработает: при одинаковой глубине выживает **один** провайдер контекста, приоритет `native` > `claude` > `agents` > `codex` > `gemini` > `opencode` > `github` > `agents-md`. Файл `.omp/AGENTS.md` в корне **затенит** корневой `AGENTS.md`, а не дополнит его. Заводить его в этом репозитории нельзя.

**Плагины.** `omp plugin install|link --scope user|project`, каталоги через `omp plugin discover`.

**MCP.** Отдельной настройки под OMP не требуется, и это тот же принцип, что со скиллами: он импортирует определения серверов из конфигураций Claude Code, Codex, Gemini CLI, OpenCode, Cursor, Windsurf, VS Code, плагинов и расширений, а корневые `mcp.json` и `.mcp.json` читает как портативный запасной источник. Собственные файлы OMP — `.omp/mcp.json` в проекте и `~/.omp/agent/mcp.json` у пользователя; `mcp.enableProjectConfig` включён по умолчанию. Для дубликата выигрывает первое найденное определение, слияния нет.

Практическое следствие для этого репозитория: `.rulesync/mcp.jsonc` — источник MCP-конфигурации, а `just sync-mcp` генерирует `.mcp.json`, `.cursor/mcp.json`, `.codex/config.toml`, `.vscode/mcp.json` и `opencode.jsonc`. OMP подхватывает результат сам; добавлять его в `RULESYNC_MCP_TARGETS` не нужно.

## Карта: сверх, дублирует, нет

**Сверх текущего стека.** `omp usage` по всем аккаунтам разом (единственное проверенное «заменяет»); `auth-broker` как общий пул учёток на ферму; `--profile` как изолированный набор auth, сессий, настроек и кеша; `--from-claude` и `--from-codex` — импорт чужой сессии, то есть прямой ответ на цель эпика; `prewalk` и `plan-yolo` как удешевление одной сессии сменой модели на полпути; `advisor` как второй голос внутри хода; `cleanse` как параллельная правка диагностик file-disjoint подагентами; встроенный LSP и DAP — но с оговоркой ниже.

Про LSP важно не обмануться. `lsp.enabled` включён, `lsp.lazy` и `lsp.shared` тоже, диагностика на запись работает — однако сама возможность требует установленного языкового сервера, а на машине 2026-09-15 нет ни одного для стеков репозитория: в `GOPATH/bin` только `buf`, `golangci-lint`, `grpcurl` и protoc-плагины, в `.config/dotnet-tools.json` один `fantomas`, в `node_modules/.bin` только `biome`. Всё это линтеры и форматтеры. Значит `gopls`, `fsautocomplete` и `typescript-language-server` не установлены, и включённый `lsp` сейчас молча ничего не даёт ни Go, ни F#, ни TypeScript. Прогнано 2026-09-15. До установки серверов «IDE внутри» остаётся объявленной возможностью, а не работающей.

**Дублирует.** Скиллы, plan mode, MCP, подагенты, worktree, commit, git-UI, веб-поиск, чтение и правку файлов.

**Чего нет.** Знания о Linear иначе как через MCP. Норматива контура и его ручного гейта. Гейта `just`. Механики pull request репозитория (инструмент `github` выключен по умолчанию и требует `gh`). Раскладки скиллов по чужим харнессам: OMP **читает** чужие каталоги, но не синхронизирует их, поэтому skillshare он не заменяет, а потребляет его результат.

## Рецепты запуска

Каждый флаг объяснён; строка без пометки о прогоне не проверялась.

Разведка и чтение, шаг 3 контура. `always-ask` оставляет свободным только чтение, поэтому случайная правка исключена механизмом, а не намерением. Не прогнано.

```powershell
omp --approval-mode always-ask --thinking high
```

Работа внутри контура, шаги 5 и 6. Режим берётся из конфига: на машине владельца это `yolo` под классификатором pi-automode, под `write` allow-лист пропускает гейт, а всё остальное спрашивает. Прогнано 2026-09-15 в headless-варианте под `write`, 2026-10-20 — через веб-интерфейс под `yolo`.

```powershell
omp
```

Неинтерактивный прогон. `-p` печатает и выходит, `--no-session` не сохраняет сессию, `--max-time` ограничивает время. **Обязательно перенаправить stdin**, иначе запуск повиснет — см. журнал ниже. Прогнано 2026-09-15.

```powershell
omp --no-session --max-time 30m -p "задача" < /dev/null
```

Проектирование до кода, шаг 4 контура. Отдельный ход планирования, который не трогает файлы, пока план не принят. Не прогнано.

```powershell
omp
# в сессии: /plan
```

Ревью среза, шаг 7 контура. `omp review` разбирает изменения, `omp security` гонит отдельный проход по уязвимостям; оба не заменяют три оси ревью норматива, а дают четвёртый независимый голос. Не прогнано.

```powershell
omp review
omp security
```

Фоновый неинтерактивный прогон, где вопрос задать некому, на машине с режимом `write` или `always-ask`. Режим `yolo` берётся **из оверлея, а не из глобального конфига**, и сопровождается запретами: под `yolo` `prompt` бесполезен, а `deny` продолжает действовать. На машине владельца оверлей не нужен — `yolo` уже глобальный. Рецепт из документации, не прогнано.

```powershell
omp --config ./ci-approvals.yml -p "задача" < /dev/null
```

## `omp commit` использовать нельзя

Команда разобрана отдельно, потому что её поведение расходится с обещанием справки и с нормативом сразу по трём осям. Проверено контролируемым повтором 2026-09-15: до запуска в дереве 3 изменённых пути, после `omp commit --dry-run` — 314, после `git reset` — снова 3.

**Стейджит всё дерево, несмотря на `--dry-run`.** Флаг описан как «Preview without committing», и коммита он действительно не делает, но перед генерацией сообщения выполняет эквивалент `git add -A`. На Windows с `core.autocrlf=true` это добавляет к индексу 308 файлов, отличающихся только переводом строк: содержательных изменений среди них нет вовсе. Дерево при этом не портится, лечится одним `git reset`, но `git status` до сброса не отвечает на вопрос «что я изменил».

**Собственный инструмент упирается в выбранный режим.** Под `write` без интерактивного UI вызов `propose_commit` отклоняется: `requires approval, but no interactive approval UI is available`. Команда не падает, а молча переходит на запасной путь с предупреждением `Commit generated using fallback due to agent failure` и кодом выхода `1`.

**Сообщение запасного пути нарушает норматив по трём пунктам разом.** Сгенерировано: `refactor: refactored proj-draft-commit-message.md and 313 others`, следом список строк `- Updated ...`. [commit-messages.md](../standards/git/commit-messages.md) требует повелительного наклонения (здесь прошедшее), запрещает имя файла в роли темы и прямо говорит «тела у коммита нет».

Вывод: коммит остаётся за `proj-write-commit` и хуком `commit-msg`. `omp commit` в этом репозитории не применяется, и это ограничение стоит держать в голове ещё и потому, что команда меняет индекс до того, как покажет результат.

## Журнал негативного пути

| Команда | Что ожидалось | Что произошло | Обход |
|---|---|---|---|
| `omp setup --check --json` | снимок состояния всех необязательных компонентов | `error: setup --check/--json requires a COMPONENT (python\|speech)` | опрашивать покомпонентно: `omp setup python --check --json` |
| `omp -p '...'` из неинтерактивной оболочки | отработает и выйдет | прогресса нет 163 секунды, фаза не меняется: `Still starting after 160s — phase: readPipedInput`. Маркер печатается в обычный вывод, `PI_DEBUG_STARTUP=1` нужен только для потоковых маркеров | перенаправить stdin: `< /dev/null`. Без этого OMP ждёт закрытия пайпа, которого не будет; с перенаправлением отработали все последующие пробы |
| `timeout 240 omp ... \| tail` в Git Bash | команда отработает за отведённое время | на 120-й секунде оболочка агента перенесла команду в фон; нативный процесс `omp` продолжил жить в фоне | снят вручную: `Stop-Process -Name omp -Force`. Снял бы его сам `timeout` — **не проверено**: процесс убит на 163-й секунде, за 77 секунд до срока |
| `git status --short` под `write` headless | выполнится | `Tool "bash" requires approval but no interactive UI available` | ожидаемое поведение, не дефект: добавить команду в `bash.patterns` либо работать интерактивно |
| нижний слой `deny`, верхний слой с другим `bash.patterns` | запрет переживёт | запрещённая команда **выполнилась** | объявлять `bash.patterns` самодостаточным списком в каждом слое |
| `omp search` при `providers.webSearchOrder: []` | откажет, провайдер не задан | отработал, выбрал OpenAI, 16 источников | гипотеза оказалась ложной, обход не нужен |
| `omp commit --dry-run` | покажет предложение, дерева не тронет | застейджил 314 путей вместо 3, код выхода `1`, сообщение собрано запасным путём | `git reset`; команду не использовать |
| `omp -p '/extensions'` | напечатает список скиллов и хуков | вывел только `Working...`, списка нет | слеш-команды смотреть в интерактивной сессии |

Отдельной строкой то, что проверить не удалось: **у `omp cleanse` нет режима предпросмотра**. Команда детектирует и сразу правит, флага `--dry-run` у неё нет. Прогонять её в дереве с незакоммиченной работой значит смешать её правки со своими, поэтому кандидат на замену шага «Механический гейт» остаётся непроверенным. Это цена самой команды, а не пропуск в разборе.

## Рекомендация владельцу

Рекомендация дана 2026-09-15, когда режимом был `write`; режим с тех пор сменён на `yolo` под классификатором, см. «Режимы одобрения». Вопросы ниже от этого не изменились, и к ним стоит вернуться отдельными задачами.

Первый — `omp cleanse` против `just verify`. Проверять его нужно в отдельном чистом дереве, потому что предпросмотра у команды нет.

Второй — `worktree.base`. Расположение дерева больше не принадлежит нормативу — его выбирает харнесс (2026-09-17), а правило снятия адресует дерево веткой из `git worktree list`, не путём, поэтому умолчание `~/.omp/wt` само по себе ничему не противоречит и чинить его проектным конфигом не нужно. Открытым остаётся видимость: `omp worktree list` смотрит только в свой каталог и деревьев репозитория не знает, а регистрирует ли команда `omp worktree` созданное дерево в этом репозитории, не проверено. Если дерево уходит мимо `git worktree list`, оно уходит и из-под правила снятия — тогда либо деревья `omp worktree` в этом репозитории не заводят, либо снятие для них записывается отдельно.

Третий — языковые серверы. Без `gopls`, `fsautocomplete` и `typescript-language-server` включённый `lsp` не даёт ничего, и «IDE внутри» — главное отличие OMP — остаётся невостребованным. Это не настройка OMP, а инструментарий машины: он же нужен редакторам и относится к воспроизводимости среды ([PER-179](https://linear.app/anticnvm/issue/per-179)). Решать, ставить ли их и через `just <стек>-tools` или лично, стоит отдельной задачей.

Четвёртый — строка OMP в таблице «Механика сред» [agent-execution-loop.md](agent-execution-loop.md). Сейчас её добавлять рано: четвёртая колонка требует прогнанного `just verify` из-под OMP на живой задаче, а этого ещё не было. Правка норматива без такого прогона закрепила бы обязательство, которое ничем не подтверждено.

Follow-up задачи этим разбором не создаются: по границе PER-264 они появляются после выбора владельца.
