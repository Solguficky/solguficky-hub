# Журнал Архитектурных Решений (ADR)

Этот документ фиксирует важные архитектурные и технологические решения, принятые в ходе проектирования платформы.

---
## Группа А: Архитектурные Принципы

### ADR-001: Выбор микросервисной архитектуры с хореографией

*   **Дата:** 20.10.2025
*   **Решение:** Система будет построена на принципах **микросервисной архитектуры**. Взаимодействие между сервисами будет осуществляться преимущественно асинхронно через шину сообщений (**хореография**), а не через центральный сервис-оркестратор.
*   **Обоснование:** Этот подход обеспечивает слабую связанность, высокую отказоустойчивость и позволяет разрабатывать, развертывать и масштабировать каждый функциональный модуль (сервис) независимо. Он также дает свободу в выборе наиболее подходящего языка программирования для каждой конкретной задачи.

### ADR-002: Выбор паттернов CQRS и Event Sourcing для stateful-сервисов

*   **Дата:** 20.10.2025
*   **Решение:** Для сервисов со сложной, конкурентной логикой управления состоянием (в первую очередь, `Auction Service`) будут применяться паттерны **CQRS** (Command Query Responsibility Segregation) и **Event Sourcing (ES)**.
*   **Обоснование:** ES предоставляет полный, неизменяемый журнал всех изменений состояния, что критично для аудита и надежности аукциона. CQRS в связке с акторной моделью элегантно решает проблемы конкурентного доступа (race conditions) без необходимости в сложных блокировках.

## Группа B: Выбор Технологий и Платформы

### ADR-003: Выбор NATS JetStream в качестве шины сообщений

*   **Дата:** 20.10.2025
*   **Решение:** В качестве основной шины для асинхронного обмена сообщениями (командами и событиями) выбран **NATS JetStream**.
*   **Обоснование:** NATS предлагает лучший баланс между простотой развертывания, высочайшей производительностью и надежностью (благодаря JetStream). Он значительно проще в настройке и управлении, чем Apache Kafka, и имеет более простую модель Pub/Sub по сравнению с гибкой, но более сложной маршрутизацией RabbitMQ.

### ADR-004: Выбор PostgreSQL в качестве основной СУБД

*   **Дата:** 20.10.2025
*   **Решение:** **PostgreSQL** будет использоваться как универсальное хранилище данных: и для стандартных CRUD-сервисов, и в качестве Event Store для Akka Persistence.
*   **Обоснование:** Минимизация операционной сложности за счет использования одной знакомой, надежной и многофункциональной СУБД для всех нужд на старте проекта.

### ADR-005: Выбор gRPC для синхронного межсервисного взаимодействия

*   **Дата:** 20.10.2025
*   **Решение:** Для прямых синхронных запросов "сервис-сервис" (например, для верификации данных) будет использоваться **gRPC**.
*   **Обоснование:** gRPC обеспечивает высокую производительность за счет HTTP/2 и бинарного формата Protobuf. Строгая типизация контрактов (`.proto` файлы) и автоматическая кодогенерация клиентов/серверов устраняют целый класс ошибок интеграции и значительно упрощают разработку в полиглотной среде.

### ADR-006: Выбор Railway в качестве хостинг-платформы

*   **Дата:** 20.10.2025
*   **Решение:** Проект будет развертываться на **Railway (PaaS)**.
*   **Обоснование:** Railway полностью абстрагирует управление инфраструктурой, серверами и оркестрацией. Это позволяет сфокусироваться на разработке продукта, а не на DevOps. Встроенные приватные сети, автоматические деплои из Git и "однокликовое" создание баз данных и брокеров идеально подходят для быстрого старта и итеративного развития микросервисной системы.

## Группа C: Выбор языков для ключевых сервисов

### ADR-007: Выбор стека для ключевых сервисов (Полиглотная модель)

*   **Дата:** 20.10.2025
*   **Решение:** Принят полиглотный подход, где язык выбирается под задачу.
    *   **API Gateway:** **Rust (Teloxide/Axum)**. Выбран за максимальную производительность, безопасность памяти и низкое потребление ресурсов, что критично для входного шлюза.
    *   **Auction Service:** **Scala + Akka**. Выбран за мощную, зрелую реализацию акторной модели и строгую типизацию, идеально подходящую для реализации сложной, отказоустойчивой логики с ES/CQRS. (F# + Akka.NET рассматривается как полностью валидная альтернатива).
    *   **Notifications & Real-Time Hub:** **Elixir + Phoenix**. Выбран за непревзойденную способность управлять миллионами легковесных конкурентных процессов, что идеально для планирования уведомлений и управления WebSocket-соединениями.
    *   **CRUD-сервисы (Events, Users и т.д.):** **C# / .NET**. Выбран как знакомый, высокопроизводительный и очень продуктивный стек для быстрой разработки стандартных stateless-сервисов.
*   **Обоснование:** Такой подход позволяет использовать сильные стороны каждого языка и экосистемы там, где они приносят максимальную пользу, создавая более эффективную и надежную систему в целом.

## Группа D: Управление контрактами и схемами

### ADR-008: Выбор Apicurio Registry для управления контрактами сообщений

*   **Дата:** 21.10.2025
*   **Статус:** Принято
*   **Контекст:** В полиглотной микросервисной архитектуре необходимо обеспечить консистентность и безопасную эволюцию схем (контрактов) асинхронных сообщений, передаваемых через шину NATS. Ручное дублирование моделей в каждом сервисе ведет к ошибкам и проблемам с синхронизацией.
*   **Рассмотренные варианты:**
    1.  **Подход "Protobuf + Git":** Хранить `.proto` файлы в отдельном Git-репозитории и настроить кодогенерацию в CI/CD каждого сервиса. Плюсы: не требует дополнительного сервиса. Минусы: нет онлайн-проверки совместимости, сложная настройка сборки для каждого языка.
    2.  **Confluent Schema Registry:** Стандарт де-факто в мире Kafka. Очень мощный, но может быть сложен в настройке и тесно связан с экосистемой JVM.
    3.  **Apicurio Registry:** Легковесный open-source реестр схем, поддерживающий Protobuf. Легко развертывается как Docker-контейнер и предоставляет онлайн-проверку совместимости.
*   **Решение:** Выбран **Apicurio Registry**.
*   **Обоснование:** Apicurio предоставляет ключевые преимущества Schema Registry (централизованное хранение, онлайн-валидация совместимости, уменьшение размера сообщений) при минимальной операционной сложности. Это решает проблему управления контрактами в полиглотной среде более надежно, чем подход с Git, и является значительно более легковесным решением по сравнению с Confluent Schema Registry. "Золотым" источником правды для схем остается Git, а Apicurio используется как "боевой" реестр, который автоматически синхронизируется через CI/CD.

## Группа E: Специфичные архитектурные паттерны

### ADR-009: Архитектура `Auction Service` (Иерархия акторов)

*   **Дата:** 22.10.2025
*   **Решение:** Внутренняя архитектура `Auction Service` будет построена на **иерархической модели акторов**. Будет существовать родительский актор `AuctionSessionActor` (координатор) и дочерние акторы `LotActor` (исполнители) для каждого лота. Оба типа акторов будут персистентными.
*   **Обоснование:** Этот паттерн идеально решает задачу управления сложным жизненным циклом аукциона. `AuctionSessionActor` отвечает за глобальные правила, фазы и последовательность торгов. `LotActor` инкапсулирует всю сложную логику, специфичную для одного лота (разные режимы торгов, анти-снайп, proxy-bids). Такое разделение ответственности делает код чище, а систему — более надежной и масштабируемой. Использование персистентности на обоих уровнях обеспечивает гранулярное и эффективное восстановление состояния.

### ADR-010: Архитектура гибридного аукциона (Клиентские приложения)

*   **Дата:** 22.10.2025
*   **Решение:** Для поддержки гибридного (офлайн/онлайн) формата аукциона будут созданы два специализированных фронтенд-приложения:
    1.  **Admin Panel:** Реализуется как **Telegram Mini App**.
    2.  **Big Screen App:** Реализуется как **стандартное Web App**.
*   **Обоснование:** Этот подход позволяет сохранить "живой" вайб аукциона, дополняя его технологиями. **Admin Panel** в виде Mini App решает ключевую проблему безопасной и бесшовной аутентификации ведущего, предоставляя ему богатый UI для управления торгами. **Big Screen App** служит "окном" в онлайн-мир для офлайн-участников, визуализируя ход торгов в реальном времени. Оба приложения взаимодействуют с бэкендом через `Real-Time Hub`.

### ADR-011: Разделение `Notifications Service` и `Real-Time Hub`

*   **Дата:** 22.10.2025
*   **Решение:** Несмотря на то, что оба сервиса используют Elixir и занимаются "доставкой" информации, они будут реализованы как **два отдельных микросервиса**.
*   **Обоснование:** Сервисы решают разные задачи. **`Notifications Service`** — это "умный" сервис с бизнес-логикой. Он отвечает за *формирование*, *планирование* и *определение получателей* уведомлений на основе бизнес-событий. **`Real-Time Hub`** — это "глупый", но быстрый транспортный шлюз. Его единственная задача — эффективно управлять WebSocket-соединениями и проталкивать в них данные, которые ему присылают. Такое разделение улучшает архитектуру, так как каждый сервис имеет одну четкую ответственность (Single Responsibility Principle).

## Группа F: Процесс Разработки

### ADR-012: Использование Protobuf + Apicurio с самого начала (не JSON)

*   **Дата:** 22.10.2025
*   **Статус:** ✅ Реализовано (23.10.2025)
*   **Контекст:** При начале разработки возникал вопрос: начать с JSON сериализации для "быстрого старта", а затем мигрировать на Protobuf, или сразу использовать Protobuf через Apicurio Registry?
*   **Рассмотренные варианты:**
    1.  **MVP с JSON:** Быстрый старт, простая отладка. Затем миграция на Protobuf.
    2.  **Сразу Protobuf:** Больше настройки на старте, но правильная архитектура с первого дня.
*   **Решение:** Выбран **вариант 2 - сразу Protobuf + Apicurio Registry**.
*   **Обоснование:**
    - Миграция с JSON на Protobuf - это не "просто замена сериализатора", а полная переработка контрактов
    - Временные решения имеют свойство становиться постоянными
    - Правильная настройка инфраструктуры в начале экономит время в долгосрочной перспективе
    - Apicurio Registry уже выбран в ADR-008, логично использовать его сразу
    - Принцип: "Делай один раз правильно, а не дважды неправильно"
*   **Реализация:**
    - ✅ Структура `contracts/proto/` создана с `.proto` файлами
    - ✅ Кодогенерация через `prost-build` настроена в `telegram-gateway`
    - ✅ NATS клиент использует Protobuf сериализацию с `schema-id` в headers
    - ✅ Docker-compose обновлен для включения Apicurio Registry SQL
    - 🚧 Автоматическая регистрация схем в Apicurio (планируется)

### ADR-013: Итеративный процесс разработки с AI-агентом

*   **Дата:** 22.10.2025
*   **Статус:** Принято
*   **Контекст:** При разработке с помощью AI-агента возникает риск "over-engineering" - реализация большого количества кода без обсуждения архитектурных решений.
*   **Решение:** Принят **строго итеративный процесс** с обязательным обсуждением решений.
*   **Процесс:**
    1. Агент предлагает архитектурное решение с обоснованием
    2. Обсуждение и утверждение подхода
    3. Реализация небольшой части (1 слой, 1 модуль, 1 интеграция)
    4. Ревью кода и решений
    5. Обновление документации при необходимости
    6. Переход к следующей итерации
*   **Обоснование:**
    - Код легче ревьюить небольшими порциями
    - Архитектурные ошибки выявляются рано
    - Документация остается актуальной
    - Обучающий эффект для разработчика
    - Снижение технического долга
*   **Требования к агенту:**
    - Размер итерации: 1-2 часа работы максимум
    - Обязательное описание решений перед кодом
    - Предложения по обновлению документации при изменении понимания
    - Фиксация нетривиальных решений в ADR
