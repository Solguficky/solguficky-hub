# Журнал Архитектурных Решений (ADR)

Этот документ фиксирует важные архитектурные и технологические решения, принятые в ходе проектирования платформы.

---
## Группа А: Архитектурные Принципы

### ADR-001: Выбор микросервисной архитектуры с хореографией

*   **Дата:** 20.10.2025
*   **Решение:** Система будет построена на принципах **микросервисной архитектуры**. Взаимодействие между сервисами будет осуществляться преимущественно асинхронно через шину сообщений (**хореография**), а не через центральный сервис-оркестратор.
*   **Обоснование:** Этот подход обеспечивает слабую связанность, высокую отказоустойчивость и позволяет разрабатывать, развертывать и масштабировать каждый функциональный модуль (сервис) независимо. Он также дает свободу в выборе наиболее подходящего языка программирования для каждой конкретной задачи.

### ADR-002: Выбор паттернов CQRS и Event Sourcing для stateful-сервисов

*   **Дата:** 20.10.2025
*   **Решение:** Для сервисов со сложной, конкурентной логикой управления состоянием (в первую очередь, `Auction Service`) будут применяться паттерны **CQRS** (Command Query Responsibility Segregation) и **Event Sourcing (ES)**.
*   **Обоснование:** ES предоставляет полный, неизменяемый журнал всех изменений состояния, что критично для аудита и надежности аукциона. CQRS в связке с акторной моделью элегантно решает проблемы конкурентного доступа (race conditions) без необходимости в сложных блокировках.

## Группа B: Выбор Технологий и Платформы

### ADR-003: Выбор NATS JetStream в качестве шины сообщений

*   **Дата:** 20.10.2025
*   **Решение:** В качестве основной шины для асинхронного обмена сообщениями (командами и событиями) выбран **NATS JetStream**.
*   **Обоснование:** NATS предлагает лучший баланс между простотой развертывания, высочайшей производительностью и надежностью (благодаря JetStream). Он значительно проще в настройке и управлении, чем Apache Kafka, и имеет более простую модель Pub/Sub по сравнению с гибкой, но более сложной маршрутизацией RabbitMQ.

### ADR-004: Выбор PostgreSQL в качестве основной СУБД

*   **Дата:** 20.10.2025
*   **Решение:** **PostgreSQL** будет использоваться как универсальное хранилище данных: и для стандартных CRUD-сервисов, и в качестве Event Store для Akka Persistence.
*   **Обоснование:** Минимизация операционной сложности за счет использования одной знакомой, надежной и многофункциональной СУБД для всех нужд на старте проекта.

### ADR-005: Выбор gRPC для синхронного межсервисного взаимодействия

*   **Дата:** 20.10.2025
*   **Решение:** Для прямых синхронных запросов "сервис-сервис" (например, для верификации данных) будет использоваться **gRPC**.
*   **Обоснование:** gRPC обеспечивает высокую производительность за счет HTTP/2 и бинарного формата Protobuf. Строгая типизация контрактов (`.proto` файлы) и автоматическая кодогенерация клиентов/серверов устраняют целый класс ошибок интеграции и значительно упрощают разработку в полиглотной среде.

### ADR-006: Выбор Railway в качестве хостинг-платформы

*   **Дата:** 20.10.2025
*   **Решение:** Проект будет развертываться на **Railway (PaaS)**.
*   **Обоснование:** Railway полностью абстрагирует управление инфраструктурой, серверами и оркестрацией. Это позволяет сфокусироваться на разработке продукта, а не на DevOps. Встроенные приватные сети, автоматические деплои из Git и "однокликовое" создание баз данных и брокеров идеально подходят для быстрого старта и итеративного развития микросервисной системы.

## Группа C: Выбор языков для ключевых сервисов

### ADR-007: Выбор стека для ключевых сервисов (Полиглотная модель)

*   **Дата:** 20.10.2025
*   **Решение:** Принят полиглотный подход, где язык выбирается под задачу.
    *   **API Gateway:** **Rust (Teloxide/Axum)**. Выбран за максимальную производительность, безопасность памяти и низкое потребление ресурсов, что критично для входного шлюза.
    *   **Auction Service:** **Scala + Akka**. Выбран за мощную, зрелую реализацию акторной модели и строгую типизацию, идеально подходящую для реализации сложной, отказоустойчивой логики с ES/CQRS. (F# + Akka.NET рассматривается как полностью валидная альтернатива).
    *   **Notifications & Real-Time Hub:** **Elixir + Phoenix**. Выбран за непревзойденную способность управлять миллионами легковесных конкурентных процессов, что идеально для планирования уведомлений и управления WebSocket-соединениями.
    *   **CRUD-сервисы (Meetups, Identity и т.д.):** **C# / .NET**. Выбран как знакомый, высокопроизводительный и очень продуктивный стек для быстрой разработки стандартных stateless-сервисов.
*   **Обоснование:** Такой подход позволяет использовать сильные стороны каждого языка и экосистемы там, где они приносят максимальную пользу, создавая более эффективную и надежную систему в целом.

## Группа D: Управление контрактами и схемами

### ADR-008: Выбор Apicurio Registry для управления контрактами сообщений

*   **Дата:** 21.10.2025
*   **Статус:** Принято
*   **Контекст:** В полиглотной микросервисной архитектуре необходимо обеспечить консистентность и безопасную эволюцию схем (контрактов) асинхронных сообщений, передаваемых через шину NATS. Ручное дублирование моделей в каждом сервисе ведет к ошибкам и проблемам с синхронизацией.
*   **Рассмотренные варианты:**
    1.  **Подход "Protobuf + Git":** Хранить `.proto` файлы в отдельном Git-репозитории и настроить кодогенерацию в CI/CD каждого сервиса. Плюсы: не требует дополнительного сервиса. Минусы: нет онлайн-проверки совместимости, сложная настройка сборки для каждого языка.
    2.  **Confluent Schema Registry:** Стандарт де-факто в мире Kafka. Очень мощный, но может быть сложен в настройке и тесно связан с экосистемой JVM.
    3.  **Apicurio Registry:** Легковесный open-source реестр схем, поддерживающий Protobuf. Легко развертывается как Docker-контейнер и предоставляет онлайн-проверку совместимости.
*   **Решение:** Выбран **Apicurio Registry**.
*   **Обоснование:** Apicurio предоставляет ключевые преимущества Schema Registry (централизованное хранение, онлайн-валидация совместимости, уменьшение размера сообщений) при минимальной операционной сложности. Это решает проблему управления контрактами в полиглотной среде более надежно, чем подход с Git, и является значительно более легковесным решением по сравнению с Confluent Schema Registry. "Золотым" источником правды для схем остается Git, а Apicurio используется как "боевой" реестр, который автоматически синхронизируется через CI/CD.

## Группа E: Специфичные архитектурные паттерны

### ADR-009: Архитектура `Auction Service` (Иерархия акторов)

*   **Дата:** 22.10.2025
*   **Решение:** Внутренняя архитектура `Auction Service` будет построена на **иерархической модели акторов**. Будет существовать родительский актор `AuctionSessionActor` (координатор) и дочерние акторы `LotActor` (исполнители) для каждого лота. Оба типа акторов будут персистентными.
*   **Обоснование:** Этот паттерн идеально решает задачу управления сложным жизненным циклом аукциона. `AuctionSessionActor` отвечает за глобальные правила, фазы и последовательность торгов. `LotActor` инкапсулирует всю сложную логику, специфичную для одного лота (разные режимы торгов, анти-снайп, proxy-bids). Такое разделение ответственности делает код чище, а систему — более надежной и масштабируемой. Использование персистентности на обоих уровнях обеспечивает гранулярное и эффективное восстановление состояния.

### ADR-010: Архитектура гибридного аукциона (Клиентские приложения)

*   **Дата:** 22.10.2025
*   **Решение:** Для поддержки гибридного (офлайн/онлайн) формата аукциона будут созданы два специализированных фронтенд-приложения:
    1.  **Admin Panel:** Реализуется как **Telegram Mini App**.
    2.  **Big Screen App:** Реализуется как **стандартное Web App**.
*   **Обоснование:** Этот подход позволяет сохранить "живой" вайб аукциона, дополняя его технологиями. **Admin Panel** в виде Mini App решает ключевую проблему безопасной и бесшовной аутентификации ведущего, предоставляя ему богатый UI для управления торгами. **Big Screen App** служит "окном" в онлайн-мир для офлайн-участников, визуализируя ход торгов в реальном времени. Оба приложения взаимодействуют с бэкендом через `Real-Time Hub`.

### ADR-011: Разделение `Notifications Service` и `Real-Time Hub`

*   **Дата:** 22.10.2025
*   **Решение:** Несмотря на то, что оба сервиса используют Elixir и занимаются "доставкой" информации, они будут реализованы как **два отдельных микросервиса**.
*   **Обоснование:** Сервисы решают разные задачи. **`Notifications Service`** — это "умный" сервис с бизнес-логикой. Он отвечает за *формирование*, *планирование* и *определение получателей* уведомлений на основе бизнес-событий. **`Real-Time Hub`** — это "глупый", но быстрый транспортный шлюз. Его единственная задача — эффективно управлять WebSocket-соединениями и проталкивать в них данные, которые ему присылают. Такое разделение улучшает архитектуру, так как каждый сервис имеет одну четкую ответственность (Single Responsibility Principle).

## Группа F: Процесс Разработки

### ADR-012: Использование Protobuf с самого начала (не JSON)

*   **Дата:** 22.10.2025
*   **Статус:** ✅ Реализовано (23.10.2025), Уточнено
*   **Контекст:** При начале разработки возникал вопрос: начать с JSON сериализации для "быстрого старта", а затем мигрировать на Protobuf, или сразу использовать Protobuf? (См. ADR-014 для решения по Schema Registry).
*   **Рассмотренные варианты:**
    1.  **MVP с JSON:** Быстрый старт, простая отладка. Затем миграция на Protobuf.
    2.  **Сразу Protobuf:** Больше настройки на старте, но правильная архитектура с первого дня.
*   **Решение:** Выбран **вариант 2 - сразу Protobuf**.
*   **Обоснование:**
    - Миграция с JSON на Protobuf - это не "просто замена сериализатора", а полная переработка контрактов
    - Временные решения имеют свойство становиться постоянными
    - Правильная настройка инфраструктуры в начале экономит время в долгосрочной перспективе
    - Принцип: "Делай один раз правильно, а не дважды неправильно"
*   **Реализация:**
    - ✅ Структура `contracts/proto/` создана с `.proto` файлами
    - ✅ Кодогенерация через `prost-build` настроена в `telegram-gateway`
    - ✅ NATS клиент использует Protobuf сериализацию
    - ❌ Использование `schema-id` в headers NATS-сообщений было убрано как избыточное для MVP.
    - ❌ Зависимость от Apicurio Registry была убрана из `docker-compose.yml`.

### ADR-013: Итеративный процесс разработки с AI-агентом

*   **Дата:** 22.10.2025
*   **Статус:** Принято
*   **Контекст:** При разработке с помощью AI-агента возникает риск "over-engineering" - реализация большого количества кода без обсуждения архитектурных решений.
*   **Решение:** Принят **строго итеративный процесс** с обязательным обсуждением решений.
*   **Процесс:**
    1. Агент предлагает архитектурное решение с обоснованием
    2. Обсуждение и утверждение подхода
    3. Реализация небольшой части (1 слой, 1 модуль, 1 интеграция)
    4. Ревью кода и решений
    5. Обновление документации при необходимости
    6. Переход к следующей итерации
*   **Обоснование:**
    - Код легче ревьюить небольшими порциями
    - Архитектурные ошибки выявляются рано
    - Документация остается актуальной
    - Обучающий эффект для разработчика
    - Снижение технического долга
*   **Требования к агенту:**
    - Размер итерации: 1-2 часа работы максимум
    - Обязательное описание решений перед кодом
    - Предложения по обновлению документации при изменении понимания
    - Фиксация нетривиальных решений в ADR

### ADR-014: Упрощенное управление контрактами (Protobuf-in-Git) для MVP

*   **Дата:** 23.10.2025
*   **Статус:** Принято
*   **Контекст:** В ADR-008 было принято решение использовать Apicurio Registry для управления схемами сообщений. В ходе реализации MVP стало очевидно, что развертывание и поддержка дополнительного сервиса (реестра схем) является избыточной сложностью на данном этапе. У нас планируется только одна версия контрактов, и онлайн-проверка совместимости пока не требуется.
*   **Решение:** На этапе MVP отказаться от использования внешнего Schema Registry (Apicurio). Использовать подход **"Protobuf-in-Git"**.
*   **Обоснование:**
    - **Простота:** Исходные `.proto` файлы являются единственным источником правды и хранятся в монорепозитории в директории `contracts/proto`.
    - **Минимальные зависимости:** Сервисам не нужен дополнительный компонент в runtime для работы с контрактами.
    - **Надежность сборки:** Кодогенерация происходит на этапе сборки сервиса (build time), что гарантирует соответствие кода и контракта.
    - **Эволюция:** Когда потребуется поддержка нескольких версий контрактов и онлайн-проверка совместимости, можно будет вернуться к рассмотрению Apicurio или аналогичного решения, не переписывая уже существующие контракты.
*   **Последствия:**
    - Это решение заменяет ADR-008.
    - Из NATS-сообщений убирается заголовок `schema-id`, так как версионирование на данном этапе не требуется.
    - `docker-compose.yml` и конфигурации сервисов упрощаются, так как из них удаляется Apicurio Registry.

## Группа G: Инфраструктура и Наблюдаемость (Observability)

### ADR-015: Использование Loki для централизованного сбора логов

**Дата**: 2025-10-23

**Статус**: Принято

### Контекст

Проекту требуется единая система для сбора, хранения и анализа логов со всех микросервисов. Текущий подход, когда каждый сервис пишет структурированные логи в `stdout`, хорошо подходит для контейнеризированных сред, но не обеспечивает централизованного доступа и поиска.

Требования к системе:
- Поддержка развертывания в Railway и локальной разработки.
- Наличие UI для поиска и фильтрации.
- Open-source или наличие щедрого бесплатного тарифа.
- Минимальные изменения в коде существующих сервисов.

### Рассмотренные варианты

1.  **Loki + Grafana**: Open-source, стандарт индустрии, индексирует только метаданные, что делает его быстрым и экономичным. Отличная интеграция с Grafana.
2.  **Datadog / Better Stack**: SaaS-решения. Просты в настройке, но являются проприетарными и могут стать дорогими при росте объемов.

### Решение

Мы принимаем **Loki** в качестве основной системы для агрегации логов. Для визуализации будет использоваться **Grafana**.

На начальном этапе мы будем использовать **Grafana Cloud**, который предоставляет щедрый бесплатный тариф. Это позволит нам быстро развернуть систему без необходимости поддерживать собственную инфраструктуру. В будущем возможен переезд на self-hosted инстанс.

### Последствия

- **Позитивные**:
    - Все логи со всех сервисов будут доступны в одном месте (Grafana).
    - Мощный язык запросов LogQL для анализа логов.
    - Заложена основа для полноценной системы observability (можно будет легко добавить метрики Prometheus и трейсы Tempo в той же Grafana).
    - Не требуется изменять код сервисов, так как они уже пишут логи в `stdout`.

- **Негативные**:
    - Необходимо настроить отправку логов (log drains) из нашей среды развертывания (Railway) в Grafana Cloud.
    - Для локальной разработки потребуется настроить `docker-compose` с Loki и Grafana.

### ADR-016: Архитектура RBAC для MVP + Action паттерн для тестируемости

*   **Дата:** 24.10.2025
*   **Статус:** Принято
*   **Контекст:**

При разработке Telegram Gateway возникла необходимость в системе ролей (RBAC) для разграничения доступа админов и обычных пользователей. Также критична была тестируемость FSM логики и UI билдеров. Наконец, нужно было определить четкие критерии, когда использовать синхронные gRPC вызовы, а когда асинхронные NATS команды.

**Требования MVP:**
- Админы должны иметь возможность создавать лоты через пошаговую форму (FSM)
- UI для админов и пользователей должен отличаться
- Вся логика (FSM, UI, хендлеры) должна быть легко тестируема без запуска бота

*   **Решение:**

**1. RBAC для MVP: Hardcoded список админов**

Для MVP система ролей реализована через конфигурацию:
- Список Telegram ID админов хранится в `configuration.yaml` (секция `auth.admins`)
- Модуль `app/auth` содержит `UserRole` enum (`Admin`, `User`)
- Функция `get_user_role(user_id, config)` определяет роль по ID
- `Dependencies` содержит helper-метод для проверки роли

**2. Модульная архитектура UI**

UI разделен на чистые функции, организованные по модулям:
```
src/app/ui/
├── common.rs          # Переиспользуемые кнопки
├── user/auction.rs    # UI для обычных пользователей
└── admin/
    ├── auction_management.rs  # Админская панель аукциона
    └── lot_creation.rs        # UI для создания лота
```

Все UI функции:
- Чистые (pure functions)
- Принимают DTO и возвращают `(String, InlineKeyboardMarkup)`
- Легко тестируются юнит-тестами

**3. Action паттерн для изоляции teloxide API**

Хендлеры не вызывают `teloxide::Bot` напрямую, а возвращают `BotAction` enum:
```rust
pub enum BotAction {
    SendMessage { chat_id, text, keyboard },
    EditMessage { chat_id, message_id, text, keyboard },
    AnswerCallback { callback_id, text },
    SendPhoto { chat_id, photo_url, caption, keyboard },
    Multiple(Vec<BotAction>),
}
```

Выполнение происходит через функцию `execute_action(&Bot, BotAction)` в модуле `helpers.rs`.

**4. FSM как чистые функции**

FSM логика изолирована в модуле `app/fsm/lot_creation.rs`:
```rust
pub struct FsmTransition {
    pub new_state: State,
    pub action: BotAction,
}

pub fn handle_title_input(chat_id, state, input) -> Result<FsmTransition, String>
```

Каждая функция:
- Валидирует ввод
- Обновляет draft
- Вычисляет новое состояние
- Вызывает UI билдер
- Возвращает `FsmTransition`

**5. Критерии выбора синхронный vs асинхронный**

**Основной критерий - природа операции:**

- **CRUD операции** (данные без состояния) → **синхронный** (gRPC/прямой вызов)
  - Простые запросы/модификации данных
  - Результат операции сразу известен
  - Примеры: `CreateLot`, `UpdateLot`, `GetAuction`, `GetUserProfile`

- **Команды к агрегатам** (stateful бизнес-логика) → **асинхронный** (NATS)
  - Требуют сложной валидации и изменения состояния
  - Event Sourcing / Actor model
  - Нужно оповестить других подписчиков
  - Примеры: `PlaceBid`, `StartAuction`, `ProcessFinalPhase`

**Дополнительные критерии:**

| Критерий | Синхронный | Асинхронный |
|----------|------------|-------------|
| **UX обратная связь** | Критична немедленная | Может быть отложена |
| **Частота** | Редкие (< 10/мин) | Частые (> 100/мин) |
| **Роль** | Админ (конфигурация) | Пользователь (действия) |
| **Broadcast** | Не нужно уведомлять | Нужно разослать события |

**Примеры классификации:**

✅ **Синхронные (CRUD):**
- `CreateLot` - просто данные, нужна валидация → прямой вызов MockAuctionService (MVP), gRPC в будущем
- `UpdateLot` - модификация данных → gRPC к Auction Service (будущее)
- `GetAuction` - query → прямой вызов (MVP), gRPC в будущем

**Важно:** CRUD операции с лотами НЕ должны идти через NATS команды. Для будущего нужен gRPC контракт `AuctionService` с методами `CreateLot`, `UpdateLot`, `DeleteLot`.

✅ **Асинхронные (Команды к агрегатам):**
- `PlaceBid` - команда к LotActor, Event Sourcing → NATS
- `StartAuction` - команда к AuctionSessionActor → NATS
- `ProcessFinalPhase` - команда к AuctionSessionActor → NATS

*   **Последствия:**

**Позитивные:**
- ✅ FSM логика легко тестируется (12 юнит-тестов реализовано)
- ✅ UI билдеры легко тестируются (8 юнит-тестов реализовано)
- ✅ Хендлеры изолированы от `teloxide` API
- ✅ Админы определяются через конфиг - быстро для MVP
- ✅ Четкие критерии для выбора sync/async
- ✅ CRUD операции не создают лишней сложности с NATS

**Негативные:**
- ⚠️ Hardcoded список админов не масштабируется
- ⚠️ При росте числа хендлеров нужно много wrapper-функций (~150 строк)
- ⚠️ Нужно помнить о различии CRUD vs команды при добавлении новых операций

**План миграции:**
- При появлении User Service заменить `get_user_role` на gRPC вызов
- Логика авторизации уже изолирована в модуле `auth` - миграция будет простой
- Структура хендлеров и FSM не потребует изменений

### ADR-017: Технологический стек Auction Service

**Дата**: 24.10.2025

**Статус**: Принято

### Контекст

Auction Service — это ключевой stateful-сервис платформы, отвечающий за проведение торгов. Требования к сервису:

1. **Event Sourcing** — полный аудит всех событий аукциона
2. **Сложная бизнес-логика** — различные режимы торгов, анти-снайп, proxy-bids
3. **Конкурентность** — множество одновременных ставок
4. **Типобезопасность** — минимизация runtime ошибок
5. **Интеграция** — gRPC для синхронных запросов, NATS для команд/событий
6. **Тестируемость** — возможность unit и integration тестов без реальной БД

### Рассмотренные варианты

#### Язык программирования

**1. Scala 3 + Akka Typed**
- ✅ Мощная типизация (ADTs, sealed traits)
- ✅ Зрелая экосистема для Event Sourcing (Akka Persistence)
- ✅ Акторная модель идеальна для конкурентной бизнес-логики
- ✅ Большое community, много примеров
- ⚠️ JVM требует больше памяти
- ⚠️ Время компиляции Scala

**2. F# + Akka.NET**
- ✅ Функциональный стиль, immutability by default
- ✅ Akka.NET поддерживает Event Sourcing
- ✅ Отличная интеграция с .NET экосистемой
- ⚠️ Меньше community и примеров для Akka.NET
- ⚠️ Akka.NET менее зрелый чем Akka JVM

**3. Rust + async actors (Actix)**
- ✅ Минимальное потребление ресурсов
- ✅ Производительность
- ⚠️ Нет готового Event Sourcing фреймворка
- ⚠️ Пришлось бы писать персистентность с нуля
- ⚠️ Акторы в Actix не типобезопасны

**Выбор:** **Scala 3 + Akka Typed** — лучший баланс между зрелостью экосистемы, типобезопасностью и production-ready Event Sourcing.

#### Фреймворк для Event Sourcing

**1. Akka Persistence Typed**
- ✅ Industry standard для Event Sourcing на JVM
- ✅ Типобезопасные акторы
- ✅ Встроенная поддержка снапшотов
- ✅ Отличная документация и примеры
- ✅ EventSourcedBehaviorTestKit для тестов без БД

**2. ZIO + ZIO Actors**
- ✅ Чистый функциональный стиль
- ✅ Testability через ZIO environment
- ⚠️ Нет готового Event Sourcing (нужна библиотека типа zio-entity)
- ⚠️ Меньше примеров production использования

**Выбор:** **Akka Persistence Typed** — battle-tested решение с Event Sourcing "из коробки".

#### gRPC фреймворк

**1. akka-grpc + akka-http**
- ✅ Нативная интеграция с Akka Typed
- ✅ ask pattern работает напрямую с ActorRef
- ✅ Один ActorSystem для акторов и gRPC
- ✅ Protobuf кодогенерация через ScalaPB

**2. http4s + fs2-grpc**
- ✅ Чистый функциональный стиль (cats-effect)
- ✅ Composable через Kleisli
- ⚠️ Нужен "мост" между Akka и cats-effect (IO ↔ Future)
- ⚠️ Два runtime (ActorSystem + IORuntime)
- ⚠️ Сложнее интегрировать с Akka Persistence

**Выбор:** **akka-grpc + akka-http** — нативная интеграция с акторами, ask pattern "из коробки".

#### NATS клиент

**1. io.nats:jnats (официальный Java клиент)**
- ✅ Официальная поддержка от NATS.io
- ✅ Зрелый, хорошо протестированный
- ✅ Поддержка JetStream
- ✅ Тонкая обертка (~100 строк) решает интероп
- ⚠️ Java API (нужна конвертация Future)

**2. Самописная обертка на Akka Streams**
- ✅ Идиоматичная для Akka (Source/Sink)
- ✅ Backpressure через Akka Streams
- ⚠️ Нужно писать и поддерживать самим
- ⚠️ Риск багов, нужны тесты

**3. nats4cats (cats-effect)**
- ⚠️ Не подходит — мы не используем cats-effect

**Выбор:** **io.nats:jnats** — официальный клиент надежен, тонкая обертка не добавляет сложности.

#### Тестирование

**1. ScalaTest + Akka TestKit Typed**
- ✅ Стандарт в Akka экосистеме
- ✅ Официальная поддержка: `ScalaTestWithActorTestKit`
- ✅ `EventSourcedBehaviorTestKit` для персистентных акторов
- ✅ Множество стилей (WordSpec, FlatSpec)
- ⚠️ Медленнее компилируется

**2. MUnit + Akka TestKit**
- ✅ Легковесный, быстрый
- ✅ Лучше для Scala 3
- ⚠️ Нет официальной интеграции с Akka
- ⚠️ Придется писать обертки

**Выбор:** **ScalaTest** — официальная поддержка Akka критична для тестирования Event Sourcing.

### Решение

**Технологический стек Auction Service:**

| Компонент | Выбор |
|-----------|-------|
| **Язык** | Scala 3.5.x |
| **Build Tool** | sbt 1.10.x |
| **Фреймворк** | Akka 2.9.x Typed |
| **Event Sourcing** | Akka Persistence Typed |
| **База данных** | PostgreSQL (Event Store) |
| **gRPC** | akka-grpc + akka-http |
| **Protobuf** | akka-grpc plugin (ScalaPB) |
| **NATS клиент** | io.nats:jnats |
| **Тестирование** | ScalaTest + Akka TestKit Typed |
| **IDE** | Cursor + Metals LSP |

**Архитектурные принципы:**

1. **Domain-Driven Design:** структура domain/, application/, infrastructure/
2. **Короткие пакеты:** `auction.domain.session` вместо `io.solguficky.auction.domain.session`
3. **Event Sourcing:** события — source of truth
4. **Типобезопасность:** sealed traits для протоколов, ADTs для команд/событий
5. **Иерархия акторов:** AuctionRegistry → AuctionSession → Lot
6. **Интеграция:** gRPC для queries, NATS для commands

### Обоснование

#### Почему Akka + Scala 3?

1. **Event Sourcing "из коробки":**
   - `EventSourcedBehavior[Command, Event, State]` — готовая абстракция
   - Персистентность в PostgreSQL через `akka-persistence-jdbc`
   - Снапшоты, recovery, retention policy

2. **Акторная модель для concurrency:**
   - Каждый лот — отдельный актор с изолированным состоянием
   - Нет race conditions, нет блокировок
   - Обработка команд последовательно внутри актора

3. **Типобезопасность:**
   - `ActorRef[Protocol]` — компилятор проверяет типы сообщений
   - Sealed traits — exhaustive pattern matching
   - Компилятор предупреждает о неполном покрытии

#### Почему akka-grpc?

```scala
val sessionRef: ActorRef[AuctionSession.Command] = ...
registry
  .ask(replyTo => GetSession(eventId, replyTo))
  .flatMap(sessionRef.ask(GetStatus.apply))
  .map(status => AuctionStatusResponse(...))
```

- ask pattern работает напрямую с ActorRef
- Один ActorSystem для акторов и gRPC
- Нет конвертации между Future и IO

#### Почему io.nats:jnats?

- Официальный клиент = надежность и поддержка
- Тонкая обертка (~100 строк) решает интероп:

```scala
class NatsPublisher(connection: Connection)(using ec: ExecutionContext):
  def publish[T <: GeneratedMessage](subject: String, message: T): Future[Unit] =
    Future(connection.publish(subject, message.toByteArray))
```

#### Почему короткие пакеты?

- `auction.domain.session` вместо `io.solguficky.auction.domain.session`
- Это внутренний микросервис, не публичная библиотека
- Меньше визуального шума, проще навигация

#### Почему Domain-Driven структура?

```
domain/        ← бизнес-логика (не зависит от gRPC/NATS)
application/   ← координация (use cases)
infrastructure/← технические детали (NATS, PostgreSQL)
```

- Четкое разделение ответственности
- Domain легко тестировать (нет зависимостей от транспорта)
- Application — тонкая обертка над domain
- Infrastructure — детали реализации

### Последствия

#### Позитивные

- ✅ **Типобезопасность на всех уровнях** — компилятор ловит ошибки
- ✅ **Event Sourcing "из коробки"** — не нужно писать с нуля
- ✅ **Тестируемость** — EventSourcedBehaviorTestKit позволяет тестировать без БД
- ✅ **Единая экосистема** — Akka для акторов, gRPC, персистентности
- ✅ **Production-ready** — Akka используется в тысячах продакшн систем
- ✅ **Audit trail** — Event Store содержит полную историю

#### Негативные

- ⚠️ **JVM memory footprint** — требует больше памяти чем Rust/Go (~500MB+ heap)
- ⚠️ **Время компиляции** — Scala компилируется медленнее (first build ~2-3 мин)
- ⚠️ **Learning curve** — нужно знать Akka, Event Sourcing, Scala
- ⚠️ **JVM startup time** — ~5-10 сек (vs ~1 сек у Rust)

#### Компромиссы

| Метрика | Scala + Akka | Rust + Actix |
|---------|--------------|--------------|
| Time to market | ✅ Быстрее (готовый Event Sourcing) | ⚠️ Медленнее (писать с нуля) |
| Memory usage | ⚠️ 500MB+ | ✅ 50MB |
| Startup time | ⚠️ 5-10 сек | ✅ 1 сек |
| Type safety | ✅ Отличная | ⚠️ Средняя (акторы не типобезопасны) |
| Event Sourcing | ✅ Production-ready | ⚠️ Нужно писать |
| Тестируемость | ✅ TestKit из коробки | ⚠️ Сложнее |

**Вывод:** Для stateful сервиса с Event Sourcing выигрыш в time to market и надежности важнее экономии памяти.

### Альтернативные решения и почему они не выбраны

**F# + Akka.NET:**
- Отличный выбор, но Akka.NET менее зрелый чем Akka JVM
- Меньше примеров Event Sourcing в production
- Community меньше

**Rust + custom Event Sourcing:**
- Пришлось бы писать Event Store, снапшоты, recovery с нуля
- Time to market намного больше
- Риск багов в критической части

**Kotlin + Ktor + Event Sourcing библиотека:**
- Нет готового Event Sourcing фреймворка уровня Akka Persistence
- Пришлось бы выбирать из менее зрелых решений

   - Time to market важнее теоретической чистоты

Если потребуется вернуться к Scala/Akka:
- Архитектура (DDD, Event Sourcing, actors) не изменится
- Protobuf контракты останутся теми же
- PostgreSQL Event Store совместим
- Миграция возможна без изменения других сервисов

### Итоговое решение

**Используем C# + Akka.NET Classic для Auction Service** с сохранением:
- Domain-Driven Design структуры
- Event Sourcing через Akka.Persistence
- Акторной иерархии (Registry → Session → Lot)
- Protobuf контрактов для gRPC и NATS
- PostgreSQL как Event Store

**Причина:** Pragmatic choice — быстрый старт важнее теоретической чистоты. Akka.NET достаточно зрелый для production, setup простой, community большой.

### ADR-018: WebSocket Gateway на C# + SignalR для MVP

**Дата**: 29.10.2025

**Статус**: Принято

### Контекст

Для поддержки Big Screen App и Admin Panel требуется сервис, который будет проталкивать события из NATS в WebSocket-соединения клиентов в реальном времени.

Изначально в архитектуре планировался `Real-Time Hub` на Elixir + Phoenix, но для MVP это избыточная сложность.

**Требования MVP:**
- Проталкивать события `events.auction.*` из NATS в WebSocket
- Поддержка подписок на конкретный аукцион (роутинг по auction_id)
- Автоматический reconnect на клиенте
- 50+ одновременных соединений

### Рассмотренные варианты

**1. Elixir + Phoenix Channels**
- ✅ Идеально для масштабирования (10k+ соединений)
- ✅ Phoenix.PubSub для distributed pub/sub
- ⚠️ Новый язык в стеке для MVP
- ⚠️ Дополнительная сложность настройки

**2. C# + SignalR**
- ✅ Единообразие стека (все сервисы на C#)
- ✅ SignalR — production-ready (используется в Microsoft Teams)
- ✅ Автоматический reconnect и fallback
- ✅ Быстрый старт
- ⚠️ Требует Redis backplane для horizontal scaling

**3. Raw WebSocket на C#**
- ⚠️ Нужно вручную реализовать reconnect, heartbeat
- ⚠️ Нет ready-made роутинга (groups)
- ⚠️ Больше кода, больше багов

### Решение

**Используем C# + ASP.NET Core + SignalR для MVP.**

**Переименование:** `Real-Time Hub` → `WebSocket Gateway` (более точное название).

### Обоснование

#### Почему C# + SignalR для MVP?

1. **Единообразие стека:**
   - Все сервисы уже на C#
   - Один набор инструментов, один язык
   - Проще онбординг разработчиков

2. **SignalR — production-ready:**
   - Используется в Microsoft Teams, Azure DevOps
   - Автоматический reconnect из коробки
   - Fallback на long-polling если WebSocket недоступен
   - Typed hubs с строгими контрактами

3. **SignalR Groups для роутинга:**
   - Клиент подписывается на `auction:123`
   - События проталкиваются только в нужную группу
   - Не нужно писать роутинг вручную

4. **Быстрый старт:**
   - `dotnet new webapi` → добавить SignalR → готово
   - Не нужно изучать Elixir/Phoenix для MVP

#### Почему не Elixir сразу?

- Для MVP ожидается 50-100 одновременных соединений
- C# + SignalR легко справляется с такой нагрузкой
- Нет смысла вводить новый язык пока нет проблем с масштабированием

### Архитектура

**Компоненты:**
```
WebSocketGateway/
├── Hubs/
│   └── AuctionHub.cs          # SignalR Hub (клиентский API)
├── Services/
│   ├── NatsEventListener.cs   # Подписка на events.auction.*
│   └── EventBroadcaster.cs    # Роутинг в SignalR Groups
└── Program.cs
```

**Поток данных:**
1. `Auction Service` публикует `BidPlacedEvent` → NATS
2. `NatsEventListener` получает событие
3. `EventBroadcaster` извлекает `auction_id` из события
4. `EventBroadcaster` отправляет в SignalR Group `auction:{id}`
5. `Big Screen App` (подписан на group) → получает JSON event
6. Frontend обновляет UI

**Роутинг через SignalR Groups:**
```csharp
await _hubContext.Clients
    .Group($"auction:{auctionId}")
    .SendAsync("AuctionEvent", eventData, ct);
```

### Последствия

#### Позитивные

- ✅ **Быстрый старт** — знакомый стек, нет learning curve
- ✅ **SignalR автоматизирует сложности** — reconnect, fallback, heartbeat
- ✅ **Groups из коробки** — не нужно писать роутинг
- ✅ **Единообразие** — все сервисы на C#, одни инструменты
- ✅ **TypeScript клиент** — официальная библиотека `@microsoft/signalr`
- ✅ **Достаточно для MVP** — 50-100 соединений не проблема

#### Негативные

- ⚠️ **Масштабирование** — для >1000 соединений нужен Redis backplane
- ⚠️ **Memory footprint** — C# тяжелее Elixir (~200MB vs ~50MB)
- ⚠️ **Horizontal scaling сложнее** — нужен Redis или sticky sessions

#### Миграционный путь

**Промежуточный этап (1000+ соединений):**
```csharp
services.AddSignalR()
    .AddStackExchangeRedis("redis:6379");
```
Позволяет horizontal scaling C# сервиса.

**Финальный этап (10k+ соединений):**
- Миграция на Elixir + Phoenix Channels
- Архитектура остается той же (NATS → WebSocket)
- Backend контракты (Protobuf) не меняются
- Клиенты обновляют JS библиотеку (SignalR → Phoenix)

### Итоговое решение

**Для MVP используем C# + SignalR** с последующей миграцией на Elixir при необходимости.

**Переименование:** `Real-Time Hub` → `WebSocket Gateway` (точнее описывает роль).

**Технологии:**
- C# 12 / .NET 8
- ASP.NET Core SignalR
- NATS.Client для подписки на события
- Serilog для логирования

**Критерии миграции на Elixir:**
- >1000 одновременных WebSocket соединений
- Проблемы с memory footprint
- Нужен distributed pub/sub без Redis

### Связанные решения

- **ADR-011**: Разделение Notifications Service и WebSocket Gateway

- **ADR-001**: Микросервисная архитектура с хореографией

### ADR-019: Разделение Meetup и Auction, формат ID - ULID

**Дата**: 30.10.2025

**Статус**: Частично заменено ADR-020 (формат ID: ULID → UUIDv7). Разделение концепций Meetup/Auction остаётся в силе.

#### Контекст

Изначально `meetup_id` использовался как идентификатор аукциона, что создавало путаницу между концепциями Meetup (событие/сходка) и Auction (процесс торгов).

**Проблемы:**
- Смешение понятий Meetup и Auction
- Неясно, какой ID использовать для команд аукциона
- Сложность при будущем расширении (несколько аукционов на один meetup)

#### Решение

**1. Разделить концепции:**
- **Meetup** - событие/сходка (future scope, пока нет сервиса)
- **Auction** - процесс торгов (текущий scope)

**2. Формат ID - ULID:**
- ULID (Universally Unique Lexicographically Sortable Identifier)
- 128-bit, формат: `01H2XCEJQTF2NBREXX3VQJHP41` (26 символов, Base32)
- Первые 48 бит = timestamp (мс), остальные 80 бит = random
- Сортируется по времени создания
- Безопасно для distributed генерации

**3. Генерация ID:**
- **telegram-gateway** генерирует ULID локально (без round-trip к сервису)
- Для MVP один захардкоженный `AUCTION_ID` в константе
- При добавлении создания аукционов - генерация через библиотеку (Rust: `ulid-rs`, C#: `Ulid.NewUlid()`)

**4. Persistence ID:**
```csharp
// AuctionActor
PersistenceId = $"auction-{auctionId}"

// LotActor остается
PersistenceId = $"lot-{lotId}"
```

**5. БД структура:**
```sql
-- lots table
auction_id VARCHAR(26) NOT NULL  -- ULID format
lot_id INT PRIMARY KEY
```

#### Почему ULID, а не GUID или INT?

| Критерий | INT | GUID v4 | ULID |
|----------|-----|---------|------|
| **Генерация** | Нужен round-trip к БД | Локально | Локально |
| **Сортировка** | ✅ По порядку | ❌ Случайный | ✅ По времени |
| **Индексы PostgreSQL** | ✅ Компактно | ⚠️ Фрагментация | ✅ Упорядочены |
| **Distributed safe** | ❌ Коллизии | ✅ Безопасно | ✅ Безопасно |
| **Читаемость** | ✅ | ⚠️ Длинный | ✅ Компактный |

#### Обоснование

1. **Семантическая ясность:**
   - `auction_id` - четко указывает на аукцион
   - `meetup_id` - можно использовать в будущем как foreign key
   - Разделение ответственности (Meetup Service ≠ Auction Service)

2. **ULID преимущества:**
   - Локальная генерация = нет дополнительного latency
   - Сортировка по времени = удобство для запросов
   - Distributed-safe = можно генерировать в любом сервисе
   - Idempotency = повторная отправка с тем же ID не создаст дубликат

3. **Event Sourcing friendly:**
   - Aggregate ID известен до команды
   - Можно создать actor на лету
   - Нет race condition при создании

#### Последствия

**Позитивные:**
- ✅ Четкое разделение концепций Meetup vs Auction
- ✅ ULID дает все преимущества GUID + сортировка
- ✅ Локальная генерация = нет round-trip
- ✅ Idempotency из коробки
- ✅ Гибкость для будущего расширения (N аукционов на meetup)

**Негативные:**
- ⚠️ Breaking change для контрактов (все сервисы обновляются разом)
- ⚠️ String ID = немного больше памяти чем INT (26 байт vs 4 байта)

**Миграционный путь:**
- Для MVP: пересоздать БД (данных нет)
- Для prod: добавить колонку `auction_id`, заполнить через скрипт, удалить `meetup_id`

#### Примеры

**Генерация ULID в Rust:**
```rust
use ulid::Ulid;
let auction_id = Ulid::new().to_string(); // "01JBEX..."
```

**Генерация ULID в C#:**
```csharp
using Ulid;
var auctionId = Ulid.NewUlid().ToString(); // "01JBEX..."
```

**Protobuf контракт:**
```protobuf
message StartAuctionCommand {
  string auction_id = 2;  // ULID format
}
```

#### Связанные решения

- **ADR-002**: Event Sourcing для stateful-сервисов
- **ADR-005**: gRPC для синхронного взаимодействия
- **ADR-009**: Иерархия акторов (AuctionActor → LotActor)

### ADR-020: UUIDv7 вместо ULID для идентификаторов

**Дата**: 18.07.2026

**Статус**: Принято. Заменяет ADR-019 в части формата ID (разделение Meetup/Auction из ADR-019 остаётся в силе).

#### Контекст

ADR-019 выбрал ULID как формат ID аукционов (а в будущем — сходок): нужны локальная генерация без похода в БД и сортируемость по времени (локальность индекса, естественный порядок для Event Sourcing). ULID эти свойства даёт, но это нестандартный формат — в каждом языке нужна сторонняя библиотека. Проект полиглотный (сейчас C#, Rust, Python; в планах Go, Kotlin, Ruby, Elixir), и каждая новая интеграция тянет за собой поиск и поддержку ULID-библиотеки.

В мае 2024 вышел RFC 9562, стандартизовавший UUIDv7 — UUID с тем же устройством, что у ULID (48 бит unix-timestamp в мс + случайные биты), и той же сортируемостью по времени. Поддержка нативная почти везде: `Guid.CreateVersion7()` в .NET 9+, крейт `uuid` с фичей `v7` в Rust, `uuid.uuid7()` в Python 3.14+ (до этого — пакет `uuid6`), функция `uuidv7()` в PostgreSQL 18+.

Боевых данных нет, ID в контрактах — `string`, поэтому миграция сейчас дешёвая; с появлением реальных данных она станет заметно дороже.

#### Рассмотренные варианты

1. **Оставить ULID** — код уже работает; но нестандарт, сторонняя зависимость в каждом языке, вечный «налог» на полиглотность.
2. **UUIDv7** — те же свойства (локальная генерация, time-ordered), стандарт IETF, нативная поддержка в рантаймах и PostgreSQL 18+; минус — строка длиннее (36 символов против 26).
3. **UUIDv4** — нативен ещё шире, но не сортируется по времени: фрагментация индекса и потеря естественного порядка в ES — свойство, ради которого выбирали ULID, теряется.

#### Решение

Заменить ULID на **UUIDv7 (RFC 9562)** для всех генерируемых сервисами ID (аукционы, будущие сходки).

**Контрактный формат**: канонический строковый UUID — 36 символов, lowercase, с дефисами (`0198f2a4-7c1e-7d3a-9b21-4f8e12ab34cd`). В Protobuf ID остаётся `string`.

**Генерация**: только нативными средствами — `Guid.CreateVersion7()` (C#), `uuid::Uuid::now_v7()` (Rust), `uuid6.uuid7()` / `uuid.uuid7()` (Python).

**Парсинг на границах** (NATS/gRPC): `Guid.TryParse` + ответ с ошибкой вместо необработанного исключения.

**Хранение**: в PostgreSQL ID пока остаётся строкой; переход на нативный тип `uuid` — отдельный пункт техдолга (при появлении Meetups Service).

#### Обоснование

Ключевой аргумент — полиглотность: единственное преимущество ULID перед UUIDv7 (компактность строки) не окупает стороннюю зависимость в каждом из 4–7 языков стека. UUIDv7 даёт идентичные свойства (локальная генерация, монотонность по времени, distributed-safe, idempotency) из стандартной библиотеки. Бонус: PostgreSQL 18+ понимает `uuidv7()` нативно, что упростит будущий переход колонок на тип `uuid`.

Миграция сделана сейчас, потому что данных нет и контракт не меняется (`string` остаётся `string`) — фактически меняется только генерация и парсинг.

#### Последствия

**Позитивные:**
- Ноль сторонних ID-библиотек во всех текущих и будущих сервисах
- Стандарт IETF — совместимость с инструментами, БД, логами из коробки
- Путь к нативному типу `uuid` в PostgreSQL

**Негативные:**
- Строка ID длиннее: 36 символов против 26 у ULID
- Смешение старых ULID и новых UUID в dev-журнале — лечится очисткой dev-БД (данных нет)
- `Guid.CreateVersion7()` требует .NET 9+ → апгрейд C#-сервисов с net8.0 (выполнен в рамках этой же миграции)

#### Связанные решения

- **ADR-019**: Разделение Meetup и Auction, формат ID — ULID (заменён в части формата ID)
- **ADR-002**: Event Sourcing для stateful-сервисов
- **ADR-007**: Полиглотная модель

### ADR-021: .NET Aspire для локальной оркестрации

**Дата**: 18.07.2026

**Статус**: Принято

#### Контекст

Локальный запуск платформы сейчас держится на трёх независимых docker-compose файлах (корневой + `services/auction-service/docker-compose.yml` + `services/notifications-service/docker-compose.yml`), которые разошлись по портам, именам сетей и версиям образов NATS/PostgreSQL. Топология «что поднять для конкретной задачи» каждый раз собирается руками, нет единого дашборда логов/трейсов, а строки подключения копипастятся между compose-файлами и `appsettings.json`.

**Требования:**
- Один источник правды для локальной топологии.
- Гибкость: возможность поднять только инфраструктуру (NATS + PostgreSQL) и запускать сервисы руками из IDE, либо поднять весь стек одной командой.
- Единое место для логов/трейсов/health при полном запуске.
- Задел на генерацию артефактов для возможного будущего деплоя на k3s, без завязки на него сейчас; актуальная граница local / production-like / hosting описана в `docs/PROJECT_CONTEXT.md`.

#### Рассмотренные варианты

**1. Статус-кво: докрутить docker-compose (единый файл + `.env`-профили)**
- ✅ Ничего нового не изучать, инструмент уже знаком.
- ✅ Не тянет дополнительный .NET AppHost-проект в репозиторий.
- ⚠️ Строки подключения и порты по-прежнему копипастятся вручную между compose и `appsettings`.
- ⚠️ Нет встроенного дашборда логов/трейсов — пришлось бы отдельно поднимать Loki/Grafana даже для лёгкой отладки.
- ⚠️ Топология «Local/Container/Off» на компонент через `.env`/profiles реализуема, но неудобно читается и легко рассинхронизируется вручную.

**2. Tilt**
- ✅ Популярен для смешанных (build from source + containers) топологий, live-reload.
- ⚠️ Ещё один язык конфигурации (Tiltfile на Python-подобном Starlark) поверх уже полиглотного стека.
- ⚠️ Не даёт нативного OTel-дашборда — трейсы всё равно нужно подключать отдельно.
- ⚠️ Не решает задачу «строки подключения сами прорастают в сервисы» — service discovery всё равно на compose/DNS.

**3. k3d (локальный k3s)**
- ✅ Ближе всего к целевой прод-топологии (k3s), меньше расхождений dev/prod.
- ⚠️ Избыточная сложность для ежедневной разработки пет-проекта (Helm/манифесты вместо одного `docker-compose up`).
- ⚠️ Решение о деплое ещё не принято (отдельный ADR «Хостинг»), рано жёстко привязываться к Kubernetes в dev-контуре.

**4. .NET Aspire (13.x)**
- ✅ Один AppHost-проект на C# — топология описывается кодом, а не YAML/DSL: `AddProject`, `AddExecutable`/`AddDockerfile` для Rust-gateway, контейнерные ресурсы для NATS/PostgreSQL.
- ✅ Service discovery и строки подключения инжектятся автоматически через `WithReference`, не копипастятся.
- ✅ Dashboard из коробки: логи, OTel-трейсы, health — закрывает то, ради чего сейчас поднимается отдельный Loki/Grafana для локальной отладки.
- ✅ `aspire publish` умеет генерировать docker-compose/Kubernetes-манифесты из той же топологии — задел на k3s-деплой без решения о нём сейчас.
- ✅ C# — родной язык для владельца проекта, минимальный порог входа по сравнению с Tilt/Starlark.
- ⚠️ Ещё одна версионируемая зависимость (Aspire CLI/SDK), которая заметно обновляется между минорными версиями.
- ⚠️ Полноценный OTel для Rust-шлюза Aspire не даёт «из коробки» — телеграм-гейтвей пока остаётся вне трассировки.

#### Решение

Используем **.NET Aspire** как единственный инструмент локальной оркестрации. AppHost-проект — в `infra/apphost/`. NATS и PostgreSQL — всегда контейнерные ресурсы Aspire; C#-сервисы и Rust-шлюз получают три режима на компонент (`Local`/`Container`/`Off`), управляемые параметрами AppHost без правки кода топологии (детали режимов — предмет отдельной итерации, см. `docs/06_TASKS/aspire-orchestration.md`).

Рукописные docker-compose файлы (`docker-compose.yml`, `services/auction-service/docker-compose.yml`, `services/notifications-service/docker-compose.yml`) удаляются по итогам миграции; при необходимости compose-файл генерируется через `aspire publish`.

#### Обоснование

1. **Устраняет копипасту, а не переносит её.** Три рукописных compose-файла с разными портами/сетями/версиями образов — сейчас источник рассинхронизации. Aspire даёт один AppHost-проект вместо трёх YAML.
2. **Dashboard закрывает наблюдаемость для dev-контура бесплатно.** Не нужно отдельно поднимать Loki/Grafana (`docker-compose.logging.yml`) ради просмотра логов при локальной отладке — это остаётся для прод/staging сценария.
3. **C# — родной язык владельца**, порог входа в AppHost-код ниже, чем в Tiltfile или Kubernetes-манифесты.
4. **Не привязывает к проду преждевременно.** `aspire publish` — генерируемый артефакт, а не решение о деплое; выбор k3s/другой платформы остаётся за отдельным ADR «Хостинг».
5. **Учебная ценность.** Событие/акторы уже изучаются через auction-service; Aspire — актуальный инструмент экосистемы .NET, знание которого пригодится и вне пет-проекта.

#### Последствия

**Позитивные:**
- ✅ Единая точка правды для топологии, меньше расхождений между окружениями разработчиков.
- ✅ Логи и трейсы C#-сервисов видны в одном дашборде без дополнительной настройки.
- ✅ `docs/03_CONTRACTS`, ADR и сервисные AGENTS.md обновляются один раз, а не в трёх compose-файлах.

**Негативные:**
- ⚠️ Aspire CLI/SDK версионируется агрессивно (минорные релизы могут ломать API) — версия фиксируется явно в `infra/apphost/apphost.csproj` и обновляется осознанно, не автоматически.
- ⚠️ Windows-специфичные риски (интеграция `cargo`-исполняемого файла через `AddExecutable`) проверяются на итерации 2 плана, до полировки остального.
- ⚠️ Rust-шлюз не получает OTel-трейсы автоматически — остаётся в scope будущей работы, не блокирует текущую миграцию.

**Миграционный путь:** по итерациям из `docs/06_TASKS/aspire-orchestration.md` (0 — ADR + скелет NATS/PostgreSQL, 1 — C#-сервисы, 2 — Rust gateway, 3 — режимы/профили, 4 — генерация compose и удаление рукописных файлов).
