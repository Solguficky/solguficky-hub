# Standard: Ветвление и pull request

> **Статус:** Active  
> **Применимость:** ветки, рабочие деревья и pull request, которые исполнитель контура создаёт сам; ветки, пришедшие из чужого инструмента, под правило имени не подпадают  
> **Связанные документы:** [commit-messages.md](commit-messages.md), [agent-execution-loop.md](../../development/agent-execution-loop.md)

Standard задаёт, от чего ветвится работа, как называются ветка и pull request, как вести несколько задач одновременно и как результат возвращается в основную линию.

## Правила

### Ветки

- Модель ветвления — gitflow. `develop` — рабочая ветка и база всей разработки, `main` хранит состояние прода.
- Перед созданием ветки обнови remote refs командой `git fetch origin`, затем создай её от `origin/develop`: `git switch -c feature/PER-84 origin/develop`.
- Имя ветки — `feature/PER-N`: префикс, идентификатор Linear, ничего больше. Слаг названия в имя не входит, идентификатор пишется в верхнем регистре.
- Одна задача — одна ветка — один pull request. Вторая задача начинается новой веткой от `develop`, а не продолжением текущей.
- Агент работает только в `feature/PER-N` своего дерева. `main` он не трогает: ни коммитом, ни мержем, ни переключением.

Имя ветки отвечает на вопрос «над чем работает это дерево», а не «занята ли задача». Требование к имени действует на ветки, которые агент создаёт по этому standard; ветки чужих инструментов вроде `cursor/` и `claude/` ему не подчиняются и признаком ничего не делают.

### Имя ветки создаётся при открытии контура

На первом шаге [контура исполнения](../../development/agent-execution-loop.md) агент собирает имя из идентификатора задачи и не использует кнопку «Copy git branch name» или поле `gitBranchName` из Linear.

### Параллельная работа в отдельном дереве

Две задачи одновременно ведутся в двух рабочих деревьях, а не переключением веток в одном. Переключение уносит незакоммиченную правку в чужую задачу и обнуляет ответ на вопрос, над чем это дерево работает.

```sh
git fetch origin
git worktree add .claude/worktrees/PER-84 -b feature/PER-84 origin/develop
```

- Одно дерево — одна задача — один исполнитель. Чужое дерево не трогают: git сам отказывает, если ветка уже занята другим деревом или уже существует. Отказ разбирают по существу, а не обходят вторым именем.
- Деревья живут в `.claude/worktrees/`; каталог закрыт корневым `.gitignore`. Дерево, созданное вне этого каталога и без правила игнорирования, попадает в `git status` основного дерева, а грязное дерево останавливает создание следующей ветки.
- Дерево stale, когда работа по его задаче кончилась, а дерево осталось: ветка слита, pull request закрыт или задача отменена. Пустота дерева признаком не является — только что созданное дерево тоже пусто, пока исполнитель читает задачу, и удалять его нельзя. `git worktree list` показывает stale-деревья наравне с рабочими и сам их не различает: признак проверяется по судьбе ветки и задачи, а не по содержимому каталога и не по возрасту.
- Дерево удаляют только после проверки, что работа запушена: `git -C <дерево> log --oneline origin/feature/PER-N..HEAD` пуст, затем `git worktree remove <дерево>`. Сравнивай именно с `origin/feature/PER-N`: сокращение `@{u}..` здесь врёт — ветка, созданная от `origin/develop`, до `git push -u` отслеживает `develop`, а без апстрима команда пишет ошибку в stderr и оставляет пустой stdout, неотличимый от «всё запушено». Ветки `origin/feature/PER-N` нет вовсе — не запушено ничего. Каталог, оставшийся без записи в git, снимает `git worktree prune`.
- Предел параллелизма задаёт рантайм, а не число деревьев. Сборка, кодогенерация и тесты в двух деревьях идут независимо: `buf` и `golangci-lint` берутся из `GOPATH`, а сгенерированный код пишется внутрь каждого дерева. Рантайм общий: `just identity-run` применяет миграции в базу `IDENTITY_DATABASE_URL` и слушает `IDENTITY_GRPC_ADDR`, поэтому второе дерево поднимает его только со своей базой и своим портом. Aspire делит с ними имена контейнеров и тома, и одновременный запуск в двух деревьях не подтверждён ([local-development.md](../../development/local-development.md)).

### Pull request

- Заголовок PR — `[PER-N] Название задачи из Linear`. По нему Linear связывает работу с задачей и переводит её статус.
- Тело PR состоит из трёх частей: «Что и зачем», «Отклонения от плана», «Осталось открытым». Пересказ диффа в тело не входит — он читается в самом PR.
- «Что и зачем» — две–пять строк намерения среза, без перечисления файлов.
- «Отклонения от плана» обязательны. Если отклонений не было, секция заполняется одной строкой об этом.
- «Осталось открытым» — неисправленные находки ревью: отложенные, оспоренные и вынесенные в другие задачи. Исправленные читаются в диффе и тредах.
- Прогон `just verify` перед сдачей обязателен.
- Копирование вывода `just verify` в тело не требуется. В тело он попадает только в двух случаях: draft-чекпоинт на красном гейте и проверка, которой в CI нет вовсе.
- PR из `feature/PER-N` вливается в `develop` через squash.
- Ревью и мерж выполняет владелец. Агент открывает PR и останавливается.

Draft pull request — не сдача, а носитель чекпоинта: им работа фиксируется, когда контур встал на вопросе к владельцу ([agent-execution-loop.md](../../development/agent-execution-loop.md)). Draft переводится в обычный PR тем же исполнителем, когда срез дописан; сам по себе draft ревью не запрашивает.

## Проверка

- `git branch --show-current` возвращает `feature/PER-N` с идентификатором в верхнем регистре — в том дереве, где идёт работа.
- После `git fetch origin` команда `git merge-base --is-ancestor origin/develop HEAD` завершается успешно: `HEAD` содержит актуальное состояние удалённого `develop`.
- `git log --oneline origin/main..main` пуст: локальный `main` не получил ни одного коммита.
- `git worktree list` не содержит деревьев, чья ветка уже слита, и `git status --short` основного дерева пуст при существующем втором дереве.
- Заголовок PR начинается с `[PER-N]`, а тело содержит все три части: «Что и зачем», «Отклонения от плана», «Осталось открытым».
