# Standard: Сообщения коммитов

> **Статус:** Active  
> **Применимость:** обычные коммиты репозитория, включая работу подагентов  
> **Не применяется:** заголовки PR — их формат задаёт [branching.md](branching.md); merge- и squash-коммиты — их сообщения формирует GitHub
> **Связанные документы:** [branching.md](branching.md), skill `proj-write-commit`

Сообщение коммита — одна строка в формате Conventional Commits. Длинного описания у коммита нет.

## Правила

- Заголовок: `type: Subject` или `type(scope): Subject`.
- После двоеточия — заглавная буква.
- Заголовок повелительный, без точки в конце, не длиннее 72 символов.
- Заголовок на английском. Тип и scope и так английские, а смешанный заголовок читается хуже обоих однородных вариантов. Документация, ADR и обсуждение остаются на русском.
- Тела у коммита нет. Если объяснение не помещается в заголовок, коммит слишком большой — раздели его. Обоснование решения живёт в ADR, а не в истории git.
- Трейлеры (`Co-Authored-By`, `Revert`) телом не считаются и допускаются после пустой строки.
- Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`, `revert`.
- `scope` — сервис или раздел (`identity`, `meetups`, `telegram-bot`, `contracts`, `adr`), а не имя файла. Если затронуто несколько разделов, scope опускается.
- Идентификатор Linear в заголовок не входит: он уже есть в имени ветки и в заголовке PR — их формат задаёт [branching.md](branching.md), по ним Linear и связывает работу.
- Документация меняется тем же коммитом, что и код, который она описывает. Отдельный `docs:` — только для изменений, у которых кода нет.

## Пример

```
feat(identity): Add access status to the profile table
fix(telegram-bot): Fail closed when Identity is unavailable
docs(adr): Record the premoderation decision as ADR-026
refactor: Extract the deep link payload parser
```

Неверно:

```
docs: обновил доки            # строчная буква, прошедшее время
feat(identity.go): Add ...    # scope — имя файла
[PER-25] Identity: ...        # идентификатор задачи вместо типа
fix: Handle retry             # ...и следом абзац объяснений в теле
```

## Проверка

Правила проверяются локально хуком `commit-msg` через lefthook: скрипт `tools/git-hooks/check-commit-message.sh`, включается один раз командой `lefthook install`.
Merge-коммиты и заготовки `fixup!` / `squash!` / `amend!` хук пропускает: их текст пишет git, а не автор.

Проверки в CI нет намеренно. Стандарт описывает, как автор пишет обычный коммит, а при squash-merge в `develop` сообщение создаёт GitHub, и к нему стандарт не применяется.
Хук обходится через `--no-verify`, и это осознанный компромисс: цена ошибки в формате заголовка ниже, чем цена заблокированного PR.

Скрипт не проверяет осмысленность заголовка: повелительное наклонение, соответствие scope содержимому изменения и размер коммита остаются предметом review.

Вручную: `git log --format=%B -20` не содержит непустых строк после заголовка, кроме трейлеров. Каждый заголовок начинается с допустимого типа, а первый символ после `: ` — заглавный.
