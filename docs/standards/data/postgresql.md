# Standard: PostgreSQL в .NET-сервисах

> **Статус:** Active  
> **Применимость:** миграции и доступ к PostgreSQL в F#- и C#-компонентах  
> **Связанные документы:** [languages/fsharp.md](../languages/fsharp.md), [testing/fsharp.md](../testing/fsharp.md), [ADR-025](../../decisions/ADR-025-meetups-fsharp-stack.md)

Норматив фиксирует набор инструментов для схемы и запросов. Identity на Go остаётся на goose и в этот документ не входит.

## F#

- Миграции применяются **DbUp** из SQL-скриптов, встроенных в сборку.
- Имя скрипта — `NNN_описание.sql` с трёхзначным номером; порядок задаёт имя, а не содержимое.
- Скрипт идемпотентен: повторный прогон на уже применённой схеме не падает. `IF NOT EXISTS` и эквивалентные конструкции обязательны, журнал DbUp сам по себе этим не считается.
- Доступ к данным — **Dapper** поверх Npgsql. EF Core в F#-сервисах не используется.

## C#

Набор выбирается по домену и удобству конкретного сервиса, а не один раз на весь репозиторий:

- DbUp и Dapper — тот же контур, что у F#, когда схема и SQL остаются явными;
- EF Core — когда модель и миграции удобнее вести в коде;
- FluentMigrator — когда миграции пишутся кодом, а не SQL-скриптами.

Смешивать два механизма миграций внутри одного сервиса нельзя.

## Проверка

- F#-сервис применяет схему через DbUp, а не через рукописный runner и не через EF Core.
- Повторный прогон миграций на уже поднятой базе успешен.
- Интеграционный тест F# поднимает PostgreSQL Testcontainers, а не sidecar CI, если boundary требует живую базу.
