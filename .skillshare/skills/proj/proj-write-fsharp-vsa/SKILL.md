# Писать функциональный вертикальный F#-срез

Порядок работы ниже, устройство среза и разобранные примеры — в нормативе [architecture/functional-slices.md](../../../docs/standards/architecture/functional-slices.md). Открой его вместе с этим skill: примеры живут там и здесь не повторяются. Языковые правила даёт `proj-write-fsharp`, тестовые — `proj-test-fsharp`.

Для Meetups устройство принято в [ADR-033](../../../docs/decisions/ADR-033-meetups-functional-vertical-slices.md) и раскрыто в [брифе](../../../docs/services/meetups.md). Для другого F#-компонента сначала найди явное решение о таком устройстве; без него этот skill архитектуру не назначает.

## 1. Назови срез продуктовым действием

Прочитай ближайший `AGENTS.md`, service brief и ADR сценария. В Meetups сверь команду или запрос со словарём [ADR-031](../../../docs/decisions/ADR-031-meetups-domain-vocabulary-and-event-form.md) и технической моделью [ADR-024](../../../docs/decisions/ADR-024-meetups-state-storage-with-domain-event-log.md).

Срез называется командой или запросом: `PublishMeetup`, `ListVisibleMeetups`. Не `MeetupService`, не `MeetupHandler`. До выбора файлов зафиксируй вход, типизированный успех, ожидаемые отказы, эффекты и границу транзакции.

## 2. Разложи срез по сложности сценария

Опорная форма нетривиального среза:

| Модуль | Ответственность | Что запрещено |
|---|---|---|
| `Types` | вход, успешный результат, error DU среза | доменная логика, зависимости |
| `Workflow` | `Deps`, отображение входа в домен, оркестрация | DI-контейнер, HTTP status, SQL |
| `Adapters` | инфраструктурный DTO и generated-тип в доменный | доменные решения |
| `Composition` | сборка `Deps` из зарегистрированных сервисов | бизнес-правила |
| `Api` | endpoint и отображение error DU в transport | вызовы инфраструктуры мимо `Workflow` |

Это опора, а не мандат: ADR-033 отказался от фиксированного набора файлов. Простой запрос живёт одним модулем; пустой `Adapters.fs` со сквозной функцией — шум. Модуль выделяется, когда у него появилась отдельная ответственность или отдельный набор зависимостей, а не ради симметрии с соседним срезом.

Срез не вызывает другой срез. Если сценарий требует двух срезов в одной транзакции, границу выбрали неверно.

## 3. Положи чистое решение в центр

Раздели решение и переход: `decide` возвращает `Result<Event, DomainError>`, `apply` возвращает только состояние. Понадобился `Result` у `apply` — проверка стоит не там.

Семантику повтора выбери до кода и вырази типом. Повтор — ошибка: `Result<Event, DomainError>`. Команда сформулирована как целевое состояние и повтором не ошибается: `Result<Event option, DomainError>`, где `Ok None` означает «состояние уже такое, события нет». Чистая функция принимает все факты значениями; загрузка, часы, UUID, SQL, публикация и transport остаются в оболочке.

## 4. Собери зависимости в composition root

`Workflow` принимает узкий record of functions либо функции отдельными аргументами. Общий `Deps` на несколько срезов не заводится: совпадение полей сегодня — совпадение, а не абстракция.

`Composition` разрешает DI, lifetime и конкретные клиенты один раз. Ниже него живут только функции и значения. Service locator, `IServiceProvider` внутри среза и общий interface на каждый модуль запрещены.

## 5. Держи отображения у владельца

Protobuf/C# DTO, Dapper row и HTTP request/response заканчиваются в своих адаптерах. Уникальное для сценария отображение живёт в срезе; общее выносится после второго реального потребителя и не становится обходным путём к доменному состоянию.

Границу «инфраструктура или общий модуль» компилятор не держит — она проверяется вопросом: функция знает про один внешний протокол, или переводит один контракт в другой. Первое — `Infrastructure/`, второе — общий модуль срезов.

Oxpecker знает HTTP и composition root; домен и `Workflow` не возвращают status code, route type и контекст фреймворка. Межсервисный transport остаётся решением contract design, а не следствием выбранного web framework.

## 6. Поддержи порядок компиляции

Обнови `.fsproj` в том же изменении: доменные типы раньше workflow, `Infrastructure` выше срезов, composition root последним потребителем. Цикл между срезами означает неверную границу, а не необходимость общего `Helpers`.

## 7. Докажи срез тестами

Через `proj-test-fsharp` отдельно проверь чистое решение, оркестрацию workflow и отображения границ. Integration test нужен для транзакции, SQL, Protobuf и HTTP wiring; E2E — только для сквозного пользовательского обещания.

Срез готов, когда один сценарий читается без обхода горизонтальных слоёв, доменное решение работает без host и I/O, а framework и generated-типы не пересекли boundary.
