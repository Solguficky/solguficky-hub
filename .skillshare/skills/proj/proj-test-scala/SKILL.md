# Тестировать Scala-код

Стек, уровни и их границы заданы нормативом: [testing-strategy.md](../../../docs/standards/testing/testing-strategy.md), раздел «Стек Scala». Форма имени — [naming.md](../../../docs/standards/testing/naming.md), раздел «Scala». Язык ведёт `proj-write-scala`. Здесь только последовательность работы; состав библиотек и версии по памяти не вводятся.

## 1. Выбери минимальный честный уровень

- Чистое доменное решение, отображение и каркас лога — L0, без `ActorSystem` и без контейнеров.
- Синхронная часть поведения актора — тоже L0: `BehaviorTestKit` с эффектами и `EventSourcedBehaviorTestKit` с цепочкой команда → событие → состояние → ответ ничего не поднимают.
- Настоящее хранилище, рестарт процесса, уникальность `(persistence_id, sequence_number)` и offset проекции — L1 с Testcontainers. In-memory журнал этого не доказывает: он живёт внутри `ActorSystem` и умирает вместе с ней.
- Уровень выше выбирается, только когда нижний физически не может доказать свойство. Тест, поднявший контейнер ради чистой функции, дорог и ничего не добавляет.

## 2. Собери детерминированный сценарий

- Время, идентификаторы и случайность приходят в SUT снаружи. Таймеры проверяются `ManualTime` с `timePasses` и `expectNoMessageFor` либо эффектом `TimerScheduled` в синхронном тесте; часы машины тест не читает.
- Данные строятся от одного валидного образца с переопределением отличия, а не полным литералом в каждом тесте: отличие от нормы и есть суть теста.
- Зависимость, которую тест не задал, обязана падать, а не возвращать молчаливый успех.

## 3. Проверь то, что наблюдаемо

- Утверждение формулируется о наблюдаемом свойстве, а не о последовательности вызовов реализации. Имя теста обязано остаться верным после разрешённого рефакторинга.
- Побочный эффект, который и есть результат работы, проверяется, а не подразумевается: запись в журнал перехватывается `ListAppender` и сверяется по полям, а не считается сделанной раз уж код её вызывает.
- Негативный путь проверяется наравне с основным: отклонённый вход, неизвестный путь, брошенное исключение.

## 4. Добавь property там, где это инвариант

- Property формулирует инвариант, а не повторяет реализацию: отклонённый переход не меняет состояние, применение принятого события увеличивает версию один раз, round trip отображения сохраняет смысл.
- Доменный тип с инвариантом получает собственный `Arbitrary`. Где генератор сужен `suchThat`, шринкер объявляется через `Shrink.suchThat`, иначе сокращённый контрпример нарушит инвариант генератора.
- Число проверок задаётся явно: умолчание моста — десять, а не сто по умолчанию ScalaCheck.
- Последовательности, где важен порядок, проверяются через `Commands` и только вместе с независимой референсной моделью. Без неё свойство проверяет реализацию против самой себя.

## 5. Проверь тест

Прогони `just <компонент>-verify`. Упавшее property повторяется по seed, который ScalaTest печатает, аргументом `-S` раннера; найденный контрпример сохраняется regression example, если описывает важный край домена.

Тест готов, когда он падает по той причине, ради которой написан, имя читается предложением о поведении, форма имени внутри файла одна, а уровень — минимальный из тех, что доказывают свойство.
