# Вести эпик

Полномочия оркестратора — раздел «Контур эпика» [норматива](../../../docs/development/agent-execution-loop.md#контур-эпика): таблица «оркестратор — владелец» и правила под ней. Читай их оттуда целиком и не воспроизводи по памяти. Здесь — последовательность и механика Orca.

Каждый лист исполняет Orca worker целым контуром задачи: `/proj-take-task PER-X`, шаги 1–11 того же норматива. Оркестратор шагов листа не делает.

## Контракт проекта

Трекер, ветвление и гейт скилл читает из контракта проекта: `docs/agents/issue-tracker.md`, `docs/agents/branching-and-pr.md`, `docs/agents/verification-gate.md`, путь от корня репозитория. Файла или названного раздела нет либо раздел пуст — назови путь и заголовок и остановись.

## Запреты

Действуют всю сессию, в том числе после сжатия контекста:

- не читать код и диффы листьев — ни файлами, ни `gh pr diff`, ни `worker-read` ради кода;
- не перезапускать молчащего worker'а: тишина, таймаут и `unverifiable` смерти не доказывают;
- не решать за владельца по таймауту;
- не опрашивать Orca в цикле и не писать watch-скриптов: Orca будит сама;
- не обходить предохранитель Orca после трёх неудачных стартов новым Run или новым Task;
- не мержить, не двигать статусы задач, не создавать ветку `feature/PER-X` за исполнителя.

## Гайд Orca

Исполняемый файл — значение `ORCA_CLI_COMMAND`, иначе `orca`. Один раз за сессию сними версионный гайд: `<orca> skills get orchestration`. Синтаксис команд бери оттуда и из `--help`, справочники — `--reference references/<file>.md` по ситуации, которую гайд называет. Команды ниже — ориентир, гайд их перекрывает. Orca не отвечает или файла нет — назови ошибку и остановись: контур эпика в этой среде не открывается.

Зависимостей между Task (`--deps`) скилл не ставит: Orca считает зависимую Task готовой по `worker_done` блокирующей, а лист эпика ждёт мержа её pull request. Зависимый лист получает Task только тогда, когда его можно запускать, — шаг 8.

## 0. Возьми идентификатор

`<ID>` — зонт эпика из аргумента `/proj-take-epic`, в верхнем регистре. Аргумента нет — спроси и остановись; эпик из бэклога не выбирай.

## 1. Начни с журнала

На каждом входе и каждом пробуждении первым делом. Журнал — `.work/EPIC-<ID>/`, формат и порядок сверки — [references/journal.md](references/journal.md).

- Журнала нет, и сводки оркестратора на зонте нет — это первый запуск: шаг 2.
- Журнал есть — это продолжение, по разделу «Возобновление» журнала. `run_id` в `run.md` есть — `run-use --id <run_id>`, новый Run не создаётся. `run_id` нет — Run ещё не создан: план показан и ждёт ответа (`plan-shown`) — шаг 3, план согласован (`plan-approved`) — шаг 5.
- Журнала нет, а сводка на зонте есть — восстанови `run.md` и `plan.md` из сводки, строкой `journal-restored` в `events.log`. Сводка и Orca не сходятся (`run-show`, `task-list`) — вопрос владельцу; Run и Task заново не заводятся.

## 2. Прими эпик

Прочитай зонт, его листья со связями и комментарии — инструментом из `docs/agents/issue-tracker.md`. Для каждого листа: статус, `delegate`, `blockedBy`, открытый pull request, метки `Area` и `Decision`.

- Лист с меткой `Decision` или без одобрения владельца в план не идёт: декомпозицию оркестратор не делает.
- Лист уже занят по сигналам захвата — в плане он «чужой», и в раздачу не идёт.

Листья вне плана в журнале остаются строкой с причиной, но в условие конца сессии не входят.

## 3. Согласуй план эпика

План называет: листья плана и их очерёдность по `blockedBy` и приоритету; предел параллелизма — по умолчанию два worker'а, из них не больше одного тяжёлого (лист задевает компонент на JVM или .NET — группы `heavy` в `tools/verify/select-recipes.sh`), меньше — если владелец так скажет; архитектурные развилки, которые видны из постановок листьев, с вариантами и рекомендацией в форме из раздела «Чекпоинты» норматива. Развилки нумеруются `D-1`, `D-2`…

Реши, что чекпоинт сработал, затем `just gate-observe plan` с сутью плана на stdin. Заведи журнал (`run.md` без `run_id`, `plan.md`), создай сводку на зонте с планом — её `comment_id` в `run.md` — и строку `plan-shown`. Покажи план в чате и жди ответа: раздача до согласования не начинается. Ответ — в `plan.md` со ссылкой на сообщение владельца, строка `plan-approved`.

## 4. Подготовь дерево листа

Один раз на лист, непосредственно перед его стартом, из своего дерева. Строка `prepared` у листа уже есть — дерево готово, шаг пропускается.

Гайд Orca советует не создавать дерево заранее; здесь это отступление осознанное: 2026-10-23 `worker-start` в новом дереве поднял claude без `.claude/settings.local.json`, тот встал на диалоге MCP-серверов и потерял постановку, а внешних скиллов в свежем дереве нет, и подхватывает их только новая сессия. Пересматривается по итогам [PER-872](https://linear.app/anticnvm/issue/per-872).

1. Сверь сигналы захвата листа по `docs/agents/issue-tracker.md`, раздел «Захват задачи». Занят — дерево не создавай, строка в журнал и вопрос.
2. `git fetch origin` в своём дереве: зависимый лист ветвится от `develop` уже со слитым блокирующим листом. Затем `<orca> worktree create --name <per-x> --repo <репозиторий> --base-branch origin/develop --linear-issue PER-X --json` без `--agent` и без `--branch`: ветку исполнитель переименует сам по `docs/agents/branching-and-pr.md`, раздел «Имя ветки». Путь дерева — в `plan.md`.
3. Скопируй `.claude/settings.local.json` из своего дерева в новое по тому же пути — в его `.claude/settings.local.json`, а не в корень: Claude читает файл только оттуда.
4. В новом дереве: `just skillshare-install`, затем `git checkout -- .skillshare/`, затем `skillshare sync --all -p`. Install выбрасывает из объявления запись, которую не пропустил аудит, и правит отслеживаемые файлы — без отката дерево грязное, и `/proj-take-task` исполнителя остановится на шаге 3.
5. Код install не доказывает установку: на выброшенной записи обёртка выходит раньше проверки остальных. Поэтому сверь списки каталогов `.claude/skills/` нового дерева и своего: совпали — дальше; в новом не хватает каталога — вопрос с именами.
6. `just agent-ready claude`: код 0 или 3 — дальше, иначе вопрос.
7. `git status --short` в новом дереве пуст. Строка `prepared` в журнал — с кодами шагов 4 и 6 и итогом сверки.

## 5. Раздай листья

Один эпик — один Run: `run-create` один раз, при первой раздаче после согласования плана, `run_id` сразу в `run.md` и в сводку.

Стартует лист плана, у которого все блокирующие листья слиты (`gh pr view`), если предел это разрешает. На каждый такой лист: шаг 4, затем Task — один раз на лист: `task-create --spec-file` без `--deps`, `task_id` в `plan.md` и в сводку. Повторный старт того же листа — только `worker-start --task`, никогда `--spec`.

Постановка (spec) начинается строкой `/proj-take-task PER-X`. Дальше: развилки плана, которые касаются листа, с выбранным вариантом и пометкой «решено владельцем в плане эпика»; для зависимого листа — что его блокирующие листья слиты, с номерами pull request; что вопросы идут оркестратору через `ask`; что сдача заканчивается `worker_done` с отчётом шага 11, ссылкой на pull request и кандидатами рефлексии после контура — они идут владельцу через сводку; что владелец ждёт внешнее ревью на каждом листе. Тулинг свежего дерева исполнитель ставит сам на шаге 3 своего контура. Не пиши «чекпоинт не нужен» и не отменяй шаги контура: чекпоинт срабатывает по условию норматива, а ответ на развилку плана даст оркестратор.

Старт: `worker-start --task <task_id> --worktree path:<дерево листа> --agent claude`. Исполнитель листа — всегда Claude. Строка `intent-start` в журнал до вызова, `started` с `dispatch_id` — после. Затем `worker-read --dispatch <id>`: исполнитель прочитал постановку и начал захват — строка `worker-read-ok`; `input_accepted` в квитанции этого не доказывает. Не начал — вопрос владельцу, а не повторный старт.

Запусти всё, что разрешают предел и очередь, и закончи ход.

## 6. Надзирай

Orca будит на каждое событие. Разбери пачку целиком, запиши события в `events.log`, затем действуй по таблице норматива.

- **`question` от worker'а.** Ответ следует из постановки листа, плана эпика, норматива или фактов журнала — `reply` и строка `R-n` в `decisions.md` с источником. Локальное обратимое решение — так же, плюс `just gate-observe decided`. Иначе — в очередь вопросов, шаг 10; worker ждёт, независимые листья идут.
- **Непредвиденное архитектурное решение.** Сначала второе мнение модели другого провайдера: отдельный Orca worker `codex` со своей Task — `worker-start --spec-file <вопрос> --worktree current --agent codex`, вопрос и запрет правок в постановке, а не Task листа; в журнале она помечена `opinion`. После старта проверь `worker-read`. Его `worker_done` — не сдача: ответ идёт в вопрос владельцу, шаг 10, а не в приёмку. Codex не стартовал — вопрос уходит без второго мнения, с причиной.
- **`escalation` со `stopReason`.** Worker остановился без сдачи. Сначала `send` с вопросом, что мешает, и закончи ход: `send` будит его сессию, и повтор в том же ходе посадил бы двух исполнителей в одно дерево. На следующем пробуждении: worker ответил — разбирай ответ; смерть доказана по `worker-list --run <run_id> --include-remote` — повтор на тот же Task в то же дерево: `worker-start --task <task_id> --retry-of <dispatch_id> --worktree path:<дерево листа> --agent claude`, размещение не наследуется. Строка `retry` с `proof=`. Новый исполнитель найдёт задачу в started-статусе и, возможно, ветку без переименования и спросит, чей захват: ответ следует из журнала — захват предыдущего dispatch этого же дерева, его остановка доказана, контур возобновляется. Второй сбой листа — лист остановлен, вопрос.
- **Тишина.** Ничего не перезапускай: вопрос владельцу.
- **`worker_done` листа.** Шаг 7.

## 7. Прими сдачу

Pull request листа ещё draft или нет вовсе — это не сдача, а остановка листа: её вопрос разбирается как `question` в шаге 6.

Иначе запусти подагента приёмки без роли, модель `sonnet` — уровень строки «Ревью на соответствие нормативу» в [agent-execution-cost.md](../../../docs/development/agent-execution-cost.md); пул недоступен — запасной выбор по абзацу «Объявленный пул недоступен» там же. Отчёт называет запрошенную модель и ту, что подагент назвал о себе. Вход и чеклист — [references/acceptance.md](references/acceptance.md). Подагент дифф не читает.

- Всё сошлось — лист ждёт мержа, строка `accepted`.
- Не сошлось — один возврат тому же worker'у через `send` со списком невыполненных шагов. Повторно не сошлось — пометка в сводке и вопрос владельцу; за исполнителя не добирай.
- Внешнее ревью не шло по причине среды — не возврат: пометка в сводке и вопрос в пачке.
- Worker сообщил провал — Task проваленным и остаётся: проваленное не отмечается выполненным.

## 8. Жди мержа и запускай зависимые

Мержит только владелец. На каждом входе сверь pull request листьев плана по `gh pr view`: слитый — строка `merged`, и в тот же день сними дерево листа, как велит корневой `AGENTS.md`: `<orca> worktree rm --worktree path:<дерево листа>` без `--force` и `--delete-branch`, ветку Linear и GitHub уже не держат. Orca отказала — дерево остаётся, пометка в сводке и вопрос. Лист плана, у которого теперь все блокирующие листья слиты и Task ещё нет, стартует по шагу 5.

## 9. Заводи новые задачи

По классу из таблицы норматива и только через `proj-create-task`:

- дефект в уже слитом листе эпика — новый лист под зонт со связью на слитый, в план строкой с пометкой класса; стартует по шагу 5;
- работа вне эпика — задача в бэклог, без Task;
- дыра в декомпозиции — черновик в сводку на зонте и вопрос владельцу; в Linear не заводится до ответа.

## 10. Спрашивай владельца пачкой

Перед вопросом — `just gate-observe ask`, вывод идёт вместе с вопросом. Вопрос получает номер `Q-n` в `questions.md` и уходит в чат Orca и в сводку на зонте (`save_comment` с `id` из `run.md`, а не новый комментарий). Вопрос, который держит лист с уже заведённой Task, дополнительно получает `gate-create --task <task_id этого листа>` — эксперимент, его поведение пишется в журнал. У вопроса по плану эпика, дыре в декомпозиции или листу без Task gate нет: gate блокирует Task, и чужую Task он остановил бы зря.

Ответ из любого места закрывает все места: `gate-resolve`, если gate был, строка в сводке, `reply` worker'у, если вопрос пришёл от него. Ответ в Linear до тебя сам не дойдёт: читай комментарии зонта и `gate-list` на каждом входе.

## 11. Закончи сессию

Условие — раздел «Контур эпика» норматива, пункт «Конец сессии». Тогда обнови сводку на зонте по разделу «Сводка на зонте» журнала и запиши `session-end`. Продолжение после мержа владелец запускает тем же `/proj-take-epic <ID>`.

Все листья плана слиты — итоговая сводка на зонте: листья и pull request, развилки `D-k` и решения `R-n`, ответы `Q-n`, новые задачи по классам, кандидаты рефлексии листьев, сбои Orca и что с ними сделано. Статус зонта не двигаешь.
