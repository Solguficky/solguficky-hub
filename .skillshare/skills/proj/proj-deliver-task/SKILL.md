# Сдать задачу

Норматив — [agent-execution-loop.md](../../../docs/development/agent-execution-loop.md). Не воспроизводи его по памяти: сами шаги контура, список неразрешённых решений ручного гейта и форма остановки читаются оттуда. Здесь только привязка шагов сдачи к инструментам Claude Code.

Скилл сдаёт задачу на ревью и раздаёт работу после сдачи подагентам. Статус задачи в трекере он не двигает, pull request не мержит.

## Контракт проекта

Гейт, ветвление, форму pull request и трекер скилл читает из контракта проекта — файлы названы путём от корня репозитория: `docs/agents/verification-gate.md`, `docs/agents/branching-and-pr.md`, `docs/agents/issue-tracker.md`. Прочитай их до первого шага. Файла или названного ниже раздела нет — назови путь и заголовок и остановись: команду гейта, базу и форму pull request не угадывай.

`<ID>` ниже — идентификатор задачи в форме из `docs/agents/issue-tracker.md`, раздел «Идентификатор задачи». «База» — ref из `docs/agents/branching-and-pr.md`, раздел «База»; «гейт» — команда из `docs/agents/verification-gate.md`, раздел «Команда гейта».

## 1. Пройди ручной гейт до коммита

Прочитай `git status --short`, дифф ветки от базы и `git diff HEAD` целиком; команда диффа ветки — в разделе «База». Дифф ветки показывает уже закоммиченное, `git diff HEAD` — то, что ещё не закоммичено; до первого коммита весь срез виден только в нём. Затем сверь с [нормативом](../../../docs/development/agent-execution-loop.md), встретилось ли по дороге решение из списка неразрешённых. Всё, что задача, принятое решение или политика контура уже разрешили, решено тобой и вопроса не требует.

Этот шаг стоит до проверок намеренно. Пункт «выход за „Границы“ задачи» виден по диффу, а не по цвету механического гейта: после зелёного гейта останавливаться уже поздно.

Неразрешённое решение встретилось — остановись здесь, назови его пункт и предложи варианты. Дальше по этому скиллу не иди: сдачи не будет. Форму остановки возьми в разделе «Как фиксируется остановка» — она зависит от того, есть ли кому ответить в этой сессии.

Переносимая форма требует draft pull request: команда — в `docs/agents/branching-and-pr.md`, раздел «Pull request», затем комментарий в задачу со ссылкой на него. Обычный pull request здесь неверен: он запрашивает ревью работы, которая ждёт ответа.

## 2. Сверь документацию с кодом

Изменение поведения, команды, контракта или правила без правки документации — не готовый срез, а половина. Адреса, по которым идёт сверка, — `docs/agents/verification-gate.md`, раздел «Сверка документации». Пройди их по одному.

Документация отстала — допиши её сейчас, тем же изменением. Это правило проекта из `AGENTS.md`, а не пожелание.

## 3. Прогони гейт

Команда гейта, правило её выбора и то, чем добрать недостающие проверки, — раздел «Команда гейта».

Сколько раз гейт гоняется и что делать с красным по окружению, задаёт раздел «Бюджет гейта» [норматива](../../../docs/development/agent-execution-loop.md): не больше двух прогонов на сдачу, итерация — рецептами компонента, окружение не чинится. Этот раздел читается целиком до первого прогона.

Перед запуском пройди раздел «Перед прогоном»: сверка базы заново, раскладка сгенерированных таргетов после правки их источников, известные ложные красные. База ушла вперёд — сначала закоммить срез и обнови его по разделу «База», потом гейт. Сверка на входе в контур здесь не защищает.

Вердикт читай по разделу «Вердикт»: код возврата самой команды, а не пайпа или харнесса.

Гейт зелёный и на изменении без тестов: он гоняет то, что есть. Отдельно сверься с нормативом тестов из `docs/agents/verification-gate.md`, раздел «Норматив», — новое правило домена, новая ветка отказа и новый use case приходят с тестом в этом же pull request.

Красный механический гейт — это пункт ручного гейта «красные проверки без чистого фикса». Чистый фикс в границах задачи — почини, проверь рецептом компонента и прогони гейт второй раз; третьего прогона нет. Причина в окружении, а не в правке, — это «гейт не оценил изменение», и окружение ты не чинишь. Причина не в изменении или фикс тянет правку вне границ — остановись и скажи. Подгонять проверку под результат нельзя.

На красном гейте не открывается pull request **на ревью**: сдавать нечего. Остановка при этом фиксируется по общему правилу — если ответ в этой сессии не дойдёт, работа уходит в чекпоинт-коммит, push и draft pull request с красным выводом в теле. Draft несёт вопрос, а не сдачу, и запрет его не касается: иначе в фоновом запуске работа и вопрос пропадут вместе со средой.

## 4. Прогони ревью

Скилл `proj-review-change`, точка отсчёта — база, источник спецификации — задача `<ID>` в трекере.

Параллельно ему запусти внешнее ревью в фоне (`run_in_background`), если есть инструмент. Шаг опциональный: ни `codex`, ни `opencode` нет в PATH — пропусти его. Сначала `git add -N` на новые файлы среза: ревью читает `git diff` от базы, а неотслеживаемый файл в нём не виден.

```
codex review --base <база> -c model="gpt-6-sol"
```

Codex нет или он упал (лимит, авторизация) — запасной путь, агент `plan` не правит файлы:

```
opencode run -m openai/gpt-6-sol --agent plan "Отревьюй изменения ветки относительно <база> (git diff <база>, включая незакоммиченное): баги, регрессии, пропущенные состояния. Для каждой находки — файл:строка и сценарий отказа."
```

Находки внешнего ревью разбираются тем же списком, что и находки осей. Не отработал ни один инструмент — в отчёте строка «внешнее ревью не шло» с причиной.

Находки разбери по одной: чинишь в границах задачи, либо решаешь судьбу по `docs/agents/branching-and-pr.md`, раздел «Ревью pull request». Названная, но не решённая находка доезжает до ревью перечнем вопросов и возвращает владельцу решение, которое принимает исполнитель. Молча проигнорированная находка ревью — та же непроверенная гипотеза, только с подписью «проверено».

## 5. Закоммить

Через skill `proj-write-commit`. Он проверит ветку, одно ли это изменение и формат заголовка.

## 6. Запушь и открой pull request

Команды, заголовок и разделы тела — `docs/agents/branching-and-pr.md`, раздел «Pull request». Порядок:

1. Проверь, не открыт ли на этой ветке pull request с чекпоинта. Второй вызов создания на ту же ветку отказывает, и сдача встаёт.
2. Pull request ещё нет — запушь ветку и создай его.
3. Draft с чекпоинта уже открыт — не создавай второй: запушь, допиши заголовок и тело и переведи его в готовый.

Пересказ диффа в тело не входит. Тело передавай файлом, а не строкой.

## 7. Отметься в трекере

Комментарий на задачу `<ID>`: ссылка на pull request, результат прогона гейта с выбранными рецептами, решения ручного гейта и то, что осталось открытым. Решения — по строке на решение, форма ниже, в шаге 8. Инструмент — `docs/agents/issue-tracker.md`, раздел «Конвенции».

Строки решений идут и сюда, и в отчёт намеренно: отчёт уходит в чат, а делегированный и фоновый запуск такого канала к владельцу не имеют, и разметить ошибку он сможет только по комментарию.

Статус задачи здесь не трогай: кто его ведёт дальше — раздел «Захват задачи» того же файла.

Автоматическое ревью pull request сам не вызывай, если `docs/agents/branching-and-pr.md`, раздел «Ревью pull request», оставляет его запуск владельцу. Его находки, если появятся, разбирает подагент на шаге 9.

## 8. Отчитайся

Ссылка на pull request, результат прогона гейта с выбранными рецептами, решения ручного гейта, отклонения от плана и то, что осталось открытым — явно, отдельной строкой.

Решения ручного гейта — это выбор, который ты сделал сам, не спросив, хотя он был близок к списку неразрешённых. Каждое идёт своей строкой: что решено и какой из трёх источников это разрешал. Решений не было — строка «решений гейта не было». По этим строкам владелец при ревью pull request размечает только ошибки — «зря спросил» или «надо было спросить»; молчание значит верно, и по накопленной разметке правится сам список. В тело pull request строки не идут: его разделы заняты другим, а отклонением от плана обычный выбор реализации не является.

Отклонение, растворённое в описании сделанного, до владельца не доходит.

## 9. Раздай работу после сдачи подагентам

Отчёт — итог контура, а работа после него истории контура не требует: основной тред, взявшийся за неё сам, пересылает эту историю на каждом ходу. Порядок и причины — раздел «После контура» [норматива](../../../docs/development/agent-execution-loop.md); здесь только инструменты.

- **Рефлексия.** Подагент на модели сессии — роли у него нет, модель не передаётся — исполняет `proj-reflect-work` по логам текущей сессии и возвращает только кандидатов. Покажи их отдельным блоком после отчёта; кандидатов нет — блока нет. Подагент остановился, не дойдя до кандидатов, — это не «кандидатов нет»: назови остановку и её причину строкой отчёта. Запись — отдельный выбор владельца.
- **Правки по ревью.** Появились комментарии автоматического ревью или владельца — подагент получает их и дифф ветки, правит дерево и возвращает, что изменил. Ты проверяешь правку рецептом затронутого компонента, коммитишь через `proj-write-commit` и пушишь; сам файлы заново не перечитываешь.

Сессия при этом не закрывается: завершение контура на сдаче вступит вместе с оркестратором PER-282.

Контур на этом закрыт. Следующая задача открывается заново через `/proj-take-task`.
