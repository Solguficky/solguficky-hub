# Сдать задачу

Норматив — [agent-execution-loop.md](../../../docs/development/agent-execution-loop.md), [branching.md](../../../docs/standards/git/branching.md) и [commit-messages.md](../../../docs/standards/git/commit-messages.md). Не воспроизводи их по памяти: сами шаги контура, список неразрешённых решений ручного гейта, форма остановки, форма PR и формат заголовка коммита читаются оттуда. Здесь только привязка шагов сдачи к инструментам Claude Code.

Скилл сдаёт задачу на ревью и на этом останавливается вместе с сессией. Статус задачи в Linear он не двигает, pull request не мержит.

## 1. Пройди ручной гейт до коммита

Прочитай `git status --short`, `git diff origin/develop...HEAD` и `git diff HEAD` целиком. Второй показывает уже закоммиченное в ветке, третий — то, что ещё не закоммичено; до первого коммита весь срез виден только в третьем. Затем сверь с [нормативом](../../../docs/development/agent-execution-loop.md), встретилось ли по дороге решение из списка неразрешённых. Всё, что задача, ADR или политика контура уже разрешили, решено тобой и вопроса не требует.

Этот шаг стоит до проверок намеренно. Пункт «выход за „Границы“ задачи» виден по диффу, а не по цвету механического гейта: после зелёного `just verify` останавливаться уже поздно.

Неразрешённое решение встретилось — остановись здесь, назови его пункт и предложи варианты. Дальше по этому скиллу не иди: сдачи не будет. Форму остановки возьми в разделе «Как фиксируется остановка» — она зависит от того, есть ли кому ответить в этой сессии.

Переносимая форма требует draft PR: `gh pr create --draft --base develop --title "[PER-N] Название задачи из Linear" --body-file <файл>`, затем `save_comment` со ссылкой на него. Обычный `gh pr create` здесь неверен: он запрашивает ревью работы, которая ждёт ответа.

## 2. Сверь документацию с кодом

Изменение поведения, команды, контракта или правила без правки документации — не готовый срез, а половина. Проверь адресно:

- новая или изменённая команда — корневой `justfile` и раздел «Команды» в `AGENTS.md`;
- новый каталог верхнего уровня или смена его роли — «Карта репозитория» в `AGENTS.md`;
- новое устойчивое правило — `docs/standards/`, а не текст скилла;
- изменение `contracts/proto/` — [integration.md](../../../docs/architecture/integration.md) и skill `proj-change-contract`.

Документация отстала — допиши её сейчас, тем же изменением. Это правило проекта из `AGENTS.md`, а не пожелание.

## 3. Прогони `just verify-changed`

`just verify-changed` — механический гейт, сужённый до компонентов, которые задевает правка; правило выбора — комментарий над рецептом в `justfile`, выбранные рецепты он печатает первой строкой. Проверки, которых в нём нет для затронутого среза, добери по `just --list`.

Сколько раз гейт гоняется и что делать с красным по окружению, задаёт раздел «Бюджет гейта» [норматива](../../../docs/development/agent-execution-loop.md): не больше двух прогонов на сдачу, итерация — рецептами компонента, окружение не чинится. Этот раздел читается целиком до первого прогона.

Перед запуском сверь базу заново: `git fetch origin`, затем `git log HEAD..origin/develop`. Вывод непуст — сначала закоммить срез и сделай rebase на `origin/develop`, потом гейт. Сверка на входе в контур здесь не защищает: `origin/develop` — общий ref всех рабочих деревьев, и его двигает любой `fetch` соседней сессии. Без этого `contracts-check` сравнивает схемы с ушедшим вперёд `develop` и читает чужие новые поля как удалённые в ветке — код 100 по файлам, которых срез не трогал.

Вердикт читай по коду возврата самого `just verify-changed`, а не пайпа или харнесса, — правило в критических правилах [AGENTS.md](../../../AGENTS.md). Перед запуском убедись, что в дереве не идёт прошлый прогон: второй прогон в том же дереве делит ресурсы с первым и даёт ложный красный. Браузерный тест `community-site-api` упал по таймауту, а одиночный прогон рецепта зелёный — повтори рецепт, а не разбирай дифф.

Гейт зелёный и на изменении без тестов: он гоняет то, что есть. Отдельно сверься с [testing-strategy.md](../../../docs/standards/testing/testing-strategy.md) — новое правило домена, новая ветка отказа и новый use case приходят с тестом в этом же pull request.

Правил `.skillshare/**` — сначала `skillshare sync --all -p`. Правил `.rulesync/**` — `just sync-mcp` и `just sync-commands`. Без раскладки таргеты расходятся с источником, и гейт краснеет: `check-agent-tools` на скиллах, `check-mcp` и `check-commands` на генератах. Генератор перезаписывает таргет целиком, отдельного `--force` для повторной раскладки не нужно.

Красный механический гейт — это пункт ручного гейта «красные проверки без чистого фикса». Чистый фикс в границах задачи — почини, проверь рецептом компонента и прогони гейт второй раз; третьего прогона нет. Причина в окружении, а не в правке, — это «гейт не оценил изменение», и окружение ты не чинишь. Причина не в изменении или фикс тянет правку вне границ — остановись и скажи. Подгонять проверку под результат нельзя.

На красном гейте не открывается pull request **на ревью**: сдавать нечего. Остановка при этом фиксируется по общему правилу — если ответ в этой сессии не дойдёт, работа уходит в чекпоинт-коммит, push и draft PR с красным выводом в теле. Draft несёт вопрос, а не сдачу, и запрет его не касается: иначе в фоновом запуске работа и вопрос пропадут вместе со средой.

## 4. Прогони ревью

Скилл `proj-review-change`, точка отсчёта — `origin/develop`, источник спецификации — задача `PER-N` в Linear.

Находки разбери по одной: чинишь в границах задачи, либо решаешь судьбу — отложить, оспорить или вынести в задачу — по [branching.md](../../../docs/standards/git/branching.md). Названная, но не решённая находка доезжает до ревью перечнем вопросов и возвращает владельцу решение, которое принимает исполнитель. Молча проигнорированная находка ревью — та же непроверенная гипотеза, только с подписью «проверено».

## 5. Закоммить

Через skill `proj-write-commit`. Он проверит ветку, одно ли это изменение и формат заголовка.

## 6. Запушь и открой pull request

Сначала проверь, не открыт ли на этой ветке PR с чекпоинта: `gh pr view --json isDraft,url`. Второй `gh pr create` на ту же ветку отказывает с `a pull request for branch ... already exists`, и сдача встаёт.

PR ещё нет:

```
git push -u origin feature/PER-N
gh pr create --base develop --title "[PER-N] Название задачи из Linear" --body-file <файл>
```

Draft с чекпоинта уже открыт — не создавай второй, а допиши тело и переведи его в готовый:

```
git push
gh pr edit --title "[PER-N] Название задачи из Linear" --body-file <файл>
gh pr ready
```

Заголовок и три части тела — по [branching.md](../../../docs/standards/git/branching.md): «Что и зачем», «Отклонения от плана», «Осталось открытым». Пересказ диффа в тело не входит.

Тело передавай файлом (`--body-file`), а не строкой: многострочный `--body` в PowerShell приезжает склеенным.

## 7. Отметься в Linear

`save_comment` на `PER-N`: ссылка на pull request, результат прогона `just verify-changed` с выбранными рецептами, решения ручного гейта и то, что осталось открытым. Решения — по строке на решение, форма ниже, в шаге 8. Инструмент — [issue-tracker.md](../../../docs/agents/issue-tracker.md).

Строки решений идут и сюда, и в отчёт намеренно: отчёт уходит в чат, а делегированный и фоновый запуск такого канала к владельцу не имеют, и разметить ошибку он сможет только по комментарию.

Статус задачи здесь не трогай: дальше его ведёт Linear по связанному PR либо владелец руками.

Затем оставь в самом pull request комментарий, который запускает CodeRabbit: сам он не ревьюит ([AGENTS.md](../../../AGENTS.md)).

```
gh pr comment <номер> --body "@coderabbitai review"
```

Разбирать его находки — работа новой сессии, а не этой.

## 8. Отчитайся и заверши сессию

`proj-reflect-work` здесь не запускается: рефлексия по контуру идёт новой сессией по разделу «После контура» [норматива](../../../docs/development/agent-execution-loop.md). Там же — куда едут выбранные наблюдение и разбор этой задачи.

Ссылка на PR, результат прогона `just verify-changed` с выбранными рецептами, решения ручного гейта, отклонения от плана и то, что осталось открытым — явно, отдельной строкой.

Решения ручного гейта — это выбор, который ты сделал сам, не спросив, хотя он был близок к списку неразрешённых. Каждое идёт своей строкой: что решено и какой из трёх источников это разрешал. Решений не было — строка «решений гейта не было». По этим строкам владелец при ревью pull request размечает только ошибки — «зря спросил» или «надо было спросить»; молчание значит верно, и по накопленной разметке правится сам список. В тело PR строки не идут: три его части заняты другим ([branching.md](../../../docs/standards/git/branching.md)), а отклонением от плана обычный выбор реализации не является.

Отклонение, растворённое в описании сделанного, до владельца не доходит.

Последняя строка отчёта: «Сессия контура завершена; рефлексия, заведение задач и правки по ревью — новой сессией» — со ссылкой на PR. Это последний ход сессии: после отчёта не делай ни одного вызова инструмента, даже если осталось время или просьба напрашивается сама. Харнесс сессию сам не закрывает, и эта строка — единственный признак, по которому владелец видит, что правило соблюдено. Правило запрещает продолжать по своей инициативе, а не отвечать владельцу: оно адресовано исполнителю, и продолжить в этой сессии владелец решает сам (RFC-013, требование 11).

Контур на этом закрыт. Следующая задача открывается заново через `/proj-take-task`.
